## Где живёт обученная модель

Мы научились записывать запуски ([трекинг](lesson:mlops.fundamentals.experiment-tracking)), версии данных ([хеши содержимого](lesson:mlops.fundamentals.data-versioning)) и воспроизводимо собирать результат ([конвейер с кешем](lesson:mlops.fundamentals.pipelines-and-caching)). Теперь у запуска есть результат - обученная модель. Её нужно сохранить так, чтобы другой процесс (сервис, который отвечает на запросы) смог загрузить ровно эту модель и знал, откуда она взялась.

Для этого нужны три вещи:

* **Формат хранения.** Как превратить модель в байты и обратно. От выбора формата зависят безопасность (не выполнится ли чужой код при загрузке) и переносимость (откроется ли файл через год в другом окружении).
* **Реестр моделей** (model registry). Каталог версий: кто обучил, по какому запуску, с какими метриками, в какой стадии жизненного цикла находится версия. Сервис спрашивает у реестра «дай модель в стадии Production», а не ищет файл по имени.
* **Правило повышения.** Какая версия имеет право стать рабочей. Обычно это сравнение метрики кандидата с текущей Production-моделью с запасом на шум.

В этом уроке модель - маленькая линейная: список признаков, веса, смещение и порог. Такая модель умещается в JSON, поэтому мы увидим всю цепочку «модель - байты - контрольная сумма - реестр - загрузка» без внешних библиотек.

## Примеры

**Пример 1. Почему не pickle.** Формат `pickle` в Python сохраняет произвольные объекты. Для этого он описывает, *как их собрать*, и это описание может включать вызов любой функции. Следующий код безвреден (вызывается `print`), но показывает механизм: функция запускается в момент `pickle.loads`.

```python run
import json
import pickle

class Payload:
    """Объект, который при распаковке вызывает произвольную функцию."""
    def __reduce__(self):
        return (print, ("внимание: код выполнился во время pickle.loads",))

blob = pickle.dumps(Payload())
pickle.loads(blob)                      # распаковка исполняет вызов, спрятанный в данных

text = '{"weights": [0.5, -1.25], "bias": 0.5}'
model = json.loads(text)                # JSON возвращает только данные: числа, строки, списки, словари
print("json:", model, type(model["weights"]).__name__)
```
```output
внимание: код выполнился во время pickle.loads
json: {'weights': [0.5, -1.25], 'bias': 0.5} list
```

Разбор:

* метод `__reduce__` сообщает pickle, как воссоздать объект: «вызови функцию `print` с таким аргументом». Вместо `print` в злонамеренном файле может стоять любая другая функция, например запуск команды в системе;
* `pickle.loads(blob)` не вернул объект `Payload`: он выполнил вызов `print` и вернул его результат. Проверить содержимое файла до распаковки нечем;
* JSON возвращает только данные: числа, строки, списки и словари. Ничего исполняемого в нём нет, поэтому `json.loads` безопасно применять к файлам от других людей, а структуру результата проверяют отдельно.

Документация Python прямо говорит, что распаковывать pickle можно только из доверенных источников ([pickle](https://docs.python.org/3/library/pickle.html)). Вторая причина избегать pickle для долгоживущих моделей - хрупкость: файл привязан к именам классов и модулей, и после переименования класса или смены версии библиотеки он может не открыться.

**Пример 2. Модель в JSON с контрольной суммой.** Сериализуем модель в каноническую JSON-запись (та же функция `canonical_json`, что в первом уроке), добавим поле `format` и сверим SHA-256 при загрузке.

```python run
import hashlib
import json

def canonical_json(obj):
    return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)

def serialize_model(model):
    return canonical_json({"format": "linear-v1", **model}).encode("utf-8")

def deserialize_model(blob, expected_sha256=None):
    if expected_sha256 is not None and hashlib.sha256(blob).hexdigest() != expected_sha256:
        raise ValueError("checksum mismatch: содержимое не совпадает с записанным при регистрации")
    data = json.loads(blob.decode("utf-8"))
    if data.get("format") != "linear-v1":
        raise ValueError(f"неподдерживаемый формат: {data.get('format')!r}")
    if len(data["weights"]) != len(data["features"]):
        raise ValueError("число весов не равно числу признаков")
    del data["format"]
    return data

model = {"name": "churn", "features": ["age", "income"], "weights": [0.5, -1.25],
         "bias": 0.5, "threshold": 0.5, "metadata": {"run_id": "run-7", "data_version": "76917f82d3e0"}}
blob = serialize_model(model)
checksum = hashlib.sha256(blob).hexdigest()
print(blob.decode("utf-8"))
print("sha256:", checksum[:16], "...")
print("round-trip:", deserialize_model(blob, checksum) == model)

tampered = blob.replace(b'"bias":0.5', b'"bias":5.0')     # подмена одного числа
for label, data, expected in (("без проверки суммы", tampered, None), ("с проверкой суммы", tampered, checksum)):
    try:
        print(label, "->", deserialize_model(data, expected)["bias"])
    except ValueError as exc:
        print(label, "-> ValueError:", exc)

old_format = blob.replace(b"linear-v1", b"linear-v0")
try:
    deserialize_model(old_format)
except ValueError as exc:
    print("чужой формат -> ValueError:", exc)
```
```output
{"bias":0.5,"features":["age","income"],"format":"linear-v1","metadata":{"data_version":"76917f82d3e0","run_id":"run-7"},"name":"churn","threshold":0.5,"weights":[0.5,-1.25]}
sha256: f740185e3446562b ...
round-trip: True
без проверки суммы -> 5.0
с проверкой суммы -> ValueError: checksum mismatch: содержимое не совпадает с записанным при регистрации
чужой формат -> ValueError: неподдерживаемый формат: 'linear-v0'
```

Разбор:

* поле `format` фиксирует версию схемы файла. Когда схема изменится, появится `linear-v2`, а старый загрузчик откажется читать незнакомое, вместо того чтобы молча понять его неправильно;
* `checksum` (SHA-256 байтов) считается один раз при регистрации и хранится рядом с версией. При загрузке сверяем: подмена `0.5` на `5.0` меняет хеш, и `deserialize_model` бросает `ValueError`. Без проверки подмена прошла бы незамеченной: файл остаётся корректным JSON;
* проверка `len(weights) == len(features)` ловит модель, у которой число весов не совпадает с числом признаков: такая модель выдавала бы ошибки или неверные ответы уже в сервисе;
* в метаданные положены `run_id` и `data_version`: по ним видно, из какого запуска и из каких данных получена модель.

**Пример 3. Версии и стадии.** Регистрируем четыре версии и пробуем повысить каждую до Production с порогом `min_delta=0.005`. В конце откатываемся на версию 1.

```python run
import hashlib

class ModelRegistry:
    STAGES = ("None", "Staging", "Production", "Archived")

    def __init__(self):
        self._models = {}   # имя -> {версия: запись}

    def register(self, name, blob, metrics, run_id):
        versions = self._models.setdefault(name, {})
        version = len(versions) + 1
        versions[version] = {"sha256": hashlib.sha256(blob).hexdigest(), "metrics": dict(metrics),
                             "run_id": run_id, "stage": "None"}
        return version

    def stages(self, name):
        return {v: rec["stage"] for v, rec in self._models[name].items()}

    def transition(self, name, version, stage):
        if stage not in self.STAGES:
            raise ValueError(f"неизвестная стадия {stage!r}")
        if stage == "Production":
            for other, rec in self._models[name].items():
                if rec["stage"] == "Production":
                    rec["stage"] = "Archived"
        self._models[name][version]["stage"] = stage

    def production(self, name):
        found = [v for v, rec in self._models[name].items() if rec["stage"] == "Production"]
        return max(found) if found else None

    def promote_if_better(self, name, version, metric, mode="max", min_delta=0.0):
        current = self.production(name)
        if current is not None:
            cand = self._models[name][version]["metrics"][metric]
            prod = self._models[name][current]["metrics"][metric]
            gain = cand - prod if mode == "max" else prod - cand
            if not gain > min_delta:
                return False
        self.transition(name, version, "Production")
        return True

reg = ModelRegistry()
for acc, run in ((0.81, "run-1"), (0.84, "run-2"), (0.8405, "run-3"), (0.79, "run-4")):
    reg.register("churn", b"weights-" + run.encode(), {"acc": acc}, run)

for version in (1, 2, 3, 4):
    promoted = reg.promote_if_better("churn", version, "acc", min_delta=0.005)
    print(f"версия {version}: повышена={promoted}, стадии={reg.stages('churn')}")

reg.transition("churn", 1, "Production")     # откат: версия 1 снова в продакшене
print("после отката:", reg.stages("churn"))
```
```output
версия 1: повышена=True, стадии={1: 'Production', 2: 'None', 3: 'None', 4: 'None'}
версия 2: повышена=True, стадии={1: 'Archived', 2: 'Production', 3: 'None', 4: 'None'}
версия 3: повышена=False, стадии={1: 'Archived', 2: 'Production', 3: 'None', 4: 'None'}
версия 4: повышена=False, стадии={1: 'Archived', 2: 'Production', 3: 'None', 4: 'None'}
после отката: {1: 'Production', 2: 'Archived', 3: 'None', 4: 'None'}
```

Разбор:

* версия 1 повышается сразу: Production пуст. Версия 2 лучше на `0.03`, это больше порога, поэтому она занимает Production, а версия 1 уходит в `Archived`;
* версия 3 лучше текущей всего на `0.0005`: такая разница меньше порога `0.005`, и повышение отклонено. Это защита от смены модели по шуму в метрике;
* версия 4 хуже текущей, улучшения нет, `False`;
* откат - просто ещё один `transition` в `Production`: версия 1 из `Archived` возвращается в работу, а версия 2 сама отправляется в `Archived`. Данные никуда не пропали, поэтому откат занимает один вызов;
* реестр хранит для каждой версии контрольную сумму и `run_id`, значит по любой версии можно найти исходный запуск в трекере.

**Попробуйте.** В примере 3 вызовите `reg.promote_if_better("churn", 3, "acc", min_delta=0.0)` вместо `0.005`. Предскажите результат и стадии версий 2 и 3. Затем подумайте, почему на практике порог выбирают не нулевым и из каких данных можно оценить, какой разброс метрики считать шумом.

## Формат, реестр и стадии

**Безопасность и переносимость формата.** Файл модели - это входные данные для сервиса, поэтому к нему относятся так же осторожно, как к любому внешнему вводу. Практические правила:

* не распаковывать pickle (и форматы на его основе) из ненадёжных источников;
* хранить данные и описание, а не исполняемые объекты: JSON для маленьких моделей, специальные форматы для больших. Так, **safetensors** хранит тензоры без исполнения кода при загрузке, а **ONNX** описывает вычислительный граф независимо от фреймворка, и модель можно запускать в другом окружении;
* записывать версию схемы (`format`) и проверять её при чтении;
* считать контрольную сумму при сохранении и сверять при загрузке: она ловит повреждение при копировании и подмену файла.

Контрольная сумма не заменяет доверие к источнику: если злоумышленник подменил и файл, и записанный рядом хеш, проверка пройдёт. Поэтому сумму хранят в реестре, куда у посторонних нет записи, а не рядом с файлом на общем диске.

**Происхождение модели (lineage).** В записи версии мы храним `run_id`. Запуск, в свою очередь, хранит параметры и теги: отпечаток конфигурации, версию данных и коммит кода (см. предыдущие уроки). Это цепочка «модель - запуск - конфигурация, данные, код». Её полнота определяет, можно ли ответить на вопросы «чем обучена модель в продакшене?» и «почему новая версия хуже?». Описание модели для людей, где собраны назначение, данные, метрики и ограничения, называют **карточкой модели** (model card).

**Стадии.** Модель проходит стадии жизненного цикла:

| Стадия | Смысл |
|---|---|
| `None` | версия только зарегистрирована |
| `Staging` | проверяется на тестовом окружении |
| `Production` | обслуживает рабочий трафик; на одно имя одна версия |
| `Archived` | выведена из работы, но сохранена для отката и аудита |

Главный инвариант реестра: у каждого имени не более одной Production-версии. Поэтому перевод версии в `Production` атомарно отправляет прежнюю в `Archived`. Откат - это повторный перевод старой версии в `Production`.

**Ворота повышения.** `promote_if_better(...)` - простейшая реализация ворот (gate): кандидат становится рабочей моделью, только если он лучше текущей больше чем на порог. Порог защищает от смены по шуму, а режимы `max` и `min` позволяют использовать метрики разной природы (точность растёт, ошибка уменьшается). Реальные ворота шире: проверки на отложенной выборке, сравнение по срезам данных, нагрузочные и контрактные тесты, ручное подтверждение.

**Как это соотносится с MLflow Model Registry.** Подробности зависят от версии, поэтому сверяйтесь с [документацией](https://mlflow.org/docs/latest/model-registry/).

| Наш код | MLflow Model Registry (по общей идее) |
|---|---|
| `register(name, blob, metrics, run_id)` | регистрация модели из запуска: зарегистрированная модель (имя) и её версии |
| номер версии 1, 2, 3 для каждого имени | версии зарегистрированной модели |
| `transition(..., stage)` | перевод версии между стадиями (Staging, Production, Archived) |
| `latest(name, stage)` и `load` | получение модели по имени и стадии или версии |
| `run_id` в записи версии | связь версии с запуском в трекере |

В новых версиях MLflow вместо стадий рекомендуют псевдонимы (aliases): версии присваивается метка вроде `champion`, и сервис обращается по метке. Идея та же (указатель на нужную версию), только метки свободные, а не фиксированный набор; сверяйтесь с документацией вашей версии. Теги и описания версий в MLflow хранят то, что у нас находится в `metrics` и в метаданных модели.

## Типичные ошибки

* **Загрузка pickle от третьих лиц.** Скачанный файл весов в формате pickle может выполнить код при открытии. Для внешних моделей выбирайте формат без исполнения кода или проверяйте происхождение файла.
* **Нет контрольной суммы.** Повреждённый или подменённый файл остаётся валидным JSON и «успешно» загружается, а модель отвечает неверно. Считайте сумму при регистрации и сверяйте при загрузке.
* **Нет поля `format` или версии схемы.** Через полгода формат изменится, и старые файлы будут прочитаны неверно, а не отклонены. Версия схемы - часть файла.
* **Несколько Production-версий одной модели.** Сервис не знает, какую из них брать, и разные реплики отвечают по-разному. Реестр должен поддерживать инвариант сам, а не полагаться на дисциплину людей.
* **Удаление старых версий.** Без архива откат невозможен. Переведите версию в `Archived`, а чистите хранилище отдельной политикой.
* **Повышение по одному числу без порога.** Метрика на конечной выборке шумит, и модель, выигравшая 0.0005, может оказаться не лучше. Порог `min_delta` и проверки на разных срезах данных уменьшают риск случайных смен.
* **Сравнение метрик разного направления.** Для ошибки (`loss`) лучше меньшее значение, для точности (`acc`) - большее. Режим сравнения должен быть явным параметром, иначе «улучшением» окажется ухудшение.
* **Возврат внутреннего состояния реестра.** Если `get` возвращает сам словарь версии, вызывающий код может случайно изменить метрики или стадию в обход методов. Возвращайте копии.
* **Реестр без связи с запуском.** Версия без `run_id` и версии данных превращается в безымянный файл: непонятно, как её воспроизвести.

## Итоги

* Модель сохраняют в формате, который хранит данные, а не исполняемые объекты: pickle из ненадёжных источников небезопасен. Файл содержит версию схемы, а при регистрации записывается SHA-256.
* Реестр моделей хранит версии (номера для каждого имени), метрики, `run_id` и стадию. Инвариант: одна Production-версия на имя; откат - перевод старой версии обратно в Production.
* Повышение до Production проходит через ворота: улучшение метрики строго больше порога в выбранном направлении (`max` или `min`).
* Мини-платформа теперь умеет повторять запуск, записывать его, версионировать данные, пропускать неизменные шаги и хранить версии моделей. В следующем уроке модель начнёт отвечать на запросы: [обслуживание модели](lesson:mlops.fundamentals.model-serving).

## Кратко для тех, кто знаком с ML

* Не использовать pickle для моделей из внешних источников; формат с данными (JSON для малых моделей, ONNX или safetensors для больших), поле `format`, SHA-256 при регистрации и проверка при загрузке.
* Реестр: имя -> версии -> (blob, sha256, metrics, run_id, stage). Один Production на имя, откат через переход Archived -> Production.
* Повышение: `improvement = cand - prod` (max) или `prod - cand` (min), условие `improvement > min_delta`.
* В MLflow это зарегистрированные модели с версиями; стадии в новых версиях заменяют псевдонимы (aliases), сверяйтесь с документацией.
