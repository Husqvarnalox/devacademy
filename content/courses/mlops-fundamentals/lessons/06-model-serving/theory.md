## Обслуживание модели: от файла с весами к ответу на запрос

Обученная и записанная в реестр модель ещё ничего не делает для пользователя. Чтобы приложение получило предсказание, кто-то должен принять запрос, подготовить признаки, посчитать ответ и вернуть его. Эта часть называется **обслуживанием** (serving). В продакшене модель почти всегда живёт за сетевым сервисом: приложение отправляет данные, сервис отвечает числом и версией модели.

Есть два способа получать предсказания:

* **онлайн-вывод** (online inference) - ответ нужен сразу, пока человек ждёт: оценка риска при оформлении заявки, ранжирование ленты. Важны задержка ответа и устойчивость сервиса;
* **пакетный вывод** (batch inference) - предсказания считаются заранее для большого набора объектов по расписанию, например раз в ночь. Важны пропускная способность и стоимость, а задержка одного объекта не важна.

В этом уроке мы напишем **логику** онлайн-сервиса без самого веб-сервера. Это обычные функции: они проверяют входные данные, считают предсказание, режут большой запрос на пачки и превращают результат в пару «код ответа, тело». Веб-фреймворк потом только передаёт им сырое тело запроса, поэтому всё можно проверить обычными тестами.

Три идеи, на которых держится урок:

* **контракт сервиса** - список признаков, их типы и допустимые границы, версия модели. Клиент и сервис договариваются о нём заранее;
* **проверка на границе** - данные проверяются в момент входа в сервис, а не где-то внутри модели. Модель вернёт число для любого входа, в том числе для ошибочного;
* **единая подготовка признаков** - в обучении и в сервисе признаки считаются одним и тем же кодом. Иначе возникает **перекос обучения и обслуживания** (training-serving skew): модель получает на входе не то, на чём училась.

## Примеры

**Пример 1. Модель не замечает ошибочный вход.** Логистическая модель считает `z = bias + сумма(w * x)` и превращает её в вероятность сигмоидой. Любое число на входе даёт число на выходе, поэтому ошибка в данных не превращается в ошибку программы.

```python run
import math

MODEL = {"features": ["age", "income"], "weights": [0.04, 0.00002], "bias": -3.0}

def score(age, income):
    z = MODEL["bias"] + MODEL["weights"][0] * age + MODEL["weights"][1] * income
    return 1 / (1 + math.exp(-z))

# обучение: income в рублях в месяц; в сервисе клиент прислал тысячи рублей
print("правильные единицы :", round(score(40, 50000), 3))
print("перепутаны единицы :", round(score(40, 50), 3))
# модель не заметила подмены: ответ выглядит как обычная вероятность
print("абсурдный возраст  :", round(score(4000, 50000), 3))
```
```output
правильные единицы : 0.401
перепутаны единицы : 0.198
абсурдный возраст  : 1.0
```

Разбор: при доходе в тысячах вместо рублей вероятность упала с 0.401 до 0.198, но ни одной ошибки не случилось: оба ответа выглядят правдоподобно. Возраст 4000 даёт уверенную вероятность 1.0. Принцип «мусор на входе - уверенный мусор на выходе» (garbage in, confident garbage out) отражает суть: защиту должен обеспечить сервис, сама модель её не даст.

**Пример 2. Проверка, предсказание и пачки.** Соберём три функции из упражнения: `validate_row` возвращает список ошибок, `predict_one` считает предсказание для корректной строки, `predict_batch` обходит строки пачками и не даёт одной плохой строке сломать остальные.

```python run
import math

MODEL = {"name": "churn", "version": 3, "features": ["age", "income_k"],
         "weights": [0.04, 0.02], "bias": -3.0, "threshold": 0.5}
SCHEMA = {"age": {"min": 18, "max": 100}, "income_k": {"min": 0, "max": None}}


def validate_row(row, schema):
    if not isinstance(row, dict):
        return ["row: expected object"]
    errors = []
    for f in sorted(schema):
        if f not in row:
            errors.append(f"{f}: missing")
            continue
        v = row[f]
        if isinstance(v, bool) or not isinstance(v, (int, float)):
            errors.append(f"{f}: expected number")
        elif not math.isfinite(v):
            errors.append(f"{f}: expected finite number")
        elif (schema[f]["min"] is not None and v < schema[f]["min"]) or \
             (schema[f]["max"] is not None and v > schema[f]["max"]):
            errors.append(f"{f}: out of range")
    errors += [f"{k}: unknown field" for k in sorted(set(row) - set(schema))]
    return errors


def predict_one(model, row):
    z = model["bias"] + sum(w * row[f] for f, w in zip(model["features"], model["weights"]))
    p = 1 / (1 + math.exp(-z)) if z >= 0 else math.exp(z) / (1 + math.exp(z))
    return {"score": round(p, 6), "label": 1 if p >= model["threshold"] else 0}


def predict_batch(model, schema, rows, size):
    if size < 1:
        raise ValueError("max_batch_size must be >= 1")
    results = []
    for start in range(0, len(rows), size):
        for i, row in enumerate(rows[start:start + size], start):
            errors = validate_row(row, schema)
            results.append({"index": i, "ok": False, "errors": errors} if errors
                           else {"index": i, "ok": True, **predict_one(model, row)})
    return {"model": f"{model['name']}:{model['version']}",
            "batches": -(-len(rows) // size), "results": results}


rows = [{"age": 40, "income_k": 50}, {"age": "40", "income_k": 50},
        {"age": 60, "income_k": 80}, {"age": 30, "income_k": 5, "promo": 1},
        {"age": 25, "income_k": 5}]
out = predict_batch(MODEL, SCHEMA, rows, 2)
print(out["model"], "пачек:", out["batches"])
for r in out["results"]:
    print(r)
```
```output
churn:3 пачек: 3
{'index': 0, 'ok': True, 'score': 0.401312, 'label': 0}
{'index': 1, 'ok': False, 'errors': ['age: expected number']}
{'index': 2, 'ok': True, 'score': 0.731059, 'label': 1}
{'index': 3, 'ok': False, 'errors': ['promo: unknown field']}
{'index': 4, 'ok': True, 'score': 0.130108, 'label': 0}
```

Разбор построчно:

* `schema[f]["min"] is not None` - `None` означает «границы нет», поэтому у `income_k` проверяется только нижняя граница;
* `isinstance(v, bool)` проверяется раньше всего: `bool` в Python - подкласс `int`, и без этой проверки `True` молча сошёл бы за число 1;
* `math.isfinite` отсекает `NaN` и бесконечности, которые не попадают ни в одну из границ и иначе прошли бы проверку диапазона (любое сравнение с `NaN` ложно);
* в `predict_one` две ветки сигмоиды: для `z >= 0` считаем `1 / (1 + e^-z)`, для отрицательного `z` - `e^z / (1 + e^z)`. В обеих `math.exp` получает неположительный аргумент и не переполняется;
* строки 1 и 3 с ошибками получили `ok: False` и список причин, остальные посчитаны; индекс сквозной, он указывает на положение строки в запросе, а не в пачке;
* 5 строк по 2 в пачке - 3 пачки: последняя неполная. Формула `-(-n // size)` - деление с округлением вверх.

**Пример 3. Коды ответа.** Функция `handle_request` получает сырую строку тела запроса и возвращает пару `(статус, тело ответа)`. Здесь вместо настоящего `predict_batch` стоит заглушка: нас интересуют только коды.

```python run
import json


def predict_batch(model, schema, rows, size):
    # заглушка вместо predict_batch из примера 2: нас интересуют только коды ответа
    return {"model": "churn:3", "batches": -(-len(rows) // size), "results": [{"index": i} for i in range(len(rows))]}


def handle_request(model, schema, body, max_instances=100, max_batch_size=32):
    try:
        payload = json.loads(body)
    except ValueError:
        return 400, {"error": "invalid json"}
    if not isinstance(payload, dict) or not isinstance(payload.get("instances"), list):
        return 400, {"error": 'expected {"instances": [...]}'}
    if len(payload["instances"]) > max_instances:
        return 413, {"error": "too many instances", "limit": max_instances}
    return 200, predict_batch(model, schema, payload["instances"], max_batch_size)


bodies = [
    '{"instances": [{"age": 40}, {"age": 50}, {"age": 60}]}',
    '{"instances": [{"age": 1}, {"age": 2}, {"age": 3}, {"age": 4}, {"age": 5}]}',
    '{"rows": []}',
    '{"instances": [1, 2',
    '{"instances": []}',
]
for body in bodies:
    status, payload = handle_request(None, None, body, max_instances=4, max_batch_size=2)
    print(status, json.dumps(payload, ensure_ascii=False))
```
```output
200 {"model": "churn:3", "batches": 2, "results": [{"index": 0}, {"index": 1}, {"index": 2}]}
413 {"error": "too many instances", "limit": 4}
400 {"error": "expected {\"instances\": [...]}"}
400 {"error": "invalid json"}
200 {"model": "churn:3", "batches": 0, "results": []}
```

Разбор: три объекта при лимите 4 - обычный ответ 200 с двумя пачками. Пять объектов - 413: запрос корректен по форме, но превышает лимит. Тело без `instances` и оборванный JSON - 400: клиент нарушил контракт. Пустой список `instances` - законный запрос, ответ 200 с нулём пачек. `json.JSONDecodeError` является подклассом `ValueError`, поэтому ловим именно его родителя.

**Попробуйте.** В примере 3 замените `max_instances=4` на `5` и предскажите ответ на второе тело. Затем в примере 2 передайте `size=5` и ответьте: сколько будет пачек и изменятся ли индексы в `results`?

## Контракт сервиса и проверка на границе

**Контракт** описывает, что сервис принимает и что возвращает. В нашем уроке он состоит из двух словарей:

| Часть контракта | Где хранится | Что описывает |
|---|---|---|
| Модель | карточка из реестра (урок [5](lesson:mlops.fundamentals.model-registry)) | `name`, `version`, `features`, `weights`, `bias`, `threshold` |
| Схема входа | рядом с моделью, версионируется вместе с ней | допустимые признаки и границы `min`/`max` (`None` - без границы) |
| Ответ | код сервиса | `model` (`имя:версия`), `results` с `score`/`label` или `errors` |

Порядок признаков и сама схема - часть модели: новая версия может потребовать другие признаки, поэтому ответ всегда содержит `имя:версия`. Тогда любое предсказание можно сопоставить с моделью и журналом экспериментов.

Проверка на границе делает три вещи:

* отсекает **структурные** ошибки: строка не объект, нет признака, лишнее поле, не число;
* отсекает **значения вне допустимой области**: отрицательный возраст, `NaN`, бесконечность. Диапазон в схеме берётся из обучающих данных и здравого смысла предметной области, а не из модели;
* возвращает ошибки **детерминированно**: признаки по алфавиту, затем лишние ключи по алфавиту. Так одна и та же ошибка всегда выглядит одинаково, и по ней можно строить тесты и метрики.

Важное свойство: `NaN` в JSON. Стандарт его не допускает, но `json.loads` в Python принимает слово `NaN` и возвращает `float('nan')`. Любое сравнение с `NaN` ложно, поэтому проверка `value < min or value > max` его пропустит. Нужна явная проверка `math.isfinite`.

## Единая подготовка признаков и перекос

Если признаки в обучении считает один код (например, ноутбук с pandas), а в сервисе другой (переписанный на другом языке), расхождения почти неизбежны: единицы измерения, обработка пропусков, порядок категорий, округление. Это и есть **перекос обучения и обслуживания**. Защита: один и тот же код преобразования используется в обоих местах (общий пакет), либо преобразование входит в сохранённую модель, и обе стороны проверяются на общем наборе примеров.

## Пачки: задержка против пропускной способности

Настоящие модели часто считают сразу много строк быстрее, чем по одной: матричные операции лучше используют процессор или видеокарту. Но пачку надо собрать, а значит, первый запрос ждёт остальных.

| Размер пачки | Плюс | Минус |
|---|---|---|
| Маленький | низкая задержка, быстрый ответ | устройство недозагружено, выше цена одного предсказания |
| Большой | высокая пропускная способность | выше задержка, больше память, одна медленная строка тормозит всю пачку |

Серверы обслуживания обычно ограничивают и размер пачки, и время ожидания её заполнения. В нашем коде `max_batch_size` - ограничение размера пачки, `max_instances` - ограничение на весь запрос: без него один клиент мог бы занять сервис гигантским телом.

## Коды ответа

| Ситуация | Код | Тело |
|---|---|---|
| Тело не JSON | 400 | `{"error": "invalid json"}` |
| JSON есть, но нет списка `instances` | 400 | `{"error": "expected {\"instances\": [...]}"}` |
| Объектов больше `max_instances` | 413 | `{"error": "too many instances", "limit": N}` |
| Всё в порядке по форме | 200 | результат `predict_batch` |

Заметьте: некорректная **отдельная строка** не превращает ответ в 400. Запрос разобран, сервис отработал, и в `results` для плохих строк стоит `ok: false`. Так клиент получает предсказания по хорошим строкам и точные причины отказа по плохим. Код 413 в актуальных стандартах HTTP называется «Content Too Large» (раньше «Payload Too Large»). Подробнее о выборе кодов - в уроке [ошибки и статусы в FastAPI](lesson:fastapi.fundamentals.errors-and-status-codes).

## Как это соотносится с реальными инструментами

Наш `handle_request` не привязан к веб-фреймворку. Вот как его можно подключить к FastAPI (блок не запускается: FastAPI в песочнице курса недоступен).

```python
from fastapi import FastAPI, Request, Response

import serving  # модуль из упражнения

app = FastAPI()
MODEL = ...   # загружается один раз при старте сервиса из реестра (урок 5)
SCHEMA = ...  # схема входа, лежащая рядом с моделью


@app.post("/predict")
async def predict(request: Request, response: Response):
    body = await request.body()  # сырые байты; json.loads принимает и их
    status, payload = serving.handle_request(MODEL, SCHEMA, body)
    response.status_code = status
    return payload


@app.get("/healthz")
def healthz():
    return {"model": f"{MODEL['name']}:{MODEL['version']}"}
```

В реальном проекте проверку структуры обычно поручают моделям `pydantic` ([урок про pydantic](lesson:fastapi.fundamentals.pydantic-models)); FastAPI тогда сам возвращает ошибку валидации (по умолчанию 422). Мы отдали эту работу `validate_row`, чтобы увидеть, что именно проверяется, и вернуть ошибки по каждой строке отдельно.

| В нашем коде | Что делают реальные инструменты |
|---|---|
| `handle_request` | обработчик маршрута в FastAPI или аналогичном фреймворке |
| `validate_row` + схема | модели pydantic, схемы входа и выхода в сервере обслуживания |
| `predict_batch` | динамическое формирование пачек во встроенных серверах моделей |
| `model` в ответе | заголовки или поля ответа с версией модели |

BentoML, TorchServe и KServe решают ту же задачу обслуживания, но с разной степенью готовности: первые два упаковывают модель в сервис с API и пачками, KServe запускает такие сервисы в Kubernetes. Точные возможности и настройки зависят от версий, сверяйтесь с документацией выбранного инструмента.

## От функции до реплик в кластере

Концептуально путь такой. Сервис вместе с моделью и зависимостями **упаковывается в образ контейнера** (см. урок про [слои и контейнеры](lesson:devops.fundamentals.containers-and-layers)): образ содержит версию кода, зависимостей и ссылку на версию модели. Оркестратор вроде Kubernetes запускает несколько **реплик** образа за общим адресом. У каждой реплики есть проба готовности (readiness probe): трафик поступает, только когда модель загружена в память и сервис отвечает на проверочный запрос. Новую версию модели выпускают теми же приёмами, что и обычный код ([стратегии выкладки](lesson:devops.fundamentals.deployment-strategies)):

* **канареечный выпуск** (canary) - сначала небольшая доля трафика идёт на новую версию, и по метрикам решается, расширять ли её;
* **теневой режим** (shadow) - новая версия получает копию трафика, её ответы записываются, но клиенту не возвращаются. Для моделей это удобно: можно сравнить предсказания старой и новой версий на живых данных без риска.

Этих шагов в упражнениях нет, потому что они требуют Docker и кластера. Но функции из урока - ровно то, что внутри образа обрабатывает запрос.

## Типичные ошибки

* **Доверять входу.** Модель вернёт число для любых данных, включая ошибочные. Без проверки границ приложение получит уверенные, но бессмысленные предсказания.
* **`isinstance(x, (int, float))` без исключения `bool`.** `True` пройдёт как число 1. Проверяйте `bool` отдельно и раньше.
* **Забыть про `NaN` и бесконечность.** `float('nan') < 0` и `float('nan') > 100` оба ложны, поэтому проверка диапазона его пропустит; нужен `math.isfinite`.
* **Сигмоида «в лоб».** `1 / (1 + math.exp(-z))` при `z` около -1000 выбрасывает `OverflowError` ещё до деления. Выбирайте формулу по знаку `z`.
* **Округлять до сравнения с порогом.** Если `p = 0.9999997`, то `round(p, 6)` даёт 1.0, и при пороге 1.0 класс изменится. Сначала сравниваем точное `p`, потом округляем для ответа.
* **Один плохой объект - ошибка всего запроса.** Клиент теряет и корректные предсказания. Ошибку строки сообщайте в `results`, а 400 оставьте для запроса, который нельзя разобрать вообще.
* **Нет лимитов.** Без `max_instances` один запрос с миллионом объектов займёт сервис, а без ограничения размера пачки память вырастет вместе с запросом.
* **Разный код подготовки признаков.** Единицы измерения или обработка пропусков в сервисе отличаются от обучения - модель молча работает хуже.

<!-- section: summary -->
## Итоги

* Онлайн-вывод отвечает на каждый запрос сразу, пакетный считает заранее; от этого зависят требования к задержке и пропускной способности.
* Контракт сервиса - версия модели, список признаков и границы; проверка на границе обязательна, потому что модель не отличает ошибочный вход от нормального.
* Пачки повышают пропускную способность за счёт задержки; лимиты на размер пачки и запроса защищают сервис.
* `400` - запрос нельзя разобрать или он не соответствует форме, `413` - слишком большой запрос, `200` - ответ с результатами по каждой строке.
* Мини-платформа теперь умеет отвечать на запросы. В следующем уроке добавим наблюдение за входными данными: [дрейф данных](lesson:mlops.fundamentals.data-drift).

## Кратко для тех, кто знаком с ML

* Контракт: версия модели + схема признаков (типы, границы) + детерминированный список ошибок; в ответе всегда `имя:версия`.
* Проверка на границе: `bool` не число, `NaN`/бесконечность отдельной ошибкой, лишние поля запрещены.
* Сигмоида: ветвление по знаку `z` вместо `exp(-z)` для всех; порог сравнивается с неокруглённым `p`.
* Статусы: невалидный JSON и неверная форма - 400, слишком много объектов - 413, ошибки по строкам внутри 200.
* Перенос: `handle_request` - тело обработчика FastAPI; упаковка в образ, реплики с readiness-пробой, канареечный или теневой выпуск в Kubernetes.
