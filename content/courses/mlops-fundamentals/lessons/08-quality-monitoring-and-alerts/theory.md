## Что значит «модель работает хорошо» в продакшене

Сервис развёрнут, дрейф входов измеряется. Остаётся главный вопрос: **модель по-прежнему отвечает правильно?** Ответить на него труднее, чем кажется: правильные ответы (метки) приходят не сразу. Заявку одобрили сегодня, вернул ли клиент кредит - станет известно через месяцы. Поэтому мониторинг модели строится слоями, от быстрых и косвенных сигналов к медленным и точным:

| Слой | Что смотрим | Когда доступно | Урок |
|---|---|---|---|
| Здоровье сервиса | задержка, доля ошибок, нагрузка | сразу | [наблюдаемость и SLO](lesson:devops.fundamentals.observability-and-slos) |
| Качество данных и дрейф | пропуски, диапазоны, PSI, KS по признакам | сразу | [дрейф данных](lesson:mlops.fundamentals.data-drift) |
| Прокси-метрики модели | распределение предсказаний, средний score, доля класса 1 | сразу | этот урок |
| Качество модели | точность, полнота и другие метрики по меткам | с задержкой | этот урок |

**Прокси-метрики** - величины, которые можно посчитать без меток и которые резко меняются при проблемах: если средний score вдруг вырос с 0.2 до 0.6, что-то изменилось во входах или в самой модели, даже когда правильных ответов пока нет.

Когда метки приходят, считаем точность по **окнам времени**: все события из интервала `[k * window, (k + 1) * window)` образуют окно `k`. В окне учитываются только события с известной меткой; чем свежее окно, тем меньше в нём размеченных событий.

Затем надо решить, когда поднимать тревогу. Один плохой интервал - не повод будить дежурного: точность любого окна колеблется. Поэтому тревога срабатывает, если плохое значение держится **несколько окон подряд**, и выключается, когда значение вернулось в норму. Иначе приходит поток ложных тревог, к которым привыкают и перестают реагировать (**усталость от тревог**, alert fatigue).

Последний шаг - **решение о переобучении**. Мы объединяем сигналы дрейфа и качества в одно решение с перечнем причин. В этом уроке решает функция; в реальной системе то же решение запускает конвейер обучения и проверку кандидата перед выкладкой.

## Примеры

**Пример 1. Точность по окнам и запоздавшие метки.** Событие содержит время `ts`, предсказание `pred` и метку `label`, которая либо уже известна, либо `None`. Метки приходят через разные задержки, поэтому новые окна размечены хуже старых.

```python run
import random


def windowed_accuracy(events, window):
    stats = {}
    for e in events:
        if e["label"] is None:
            continue
        n, ok = stats.get(e["ts"] // window, (0, 0))
        stats[e["ts"] // window] = (n + 1, ok + (e["pred"] == e["label"]))
    return [{"window": w, "n": n, "accuracy": round(ok / n, 4)} for w, (n, ok) in sorted(stats.items())]


rng = random.Random(5)
events = []
for ts in range(300):                       # 1 событие в секунду, окно 100 секунд
    truth = rng.randrange(2)
    pred = truth if rng.random() < 0.9 else 1 - truth
    delay = 20 + (ts % 7) * 30              # метка приходит через delay секунд после события
    known = ts + delay <= 300               # в момент отчёта (t = 300) метка уже известна?
    events.append({"ts": ts, "pred": pred, "label": truth if known else None})

print("всего событий:", len(events), "| с меткой:", sum(e["label"] is not None for e in events))
for row in windowed_accuracy(events, 100):
    print(row)
```
```output
всего событий: 300 | с меткой: 191
{'window': 0, 'n': 100, 'accuracy': 0.85}
{'window': 1, 'n': 69, 'accuracy': 0.8551}
{'window': 2, 'n': 22, 'accuracy': 0.9545}
```

Разбор построчно:

* `e["ts"] // window` - номер окна; событие в момент `ts = 100` относится уже к окну 1, а не к окну 0;
* события с `label = None` пропускаются: «метка неизвестна» не означает «ответ неверен»;
* `ok + (e["pred"] == e["label"])` - сравнение даёт `True` или `False`, которые складываются как 1 и 0;
* в итоге в окне 0 размечены все 100 событий, в окне 1 - 69, в окне 2 - только 22. Точность в окне 2 (0.9545) завышена: среди размеченных оказались события с короткой задержкой метки, и выборка смещена. Поэтому в решении нужен минимум размеченных событий `min_samples`.

**Пример 2. Правило «значение плохое N окон подряд».** Это упрощённый аналог условия `for` в правилах Prometheus: тревога включается (`firing`), когда условие истинно `for_windows` окон подряд, и выключается (`resolved`), когда оно перестаёт быть истинным. Значение `None` означает «данных нет»: оно не прерывает серию и не сбрасывает счётчик.

```python run
def evaluate_rule(values, threshold, for_windows, direction="below"):
    events, streak, firing = [], 0, False
    for i, v in enumerate(values):
        if v is None:
            continue
        bad = v < threshold if direction == "below" else v > threshold
        if bad:
            streak += 1
            if streak >= for_windows and not firing:
                firing = True
                events.append([i, "firing"])
        else:
            streak = 0
            if firing:
                firing = False
                events.append([i, "resolved"])
    return events


accuracy = [0.91, 0.84, 0.90, 0.92, 0.83, 0.82, 0.81, None, 0.80, 0.90, 0.91, 0.84, 0.92]
for k in (1, 2, 3):
    print(f"for_windows = {k}:", evaluate_rule(accuracy, 0.85, k))
```
```output
for_windows = 1: [[1, 'firing'], [2, 'resolved'], [4, 'firing'], [9, 'resolved'], [11, 'firing'], [12, 'resolved']]
for_windows = 2: [[5, 'firing'], [9, 'resolved']]
for_windows = 3: [[6, 'firing'], [9, 'resolved']]
```

Разбор: при `for_windows = 1` тревога включается на каждый провал и выключается через окно - три включения за 13 окон. При `2` остаётся одна тревога, на индексе 5, когда серия плохих значений 0.83, 0.82 уже длилась два окна. При `3` она включается на индексе 6. Пропуск данных (`None` на индексе 7) серию не прерывает: 0.80 на индексе 8 продолжает тревогу, а 0.90 на индексе 9 закрывает её. Одиночные просадки 0.84 на индексах 1 и 11 тревоги при `for_windows >= 2` не дают.

**Пример 3. От событий к решению о переобучении.** Объединим всё: сгенерируем события с деградацией модели после момента 300, посчитаем точность по окнам, проверим правило и примем решение вместе с результатом дрейфа из прошлого урока.

```python run
import random


def windowed_accuracy(events, window):
    stats = {}
    for e in events:
        if e["label"] is None:
            continue
        n, ok = stats.get(e["ts"] // window, (0, 0))
        stats[e["ts"] // window] = (n + 1, ok + (e["pred"] == e["label"]))
    return [{"window": w, "n": n, "accuracy": round(ok / n, 4)} for w, (n, ok) in sorted(stats.items())]


def evaluate_rule(values, threshold, for_windows):
    events, streak, firing = [], 0, False
    for i, v in enumerate(values):
        if v is None:
            continue
        if v < threshold:
            streak += 1
            if streak >= for_windows and not firing:
                firing = True
                events.append([i, "firing"])
        else:
            streak = 0
            if firing:
                firing = False
                events.append([i, "resolved"])
    return events


def retraining_decision(drift_rows, accuracy_rows, min_accuracy, min_samples=30):
    reasons = [f"drift:{r['feature']}" for r in drift_rows if r["status"] == "alert"]
    eligible = [r for r in accuracy_rows if r["n"] >= min_samples]
    if not eligible:
        reasons.append("quality:insufficient-data")
    elif eligible[-1]["accuracy"] < min_accuracy:
        reasons.append(f"quality:{eligible[-1]['accuracy']:.4f}<{min_accuracy:.4f}")
    retrain = any(r.startswith("drift:") or (r.startswith("quality:") and r != "quality:insufficient-data") for r in reasons)
    return {"retrain": retrain, "reasons": reasons}


rng = random.Random(2024)
events = []
for ts in range(600):                                  # 10 окон по 60 секунд
    truth = rng.randrange(2)
    p_correct = 0.93 if ts < 300 else 0.72              # после t = 300 модель деградирует
    pred = truth if rng.random() < p_correct else 1 - truth
    labelled = ts < 540 and rng.random() > 0.05         # последние метки ещё не пришли
    events.append({"ts": ts, "pred": pred, "label": truth if labelled else None})
rng.shuffle(events)                                     # порядок прибытия не важен

rows = windowed_accuracy(events, 60)
print("окна с метками:", " ".join(f"{r['window']}:{r['accuracy']:.2f}(n={r['n']})" for r in rows))

series = [None] * 10
for r in rows:
    series[r["window"]] = r["accuracy"]
print("тревога:", evaluate_rule(series, 0.85, 2))

drift = [{"feature": "age", "psi": 0.31, "ks": 0.2, "status": "alert"},
         {"feature": "income", "psi": 0.02, "ks": 0.04, "status": "ok"}]
print("решение:", retraining_decision(drift, rows, 0.85))
print("без дрейфа:", retraining_decision([], rows[:4], 0.85))
```
```output
окна с метками: 0:0.90(n=58) 1:0.93(n=60) 2:0.98(n=58) 3:0.96(n=56) 4:0.89(n=57) 5:0.79(n=56) 6:0.69(n=59) 7:0.74(n=58) 8:0.73(n=55)
тревога: [[6, 'firing']]
решение: {'retrain': True, 'reasons': ['drift:age', 'quality:0.7273<0.8500']}
без дрейфа: {'retrain': False, 'reasons': []}
```

Разбор построчно:

* события перемешаны (`rng.shuffle`) - функция не должна рассчитывать на порядок;
* окно 9 (последние 60 секунд) целиком без меток и в `rows` не попало; ряд `series` для него остаётся `None`;
* точность упала в окнах 5 и 6 (0.79 и 0.69), причём окно 5 начинается ровно с `ts = 300`; серия из двух плохих окон даёт тревогу на индексе 6, а не 5;
* `retraining_decision` берёт **последнюю** строку с достаточным числом событий: окно 8 (0.7273 при пороге 0.85) вместе с дрейфом признака `age` даёт `retrain = True` и две причины;
* без дрейфа и по первым четырём окнам причин нет.

**Попробуйте.** В примере 3 поменяйте порог правила с `0.85` на `0.75` и предскажите, на каком окне теперь включится тревога и включится ли вообще. Затем поменяйте `min_samples` в `retraining_decision` на `58` и посмотрите, какая строка станет «последней подходящей».

## Окна и метки

`windowed_accuracy` группирует события по `ts // window`, считает среди размеченных долю `pred == label` и округляет до четырёх знаков. Результат отсортирован по номеру окна, в него входят только окна, где есть хотя бы одно размеченное событие. Свойства:

* порядок входных событий не важен;
* `ts`, кратные размеру окна, начинают новое окно;
* точность считается по размеченным событиям, поэтому важно сопровождать её числом `n`;
* метки, пришедшие позже, меняют уже посчитанные окна: отчёт по прошлым окнам можно пересчитывать;
* размеченные события могут быть нерепрезентативны: метки по спорным случаям часто приходят позже или не приходят вообще.

## Правило тревоги с условием «N подряд»

`evaluate_rule(values, threshold, for_windows, direction)` проходит по ряду значений метрики и хранит два состояния: счётчик подряд идущих плохих значений и признак «тревога включена».

| Событие | Что происходит |
|---|---|
| значение `None` | пропускаем: ни счётчик, ни состояние не меняются |
| значение плохое (`< threshold` при `below`, `> threshold` при `above`) | счётчик увеличивается; когда он достигает `for_windows` и тревоги ещё нет, пишем `[i, "firing"]` |
| значение хорошее | счётчик сбрасывается; если тревога была включена, пишем `[i, "resolved"]` |

Сравнения строгие: значение, равное порогу, считается хорошим. Пока тревога включена, повторные плохие значения новых событий не создают. Это защищает от лавины сообщений.

Для ряда, который «дребезжит» около порога (flapping), `for_windows` сглаживает шум, но создаёт задержку: тревога приходит не раньше `for_windows`-го плохого окна. Другой приём - **гистерезис**: порог включения и порог выключения различаются (например, включить при точности ниже 0.85, выключить при выше 0.88), так что тревога не переключается из-за значений вблизи одной границы. Мы его не реализуем, но идея та же.

## Решение о переобучении

`retraining_decision(drift_rows, accuracy_rows, min_accuracy, min_samples=30)` собирает список причин:

1. для каждой строки отчёта о дрейфе со статусом `alert` (в исходном порядке) - `drift:<признак>`;
2. берётся **последняя** строка точности, где `n >= min_samples`; если её точность **ниже** `min_accuracy` - причина вида `quality:0.7273<0.8500` (точность и минимум с четырьмя знаками после запятой) (точность, равная минимуму, не причина);
3. если подходящих строк нет вовсе - причина `quality:insufficient-data`: сведений недостаточно, и само по себе это переобучение не запускает.

`retrain` равно `True`, если есть хотя бы одна причина `drift:` или `quality:` (кроме `insufficient-data`). Отсутствие доказательств хорошего качества не равно доказательству плохого, поэтому на нехватке данных не переобучаем автоматически, но причину показываем, чтобы её увидел человек.

## Как это соотносится с реальными инструментами

В Prometheus правила тревог описываются в файле и вычисляются периодически. Условие `for` держит тревогу в состоянии ожидания, пока условие не будет выполняться заданное время подряд (формат правила ниже; имя метрики `model_accuracy_window` выбрано для примера, её нужно экспортировать из сервиса самостоятельно). Блок не запускается: Prometheus в песочнице курса недоступен.

```yaml
groups:
  - name: model-quality
    rules:
      - alert: ModelAccuracyLow
        expr: model_accuracy_window < 0.85
        for: 2h
        labels:
          severity: ticket
        annotations:
          summary: "Точность модели ниже 0.85 в течение двух часов"
```

| В нашем коде | В Prometheus и Grafana |
|---|---|
| `threshold`, `direction` | выражение `expr` с оператором сравнения |
| `for_windows` | длительность `for` (в единицах времени, а не в окнах) |
| событие `firing` / `resolved` | состояние алерта; доставка уведомлений обычно отдельный компонент (Alertmanager) |
| `None` в ряду | отсутствие ряда в выборке; пропажу данных контролируют отдельными правилами, например с `absent()` |
| `severity` (в примере выше) | метки (`labels`), по которым уведомления маршрутизируются: страница дежурному или тикет |
| ряд `accuracy` по окнам | панель Grafana с графиком метрики и порогом |

У нас пропуск данных не меняет состояние, а в реальном Prometheus поведение при отсутствии данных нужно проверить на своей конфигурации. Не все метрики качества надо превращать в страницы дежурному: срочные симптомы (сервис недоступен, задержка выросла) идут как «разбудить», медленные (дрейф, падение точности) - как тикет на рабочее время.

## Замкнутый контур

Решение о переобучении - не конец, а вход следующего этапа:

1. мониторинг (этот урок и [дрейф](lesson:mlops.fundamentals.data-drift)) выдаёт `retrain = True` и причины;
2. запускается конвейер обучения с новой версией данных и конфигурации ([конвейеры и кеш](lesson:mlops.fundamentals.pipelines-and-caching));
3. кандидат попадает в [реестр моделей](lesson:mlops.fundamentals.model-registry) и проходит проверки перед переводом в стадию Production;
4. выкладка идёт постепенно, например канареечно, а результат сравнивается со старой моделью ([стратегии выкладки](lesson:devops.fundamentals.deployment-strategies));
5. новая модель попадает под тот же мониторинг, и контур замыкается.

Автоматический запуск обучения не означает автоматическую замену модели: каждый следующий шаг - это проверка, которую кандидат может не пройти.

<!-- section: mistakes -->
## Типичные ошибки

* **Считать отсутствие метки ошибкой.** `None` - «не знаем», а не «ответ неверен». Тогда в свежих окнах точность была бы заниженной.
* **Доверять окну с малым числом событий.** Точность по 5 событиям колеблется от 0 до 1. Требуйте `min_samples` и выводите `n` рядом с точностью.
* **Тревога по одному плохому окну.** Любой шум даёт ложную тревогу; через неделю на неё перестают смотреть. Используйте `for_windows` или гистерезис.
* **Пропуск данных как «всё хорошо» или «всё плохо».** Отсутствие значения должно быть отдельным состоянием: оно не сбрасывает серию и не поднимает тревогу, но о пропаже источника нужна своя проверка.
* **Сравнивать округлённую точность с порогом вместо точного значения.** В нашем коде порог сравнивается со значением, округлённым до четырёх знаков. На граничных значениях это может дать другой результат, чем расчёт без округления; решите заранее, что используется в правиле.
* **Брать для решения старую строку вместо последней подходящей.** Старое низкое значение не должно запускать переобучение, если свежие окна в порядке.
* **Автоматически подменять модель после переобучения.** Кандидат должен пройти проверки реестра и постепенную выкладку.
* **Мониторить только качество и не смотреть на входы.** Метки приходят с задержкой, и о проблеме вы узнаете, когда ущерб уже нанесён; дрейф входов даёт ранний сигнал.

<!-- section: summary -->
## Итоги

* Мониторинг модели строится слоями: здоровье сервиса, качество данных и дрейф, прокси-метрики, качество по меткам с задержкой.
* Точность считается по окнам среди размеченных событий; у каждого окна есть число `n`, и малым окнам доверять нельзя.
* Условие «N окон подряд» (аналог `for` в Prometheus) уменьшает число ложных тревог; серия прерывается хорошим значением, а `None` её не трогает.
* Решение о переобучении объединяет дрейф и качество и всегда сообщает причины; нехватка данных причина для внимания человека, а не для автоматического запуска.
* Контур замыкается так: мониторинг, решение, конвейер, реестр с проверками, канареечная выкладка, снова мониторинг.

**Чего курс не охватывает.** Мы не устанавливали и не запускали настоящие MLflow и DVC: упражнения воспроизводят их идеи, а не интерфейсы. Docker и Kubernetes разобраны только на уровне понятий, как и хранилища признаков (feature stores). Мы не разбирали онлайн A/B-тесты, где сравнение моделей идёт на живых пользователях со статистической проверкой результата. За рамками остались также безопасность и приватность данных, объяснимость и справедливость моделей. Это следующие шаги, когда вы будете работать с реальными инструментами; опора на идеи из курса поможет читать их документацию.

## Кратко для тех, кто знаком с ML

* `windowed_accuracy`: окно `ts // window`, только размеченные события, `n` рядом с точностью; пустые окна не возвращаются.
* `evaluate_rule`: аналог Prometheus `for`: счётчик подряд плохих значений, `None` - нет данных (состояние не меняется), строгие сравнения, повторные срабатывания не создают событий.
* `retraining_decision`: причины `drift:<f>` для alert, затем качество по последней строке с `n >= min_samples`; точность, равная минимуму, не причина; `insufficient-data` сам по себе не запускает переобучение.
* Контур: мониторинг, решение, конвейер, реестр с проверками, канареечная выкладка. Сигнал тревоги не заменяет человека в цикле выкладки.
