## Зачем версионировать данные

Код версионируют давно: Git помнит, что изменилось в каждом коммите. С данными сложнее. Таблица на 5 ГБ в репозиторий не помещается, а в именах файлов появляется `data_final.csv`, потом `data_final_v2.csv`, потом `data_final_v2_fixed.csv`. Через месяц никто не скажет, чем отличаются эти файлы, какой из них использовался для вчерашней модели и совпадает ли «тот же» файл на ноутбуке коллеги с вашим.

Имя файла - договорённость людей, а не свойство данных. Надёжнее вычислять версию из самого содержимого. Это называется **адресацией по содержимому** (content addressing): объект получает имя по хешу своих байтов. Два файла с одинаковым содержимым имеют одинаковое имя, а изменение хотя бы одного байта даёт новое.

Из этой идеи собирается вся система версионирования данных:

* **хеш файла** - SHA-256 его байтов, идентификатор содержимого;
* **манифест** (manifest) - небольшой текстовый список «путь - хеш» для всего набора данных; его можно хранить в Git рядом с кодом;
* **версия набора** - короткий хеш от манифеста: меняется при любой правке, добавлении, удалении или переименовании файла;
* **кеш объектов** - хранилище, где файлы лежат под именами-хешами; сами большие данные находятся там (или в удалённом хранилище), а в репозитории остаётся только манифест.

Похоже устроены, например, DVC и Git: команда `dvc add` превращает файл в запись «путь - хеш», а сами данные уезжают в кеш. В этом уроке мы сделаем то же самое сами. После него у запуска обучения появятся три записанных входа: конфигурация (отпечаток из [первого урока](lesson:mlops.fundamentals.reproducibility)), версия данных (этот урок) и версия кода (коммит Git). Вместе они однозначно определяют запуск.

## Примеры

**Пример 1. От файлов к версии набора.** Построим манифест каталога и посчитаем его версию. Затем правим один файл, затем возвращаем его назад.

```python run
import hashlib
import os
import tempfile
from pathlib import Path

def file_digest(path, chunk_size=65536):
    sha = hashlib.sha256()
    with open(path, "rb") as f:
        while chunk := f.read(chunk_size):
            sha.update(chunk)
    return sha.hexdigest()

def build_manifest(root):
    root = Path(root)
    entries = {p.relative_to(root).as_posix(): file_digest(p) for p in root.rglob("*") if p.is_file()}
    return dict(sorted(entries.items()))

def dataset_version(manifest):
    text = "".join(f"{digest}  {path}\n" for path, digest in sorted(manifest.items()))
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]

with tempfile.TemporaryDirectory(dir=os.getcwd()) as root:
    root = Path(root)
    (root / "raw").mkdir()
    (root / "raw" / "train.csv").write_text("id,y\n1,0\n2,1\n", encoding="utf-8")
    (root / "labels.txt").write_text("0\n1\n", encoding="utf-8")

    manifest = build_manifest(root)
    for path, digest in manifest.items():
        print(digest[:16], path)
    print("версия:", dataset_version(manifest))

    # меняем одну запись в одном файле
    (root / "raw" / "train.csv").write_text("id,y\n1,0\n2,1\n3,1\n", encoding="utf-8")
    print("после правки:", dataset_version(build_manifest(root)))

    # возвращаем исходное содержимое
    (root / "raw" / "train.csv").write_text("id,y\n1,0\n2,1\n", encoding="utf-8")
    print("после отката:", dataset_version(build_manifest(root)))
```
```output
82c1315e6c757f33 labels.txt
8fe2160aff977a6c raw/train.csv
версия: 76917f82d3e0
после правки: 8348c59c3fad
после отката: 76917f82d3e0
```

Разбор построчно:

* `file_digest` читает файл блоками: `f.read(chunk_size)` возвращает пустые байты в конце файла, и цикл заканчивается. Метод `update` можно вызывать много раз, результат равен хешу всего содержимого. Память занимает один блок, поэтому файл на десятки гигабайт не проблема;
* в `build_manifest` ключ - относительный путь через `as_posix()` (всегда с `/`, на любой операционной системе), а значения - хеши. `sorted` делает порядок ключей одинаковым на любой машине: порядок обхода каталога не гарантирован;
* `dataset_version` хеширует строки «хеш, два пробела, путь» - формат, как у утилиты `sha256sum`. Версия зависит и от содержимого файлов, и от их путей;
* после правки версия изменилась, после отката вернулась прежняя: версия - функция содержимого, а не истории изменений.

**Пример 2. Что изменилось между версиями.** Сравнение двух манифестов отвечает на вопрос «чем версия 2 отличается от версии 1». Если файл поменял только путь, его хеш остаётся прежним, и это переименование, а не удаление с добавлением.

```python run
def diff_manifests(old, new):
    added = sorted(set(new) - set(old))
    removed = sorted(set(old) - set(new))
    modified = sorted(p for p in set(old) & set(new) if old[p] != new[p])
    removed_by, added_by = {}, {}
    for p in removed:
        removed_by.setdefault(old[p], []).append(p)
    for p in added:
        added_by.setdefault(new[p], []).append(p)
    renamed = sorted([r, a] for digest, rs in removed_by.items() for r, a in zip(rs, added_by.get(digest, [])))
    gone = {r for r, _ in renamed}
    came = {a for _, a in renamed}
    return {"added": [p for p in added if p not in came], "removed": [p for p in removed if p not in gone],
            "modified": modified, "renamed": renamed}

v1 = {"raw/a.csv": "h-a", "raw/b.csv": "h-b", "raw/c.csv": "h-c", "labels.txt": "h-l"}
v2 = {"clean/a.csv": "h-a", "raw/b.csv": "h-b2", "raw/d.csv": "h-d", "labels.txt": "h-l"}
for kind, paths in diff_manifests(v1, v2).items():
    print(f"{kind:9}", paths)
```
```output
added     ['raw/d.csv']
removed   ['raw/c.csv']
modified  ['raw/b.csv']
renamed   [['raw/a.csv', 'clean/a.csv']]
```

Разбор: для простоты вместо настоящих хешей используются короткие строки `h-a`, `h-b` и так далее - манифест это обычный словарь. `raw/a.csv` исчез, а `clean/a.csv` появился с тем же `h-a`, поэтому они связаны в `renamed` и выпали из `added` и `removed`. `raw/b.csv` на месте, но с другим хешем - `modified`. `raw/c.csv` и `raw/d.csv` не нашли пару по хешу, поэтому остались `removed` и `added`. Группировка по хешу в словарях и `zip` по отсортированным спискам задают порядок связывания, когда одинаковых хешей несколько: i-й удалённый с i-м добавленным.

**Пример 3. Кеш объектов и восстановление.** Копируем каждый файл в кеш под именем-хешем, а манифест сохраняем отдельно. Затем «теряем» рабочий каталог и восстанавливаем его по манифесту.

```python run
import hashlib
import json
import os
import shutil
import tempfile
from pathlib import Path

def file_digest(path):
    return hashlib.sha256(Path(path).read_bytes()).hexdigest()

def store_object(cache_dir, path):
    digest = file_digest(path)
    target = Path(cache_dir) / digest[:2] / digest[2:]
    if not target.exists():
        target.parent.mkdir(parents=True, exist_ok=True)
        shutil.copyfile(path, target)
    return digest

with tempfile.TemporaryDirectory(dir=os.getcwd()) as tmp:
    tmp = Path(tmp)
    data, cache = tmp / "data", tmp / "cache"
    (data / "copy").mkdir(parents=True)
    (data / "train.csv").write_text("id,y\n1,0\n2,1\n", encoding="utf-8")
    (data / "copy" / "train_backup.csv").write_text("id,y\n1,0\n2,1\n", encoding="utf-8")   # тот же текст
    (data / "labels.txt").write_text("0\n1\n", encoding="utf-8")

    manifest = {p.relative_to(data).as_posix(): store_object(cache, p) for p in sorted(data.rglob("*")) if p.is_file()}
    print("файлов в данных:", len(manifest), "| объектов в кеше:", sum(1 for p in cache.rglob("*") if p.is_file()))
    (tmp / "data.manifest.json").write_text(json.dumps(manifest, indent=1, sort_keys=True), encoding="utf-8")
    print("размер манифеста:", (tmp / "data.manifest.json").stat().st_size, "байт")

    shutil.rmtree(data)                       # рабочая копия потеряна
    for rel, digest in json.loads((tmp / "data.manifest.json").read_text(encoding="utf-8")).items():
        out = data / rel
        out.parent.mkdir(parents=True, exist_ok=True)
        shutil.copyfile(cache / digest[:2] / digest[2:], out)   # восстановление по манифесту
    print("восстановлено:", sorted(p.relative_to(data).as_posix() for p in data.rglob("*") if p.is_file()))
    print("train.csv:", repr((data / "train.csv").read_text(encoding="utf-8")))
```
```output
файлов в данных: 3 | объектов в кеше: 2
размер манифеста: 261 байт
восстановлено: ['copy/train_backup.csv', 'labels.txt', 'train.csv']
train.csv: 'id,y\n1,0\n2,1\n'
```

Разбор:

* файлов три, а объектов в кеше два: `train.csv` и его копия имеют одно содержимое и один хеш, поэтому хранятся один раз. Манифест при этом помнит оба пути;
* первые два символа хеша становятся именем подкаталога, остальные - именем файла. Так в одном каталоге не накапливаются миллионы файлов (приём заимствован из Git);
* манифест - JSON на пару сотен байт. Его можно положить в Git, а данные остаются в кеше; для восстановления нужны только манифест и доступ к кешу (локальному или удалённому);
* `if not target.exists()` делает сохранение идемпотентным: повторный вызов для того же содержимого ничего не копирует.

**Попробуйте.** В примере 3 перед восстановлением удалите из кеша один объект (`next(cache.rglob("*/*")).unlink()`) и посмотрите, на каком файле восстановление остановится. Подумайте, как сделать восстановление безопаснее: что нужно проверить, прежде чем копировать объект в рабочий каталог.

## Манифест, версия и кеш

**Хеш содержимого.** SHA-256 превращает любую последовательность байтов в 256 бит (64 шестнадцатеричных символа). Случайное совпадение хешей двух разных файлов практически невозможно, а совпадение хешей одинаковых файлов гарантировано. На этом свойстве держится вся система: «тот же хеш - те же данные».

**Манифест.** Словарь `{относительный путь: хеш}`. Три договорённости делают его пригодным для сравнения между машинами:

* пути относительные и с `/` (`as_posix()`), а не абсолютные и не с `\`;
* ключи отсортированы, чтобы файл манифеста выглядел одинаково при любом порядке обхода;
* в манифест входят только файлы: пустые каталоги не имеют содержимого и версии не влияют (в Git, например, они тоже не хранятся).

**Версия набора.** Короткий хеш от строк манифеста. В строку входит и хеш, и путь: переименование меняет версию, даже если байты те же. Формат «хеш, два пробела, путь» совпадает с форматом файла утилиты `sha256sum`, поэтому её удобно использовать для самопроверки.

**Различия версий.** `diff_manifests` сводится к операциям над множествами путей: добавленные, удалённые, изменённые (общий путь, другой хеш). Переименование определяется по хешу: если у удалённого и добавленного путей одинаковое содержимое, это один файл с новым именем. Когда одинаковых хешей несколько (дубликаты данных), однозначной пары нет, и нужно правило: мы связываем i-й удалённый с i-м добавленным по алфавиту, остальные остаются удалёнными или добавленными. Важно, что правило детерминировано: один и тот же вход всегда даёт один и тот же ответ.

**Кеш по содержимому.** Объект с хешем `d` лежит в `cache/d[:2]/d[2:]`. Свойства:

* одинаковое содержимое хранится один раз, сколько бы путей на него ни указывало;
* объект никогда не меняется: новое содержимое - новый хеш - новый объект. Поэтому повторное сохранение не нужно и его пропускают;
* «удалить версию данных» означает убрать записи манифеста; объекты, на которые больше никто не ссылается, чистят отдельным проходом (сборка мусора).

**Что хранить в Git, а что в кеше.** В Git кладут манифест (маленький текстовый файл, который показывает построчный diff). В кеше и удалённом хранилище лежат тяжёлые данные. Чтобы получить версию данных, нужен манифест из нужного коммита и доступ к объектам.

**Как это соотносится с DVC.** Подробности зависят от версии, поэтому сверяйтесь с [документацией DVC](https://dvc.org/doc).

| Наш код | DVC (по общей идее) |
|---|---|
| `build_manifest` и хеши файлов | `dvc add data/` создаёт маленький файл `.dvc` с хешем данных |
| манифест в Git | файл `.dvc` или `dvc.lock` в Git |
| `store_object` и кеш | локальный кеш DVC, адресуемый по хешу |
| `diff_manifests` | `dvc diff` показывает различия между версиями |
| восстановление по манифесту | `dvc checkout` приводит рабочий каталог в соответствие с указателем |
| передача объектов в хранилище | `dvc push` и `dvc pull` синхронизируют кеш с удалённым хранилищем |

Алгоритм хеширования и точная раскладка кеша в DVC определяются его версией и настройками, поэтому наша раскладка `d[:2]/d[2:]` годится как модель идеи, а не как описание формата конкретного инструмента.

**Полная идентичность запуска.** Запуск обучения определяется тремя версиями: **код** (коммит Git), **данные** (`dataset_version`) и **конфигурация** (`config_fingerprint` из первого урока). Их можно записать в параметры или теги запуска в трекере из [прошлого урока](lesson:mlops.fundamentals.experiment-tracking). Если у двух запусков равны все три версии (и окружение), результаты должны совпасть; если нет - различие нужно искать в недетерминизме.

## Типичные ошибки

* **Версия из имени, даты или размера.** `data_final_v2_fixed.csv`, время изменения и размер не гарантируют ничего: после копирования или `git checkout` время меняется у неизменных файлов, а размер совпадает у разных. Считайте версию из содержимого.
* **Чтение файла целиком.** `Path.read_bytes()` на файле в десятки гигабайт исчерпает память. Читайте блоками и подавайте их в `update`.
* **Абсолютные пути и обратные слэши в манифесте.** Манифест с путём `C:\data\a.csv` нельзя сравнить с манифестом на другой машине. Используйте относительные пути и `as_posix()`.
* **Непредсказуемый порядок.** Порядок обхода каталога зависит от файловой системы. Если ключи манифеста не отсортированы, одинаковые наборы дадут разные версии. Сортируйте всегда.
* **Хеш от пути и времени вместе с содержимым.** Версия, которая зависит от даты создания, меняется при копировании каталога. В версии должны участвовать только путь и содержимое.
* **Перезапись существующего объекта кеша.** Объект неизменяем: запись поверх него без необходимости тратит время и при сбое посередине может оставить повреждённый файл. Проверяйте наличие до копирования. В промышленных системах дополнительно пишут во временный файл и переименовывают его на место, чтобы оборванная запись не выглядела готовым объектом.
* **Путаница «переименован» и «изменён».** Файл, у которого поменялись и путь, и содержимое, - это удаление старого и добавление нового; связывать пары нужно только по равному хешу.
* **Данные в Git вместе с кодом.** Большие файлы раздувают репозиторий навсегда. В Git должен лежать указатель (манифест), а не данные.

## Итоги

* Версия данных вычисляется из содержимого: хеш файла, манифест «путь - хеш», короткая версия набора от манифеста.
* `diff_manifests` показывает, что изменилось между версиями, и отличает переименование от удаления и добавления по равному хешу.
* Кеш, адресуемый по содержимому, хранит одинаковые данные один раз и никогда не перезаписывает готовый объект; в Git остаётся только небольшой манифест.
* Идентичность запуска = версия кода + версия данных + отпечаток конфигурации. Каждую из них мы теперь умеем вычислять.
* В следующем уроке эти отпечатки станут ключами кеша шагов конвейера: [конвейеры и кеширование](lesson:mlops.fundamentals.pipelines-and-caching).

## Кратко для тех, кто знаком с ML

* Версия данных = хеш манифеста `{относительный путь: sha256}`; в строки хеширования входят хеш и путь, ключи отсортированы.
* Хешировать файлы блоками (`while chunk := f.read(n): sha.update(chunk)`); хранить объекты как `cache/<h[:2]>/<h[2:]>`; не перезаписывать готовые.
* В Git хранится манифест (в DVC - файл `.dvc` или `dvc.lock`), данные лежат в кеше и удалённом хранилище; детали зависят от версии DVC.
* Полная идентичность запуска: commit кода + `dataset_version` + `config_fingerprint`.
