## Зачем нужен журнал экспериментов

За неделю работы над моделью легко накопить два десятка запусков: меняли скорость обучения, набор признаков, размер выборки. Через неделю возникает вопрос: «какой из них был лучшим и чем он отличался от соседних?». Если результаты записаны в таблицу вручную, в ней обычно есть итоговое число и пара параметров. Нет другого: какой версией данных и кода получен результат, как менялась метрика по ходу обучения, завершился ли запуск или упал на середине, кто его запускал.

**Запуск** (run) - одна попытка обучения, записанная целиком. Журнал экспериментов, или **трекер**, хранит для каждого запуска:

* **параметры** (params) - входы, которые мы задали: скорость обучения, число эпох, отпечаток конфигурации из [предыдущего урока](lesson:mlops.fundamentals.reproducibility);
* **метрики** (metrics) - числа, измеренные во время запуска. Каждая запись содержит имя, значение и **шаг** (step), поэтому видна кривая, а не одна точка;
* **теги** (tags) - свободные пометки: автор, ветка кода, ссылка на задачу;
* **статус** (status) - выполняется, завершён, упал;
* **артефакты** (artifacts) - файлы запуска: веса модели, графики. В нашем упражнении их нет, они рассматриваются в уроке про реестр моделей.

Настоящие трекеры (MLflow, Weights & Biases и другие) делают то же самое, добавляя веб-интерфейс и сервер. В этом уроке мы построим минимальный трекер на файлах и каталогах: так хорошо видно, что именно записывается, и это пригодится для всех следующих уроков.

## Примеры

**Пример 1. Как выглядит запуск на диске.** Запуск - это каталог. Параметры и метаданные лежат в двух небольших файлах, а метрики дописываются в журнал по одной строке.

```python run
import json
import os
import tempfile
from pathlib import Path

def canonical_json(obj):
    return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)

def start_run(root, run_id, params, tags=None):
    run_dir = Path(root) / run_id
    run_dir.mkdir(parents=True)
    (run_dir / "params.json").write_text(canonical_json(params), encoding="utf-8")
    meta = {"run_id": run_id, "status": "RUNNING", "tags": tags or {}}
    (run_dir / "meta.json").write_text(canonical_json(meta), encoding="utf-8")
    return run_dir

def log_metric(root, run_id, key, value, step):
    line = canonical_json({"key": key, "step": step, "value": value}) + "\n"
    with open(Path(root) / run_id / "metrics.jsonl", "a", encoding="utf-8") as f:
        f.write(line)

with tempfile.TemporaryDirectory(dir=os.getcwd()) as root:
    start_run(root, "run-a", {"lr": 0.1, "epochs": 3}, {"автор": "Ана"})
    for step, loss in enumerate([0.9, 0.5, 0.3]):
        log_metric(root, "run-a", "loss", loss, step)
    for path in sorted(Path(root).rglob("*")):
        if path.is_file():
            print(path.relative_to(root).as_posix())
            print("   ", path.read_text(encoding="utf-8").rstrip().replace("\n", "\n    "))
```
```output
run-a/meta.json
    {"run_id":"run-a","status":"RUNNING","tags":{"автор":"Ана"}}
run-a/metrics.jsonl
    {"key":"loss","step":0,"value":0.9}
    {"key":"loss","step":1,"value":0.5}
    {"key":"loss","step":2,"value":0.3}
run-a/params.json
    {"epochs":3,"lr":0.1}
```

Разбор построчно:

* `canonical_json` - та же функция, что в предыдущем уроке. Ключи отсортированы, пробелов нет, а значит, файл с одними и теми же данными всегда выглядит одинаково и его удобно сравнивать;
* `run_dir.mkdir(parents=True)` без `exist_ok` выбросит `FileExistsError`, если запуск с таким `run_id` уже есть. Это защита от случайной перезаписи чужих результатов;
* `meta.json` получает статус `RUNNING`: пока обучение идёт, запуск числится незавершённым;
* `log_metric` открывает файл в режиме `"a"` и дописывает одну строку. Формат «одна JSON-запись на строку» называется JSON Lines. Журнал растёт в конец, а старые строки не переписываются;
* кириллица в теге хранится как есть (`ensure_ascii=False`), файл читается глазами без `\u`-последовательностей.

**Пример 2. Два запуска и выбор лучшего.** Обучим модель `y = w * x` градиентным спуском с двумя скоростями обучения, запишем среднеквадратичную ошибку на каждой эпохе и найдём лучший запуск. Вспомогательные функции чтения и поиска здесь сокращены: проверок входных данных нет, в упражнении они нужны.

```python run
import json
import os
import tempfile
from pathlib import Path

def canonical_json(obj):
    return json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)

def read_json(path):
    return json.loads(Path(path).read_text(encoding="utf-8"))

def start_run(root, run_id, params):
    run_dir = Path(root) / run_id
    run_dir.mkdir(parents=True)
    (run_dir / "params.json").write_text(canonical_json(params), encoding="utf-8")
    (run_dir / "meta.json").write_text(canonical_json({"run_id": run_id, "status": "RUNNING", "tags": {}}), encoding="utf-8")

def log_metric(root, run_id, key, value, step):
    with open(Path(root) / run_id / "metrics.jsonl", "a", encoding="utf-8") as f:
        f.write(canonical_json({"key": key, "step": step, "value": value}) + "\n")

def end_run(root, run_id, status):
    path = Path(root) / run_id / "meta.json"
    meta = read_json(path)
    meta["status"] = status
    path.write_text(canonical_json(meta), encoding="utf-8")

def load_run(root, run_id):
    run_dir = Path(root) / run_id
    meta, history = read_json(run_dir / "meta.json"), {}
    for line in (run_dir / "metrics.jsonl").read_text(encoding="utf-8").splitlines():
        rec = json.loads(line)
        history.setdefault(rec["key"], []).append([rec["step"], rec["value"]])
    for points in history.values():
        points.sort(key=lambda p: p[0])
    return {**meta, "params": read_json(run_dir / "params.json"),
            "metrics": {k: pts[-1][1] for k, pts in history.items()}, "history": history}

def best_run(root, metric, mode="max"):
    best_id, best_value = None, None
    for run_dir in sorted(p for p in Path(root).iterdir() if p.is_dir()):
        run = load_run(root, run_dir.name)
        if run["status"] != "FINISHED" or metric not in run["metrics"]:
            continue
        value = run["metrics"][metric]
        if best_value is None or (value > best_value if mode == "max" else value < best_value):
            best_id, best_value = run_dir.name, value
    return best_id

def train(root, run_id, lr, epochs):
    """Градиентный спуск для y = w * x на пяти точках; в журнал пишем среднеквадратичную ошибку по эпохам."""
    xs, ys = [1, 2, 3, 4, 5], [2.1, 3.9, 6.2, 7.8, 10.1]
    start_run(root, run_id, {"lr": lr, "epochs": epochs})
    w = 0.0
    for epoch in range(epochs):
        grad = sum(2 * (w * x - y) * x for x, y in zip(xs, ys)) / len(xs)
        w -= lr * grad
        mse = sum((w * x - y) ** 2 for x, y in zip(xs, ys)) / len(xs)
        log_metric(root, run_id, "mse", round(mse, 4), epoch)
    end_run(root, run_id, "FINISHED")

with tempfile.TemporaryDirectory(dir=os.getcwd()) as root:
    train(root, "run-slow", lr=0.001, epochs=10)
    train(root, "run-fast", lr=0.01, epochs=10)
    for run_id in ("run-slow", "run-fast"):
        run = load_run(root, run_id)
        print(run_id, run["status"], run["params"], "mse по эпохам:", [v for _, v in run["history"]["mse"]][::3], "итог:", run["metrics"]["mse"])
    print("лучший запуск (min mse):", best_run(root, "mse", mode="min"))
```
```output
run-slow FINISHED {'epochs': 10, 'lr': 0.001} mse по эпохам: [42.2603, 36.9827, 32.3644, 28.3232] итог: 28.3232
run-fast FINISHED {'epochs': 10, 'lr': 0.01} mse по эпохам: [26.8889, 6.0723, 1.3844, 0.3287] итог: 0.3287
лучший запуск (min mse): run-fast
```

Разбор:

* `train` не знает, где и как хранятся метрики: она только вызывает `start_run`, `log_metric` и `end_run`. Так же устроен код с настоящим трекером: функцию обучения почти не меняют, добавляются вызовы журнала;
* `load_run` собирает запуск обратно из файлов. `history` - вся кривая, `metrics` - только её последняя точка. `[::3]` в `print` выводит каждую третью эпоху, чтобы строка не была длинной;
* `best_run` перебирает каталоги в алфавитном порядке и берёт запуск с наименьшей итоговой ошибкой. Скорость `0.01` за десять эпох дошла до `0.3287`, а `0.001` остановилась на `28.3232`: при одинаковом числе эпох запуск с большей скоростью обучения успел продвинуться дальше к минимуму, а медленный ещё далеко от него;
* `sorted(...)` над каталогами нужен для детерминизма: порядок, в котором файловая система отдаёт имена, не гарантируется.

**Пример 3. Шаги приходят в произвольном порядке.** В реальном обучении метрики пишут разные потоки, а при перезапуске шаг могут записать дважды. Поэтому историю сортируют по шагу, а итоговым значением берут последнюю точку.

```python run
import json

# строки metrics.jsonl так, как они легли в файл: шаг 2 записан раньше шага 1, шаг 3 - дважды
lines = [
    '{"key":"val_loss","step":0,"value":0.90}',
    '{"key":"val_loss","step":2,"value":0.55}',
    '{"key":"val_loss","step":1,"value":0.70}',
    '{"key":"val_loss","step":3,"value":0.60}',
    '{"key":"val_loss","step":3,"value":0.58}',
]
history = []
for line in lines:
    rec = json.loads(line)
    history.append([rec["step"], rec["value"]])

history.sort(key=lambda point: point[0])
print("история:", history)
print("итоговое значение:", history[-1][1])
print("лучший шаг:", min(history, key=lambda point: point[1])[0])
```
```output
история: [[0, 0.9], [1, 0.7], [2, 0.55], [3, 0.6], [3, 0.58]]
итоговое значение: 0.58
лучший шаг: 2
```

Разбор: `list.sort` устойчива, то есть равные по ключу элементы сохраняют исходный порядок. Две точки шага 3 остались в порядке записи, и последней оказалась `0.58`, поэтому она и считается итоговой. Обратите внимание на последние две строки: итоговое значение (`0.58`) и лучшее за всё время (`0.55` на шаге 2) - разные величины. Какую из них сравнивать между запусками, нужно решить заранее и записать в правила команды.

**Попробуйте.** В примере 2 добавьте запуск `train(root, "run-big", lr=0.1, epochs=10)` и посмотрите на его кривую `mse`. Предскажите заранее, что произойдёт с кривой `mse` при такой скорости обучения (подсказка: шаг слишком велик), совпадёт ли её лучшая точка с итоговой и какой запуск вернёт `best_run`.

## Устройство запуска и трекера

Запуск складывается из пяти частей, а над журналом есть три операции: начать запуск, найти лучший, сравнить. Таблица показывает, что хранится, где это лежит в нашем трекере и как называется в MLflow (названия вызовов приведены для ориентира, точное API зависит от версии, сверяйтесь с [документацией MLflow Tracking](https://mlflow.org/docs/latest/tracking/)).

| Часть запуска | Что это | Файл в нашем трекере | MLflow |
|---|---|---|---|
| Параметры | входы запуска, не меняются в процессе | `params.json` | `mlflow.log_param`, `mlflow.log_params` |
| Метрики | числа с именем и шагом, кривая во времени | `metrics.jsonl` | `mlflow.log_metric(key, value, step)` |
| Теги | свободные пометки, можно менять | `meta.json`, поле `tags` | `mlflow.set_tag` |
| Статус | RUNNING, FINISHED, FAILED | `meta.json`, поле `status` | `mlflow.start_run` и `mlflow.end_run(status)` |
| Артефакты | файлы запуска: веса, графики | в упражнении нет | `mlflow.log_artifact` |
| Начало запуска | создать запись и каталог | `start_run` | `mlflow.start_run` |
| Поиск и сортировка | выбрать лучший запуск | `best_run`, `compare_runs` | `mlflow.search_runs` с параметром `order_by` |

Веб-сервисы вроде Weights & Biases решают ту же задачу: запуск с параметрами, метриками по шагам и тегами, плюс интерфейс для сравнения. Сам набор понятий от инструмента почти не зависит, и именно он важен.

**Параметры и метрики - разные сущности.** Параметр задаёт вход (`lr = 0.1`), метрика измеряет результат (`accuracy = 0.83` на шаге 100). Параметры записывают один раз при старте, а метрики - много раз по ходу. Поэтому для них разные файлы и разные операции: перезапись против дозаписи.

**Шаг** - целое число `>= 0`: номер итерации, эпохи или любая монотонная ось. Для ключа метрики последовательность `[step, value]` - это кривая. Мы принимаем только конечные числа: `NaN` и бесконечность отвергаются на записи (иначе они попали бы в файл, а JSON их не допускает), как и `bool` (в Python `True` - это целое `1`, и такое значение почти наверняка ошибка).

**Итоговое значение.** Мы определили `metrics[key]` как значение последней точки кривой (наибольший шаг; при равных шагах - более поздняя строка файла). Это правило нужно зафиксировать, иначе два человека сравнивают разные величины. Альтернативы - минимум или максимум за всё время - тоже допустимы, но их записывают как отдельные метрики (`best_val_loss`).

**Статус и выбор лучшего.** Запуск, который ещё идёт или упал, не может претендовать на «лучшую модель»: его метрика отражает промежуточное состояние. Поэтому `best_run` учитывает только `FINISHED`. Ничья разрешается детерминированно: первый по алфавиту `run_id`; иначе результат зависел бы от порядка, в котором файловая система отдаёт каталоги.

**Сравнение запусков.** `compare_runs` отвечает на вопрос «что изменилось?». В `params` выводятся только отличающиеся ключи: если у двух запусков отличаются два параметра из двадцати, нужно увидеть именно эти два. В `metrics` выводятся все ключи, потому что при сравнении интересны и равные значения.

**Связь с предыдущим уроком.** Хороший `run_id` или тег `config_fingerprint` берут из отпечатка конфигурации: два запуска с одним отпечатком (и одними данными, и одним кодом) должны давать одинаковые метрики, а различие означает недетерминизм. Теперь отпечаток есть где хранить, и по нему можно искать повторы.

## Типичные ошибки

* **Таблица вместо журнала.** Результаты, переписанные вручную в таблицу или в имя файла (`model_final_v3_best.pkl`), быстро теряют связь с параметрами и данными. Записывайте параметры в момент запуска, а не после.
* **Перезапись запуска с тем же `run_id`.** Если `start_run` молча заменяет каталог, прошлый результат исчезает. Лучше получить `FileExistsError` и выбрать новый идентификатор.
* **Запись метрик одним перезаписываемым JSON.** Для длинного обучения каждый шаг переписывает весь файл, а падение посередине записи оставляет повреждённый файл. Дозапись по строке дешевле и безопаснее.
* **`NaN` в метриках.** Расходящееся обучение выдаёт `NaN` в loss. Если такое значение записать, его не поймут ни стандартный JSON, ни сравнение: `nan > 0.5` всегда ложно. Лучше отклонить значение и пометить запуск как `FAILED`.
* **Сравнение по лучшей точке кривой вместо итоговой.** Модель, которая на шаге 2 имела минимум `val_loss`, а к концу переобучилась, нельзя считать лучшей, если в продакшен попадёт последний чекпойнт. Решите заранее, какое значение сравниваете.
* **Выбор лучшего среди упавших запусков.** Упавший запуск мог записать красивое число на раннем шаге и ни разу не дойти до модели. Фильтруйте по статусу.
* **Порядок каталогов из `os.listdir`.** Он не гарантирован. Сортируйте имена, особенно когда от порядка зависит результат (ничья в `best_run`).

<!-- section: summary -->
## Итоги

* Запуск = параметры + метрики по шагам + теги + статус (+ артефакты). Без такой записи результаты нельзя ни сравнить, ни воспроизвести.
* Параметры и метаданные - небольшие JSON-файлы в канонической форме, метрики - журнал JSON Lines, в который дописывают по строке.
* Итоговое значение метрики - последняя точка кривой; лучший запуск выбирают только среди `FINISHED` с детерминированным правилом при ничьей.
* Наш мини-трекер соответствует основным вызовам MLflow Tracking (`start_run`, `log_param`, `log_metric`, `set_tag`, `end_run`, `search_runs`): понятия те же, отличается инфраструктура.
* В следующем уроке к запуску добавится версия данных: [версионирование данных по хешам](lesson:mlops.fundamentals.data-versioning).

## Кратко для тех, кто знаком с ML

* Запуск в трекере: `params` пишутся один раз, `metrics` - временные ряды `(key, step, value)`, `tags` и `status` - метаданные. Артефакты (веса, графики) хранятся отдельно от метрик.
* Мини-трекер на файлах: `params.json`, `meta.json` и `metrics.jsonl` (JSON Lines, дозапись). `best_run` - аналог `mlflow.search_runs(order_by=[...])` с фильтром по статусу.
* Итог метрики = последняя точка кривой; лучшее за всё время хранится отдельной метрикой. Ничьи разрешайте детерминированно.
* Метрики `NaN` и `inf` отклоняйте при записи; упавшие запуски не должны попадать в выбор лучшей модели.
