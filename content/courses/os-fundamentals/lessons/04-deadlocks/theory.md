## Когда все ждут друг друга

Два потока. Первый захватил замок `A` и хочет `B`, второй захватил `B` и хочет `A`. Каждый ждёт события, которое может вызвать только другой, - **взаимная блокировка** (deadlock). Программа не падает с ошибкой: она просто зависает, и потоки остаются в состоянии `WAITING` ([см. состояния](lesson:os.fundamentals.processes-and-system-calls)) навсегда.

Те же истории бывают не только с замками: два процесса держат по части ресурсов (принтер и сканер, строки таблицы в базе данных) и просят недостающие.

Деньги в банке дают хорошую аналогию для третьей идеи. Банкир одалживает деньги клиентам с кредитными лимитами. Он выдаёт очередной кредит, только если после этого сможет дать каждому клиенту дойти до его лимита по очереди и получить деньги обратно. Если такой порядок есть, состояние безопасно. Это и есть **алгоритм банкира**.

## Условия Коффмана

Взаимная блокировка возможна только при одновременном выполнении четырёх условий:

1. **Взаимное исключение** - ресурс в каждый момент используется одним процессом.
2. **Удержание и ожидание** - процесс держит ресурсы и просит новые.
3. **Отсутствие вытеснения** - ресурс нельзя отобрать насильно, только освободить добровольно.
4. **Круговое ожидание** - есть цепочка процессов `P1 -> P2 -> ... -> Pk -> P1`, где каждый ждёт ресурс, удерживаемый следующим.

Это даёт стратегию: нарушить любое из условий.

| Стратегия | Что делаем | Цена |
|---|---|---|
| Круговое ожидание | Нумерация замков, захват строго по возрастанию | Нужна дисциплина во всём коде |
| Удержание и ожидание | Захватывать всё сразу или отпускать всё при неудаче (`try`-захват, откат) | Потеря эффективности, возможны повторы (livelock) |
| Отсутствие вытеснения | Разрешить отобрать ресурс (откат транзакции) | Не всякий ресурс можно отобрать |
| Взаимное исключение | Структуры без блокировок, неизменяемые данные | Применимо не везде |

## Граф ресурсов и ожидания

В **графе распределения ресурсов** две вершины: процессы и ресурсы. Ребро `ресурс -> процесс` значит «ресурс удерживается процессом», ребро `процесс -> ресурс` - «процесс просит ресурс». Если у каждого ресурса один экземпляр, можно свернуть граф в **граф ожидания**: ребро `P -> Q`, когда P ждёт то, что держит Q. Тогда **цикл в графе равносилен блокировке**. Если у ресурса несколько экземпляров, цикл - лишь необходимое условие, и нужны более общие алгоритмы обнаружения (тот же алгоритм банкира без `Max`, на реальных запросах).

## Четыре подхода

* **Предотвращение** - нарушить одно из условий Коффмана заранее (нумерация замков).
* **Избегание** - знать будущие потребности и не входить в небезопасные состояния (банкир).
* **Обнаружение и восстановление** - разрешить блокировки, периодически искать цикл и завершать/откатывать процесс (так делают СУБД, откатывая одну из транзакций).
* **Игнорирование** («страусиный алгоритм») - если блокировки редки, а перезапуск дёшев, универсальной защиты не строят. Для общего ядра это распространённый выбор; приложения должны защищаться сами.

## Алгоритм банкира

Для `n` процессов и `m` типов ресурсов храним `Available[m]` (свободно), `Allocation[n][m]` (выдано), `Max[n][m]` (максимальная потребность) и вычисляем `Need = Max - Allocation`.

**Проверка безопасности.**

1. `Work = Available`, все процессы не завершены.
2. Найти незавершённый `i`, у которого `Need[i] <= Work` покомпонентно. Если нет - перейти к шагу 4.
3. «Завершить» его: `Work += Allocation[i]`; пометить; вернуться к шагу 2.
4. Если все завершены - состояние **безопасно**, порядок завершения - **безопасная последовательность**. Иначе **небезопасно**.

Безопасных последовательностей обычно несколько; для воспроизводимости мы всегда берём процесс с наименьшим индексом и после каждого завершения начинаем поиск с `P0`. Для запроса `Request[i]` банкир проверяет `Request <= Need`, `Request <= Available`, **пробно** выдаёт ресурсы и запускает проверку безопасности; если она провалилась - откатывает и заставляет процесс ждать.

**Безопасно не значит «блокировки нет», а небезопасно не значит «блокировка есть».** Безопасное состояние гарантирует, что существует способ завершить всех. Небезопасное - что гарантии нет: если процессы запросят максимум в неудачном порядке, система заблокируется.

## Цикл в графе ожидания

Граф ожидания задан словарём «кто → кого ждёт». Найдём цикл поиском в глубину с тремя цветами вершин:

```python run
def find_cycle(wait_for):
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {p: WHITE for p in wait_for}
    stack = []

    def dfs(p):
        color[p] = GRAY
        stack.append(p)
        for q in wait_for.get(p, []):
            if color.get(q, WHITE) == GRAY:
                return stack[stack.index(q):] + [q]
            if color.get(q, WHITE) == WHITE:
                found = dfs(q)
                if found:
                    return found
        stack.pop()
        color[p] = BLACK
        return None

    for p in wait_for:
        if color[p] == WHITE:
            found = dfs(p)
            if found:
                return found
    return None


print(find_cycle({"T1": ["T2"], "T2": ["T3"], "T3": ["T1"], "T4": ["T1"]}))
print(find_cycle({"T1": ["T2"], "T2": ["T3"], "T3": [], "T4": ["T1"]}))
```
```output
['T1', 'T2', 'T3', 'T1']
None
```

T4 ждёт T1, но сам в цикл не входит: он не заблокирован «навечно», а лишь стоит позади.

## Блокировка с таймаутом вместо вечного ожидания

Поток уже держит замок и пытается взять его второй раз. Обычный `acquire()` повис бы навсегда; с таймаутом получаем сигнал тревоги:

```python run
import threading

lock = threading.Lock()
lock.acquire()
got = lock.acquire(timeout=0.05)     # повторный захват из того же потока
print("захвачен второй раз:", got)
lock.release()
```
```output
захвачен второй раз: False
```

Такие таймауты - не решение, а страховка: они превращают «зависание» в ошибку, которую можно записать в лог.

## Порядок захвата устраняет цикл

Два потока берут два замка. Поток 2 «логически» хочет сначала `B`, затем `A`, но код сортирует замки по номеру, и круговое ожидание невозможно:

```python run
import threading

locks = {1: threading.Lock(), 2: threading.Lock()}
done = []


def work(name, wanted):
    for number in sorted(wanted):         # глобальный порядок
        locks[number].acquire()
    done.append(name)
    for number in sorted(wanted, reverse=True):
        locks[number].release()


t1 = threading.Thread(target=work, args=("T1", [1, 2]))
t2 = threading.Thread(target=work, args=("T2", [2, 1]))
t1.start()
t2.start()
t1.join()
t2.join()
print(sorted(done))
```
```output
['T1', 'T2']
```

## Банкир на бумаге

Один тип ресурса, 12 единиц. Allocation: P0 = 5, P1 = 2, P2 = 2, свободно 3. Max: 10, 4, 9. Need: 5, 2, 7. `Work = 3`: P0 не подходит (5 > 3), P1 подходит (2 <= 3), `Work = 5`; поиск заново с P0: 5 <= 5, `Work = 10`; P2: 7 <= 10. Последовательность **P1, P0, P2** - состояние безопасно. Если бы P2 получил ещё одну единицу (Allocation 3, свободно 2), то после P1 было бы `Work = 4`, а Need P0 = 5 и Need P2 = 6 - ни один не подходит, состояние **небезопасно**.

## Типичные ошибки

* **Считать небезопасное состояние блокировкой.** Это условие риска.
* **Забыть перезапустить поиск с P0.** При «продолжении с места остановки» получится другая (тоже допустимая) последовательность, и ваш ответ не совпадёт с эталонным: правила порядка нужно оговаривать.
* **Путать Need и Max.** Банкир сравнивает с `Work` оставшуюся потребность, а не максимальную.
* **Захватывать замки в разном порядке в разных функциях.** Классическая причина блокировок в реальных программах: код `transfer(a, b)` и `transfer(b, a)`.
* **Вызывать чужой код под замком.** Колбэк может захватить другой замок, и вы получите неочевидный порядок.
* **Лечить блокировку таймаутом без анализа причины.** Таймаут скрывает проблему; правильный ответ - иерархия замков или другая структура данных.

## Итоги

* Блокировка требует четырёх условий Коффмана одновременно; нарушаем любое.
* Для единственных экземпляров ресурсов цикл в графе ожидания равен блокировке.
* Стратегии: предотвращение, избегание (банкир), обнаружение с восстановлением, игнорирование.
* Безопасная последовательность гарантирует завершение всех процессов; небезопасное состояние - риск, не факт блокировки.
