## Один процесс, много потоков

Процесс получает адресное пространство и ресурсы, а **поток** (thread) - это одна линия исполнения внутри процесса: свой счётчик команд, регистры и стек. Потоки одного процесса делят **кучу, глобальные переменные и открытые файлы**. Поэтому потоки легче процессов (общее не копируется) и общаться им проще: достаточно записать в общую переменную. Но общая память - источник главной проблемы конкурентности.

Возьмём `counter += 1`. Для процессора это три шага: загрузить значение из памяти в регистр, прибавить 1, записать обратно. Два потока делают это одновременно:

1. поток A загрузил 0;
2. планировщик переключился ([переключение контекста](lesson:os.fundamentals.processes-and-system-calls) может произойти между любыми двумя инструкциями);
3. поток B загрузил 0, прибавил 1, записал 1;
4. поток A прибавил 1 к своему регистру (0 + 1) и записал 1.

Два инкремента, результат 1: одно обновление потеряно. Это **гонка** (race condition): результат зависит от порядка планирования. Самое неприятное в ней - она проявляется редко и непредсказуемо.

Лечится это **взаимным исключением**: участок кода, где поток читает и пишет общие данные (**критическая секция**), в каждый момент выполняет только один поток. Для этого есть примитивы синхронизации: мьютекс, семафор, условная переменная.

## Критическая секция

Решение задачи критической секции должно обеспечивать:

* **взаимное исключение** - внутри секции не больше одного потока;
* **прогресс** - если секция свободна и кто-то хочет войти, решение о том, кто войдёт, принимается за конечное время и не зависит от потоков вне секции;
* **ограниченное ожидание** - поток, захотевший войти, дождётся своей очереди после конечного числа чужих входов (нет голодания).

Программных решений без поддержки процессора (алгоритм Петерсона) недостаточно на современных процессорах с переупорядочиванием операций; реальные блокировки строятся на атомарных инструкциях (`compare-and-swap`, `test-and-set`) и ядре: если замок занят, поток засыпает (`WAITING`), а не крутится.

## Примитивы

**Мьютекс** (mutex, lock) - замок с двумя операциями: `lock` (захватить, при занятости ждать) и `unlock`. Хозяин - тот, кто захватил. Всегда освобождайте замок: в Python - `with lock:`.

**Семафор** - целый счётчик с атомарными операциями `wait`/`acquire` (уменьшить, а при нуле ждать) и `post`/`release` (увеличить и разбудить ждущего). Семафор со значением 1 даёт взаимное исключение; со значением N - ограничивает число одновременных пользователей ресурса (пул соединений). У семафора нет «хозяина»: release может сделать другой поток, поэтому он годится и для сигналов «событие произошло».

**Условная переменная** (condition variable) нужна, когда поток должен дождаться **условия** над общими данными («очередь не пуста»). Она всегда используется вместе с мьютексом, который защищает само условие: `wait` атомарно отпускает мьютекс и засыпает, а при пробуждении снова захватывает его. Образец:

```
with cond:                       # захват мьютекса
    while not условие:           # while, а не if!
        cond.wait()
    ... работа ...
```

`while` необходим по двум причинам: пробуждение может быть ложным, а между `notify` и повторным захватом мьютекса другой поток мог «украсть» результат и вернуть условие в ложное состояние.

## Python и GIL

В CPython стандартной сборки байт-код выполняет один поток за раз: его держит **GIL** (global interpreter lock). Из этого следует:

* потоки **не ускоряют** вычисления, нагружающие CPU (для них - процессы или нативные расширения), но хорошо подходят для ожидания ввода-вывода, потому что GIL освобождается на время блокирующих системных вызовов;
* GIL защищает **интерпретатор**, а не вашу логику: `counter += 1` - несколько инструкций байт-кода, и переключение потоков возможно между ними. Составные «прочитать-изменить-записать» операции без блокировки небезопасны и с GIL;
* в сборках без GIL (free-threaded, с Python 3.13; статус зависит от версии, см. документацию) корректная синхронизация важна ещё сильнее.

Подробно о моделях конкурентности Python: [«Модели конкурентности»](lesson:python.concurrency.concurrency-models) и [«Потоки и синхронизация»](lesson:python.concurrency.threading-and-synchronization). В других языках те же идеи: [потоки в Rust](lesson:rust.fundamentals.concurrency-fearless), [горутины и каналы в Go](lesson:go.fundamentals.goroutines-and-channels), [потоки и виртуальные потоки в Java](lesson:java.fundamentals.threads-executors-virtual).

**Инверсия приоритетов.** Если низкоприоритетный поток держит замок, нужный высокоприоритетному, а средний не даёт ему работать, высокий фактически ждёт среднего. Известный случай - сбой марсохода Mars Pathfinder; решение - наследование приоритета (priority inheritance), которое есть в POSIX как опция мьютексов.

## Гонка без случайности

Чтобы продемонстрировать потерю обновления без недетерминизма, переключим «потоки» вручную. Два генератора выполняют `LOAD`, `ADD`, `STORE` и отдают управление после каждого шага; расписание задаём мы:

```python run
x = 0


def increment(name):
    global x
    reg = x
    print(name, "LOAD ", reg)
    yield
    reg += 1
    print(name, "ADD  ", reg)
    yield
    x = reg
    print(name, "STORE", x)
    yield


a, b = increment("A"), increment("B")
for who in [a, b, a, a, b, b]:      # перемежение: оба загружают 0
    next(who)
print("итог:", x, "(ожидалось 2)")
```
```output
A LOAD  0
B LOAD  0
A ADD   1
A STORE 1
B ADD   1
B STORE 1
итог: 1 (ожидалось 2)
```

Это та же модель, что в упражнении: расписание `0 1 0 0 1 1`.

## Мьютекс чинит гонку

Теперь настоящие потоки Python. Четыре потока по 10 000 инкрементов; операция в критической секции под замком, поэтому результат всегда один:

```python run
import threading

counter = 0
lock = threading.Lock()


def worker():
    global counter
    for _ in range(10_000):
        with lock:
            counter += 1


threads = [threading.Thread(target=worker) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter)
```
```output
40000
```

Версия без `with lock:` могла бы дать число меньше 40 000 (а в некоторых версиях CPython и всегда 40 000, потому что переключение потока между байт-кодами случается редко). Такой код всё равно неверен: полагаться на детали интерпретатора нельзя. Пример не запускается в курсе, потому что его результат недетерминирован:

```python
# НЕ ДЕЛАЙТЕ ТАК: результат зависит от версии и от планирования
def worker():
    global counter
    for _ in range(10_000):
        counter += 1
```

## Семафор ограничивает параллелизм

Пул из двух «соединений»: пять потоков хотят работать, но одновременно внутри не больше двух. Максимум замеряем под отдельным замком:

```python run
import threading
import time

pool = threading.Semaphore(2)
guard = threading.Lock()
inside = 0
peak = 0


def job():
    global inside, peak
    with pool:
        with guard:
            inside += 1
            peak = max(peak, inside)
        time.sleep(0.02)
        with guard:
            inside -= 1


threads = [threading.Thread(target=job) for _ in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("не больше двух:", peak <= 2)
```
```output
не больше двух: True
```

## Условная переменная: очередь «производитель - потребитель»

Потребитель ждёт, пока в очереди появится элемент. Проверка условия - в цикле `while`:

```python run
import threading
from collections import deque

queue = deque()
cond = threading.Condition()
result = []


def consumer(count):
    for _ in range(count):
        with cond:
            while not queue:
                cond.wait()
            result.append(queue.popleft())


def producer(count):
    for i in range(count):
        with cond:
            queue.append(i * i)
            cond.notify()


c = threading.Thread(target=consumer, args=(5,))
p = threading.Thread(target=producer, args=(5,))
c.start()
p.start()
p.join()
c.join()
print(result)
```
```output
[0, 1, 4, 9, 16]
```

Результат детерминирован, потому что очередь FIFO и один потребитель, хотя порядок шагов потоков может быть разным.

## Типичные ошибки

* **«С GIL гонок нет».** `counter += 1`, проверка-затем-действие (`if key not in d: d[key] = ...`) и другие составные операции требуют блокировки.
* **Захват одного замка дважды в одном потоке.** `threading.Lock` не рекурсивен: второй `acquire` в том же потоке повиснет. Для такого случая есть `RLock`, но чаще нужно перестроить код.
* **Забытый `unlock`.** Исключение между `acquire` и `release` оставляет замок захваченным навсегда. Используйте `with`.
* **`if` вместо `while` при ожидании на условной переменной.** Ломается на ложных пробуждениях и при нескольких потребителях.
* **Слишком крупная блокировка.** Защита всей программы одним замком убивает параллелизм; слишком мелкие замки ведут к [взаимным блокировкам](lesson:os.fundamentals.deadlocks) - следующая тема.
* **Нескольких замков в разном порядке.** Один из главных источников взаимных блокировок.
* **Надежда на `time.sleep` как синхронизацию.** Пауза не гарантирует порядок; используйте `join`, `Event`, `Condition`.

<!-- section: summary -->
## Итоги

* Потоки делят память процесса; гонка возникает, когда результат зависит от перемежения шагов `LOAD`, `ADD`, `STORE`.
* Критическая секция требует взаимного исключения, прогресса и ограниченного ожидания.
* Мьютекс защищает данные, семафор считает ресурсы и сигналы, условная переменная ждёт условие (всегда в `while`).
* GIL не делает программу потокобезопасной: он лишь защищает внутренности интерпретатора.
* Разными потоками можно «заблокировать друг друга навсегда» - об этом [следующий урок](lesson:os.fundamentals.deadlocks).
