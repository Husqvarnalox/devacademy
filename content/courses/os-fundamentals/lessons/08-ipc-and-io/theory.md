## Процессы не видят память друг друга

Изоляция адресных пространств ([урок о процессах](lesson:os.fundamentals.processes-and-system-calls)) защищает процессы друг от друга, но программам всё равно нужно обмениваться данными: оболочка соединяет `ls | grep txt`, браузер говорит с процессом-рендерером, сервер принимает запросы. Для этого ядро даёт механизмы **межпроцессного взаимодействия** (IPC):

* **канал** (pipe) - однонаправленный поток байт между родственными процессами;
* **сокет** - двунаправленный канал, в том числе между машинами;
* **сигнал** - короткое асинхронное уведомление без данных;
* **общая память** - одна и та же страница в адресных пространствах двух процессов (самый быстрый путь, но синхронизация целиком на вас, см. [потоки и синхронизация](lesson:os.fundamentals.threads-and-synchronization)).

Главное в каналах и сокетах - **буфер ограниченного размера в ядре**. Он превращает обмен в знакомую задачу «производитель - потребитель»: писатель ждёт, когда буфер полон, читатель - когда пуст. Тот же принцип у каналов в Go ([горутины и каналы](lesson:go.fundamentals.goroutines-and-channels)).

## Семантика канала

Канал имеет два конца: для записи и для чтения. Правила (для блокирующего режима):

1. **`write`** кладёт данные в буфер. Если места не хватает, записывает сколько влезло и **блокируется**, пока читатель не освободит место и запись не завершится целиком.
2. **`read(k)`** возвращает **не более `k`** байт: сколько есть сейчас. Если буфер пуст и писатель жив - блокируется.
3. Если буфер пуст и **все концы записи закрыты** - `read` возвращает `0`. Это **EOF**, а не ошибка.
4. Если закрыты **все концы чтения**, запись бессмысленна: процесс получает **SIGPIPE** (по умолчанию он завершается), а если сигнал игнорируется - `write` возвращает ошибку `EPIPE`. В Python сигнал игнорируется, и вы увидите `BrokenPipeError`.

Из пункта 2 следует главное правило практики: **`read` может вернуть меньше, чем вы просили**, поэтому данные известной длины читают в цикле до нужного объёма или до EOF. Тот же закон верен для сокетов.

Из пунктов 3 и 4 следует важная дисциплина: **закрывайте ненужные концы**. Если читатель не закрыл свой дубликат дескриптора записи, он никогда не увидит EOF, потому что формально писатель жив.

## Блокирующий, неблокирующий и мультиплексированный ввод-вывод

* **Блокирующий**: вызов ждёт, пока операция возможна. Просто, но поток занят ожиданием; для многих соединений нужно много потоков.
* **Неблокирующий**: если операция невозможна сейчас, вызов завершается ошибкой `EAGAIN` (в Python `BlockingIOError`). Код сам решает, что делать дальше.
* **Мультиплексирование** (`select`, `poll`, `epoll`, `kqueue`): один вызов ждёт готовности сразу многих дескрипторов; затем читают только готовые. Это основа асинхронных серверов (см. [модели конкурентности в Python](lesson:python.concurrency.concurrency-models)).

## Сигналы

Сигнал - уведомление процессу: `SIGINT` (Ctrl+C), `SIGTERM` (просьба завершиться), `SIGKILL` (принудительное завершение, перехватить нельзя), `SIGPIPE`, `SIGCHLD`. Процесс может задать обработчик, игнорировать сигнал или оставить действие по умолчанию. Обработчик выполняется асинхронно, поэтому в нём можно делать очень мало: безопаснее всего поставить флаг и вернуться в основной цикл.

## Канал внутри одного процесса

```python run
import os

r, w = os.pipe()                 # два файловых дескриптора: чтение и запись
os.write(w, b"hello pipe")
print(os.read(r, 5))             # просили 5 - получили 5
print(os.read(r, 100))           # просили 100 - получили то, что осталось
os.close(w)                      # закрыли единственный конец записи
print(os.read(r, 100))           # пусто и записи закрыты: EOF
os.close(r)
```
```output
b'hello'
b' pipe'
b''
```

Последний `read` вернул пустые байты, то есть 0: это EOF.

## Пустой и полный канал в неблокирующем режиме

```python run
import os

r, w = os.pipe()
os.set_blocking(r, False)
os.set_blocking(w, False)

try:
    os.read(r, 10)               # канал пуст, писатель жив
except BlockingIOError:
    print("empty pipe: BlockingIOError")

total = 0
try:
    while True:
        total += os.write(w, b"x" * 1024)
except BlockingIOError:
    print("full pipe: BlockingIOError")
print("capacity at least 4096:", total >= 4096)   # точное число зависит от системы
```
```output
empty pipe: BlockingIOError
full pipe: BlockingIOError
capacity at least 4096: True
```

Точная ёмкость канала зависит от системы, поэтому мы печатаем только проверку нижней границы.

## SIGPIPE как исключение

```python run posix
import os

r, w = os.pipe()
os.close(r)                      # читателей больше нет
try:
    os.write(w, b"data")
except BrokenPipeError:
    print("BrokenPipeError: no readers")
os.close(w)
```
```output
BrokenPipeError: no readers
```

В C та же запись убила бы процесс сигналом. Python по умолчанию игнорирует SIGPIPE, и сигнал превращается в исключение.

## Готовность дескриптора и сигнал самому себе

```python run posix
import os, select, signal

r, w = os.pipe()
ready, _, _ = select.select([r], [], [], 0)
print("ready before write:", ready == [r])
os.write(w, b"!")
ready, _, _ = select.select([r], [], [], 0)
print("ready after write: ", ready == [r])

got = []
signal.signal(signal.SIGUSR1, lambda signum, frame: got.append(signal.Signals(signum).name))
signal.raise_signal(signal.SIGUSR1)     # доставка сигнала самому себе
print("handler received:", got)
os.close(r); os.close(w)
```
```output
ready before write: False
ready after write:  True
handler received: ['SIGUSR1']
```

`select` с нулевым таймаутом просто опрашивает состояние: до записи читать нечего, после - дескриптор готов.

## Каркас симулятора

Для упражнения достаточно одного цикла по ходам. Писатель и читатель - два «процесса», которые по очереди делают шаг; блокировка - это шаг, который не смог продвинуться:

```python
turn = 0
while not (p_done and c_done):
    who = "producer" if turn % 2 == 0 else "consumer"
    turn += 1
    if who == "producer" and not p_done:
        ...   # дописать остаток или взять новую запись; если нет места - заблокироваться
    elif who == "consumer" and not c_done:
        ...   # прочитать min(запрос, fill); если пусто - EOF или блокировка
```

Состояние «заблокирован» не нужно хранить как отдельный режим: достаточно помнить, что запись или запрос не доведены до конца (`rem`, `want`), и один раз напечатать сообщение.

## Типичные ошибки

* **Считать, что `read(n)` вернёт ровно `n` байт.** Он вернёт не больше `n`; читайте в цикле.
* **Не закрыть лишние концы канала.** Читатель держит открытым и конец записи, поэтому не получает EOF и зависает навсегда.
* **Принимать `0` за ошибку.** Это EOF; ошибки приходят как исключения или `-1` в C.
* **Писать в канал без читателей и не ждать SIGPIPE.** В C сервер, пишущий в закрытое соединение, внезапно завершается; нужно игнорировать сигнал и обрабатывать `EPIPE`.
* **Делать в обработчике сигнала много работы** (выделять память, печатать, брать блокировки): он прерывает программу в произвольном месте. Ставьте флаг.
* **Заполнять оба конца в одном потоке с блокирующим вводом-выводом:** запись в полный канал при отсутствии читателя в другом потоке - гарантированная взаимная блокировка (см. [взаимные блокировки](lesson:os.fundamentals.deadlocks)).

## Итоги

* IPC - это канал, сокет, сигнал и общая память; у первых двух в ядре есть ограниченный буфер.
* Запись в полный канал и чтение из пустого блокируют; закрытый конец записи даёт читателю EOF (`read` вернул 0), закрытый конец чтения даёт писателю SIGPIPE/EPIPE.
* `read` возвращает не больше запрошенного: читайте в цикле.
* Неблокирующий режим и `select`/`poll` позволяют одному потоку обслуживать много дескрипторов.
* Симулятор блокировок сводится к циклу по ходам и состоянию «операция не завершена».
