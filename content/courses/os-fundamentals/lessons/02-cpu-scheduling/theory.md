## Кому отдать процессор

На машине десятки готовых процессов, а ядро одно. **Планировщик** решает, какой из `READY`-процессов станет `RUNNING` (см. [состояния процесса](lesson:os.fundamentals.processes-and-system-calls)). Хорошего ответа «для всех сразу» не существует, потому что цели конфликтуют:

* **быстрый отклик** - интерактивная программа должна реагировать на нажатие клавиши немедленно;
* **малое время оборота** - пакетное задание должно закончиться как можно раньше;
* **справедливость** - никто не должен ждать бесконечно;
* **малые накладные расходы** - переключение контекста не должно съедать всё время.

Чтобы сравнивать алгоритмы, вводят три метрики для каждого процесса:

* **оборот** (turnaround) = момент завершения - момент прихода;
* **ожидание** (waiting) = оборот - длительность выполнения (время, проведённое в очереди READY);
* **отклик** (response) = момент первого запуска - момент прихода.

Результат работы планировщика рисуют как **диаграмму Ганта**: временная шкала и кто на ней работал. Например, `0-4 P1`, `4-7 P2` означает, что P1 исполнялся с момента 0 до 4, потом P2 с 4 до 7.

## Алгоритмы

Считаем, что длительность следующей пачки CPU (burst) известна. На практике ОС её не знает, и это главное ограничение SJF.

**FCFS** (first come, first served) - по порядку прихода, без вытеснения. Проста, но страдает от **эффекта конвоя**: одно длинное задание задерживает все короткие.

**SJF** (shortest job first) - из готовых берётся самое короткое; без вытеснения. Если все пришли одновременно, это оптимально по среднему времени оборота. Минус: длинные задания могут ждать бесконечно (голодание), а длительность нужно оценивать.

**SRTF** (shortest remaining time first) - вытесняющий SJF: в каждый момент работает процесс с минимальным **оставшимся** временем. Приход короткого задания вытесняет длинное. Нужно правило для ничьих: в курсе - сначала более ранний приход, затем порядок записи.

**Round Robin** (RR) - каждому по кванту `q` по кругу. Готовые стоят в FIFO-очереди; процесс, не успевший закончиться, уходит в хвост. Отклик хороший: процесс ждёт первого запуска не дольше `(n-1)*q`. Оборот хуже, чем у SJF. Выбор кванта - компромисс: при `q -> ∞` получается FCFS, при слишком малом `q` время тратится на переключения. Практическое правило из учебников: квант заметно больше стоимости переключения контекста, но достаточно мал для отклика.

**Приоритеты.** Каждому процессу присваивается число; выбирается наибольший приоритет, при равенстве - RR. Приоритеты могут быть статическими или динамическими. Опасность - **голодание**: низкоприоритетный процесс может никогда не запуститься. Лекарство - **старение** (aging): приоритет ожидающих процессов растёт со временем. Другая беда - **инверсия приоритетов**, когда низкоприоритетный процесс держит ресурс, нужный высокому (она ещё встретится в [уроке о синхронизации](lesson:os.fundamentals.threads-and-synchronization)).

Реальные планировщики сочетают идеи: **MLFQ** (многоуровневые очереди с обратной связью) использует несколько приоритетных очередей и «учится» по поведению процесса, не зная длительности заранее; планировщик общего назначения Linux стремится дать каждому справедливую долю времени. Вытесняющие алгоритмы требуют прерывания таймера: без него ядро не отберёт процессор у процесса, который не отдаёт его добровольно.

### Тонкости симуляции

* **Время дискретно**, события происходят в целые моменты.
* Если процесс приходит ровно в момент окончания кванта, нужно **заранее** договориться, кто встанет в очередь первым. Мы выбираем: новичок раньше вытесненного (так делает большинство учебников). Другое решение даст другой, но тоже «правильный» результат; поэтому в условиях задач правило всегда записывают.
* **Простой процессора**: если нет готовых, но будут позже, время «перематывается» до следующего прихода, а в диаграмме появляется сегмент `idle`.

## Эффект конвоя в цифрах

Задание из учебника OSTEP: A длится 100, B и C по 10, все пришли в момент 0. Посчитаем оборот при FCFS (A, B, C) и SJF (B, C, A):

```python run
def avg_turnaround(order, burst):
    t = 0
    total = 0
    for name in order:
        t += burst[name]
        total += t          # приход 0, поэтому оборот = момент завершения
    return total / len(order)


burst = {"A": 100, "B": 10, "C": 10}
print("FCFS", avg_turnaround(["A", "B", "C"], burst))
print("SJF ", avg_turnaround(sorted(burst, key=burst.get), burst))
```
```output
FCFS 110.0
SJF  50.0
```

SJF в два с лишним раза лучше: короткие задания перестали стоять за длинным.

## Round Robin: отклик и ожидание

Три задания по 5 единиц, квант 1. Ниже минимальная симуляция, которая возвращает диаграмму как список имён по единицам времени. Все пришли в момент 0, поэтому вопроса про порядок прихода нет:

```python run
from collections import deque


def rr_timeline(bursts, q):
    queue = deque(bursts)           # имена в порядке прихода
    rest = dict(bursts)
    line = []
    while queue:
        name = queue.popleft()
        run = min(q, rest[name])
        line += [name] * run
        rest[name] -= run
        if rest[name]:
            queue.append(name)
    return line


line = rr_timeline({"A": 5, "B": 5, "C": 5}, 1)
print("".join(line))
first = {n: line.index(n) for n in "ABC"}
print("отклик:", first, "средний:", sum(first.values()) / 3)
print("оборот A:", len(line) - line[::-1].index("A"))
```
```output
ABCABCABCABCABC
отклик: {'A': 0, 'B': 1, 'C': 2} средний: 1.0
оборот A: 13
```

Отклик в среднем 1 - для FCFS он был бы (0+5+10)/3 = 5. Зато оборот хуже: A завершается в 13, а не в 5. Классический обмен: RR выигрывает в отклике, но проигрывает в обороте.

## Каркас симулятора

Основа решения упражнения: «пришедшие к моменту t» переносятся в очередь функцией, а порядок «сначала новички, потом вытесненный» задаётся последовательностью вызовов:

```python run
from collections import deque

arrivals = [("A", 0), ("B", 1), ("C", 2)]    # уже отсортированы по приходу
queue = deque()
i = 0


def admit(t):
    global i
    while i < len(arrivals) and arrivals[i][1] <= t:
        queue.append(arrivals[i][0])
        i += 1


t = 0
admit(t)
cur = queue.popleft()         # A работает с 0 по 2 (квант 2)
t += 2
admit(t)                      # B (приход 1) и C (приход 2) - до вытесненного A
queue.append(cur)             # A возвращается в хвост
print(list(queue))
```
```output
['B', 'C', 'A']
```

## Типичные ошибки

* **Считать ожидание от нуля, а не от прихода.** Ожидание процесса, пришедшего в момент 5 и завершившегося в 12 при длительности 4, равно 12 - 5 - 4 = 3.
* **Забыть про простой.** Если следующий процесс приходит позже, чем закончил предыдущий, время нужно перемотать, а не продолжать с `t`.
* **Вернуть вытесненный процесс в очередь до приёма новичков.** Меняется порядок обслуживания и, как следствие, все метрики.
* **Перепутать отклик и ожидание.** Отклик - до первого запуска, ожидание - вся суммарная задержка в очереди READY.
* **Использовать SJF по заявленной длительности и думать, что это работает в ОС.** Реальное ядро длительность не знает.
* **Сравнивать метрики на одном примере.** Вывод «алгоритм X лучше» зависит от нагрузки: RR выигрывает у SJF по отклику, но проигрывает по обороту.

## Итоги

* Метрики: оборот = завершение - приход; ожидание = оборот - длительность; отклик = первый запуск - приход.
* FCFS прост, но даёт эффект конвоя; SJF/SRTF минимизируют среднее ожидание, но требуют знать длительности и могут морить длинные задания.
* RR даёт хороший отклик и справедливость; квант - компромисс между откликом и накладными расходами.
* Приоритеты полезны, но требуют старения против голодания.
* Диаграмма Ганта и аккуратные соглашения о ничьих - половина любой симуляции. Далее: как процессы (и потоки) работают одновременно с общими данными - [потоки и синхронизация](lesson:os.fundamentals.threads-and-synchronization).
