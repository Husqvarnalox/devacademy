## Как гарантированно «прибрать за собой»

Многие ресурсы нужно не только получить, но и вернуть: закрыть файл, освободить блокировку, откатить транзакцию, восстановить настройку. Если забыть, программа «течёт»: файлы остаются открытыми, блокировки - занятыми. Ещё хуже, когда посередине случилось исключение и код очистки просто не дошёл до выполнения.

В [основах](lesson:python.fundamentals.errors-and-files) вы видели `with open(...) as f:`. Эта инструкция - общий механизм Python: **контекстный менеджер** - объект, который знает, что сделать при входе в блок и при выходе из него, причём выход происходит *всегда*: и после обычного завершения, и после исключения, и после `return` или `break` внутри блока.

Контекстный менеджер - это «try/finally, упакованный в объект». Поэтому правильно писать не `f = open(...); ...; f.close()`, а `with open(...) as f: ...`. В этом уроке мы напишем свои менеджеры двумя способами (классом и через декоратор `@contextmanager` на [генераторе](lesson:python.advanced.iterators-and-generators)) и познакомимся с готовыми инструментами `contextlib.suppress` и `ExitStack`.

Отдельно разберём, почему методу `__del__` (деструктору) доверять освобождение ресурсов нельзя.

<!-- section: precise -->
## Протокол `with`

Инструкция

```python
with expr as name:
    body
```

выполняется примерно так:

1. Вычисляется `expr`, получается менеджер `mgr`.
2. Вызывается `mgr.__enter__()`; её результат привязывается к `name` (часть `as name` необязательна).
3. Выполняется `body`.
4. Вызывается `mgr.__exit__(exc_type, exc_value, traceback)`. Если тело завершилось без исключения, все три аргумента равны `None`.
5. Если `__exit__` вернул **истинное** значение, активное исключение подавляется и выполнение продолжается после блока. Если вернул ложное (в том числе `None`) - исключение продолжает подниматься.

`__exit__` вызывается и при `return`, `break`, `continue` внутри тела. Если `__enter__` сам упал, `__exit__` не вызывается (менеджер ещё не вошёл). Подавлять исключения нужно осторожно: возвращайте `True` только для конкретных, ожидаемых ошибок. Сам `__exit__` не должен вызывать исключение «по привычке»: чтобы пробросить текущее, достаточно вернуть ложное значение.

**contextlib.contextmanager.** Декоратор превращает генераторную функцию с **одним** `yield` в менеджер. Код до `yield` - это `__enter__`, значение справа от `yield` - результат `as`, код после `yield` - `__exit__`. Если в теле `with` возникло исключение, оно бросается в генератор в точке `yield`. Поэтому очистку надо помещать в `try/finally` (иначе при ошибке она не выполнится), а подавить исключение можно, перехватив его в `except` и не бросив повторно.

**contextlib.suppress(*exceptions)** - готовый менеджер, подавляющий указанные исключения: `with suppress(FileNotFoundError): os.remove(path)`.

**contextlib.ExitStack** - стек менеджеров для случаев, когда их число заранее неизвестно или они входят условно. `stack.enter_context(cm)` входит в менеджер и регистрирует его выход, `stack.callback(func, *args)` регистрирует произвольную функцию очистки. При выходе всё закрывается в порядке LIFO (обратном порядку регистрации). Если вход в очередной менеджер упал, уже зарегистрированные закроются.

**Несколько менеджеров в одном with.** `with A() as a, B() as b:` эквивалентно вложенным блокам: B закрывается раньше A. С Python 3.10 список можно оформить в скобках.

**Почему не `__del__`.** `__del__` вызывается при удалении объекта, но язык не гарантирует ни момент, ни сам факт вызова. В CPython объект без циклических ссылок удаляется сразу при обнулении счётчика ссылок, поэтому `__del__` часто «срабатывает вовремя» - и вводит в заблуждение. В других реализациях Python, при ссылочных циклах или при завершении интерпретатора вызов может запоздать или не произойти. Исключения внутри `__del__` не пробрасываются, а лишь выводятся как предупреждения. Надёжное освобождение ресурса привязывают к `with` (или `try/finally`).

## Примеры

**Пример 1. Менеджер классом: порядок вызовов и подавление.**

```python run
class Verbose:
    def __init__(self, suppress):
        self.suppress = suppress

    def __enter__(self):
        print("вход")
        return "ресурс"

    def __exit__(self, exc_type, exc, tb):
        print("выход:", exc_type.__name__ if exc_type else None)
        return self.suppress

with Verbose(False) as r:
    print("тело", r)

with Verbose(True):
    print("тело 2")
    raise ValueError("сбой")
print("продолжаем после with")

try:
    with Verbose(False):
        raise KeyError("k")
except KeyError:
    print("KeyError дошёл наружу")
```
```output
вход
тело ресурс
выход: None
вход
тело 2
выход: ValueError
продолжаем после with
вход
выход: KeyError
KeyError дошёл наружу
```

**Пример 2. @contextmanager и гарантия очистки.**

```python run
from contextlib import contextmanager

@contextmanager
def opened(name):
    print("открываю", name)
    try:
        yield name.upper()
    finally:
        print("закрываю", name)

with opened("файл") as value:
    print("работаю с", value)

try:
    with opened("сокет"):
        raise RuntimeError("ошибка в теле")
except RuntimeError as exc:
    print("поймали:", exc)
```
```output
открываю файл
работаю с ФАЙЛ
закрываю файл
открываю сокет
закрываю сокет
поймали: ошибка в теле
```

**Пример 3. suppress и ExitStack.**

```python run
import os
from contextlib import ExitStack, contextmanager, suppress

with suppress(FileNotFoundError):
    os.remove("/definitely/not/here.txt")
print("ошибки не было")

@contextmanager
def res(name):
    print("открыт", name)
    try:
        yield name
    finally:
        print("закрыт", name)

with ExitStack() as stack:
    names = [stack.enter_context(res(n)) for n in ["A", "B", "C"]]
    stack.callback(print, "последний обработчик")
    print("внутри:", names)
```
```output
ошибки не было
открыт A
открыт B
открыт C
внутри: ['A', 'B', 'C']
последний обработчик
закрыт C
закрыт B
закрыт A
```

**Пример 4. Почему with надёжнее __del__.**

```python run
import gc

gc.disable()

class Leaky:
    def __del__(self):
        print("__del__ вызван")

a = Leaky()
a.me = a          # ссылочный цикл
del a
print("после del")
gc.collect()
print("после collect")

import io

with io.StringIO("данные") as f:
    f.read()
print("поток закрыт:", f.closed)
```
```output
после del
__del__ вызван
после collect
поток закрыт: True
```

## Типичные ошибки

* **Закрытие вручную без `try/finally`.** `f.close()` не выполнится, если выше случилось исключение. Используйте `with`.
* **`@contextmanager` без `try/finally`.** Код после `yield` будет пропущен при ошибке в теле, ресурс останется занятым.
* **Два `yield` в генераторном менеджере** - `RuntimeError`: он должен выдать значение ровно один раз.
* **Слишком широкое подавление.** `__exit__`, всегда возвращающий `True`, скрывает настоящие ошибки. Подавляйте конкретные типы.
* **Возврат `True` из `__exit__` «на всякий случай»** - то же самое, что `except: pass`.
* **Ожидание, что `__exit__` вызовется при падении `__enter__`.** Не вызовется: очищать частично созданное состояние нужно внутри самого `__enter__`.
* **Одноразовые менеджеры.** Объект из `@contextmanager` можно использовать в `with` один раз; создавайте новый вызовом функции.
* **Опора на `__del__`.** Закрывайте ресурсы явно.

<!-- section: summary -->
## Итог

* `with` вызывает `__enter__`, затем тело, затем `__exit__(exc_type, exc, tb)` - всегда; истинное значение из `__exit__` подавляет исключение.
* `@contextmanager`: код до `yield` - вход, после `yield` - выход; очистку держите в `try/finally`.
* `suppress` подавляет конкретные исключения; `ExitStack` собирает произвольное число ресурсов и закрывает их в обратном порядке.
* `__del__` не гарантирует ни момента, ни факта вызова - для ресурсов он не годится.
