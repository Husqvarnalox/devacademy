## Три способа повторно использовать код и описать «что умеет объект»

Допустим, вам нужны разные фигуры с одним и тем же методом `describe()`, или стек, или набор независимых «возможностей», которые можно подмешивать к сервису. В Python есть три основных инструмента.

**Наследование** (`class Circle(Shape)`) говорит «Circle *является* Shape». Подкласс получает методы родителя и может переопределить их. Класс умеет наследоваться от нескольких родителей сразу, и тогда нужно знать, в каком порядке Python ищет методы: этот порядок называется **MRO** (method resolution order).

**Композиция** (`self._items = []` внутри `Stack`) говорит «Stack *имеет* список». Вы используете чужой объект внутри и открываете наружу только то, что нужно. Композиция проще в сопровождении: изменение внутренней реализации не ломает пользователей класса, а ненужные методы не просачиваются в публичный интерфейс.

**Интерфейсы** описывают, какие методы объект обязан иметь. В Python их два вида. `abc.ABC` - *номинальный* интерфейс: подкласс явно наследуется от абстрактного класса и обязан реализовать все помеченные методы. `typing.Protocol` - *структурный* интерфейс: подходит любой класс, у которого есть нужные методы, наследоваться не надо. Второй вариант - формализованная **утиная типизация**: «если оно крякает как утка и ходит как утка, значит, это утка».

Эмпирическое правило: сначала думайте о композиции и интерфейсах; наследование берите, когда есть настоящая связь «является» и общая реализация, которую стоит разделить. О том, как устроены атрибуты и методы, см. [урок про классы](lesson:python.advanced.classes-and-objects).

## Подробности

**MRO и C3.** У каждого класса есть `__mro__` - кортеж классов, в порядке которого ищется атрибут (`Class.__mro__`, `Class.mro()`). Порядок вычисляется алгоритмом **C3-линеаризации**, который гарантирует: подкласс всегда стоит раньше родителей; порядок, в котором родители перечислены в `class C(A, B)`, сохраняется; в ромбовидной иерархии общий предок встаёт после всех своих потомков и встречается ровно один раз. Если такой порядок построить нельзя (например, `class C(A, B)` при том, что `B` является подклассом `A`), создание класса завершается `TypeError`.

**super().** `super()` без аргументов в методе класса `K` возвращает прокси, который ищет атрибут в MRO *типа self*, начиная с класса, **следующего после `K`**. Поэтому `super()` - не «вызвать родителя», а «передать управление следующему в цепочке». Из-за этого в классе `B(A)`, использованном в ромбе `D(B, C)`, вызов `super().method()` из `B` может попасть в `C`, а не в `A`.

**Кооперативное множественное наследование.** Чтобы цепочка работала в любых комбинациях, **все** классы в ней должны вызывать `super().method(...)`, передавать дальше то, что не обработали сами, и иметь общий корень, который принимает вызов и завершает цепочку (нередко это базовый класс с «пустым» методом). Для `__init__` обычно используют именованные аргументы и `**kwargs`. Прямой вызов `Base.method(self)` вместо `super()` обрывает цепочку и ведёт к повторным вызовам общего предка.

**Композиция против наследования.** Наследование жёстко связывает подкласс с реализацией родителя (проблема «хрупкого базового класса») и раскрывает весь его интерфейс: `class Stack(list)` получит `insert`, `sort`, `remove`, нарушающие инвариант стека. Композиция делегирует: `Stack` хранит список и реализует `push`/`pop`. Наследование уместно при отношении «является» и когда подкласс можно подставить вместо родителя без сюрпризов.

**abc.ABC.** Класс, унаследованный от `ABC` (метакласс `ABCMeta`), с методами `@abstractmethod` нельзя инстанцировать, пока подкласс не переопределит все абстрактные методы: при `Shape()` поднимается `TypeError`. Абстрактный класс может содержать и обычные методы с общей реализацией. Класс также можно зарегистрировать как «виртуального» подкласса через `ABC.register`.

**typing.Protocol.** Класс, унаследованный от `Protocol`, описывает требуемые методы и атрибуты. Для статических анализаторов (mypy, Pyright) любой класс с совместимой структурой считается подходящим без наследования. Во время выполнения Protocol сам по себе ничего не проверяет. С декоратором `@runtime_checkable` работают `isinstance` и `issubclass`, но проверяется только **наличие** атрибутов с нужными именами, а не сигнатуры и типы. Экземпляры самого Protocol создавать нельзя. Статическая проверка протоколов требует mypy или Pyright; в этом курсе они не установлены (интеграция запланирована).

**Duck typing и EAFP.** Утиная типизация - стиль, при котором код просто вызывает нужный метод, не проверяя тип объекта, и обрабатывает `AttributeError`/`TypeError` при необходимости (подход EAFP - «проще попросить прощения», см. [исключения](lesson:python.fundamentals.errors-and-files)). Protocol добавляет к этому описание ожиданий, а ABC - явный контракт.

## Примеры

**Пример 1. MRO ромба и порядок поиска.**

```python run
class A:
    def who(self):
        return "A"

class B(A):
    pass

class C(A):
    def who(self):
        return "C"

class D(B, C):
    pass

print([k.__name__ for k in D.__mro__])
print(D().who())

try:
    class Bad(A, B):
        pass
except TypeError:
    print("TypeError: нельзя построить MRO")
```
```output
['D', 'B', 'C', 'A', 'object']
C
TypeError: нельзя построить MRO
```

**Пример 2. Кооперативный super() в ромбе.**

```python run
class Base:
    def run(self):
        print("Base")

class Left(Base):
    def run(self):
        print("Left")
        super().run()

class Right(Base):
    def run(self):
        print("Right")
        super().run()

class Both(Left, Right):
    def run(self):
        print("Both")
        super().run()

Both().run()
print("---")

class Broken(Base):
    def run(self):
        print("Broken")
        Base.run(self)

class Mixed(Broken, Right):
    pass

Mixed().run()
```
```output
Both
Left
Right
Base
---
Broken
Base
```

**Пример 3. Наследование от list и композиция.**

```python run
class BadStack(list):
    def push(self, x):
        self.append(x)

class Stack:
    def __init__(self):
        self._items = []
    def push(self, x):
        self._items.append(x)
    def pop(self):
        return self._items.pop()
    def __len__(self):
        return len(self._items)

b = BadStack()
b.push(1)
b.insert(0, 99)
print(b)

s = Stack()
s.push(1)
print(len(s), hasattr(s, "insert"), hasattr(b, "insert"))
```
```output
[99, 1]
1 False True
```

**Пример 4. ABC и Protocol.**

```python run
from abc import ABC, abstractmethod
from typing import Protocol, runtime_checkable

class Shape(ABC):
    @abstractmethod
    def area(self): ...

try:
    Shape()
except TypeError:
    print("Shape() нельзя создать")

class Square(Shape):
    def __init__(self, s):
        self.s = s
    def area(self):
        return self.s ** 2

print(Square(3).area(), isinstance(Square(1), Shape))

@runtime_checkable
class Closer(Protocol):
    def close(self) -> None: ...

class Resource:
    def close(self):
        print("закрыто")

print(isinstance(Resource(), Closer), isinstance(42, Closer))
print(issubclass(Resource, Shape))
```
```output
Shape() нельзя создать
9 True
True False
False
```

## Типичные ошибки

* **Вызов `Base.method(self)` вместо `super().method()`** в иерархии с несколькими родителями: часть классов цепочки пропускается или общий предок вызывается дважды.
* **Забыли вызвать `super()` в одном из классов цепочки.** Остальные участники никогда не выполнятся.
* **Наследование ради повторного использования кода.** `class Stack(list)` раскрывает чужой интерфейс. Если нет отношения «является», берите композицию.
* **Глубокие иерархии.** Чем больше уровней, тем труднее понять, какой метод сработает. Предпочитайте плоские структуры и небольшие миксины.
* **Ожидание, что `isinstance(x, SomeProtocol)` проверяет сигнатуры.** Проверяется лишь наличие имён, и только с `@runtime_checkable`.
* **`isinstance` с Protocol без `@runtime_checkable`** поднимает `TypeError`.
* **Путаница ABC и Protocol.** ABC требует наследования (или `register`); Protocol - структурная проверка, но настоящую проверку типов делает статический анализатор (mypy или Pyright, их интеграция в платформе запланирована).
* **Хрупкий порядок баз.** `class C(Mixin, Base)` и `class C(Base, Mixin)` имеют разные MRO; миксины обычно перечисляют первыми.
* **`@abstractmethod` в классе без `ABC`/`ABCMeta`** - декоратор не запрещает создание экземпляров.

## Итог

* MRO вычисляется алгоритмом C3: подклассы раньше родителей, порядок баз сохраняется, общий предок один раз. Смотрите `Class.__mro__`.
* `super()` передаёт управление следующему классу в MRO экземпляра; для кооперативной цепочки все участники вызывают `super()` и делят общий корень.
* Композиция («имеет») обычно проще и безопаснее наследования («является»).
* `ABC` + `@abstractmethod` - номинальный контракт; `Protocol` - структурный (утиная типизация с описанием); `@runtime_checkable` проверяет только наличие имён.
* Для настоящей статической проверки протоколов нужны mypy или Pyright, которых пока нет в среде.
