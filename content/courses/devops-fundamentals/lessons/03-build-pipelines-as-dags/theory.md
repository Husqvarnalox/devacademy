## Конвейер - это граф

Сборка программы состоит из шагов: получить код, проверить стиль, запустить тесты, собрать, опубликовать. Шаги зависят друг от друга: нельзя публиковать то, что не собрано. Но не все зависимости обязательны: проверка стиля и юнит-тесты друг от друга не зависят и могут идти одновременно.

Такую структуру описывают **графом**: вершина - задание (job), ребро «A нужно для B» - зависимость (`needs`). Граф **направленный** (зависимость имеет направление) и **ациклический** (без циклов): иначе задания ждали бы друг друга вечно. Сокращённо - **DAG** (directed acyclic graph).

Из графа можно получить три полезные вещи:

* **порядок выполнения** - любой порядок, в котором задание идёт после всех своих зависимостей (топологическая сортировка);
* **стадии** - группы заданий, которые можно запускать одновременно;
* **критический путь** - самая долгая цепочка зависимых заданий; быстрее неё конвейер выполниться не может, сколько ни добавляй исполнителей.

Такое же представление лежит в основе GitHub Actions (`needs`), GitLab CI (`needs`), систем сборки (Make, Gradle, Bazel) и планировщиков данных. Это те же идеи, что и в [задаче о взаимной блокировке](lesson:os.fundamentals.deadlocks): цикл ожидания - это тупик.

## Топологический порядок, стадии, цикл

**Уровень задания.** Определяется рекурсивно: `уровень = 0`, если зависимостей нет; иначе `1 + максимум уровней зависимостей`. Задания одного уровня независимы друг от друга и могут идти параллельно. Стадия `k` - задания уровня `k` (нумерация с единицы).

**Алгоритм Кана.** Повторять: взять все задания, чьи зависимости уже выполнены, - это очередная стадия; выполнить их; продолжать. Если на каком-то шаге заданий осталось, но ни одно не готово, значит, они зависят друг от друга по кругу (или от такого цикла): **цикл**. Сообщение об ошибке должно называть все невыполнимые задания, чтобы автор мог найти зацикленный фрагмент.

**Проверки до запуска.**

* зависимость от несуществующего задания - ошибка конфигурации;
* повторное определение имени - неоднозначность;
* зависимость от самого себя - частный случай цикла.

**Время.** Для заданий с длительностями `d` (неограниченное число исполнителей) время завершения `finish(j) = d(j) + max(finish(зависимостей))` (для заданий без зависимостей максимум равен 0). Общее время - максимум `finish`; **критический путь** получают, двигаясь назад от задания с максимальным `finish` к зависимости, завершившейся ровно в момент старта. Если несколько кандидатов равны, нужно выбирать **детерминированно** (например, первое по алфавиту), иначе результат нельзя тестировать.

**Ускорение** = сумма длительностей / общее время. Оно не превышает ширину самой широкой стадии и всегда ограничено критическим путём.

Модель честно упрощена: реальные системы добавляют условия запуска, повторные попытки, матрицы заданий, кеширование и ограниченное число исполнителей; здесь они не моделируются.

## Стадии по уровням

```python run
jobs = {
    "lint": [],
    "unit": [],
    "build": ["lint", "unit"],
    "docs": ["lint"],
    "publish": ["build", "docs"],
}
level = {}


def level_of(job):
    if job not in level:
        level[job] = 1 + max((level_of(d) for d in jobs[job]), default=0)
    return level[job]


for j in jobs:
    level_of(j)
for stage in sorted(set(level.values())):
    print(stage, sorted(j for j, l in level.items() if l == stage))
```
```output
1 ['lint', 'unit']
2 ['build', 'docs']
3 ['publish']
```

Рекурсия с запоминанием работает только для ациклических графов: при цикле она ушла бы в бесконечную рекурсию. Поэтому для настоящих конвейеров предпочтительнее итеративный алгоритм Кана, который умеет сообщить о цикле.

## Алгоритм Кана и обнаружение цикла

```python run
def stages(jobs):
    done, result = set(), []
    remaining = set(jobs)
    while remaining:
        ready = sorted(j for j in remaining if all(d in done for d in jobs[j]))
        if not ready:
            return None, sorted(remaining)
        result.append(ready)
        done.update(ready)
        remaining -= set(ready)
    return result, []


ok = {"a": [], "b": ["a"], "c": ["a"], "d": ["b", "c"]}
bad = {"a": ["c"], "b": ["a"], "c": ["b"], "d": [], "e": ["d", "c"]}
print(stages(ok))
print(stages(bad))
```
```output
([['a'], ['b', 'c'], ['d']], [])
(None, ['a', 'b', 'c', 'e'])
```

Во втором графе `d` не зависит ни от кого и был бы выполнен, но `a`, `b`, `c` зациклены, а `e` ждёт `c`. Алгоритм остановился, когда ни одно из оставшихся заданий не готово, и сообщил `["a", "b", "c", "e"]` - всех, кого нельзя запустить. Задание `d` вышло из `remaining` ещё на первом шаге.

## Критический путь

```python run
dur = {"fetch": 3, "a": 7, "b": 9, "report": 4}
needs = {"fetch": [], "a": ["fetch"], "b": ["fetch"], "report": ["a", "b"]}
finish = {}
for j in ["fetch", "a", "b", "report"]:      # порядок уже топологический
    finish[j] = dur[j] + max((finish[d] for d in needs[j]), default=0)
print("finish:", finish)
print("wall:", max(finish.values()), "sequential:", sum(dur.values()))
cur, path = "report", ["report"]
while needs[cur]:
    start = finish[cur] - dur[cur]
    cur = min(d for d in needs[cur] if finish[d] == start)
    path.append(cur)
print("critical path:", " > ".join(reversed(path)))
```
```output
finish: {'fetch': 3, 'a': 10, 'b': 12, 'report': 16}
wall: 16 sequential: 23
critical path: fetch > b > report
```

Если ускорить `a` с 7 до 1 секунды, время не изменится: узкое место - `b`. Оптимизируйте то, что лежит на критическом пути.

## Типичные ошибки

* **Выполнять все задания по порядку.** Теряется параллелизм: граф зависимостей нужен, чтобы запускать независимое одновременно.
* **Не указывать зависимость, которая есть на самом деле.** Задание «повезло» выполниться после нужного при последовательном запуске, а при параллельном ломается как гонка.
* **Лишние зависимости.** `needs` «на всякий случай» удлиняет критический путь; оставляйте только необходимые.
* **Не проверять циклы и несуществующие имена до запуска.** Ошибка опечатки в имени должна быть найдена за миллисекунды, а не после получаса работы.
* **Неопределённый порядок при равенстве.** Если результат зависит от порядка в хеш-таблице, конвейер непредсказуем и неотлаживаем; сортируйте или задавайте правило выбора.
* **Считать ускорение равным числу исполнителей.** Его ограничивает критический путь и ширина стадий.
* **Оптимизировать не то.** Ускорение задания вне критического пути не меняет общего времени.
* **Рекурсивный обход без защиты от цикла.** Бесконечная рекурсия вместо понятной ошибки.

## Итоги

* Конвейер - DAG: вершины - задания, рёбра - зависимости (`needs`); циклы запрещены.
* Алгоритм Кана даёт стадии (параллельные группы) и обнаруживает цикл: остались задания, но ни одно не готово.
* До запуска проверяйте неизвестные зависимости, повторы имён и циклы.
* Время при неограниченном параллелизме - длина критического пути; ускорение ограничено им и шириной стадий.
* Результат должен быть детерминированным: при равенстве выбирайте по явному правилу.
