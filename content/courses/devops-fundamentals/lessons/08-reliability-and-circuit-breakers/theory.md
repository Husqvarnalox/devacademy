## Сбои неизбежны: вопрос в том, как система на них реагирует

Сеть теряет пакеты, зависимости медленно отвечают, процессы падают. Надёжность - не отсутствие сбоев, а способность их переживать. Три базовых приёма:

* **Проверки здоровья** (health checks): платформа периодически спрашивает экземпляр «ты жив?» и «ты готов принимать трафик?» и реагирует: перезапускает или убирает из балансировки;
* **Повторы с отступом** (retry with backoff): кратковременный сбой часто проходит сам, поэтому запрос повторяют, но с растущей паузой и случайным разбросом, чтобы не добить сервер;
* **Размыкатель цепи** (circuit breaker): если зависимость явно неисправна, перестаём её дёргать и сразу возвращаем ошибку, давая ей время восстановиться.

Если же сбой всё-таки дошёл до пользователей, вступает **процесс работы с инцидентом**. Он опирается на сигналы из [предыдущего урока](lesson:devops.fundamentals.observability-and-slos): алерт сообщает о проблеме, бюджет ошибок показывает масштаб.

## Проверки, повторы, размыкатель, инциденты

**Три вида проб (на примере Kubernetes).**

* **liveness** - «процесс жив, не завис»: при провале контейнер **перезапускается**. Проверка должна быть дешёвой и не зависеть от внешних сервисов, иначе сбой базы перезапустит все экземпляры;
* **readiness** - «готов принимать запросы»: при провале экземпляр **исключается из балансировки**, но не перезапускается; подходит для прогрева и временной недоступности зависимостей;
* **startup** - «приложение ещё запускается»: пока не прошла, остальные пробы не выполняются; нужна для медленного старта.

**Повторы с экспоненциальным отступом.** Задержка перед повтором номер `attempt` (с 0): `delay = min(cap, base x 2^attempt)`. Верхняя граница `cap` не даёт паузам расти бесконечно. **Jitter** добавляет случайность: при «полном jitter» берут случайное число от 0 до `delay`. Без него тысячи клиентов, начавшие одновременно, повторяют запросы одной волной (thundering herd). Правила безопасных повторов:

1. повторяйте только **идемпотентные** операции (чтение, PUT) либо операции с ключом идемпотентности (см. [урок про идемпотентность](lesson:system-design.fundamentals.consistency-and-idempotency));
2. ограничьте число попыток **и** общий срок (дедлайн);
3. повторяйте только временные ошибки (таймаут, 503), а не ошибки клиента (400, 404);
4. в тестах делайте jitter **детерминированным** (источник случайности с фиксированным зерном или отключённый jitter), иначе результаты нельзя воспроизвести.

**Размыкатель цепи** - автомат с тремя состояниями:

* `closed` - вызовы проходят; считаются сбои **подряд**; успех обнуляет счётчик; при достижении порога размыкатель становится `open`;
* `open` - вызовы **отклоняются сразу**, без обращения к зависимости; после таймаута (`t - opened_at >= timeout`) размыкатель переходит в `half_open`;
* `half_open` - пропускаются пробные вызовы; накопив нужное число успехов подряд, размыкатель закрывается; первый же сбой снова открывает его и перезапускает таймаут.

Размыкатель защищает и зависимость (ей дают отдохнуть), и вызывающего (не тратит потоки и время на заведомо безуспешные вызовы). Пример ниже и упражнение моделируют логику по заданной последовательности событий: реальных сетевых вызовов нет.

**Инцидент.** Типичные стадии: **обнаружение** (алерт), **оценка и приоритет**, **смягчение** (откат версии, отключение функции, перенаправление трафика - сначала остановить ущерб), **восстановление**, **разбор** (постмортем без поиска виноватых и с конкретными действиями). Первопричину ищут после смягчения, а не вместо него.

## Расписание повторов с jitter

```python run
BASE_MS, CAP_MS = 100, 1000


def limit(attempt):
    return min(CAP_MS, BASE_MS * 2 ** attempt)


class Lcg:
    """Детерминированный генератор: одинаковое зерно - одинаковые числа."""

    def __init__(self, seed):
        self.state = seed

    def next_below(self, upper):
        self.state = (self.state * 1103515245 + 12345) % 2 ** 31
        return self.state % upper


rng = Lcg(42)
print("attempt  no_jitter  full_jitter")
for attempt in range(7):
    plain = limit(attempt)
    jittered = rng.next_below(plain + 1)
    print(f"{attempt:>7}  {plain:>9}  {jittered:>11}")
```
```output
attempt  no_jitter  full_jitter
      0        100           79
      1        200          122
      2        400          100
      3        800          367
      4       1000          547
      5       1000          938
      6       1000          893
```

Без jitter задержки растут 100, 200, 400, 800 и упираются в `cap = 1000`. С полным jitter каждая задержка лежит в диапазоне `0..limit`, и разные клиенты (с разными зёрнами) повторяют запросы в разные моменты. Фиксированное зерно делает вывод воспроизводимым.

## Повторы с лимитом попыток

```python run
def call_with_retries(outcomes, max_attempts):
    """outcomes: исходы последовательных вызовов (True - успех)."""
    waited = 0
    for attempt in range(max_attempts):
        if outcomes[attempt]:
            return f"success on attempt {attempt + 1}, waited {waited} ms"
        if attempt < max_attempts - 1:
            waited += min(1000, 100 * 2 ** attempt)
    return f"gave up after {max_attempts} attempts, waited {waited} ms"


print(call_with_retries([False, False, True], 4))
print(call_with_retries([False, False, False, False], 4))
```
```output
success on attempt 3, waited 300 ms
gave up after 4 attempts, waited 700 ms
```

В первом случае успех пришёл на третьей попытке после пауз 100 и 200 мс. Во втором лимит исчерпан: последняя неудача не сопровождается паузой, и вызывающий получает ошибку, которую должен обработать (деградация, сообщение пользователю). Бесконечные повторы - антипаттерн.

## Размыкатель цепи на нескольких вызовах

```python run
class Breaker:
    def __init__(self, threshold, timeout):
        self.threshold, self.timeout = threshold, timeout
        self.state, self.failures, self.opened_at = "closed", 0, 0

    def call(self, t, ok):
        if self.state == "open" and t - self.opened_at >= self.timeout:
            self.state = "half_open"
        if self.state == "open":
            return "rejected"
        if ok:
            self.state, self.failures = "closed", 0
            return "ok"
        self.failures += 1
        if self.state == "half_open" or self.failures >= self.threshold:
            self.state, self.opened_at = "open", t
        return "fail"


b = Breaker(threshold=2, timeout=10)
for t, ok in [(0, False), (1, False), (2, True), (11, True), (12, True)]:
    print(t, b.call(t, ok), b.state)
```
```output
0 fail closed
1 fail open
2 rejected open
11 ok closed
12 ok closed
```

Два сбоя подряд открывают размыкатель в момент 1. Вызов в момент 2 отклонён, хотя он был бы успешным: зависимость не трогают. В момент 11 таймаут истёк, проба успешна, размыкатель закрыт. Упрощение: здесь достаточно одной пробы; в упражнении число проб задаётся параметром.

## Типичные ошибки

* **Повторы без отступа.** Клиенты бьют по уже перегруженному серверу и усугубляют сбой.
* **Отступ без jitter.** Клиенты синхронизируются и повторяют запросы волнами.
* **Повторы без лимита и дедлайна.** Очереди растут, ресурсы удерживаются, пользователь ждёт вечно.
* **Повторять неидемпотентные операции.** Двойное списание, дубли заказов; нужны ключи идемпотентности.
* **Повторять ошибки клиента.** 400 и 404 не пройдут от повтора.
* **Повторы на каждом уровне стека.** Три слоя по три попытки дают девятикратную нагрузку; повторяйте на одном уровне.
* **Liveness-проба, зависящая от базы данных.** Сбой базы перезапускает все экземпляры, усугубляя ситуацию.
* **Одна проба на всё.** Смешивание liveness и readiness приводит к лишним перезапускам или к трафику на неготовый экземпляр.
* **Размыкатель без таймаута или с одним общим счётчиком на разные зависимости.** Сбой одной зависимости блокирует все остальные.
* **Считать все сбои подряд, не сбрасывая счётчик при успехе.** Размыкатель откроется от редких, не связанных между собой ошибок.
* **Искать первопричину вместо смягчения.** Пока вы разбираетесь, пользователи продолжают страдать: сначала откат или отключение функции.
* **Постмортем «виноват такой-то».** Разбор должен менять процесс и систему, а не наказывать людей.

## Итоги

* liveness перезапускает, readiness убирает из балансировки, startup защищает медленный запуск.
* Повтор: `min(cap, base x 2^attempt)`, плюс jitter, лимит попыток и дедлайн; повторять можно идемпотентное и только временные ошибки.
* Размыкатель: `closed -> open` по порогу сбоев подряд, `open -> half_open` по таймауту (нестрого), `half_open -> closed` после нужного числа успехов, любой сбой в `half_open` возвращает в `open`.
* Инцидент: сначала смягчить, затем восстановить, затем разобрать без поиска виноватых.
* Весь курс складывается в цикл: код и ветки, сборочный конвейер, образ, конфигурация, выпуск, наблюдение и реакция - и обратно к метрикам DORA.
