## Как узнать, что у системы всё хорошо

Когда система в продакшене, нельзя «посмотреть внутрь» отладчиком. О её состоянии судят по **сигналам**, которые она сама испускает. **Наблюдаемость** (observability) - свойство системы, при котором по этим сигналам можно ответить на вопросы, которых не ожидали заранее. Три основных сигнала:

* **логи** - записи отдельных событий (запрос обработан, ошибка соединения). Подробны, но дороги в хранении и поиске. Лучше **структурные** (JSON): их разбирают программы;
* **метрики** - числа, агрегированные во времени (запросов в секунду, доля ошибок, задержка). Дёшевы и хороши для панелей и алертов, но теряют детали;
* **трассировки** - путь одного запроса через несколько сервисов с временем каждого шага. Показывают, **где** потеряно время.

Чтобы метрики превратить в решения, нужны договорённости об уровне обслуживания:

* **SLI** (индикатор) - то, что измеряем: например, доля успешных запросов или задержка;
* **SLO** (цель) - целевое значение SLI: «99.9% запросов успешны за 30 дней»;
* **бюджет ошибок** - допустимая доля плохих событий: `1 - SLO`. Если бюджет расходуется быстро, команда замедляет выпуск новых функций и занимается надёжностью; если бюджет не тронут - можно рисковать больше.

Эти понятия замыкают цикл из прошлых уроков: канареечный выпуск ([предыдущий урок](lesson:devops.fundamentals.deployment-strategies)) решает по таким метрикам, а метрики DORA из [первого урока](lesson:devops.fundamentals.what-is-devops-and-dora) измеряют сам процесс поставки.

## Перцентили, доступность, бюджет, алерты

**Почему не среднее.** Задержки распределены с «длинным хвостом». Среднее смешивает быстрые и медленные запросы и не отвечает на вопрос «сколько ждёт неудачливый пользователь». Поэтому используют **перцентили**: `p95` - значение, которое не превышают 95% запросов.

**Метод nearest-rank (ближайший ранг).** Для `n` значений, отсортированных по возрастанию, и процента `p` (0 < p <= 100): `rank = ceil(p x n / 100)`, перцентиль - элемент с этим рангом (нумерация с 1). Результат - всегда реально наблюдённое значение. В целых числах `ceil(a / b) = -(-a // b)`. Другие методы (интерполяция) дают другие числа; важно **заявить метод явно**, иначе цифры нельзя сравнивать. Перцентили нельзя усреднять между сервисами: p99 объединённого набора - не среднее p99.

**Доступность как SLI.** Для HTTP-сервиса обычно «хорошее событие» - ответ не 5xx. Ответы 4xx - ошибка клиента (неверный запрос), в доступность сервиса не засчитываются как сбой; решение зависит от продукта и должно быть зафиксировано. `доступность = хорошие / все`.

**Бюджет ошибок.** При SLO `s` (доля, например 0.999) на `n` запросов допустимо `n x (1 - s)` плохих. Остаток бюджета = допустимо минус фактически плохие; отрицательный остаток означает **нарушенный SLO**. Для точных долей (99.9% = 999/1000) используйте рациональные числа, а не `float`.

**Алерты и `for`.** Правило оповещения проверяется периодически. Чтобы не будить людей из-за одиночного всплеска, вводят время ожидания `for`:

* `inactive` - условие ложно;
* `pending` - условие стало истинным, но ещё не продержалось `for`;
* `firing` - условие истинно не менее `for` подряд: уведомление отправляется;
* если условие стало ложным, алерт возвращается в `inactive` (из `firing` это «resolved»).

Алерты строят на **симптомах** (рост доли ошибок, задержка), которые чувствует пользователь, а не на причинах (загрузка процессора): причин много, симптом один. Если у ряда на очередной проверке нет значения, условие считается ложным.

Упражнение и задача считают всё по заранее заданным данным: это модель логики, а не работа с настоящими системами сбора метрик.

## Среднее против перцентилей

```python run
import math

latencies = [10] * 99 + [5000]
mean = sum(latencies) / len(latencies)
srt = sorted(latencies)


def nearest_rank(values, p):
    return values[math.ceil(p * len(values) / 100) - 1]


print("mean:", mean)
print("p50:", nearest_rank(srt, 50), "p99:", nearest_rank(srt, 99), "p100:", nearest_rank(srt, 100))
```
```output
mean: 59.9
p50: 10 p99: 10 p100: 5000
```

Среднее 59.9 мс ничего не говорит ни о типичном запросе (10 мс), ни о худшем (5000 мс). Заметьте, что при `n = 100` значение p99 - 99-е по порядку, то есть 10: один сверхмедленный запрос не попадает в p99, но виден в p100. Вот почему выбирают несколько перцентилей и следят за максимумом.

## Разбор структурного журнала и бюджет ошибок

```python run
import json
from fractions import Fraction

logs = [
    '{"status": 200, "latency_ms": 12}',
    '{"status": 200, "latency_ms": 18}',
    'broken line',
    '{"status": 500, "latency_ms": 250}',
    '{"status": 200, "latency_ms": 15}',
]
good = bad = skipped = 0
for line in logs:
    try:
        rec = json.loads(line)
    except ValueError:
        skipped += 1
        continue
    if rec["status"] >= 500:
        bad += 1
    else:
        good += 1
n = good + bad
slo = Fraction("99.9") / 100
budget = n * (1 - slo)
print("requests:", n, "skipped:", skipped)
print("availability:", Fraction(good, n))
print("budget (bad requests allowed):", float(budget))
print("remaining:", float(budget - bad))
```
```output
requests: 4 skipped: 1
availability: 3/4
budget (bad requests allowed): 0.004
remaining: -0.996
```

При SLO 99.9% на 4 запроса допустимо `0.004` плохих; один сбой уже превышает бюджет. Малые выборки малоинформативны: для оценки SLO нужны окно и объём трафика, достаточные, чтобы доля имела смысл.

## Алерт с for: pending, firing, сброс

```python run
def evaluate(samples, threshold, hold):
    state, since, events = "inactive", None, []
    for t, value in samples:
        if value > threshold:
            if state == "inactive":
                state, since = "pending", t
                events.append((t, "pending"))
            if state == "pending" and t - since >= hold:
                state = "firing"
                events.append((t, "firing"))
        elif state != "inactive":
            events.append((t, "inactive"))
            state = "inactive"
    return events


samples = [(0, 1), (60, 9), (120, 9), (180, 9), (240, 1), (300, 9), (360, 1)]
print(evaluate(samples, threshold=5, hold=120))
```
```output
[(60, 'pending'), (180, 'firing'), (240, 'inactive'), (300, 'pending'), (360, 'inactive')]
```

Первый всплеск (60-180) держится 120 секунд и вызывает `firing` ровно в 180 (условие нестрогое: `>= hold`). Второй всплеск в 300 длится одну проверку и сбрасывается, не дойдя до `firing`: без `for` он разбудил бы дежурного, с `for` - нет.

## Типичные ошибки

* **Смотреть только на среднее.** Хвост задержки скрыт; используйте перцентили.
* **Усреднять перцентили.** p99 двух сервисов нельзя усреднить, чтобы получить p99 объединения.
* **Не называть метод вычисления перцентиля.** Интерполяция и nearest-rank дают разные числа.
* **Считать 4xx ошибками сервиса.** Клиентские ошибки не нарушают SLO доступности, если иное не оговорено.
* **SLO 100%.** Бюджет нулевой: любой сбой нарушает цель, а выпуск новых версий невозможен; цель должна быть достижимой и осмысленной.
* **Алерт без `for`.** Дребезг: срабатывание и сброс на каждом всплеске, усталость от алертов.
* **Слишком длинный `for`.** Реальный инцидент обнаруживается поздно; подбирайте время под цену задержки обнаружения.
* **Алерт на причину, а не на симптом.** Загрузка CPU не равна проблеме для пользователя.
* **Падение разбора на битой строке лога.** Некорректные записи надо считать и пропускать.
* **Путать bool и int.** В Python `True` - это `int`, и проверка `isinstance(x, int)` пропустит его; исключайте `bool` явно.
* **Метрики с неограниченной кардинальностью.** Метка с идентификатором пользователя создаёт миллионы рядов; такие данные место в логах.

## Итоги

* Три сигнала: логи (события), метрики (агрегаты), трассировки (путь запроса).
* SLI измеряет, SLO задаёт цель, бюджет ошибок = 1 - SLO и показывает, сколько надёжности можно потратить.
* Перцентили по nearest-rank: `ceil(p x n / 100)`-й элемент отсортированного списка; метод нужно называть.
* Доступность = хорошие / все; остаток бюджета = допустимо - плохие, отрицательный означает нарушение SLO.
* Алерт с `for` проходит `inactive -> pending -> firing` и сбрасывается при ложном условии; пропавший ряд считается ложным условием.
* Дальше: что делать, когда система всё-таки ломается, - [надёжность, повторы и размыкатель цепи](lesson:devops.fundamentals.reliability-and-circuit-breakers).
