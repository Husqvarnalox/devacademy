## Как выпустить новую версию

Новую версию нужно заменить старую так, чтобы пользователи не заметили. Есть несколько способов, и у каждого свой компромисс между риском, простоем и стоимостью.

* **Recreate (пересоздание).** Остановить старую версию, запустить новую. Просто, но есть простой.
* **Rolling update (постепенная замена).** Экземпляры заменяются по несколько за раз: пока новые не готовы, старые продолжают работать. Простоя нет, но на время выпуска в работе обе версии одновременно, и они должны быть совместимы по данным и протоколам.
* **Blue-green.** Две полноценные среды: старая (blue) обслуживает пользователей, новая (green) поднимается и проверяется рядом; затем трафик переключается одним действием. Откат - обратное переключение, но стоимость - вдвое больше ресурсов на время выпуска.
* **Canary (канарейка).** Новая версия получает небольшую долю трафика (например, 5%), автоматика сравнивает её с базовой и постепенно увеличивает долю или откатывает. Ошибка затрагивает только малую часть пользователей.

Канареечный выпуск превращает наблюдение (мониторинг из [следующего урока](lesson:devops.fundamentals.observability-and-slos)) в решение: **продвигать, ждать или откатывать**. Это замкнутая петля обратной связи, о которой шла речь в [первом уроке](lesson:devops.fundamentals.what-is-devops-and-dora).

## Сравнение стратегий и правило канарейки

| Стратегия | Простой | Ресурсы | Охват ошибки | Скорость отката |
| --- | --- | --- | --- | --- |
| Recreate | есть | 1x | все пользователи | перевыпуск |
| Rolling | нет | 1x + запас (maxSurge) | растёт по мере замены | обратная замена, медленно |
| Blue-green | нет | 2x на время выпуска | все после переключения | мгновенно (переключение) |
| Canary | нет | 1x + доля | малая доля на шаге | быстро (снять трафик) |

**Rolling update и готовность.** Контроллер не должен выключить старый экземпляр, пока новый не прошёл проверку готовности (readiness). Параметры вроде `maxUnavailable` и `maxSurge` ограничивают, сколько экземпляров можно одновременно выключить или добавить сверх нормы.

**Канареечное решение.** На каждом шаге (5%, 25%, 50%, 100% трафика) собирается окно наблюдения: запросы и ошибки у базовой версии и у канарейки **в одно и то же время**. Решение:

1. Если у канарейки запросов меньше минимума `MIN_REQUESTS` - **HOLD**: данных мало, оставаться на шаге. Малая выборка шумна: 1 ошибка из 10 запросов - 10%, но это не вывод.
2. Допустимая доля ошибок `allowed = max(ABS_FLOOR, FACTOR x доля_ошибок_базовой)`. Абсолютный порог защищает от случая, когда база идеальна (доля 0), а относительный учитывает фоновый уровень ошибок (если базовая версия уже ошибается в 5% запросов, канарейка с 6% не хуже).
3. Если доля ошибок канарейки **строго больше** `allowed` - **ROLLBACK**: вернуть вес 0.
4. Иначе - **PROMOTE** на следующий шаг, а на последнем шаге - **COMPLETE**.

Доли сравнивают точно: рациональные числа (`Fraction`) или перекрёстное умножение целых, а не `float`, иначе граничные случаи («ровно 1%») дают случайные результаты.

**Откат и данные.** Возврат кода не возвращает данные. Если новая версия записала данные в новом формате или миграция удалила столбец, старая версия может не заработать. Поэтому изменения схемы делают **расширяющими, а не ломающими**: добавили столбец -> перешли на новый код -> удалили старый столбец отдельным выпуском. Идемпотентность операций ([урок про согласованность](lesson:system-design.fundamentals.consistency-and-idempotency)) помогает безопасно повторять шаги выпуска.

В упражнении моделируется только решающая логика. Распределение трафика, проверки готовности и сбор метрик в настоящих системах (Kubernetes, Argo Rollouts, сервис-меш) вынесены за рамки.

## Доля трафика и охват ошибки

Если ошибка в новой версии возникает в каждом десятом запросе, то канарейка с 5% трафика заденет 0.5% всех запросов, а полный выпуск - 10%.

```python run
from fractions import Fraction

error_per_request = Fraction(1, 10)
for weight in (5, 25, 50, 100):
    share = Fraction(weight, 100) * error_per_request
    print(f"canary {weight:3}% -> {float(share * 100):5.1f}% of all requests fail")
```
```output
canary   5% ->   0.5% of all requests fail
canary  25% ->   2.5% of all requests fail
canary  50% ->   5.0% of all requests fail
canary 100% ->  10.0% of all requests fail
```

Канарейка не предотвращает ошибку, но ограничивает вред, пока автоматика не откатит выпуск.

## Решение для одного окна

```python run
from fractions import Fraction


def decide(base_req, base_err, can_req, can_err, min_requests=200, floor_permille=10, factor=2):
    if can_req < min_requests:
        return "HOLD"
    base = Fraction(base_err, base_req) if base_req else Fraction(0)
    allowed = max(Fraction(floor_permille, 1000), factor * base)
    return "ROLLBACK" if Fraction(can_err, can_req) > allowed else "PROMOTE"


windows = [
    (10000, 20, 500, 2),     # 0.4% против допустимого 1%
    (10000, 20, 100, 50),    # мало запросов: решение откладывается
    (10000, 20, 2500, 100),  # 4% > 1%
    (10000, 20, 300, 3),     # ровно 1%: порог нестрогий
    (10000, 500, 1000, 140), # база 5%, допустимо max(1%, 2 x 5%) = 10%: 14% - откат
]
for w in windows:
    print(w, "->", decide(*w))
```
```output
(10000, 20, 500, 2) -> PROMOTE
(10000, 20, 100, 50) -> HOLD
(10000, 20, 2500, 100) -> ROLLBACK
(10000, 20, 300, 3) -> PROMOTE
(10000, 500, 1000, 140) -> ROLLBACK
```

Обратите внимание на ровно 1%: `ROLLBACK` только при **строгом** превышении, поэтому `3/300` проходит. Точная арифметика делает такие границы воспроизводимыми.

## Типичные ошибки

* **Решать по малой выборке.** Одна ошибка при 20 запросах - не 5%-я деградация; используйте минимум запросов или статистический тест.
* **Сравнивать с вчерашним днём.** Трафик и состав пользователей меняются; сравнивайте канарейку с базовой версией в то же время и на сопоставимой нагрузке.
* **Только абсолютный порог.** Если базовая версия и так ошибается в 5% запросов, порог 1% откатит любой выпуск; нужен и относительный критерий.
* **Только относительный порог.** При идеальной базе (0 ошибок) любая одна ошибка в канарейке превысит порог; нужен абсолютный пол.
* **Float в границах.** Сравнение `0.01` и `3/300` через `float` может дать неожиданный результат; используйте точные доли.
* **Откат без проверки совместимости данных.** Ломающая миграция делает откат невозможным; расширяйте схему, потом сжимайте.
* **Blue-green с общей базой данных без плана.** Переключение мгновенное, а данные общие: несовместимость схем проявится сразу у всех.
* **Нет проверки готовности в rolling update.** Трафик придёт на экземпляр, который ещё не прогрет; старые уже выключены.
* **Автоматизировать выпуск без автоматического отката.** Тогда скорость выпуска вырастет, а скорость восстановления - нет.

## Итоги

* Стратегии: recreate (простой), rolling (постепенно), blue-green (мгновенный откат, двойные ресурсы), canary (малая доля трафика).
* Rolling update требует проверок готовности и совместимости двух версий; blue-green - вдвое больше ресурсов; canary - хороших метрик.
* Канареечное решение: мало данных -> HOLD; доля ошибок канарейки больше max(абсолютный пол, коэффициент x база) -> ROLLBACK; иначе PROMOTE, на последнем шаге COMPLETE.
* Сравнивайте точными долями и в один период с базовой версией.
* Откат кода не откатывает данные: делайте миграции совместимыми.
