## Образ, слой, контейнер

Чтобы программа одинаково работала у разработчика, в CI и в продакшене, её упаковывают вместе с зависимостями. Результат - **образ** (image): неизменяемый набор файлов плюс метаданные запуска (команда, переменные). **Контейнер** - запущенный из образа процесс, которому ядро показывает свою файловую систему, сеть и список процессов. В отличие от виртуальной машины у контейнера нет своего ядра: он использует ядро хоста, а изоляцию дают механизмы ядра (пространства имён и cgroups; процессы и их изоляция разобраны в [курсе по операционным системам](lesson:os.fundamentals.processes-and-system-calls)).

Образ строится по **Dockerfile** - списку инструкций. Многие из них создают **слой** (layer): `RUN` фиксирует изменения файловой системы после команды, `COPY` и `ADD` добавляют файлы. Другие (`ENV`, `CMD`, `USER`, `WORKDIR`) записывают метаданные. Слои неизменяемы, поэтому их можно **кешировать** и переиспользовать между сборками: если ничего не изменилось, сборщик берёт готовый слой вместо повторного выполнения.

Главное правило кеша: **изменение любого слоя пересобирает все следующие**. Поэтому порядок инструкций - это порядок «от редко меняющегося к часто меняющемуся»: сначала базовый образ, потом файлы зависимостей и их установка, и только затем исходный код.

## Когда слой берётся из кеша

Для инструкции с номером `i` слой переиспользуется, только если одновременно верно:

1. все предыдущие инструкции в этой стадии взяты из кеша;
2. текст инструкции не изменился;
3. для `COPY` и `ADD`: не изменились копируемые файлы (сборщик сравнивает контрольные суммы).

Для `RUN` содержимое проверяется не по результату, а по тексту команды: команда `RUN pip install -r requirements.txt` останется в кеше, даже если внешний мир изменился (например, вышла новая версия пакета). Это экономит время, но означает, что кеш не «видит» изменений вне Dockerfile.

**Контекст сборки и `.dockerignore`.** Сборщик получает каталог (контекст). Всё, что в нём лежит, считается входом: файл `.dockerignore` в корне контекста исключает пути (каталоги вроде `.git/` и `node_modules`, шаблоны `*.md` для корня, `**/*.pyc` на любой глубине). Исключённые файлы не копируются и не инвалидируют `COPY`. Файл нужно писать **первым**, до Dockerfile: без него правка любого локального файла сбросит кеш `COPY . .`, а в образ попадут секреты (`.env`) и мусор.

**Многоступенчатая сборка.** Dockerfile может состоять из нескольких стадий (`FROM ... AS build`). Каждая стадия имеет свою цепочку кеша. `COPY --from=build /out/app /usr/local/bin/app` берёт готовый результат из другой стадии; если стадия `build` пересобралась, этот `COPY` тоже пересобирается. Итоговая стадия не содержит компиляторов и исходников - образ меньше и безопаснее.

**Практики.**

* закрепляйте версию базового образа (`python:3.12-slim`, не `latest`; для строгой воспроизводимости - дайджест);
* запускайте процесс от непривилегированного пользователя с числовым идентификатором (`USER 10001`);
* не передавайте секреты через `ARG` и `ENV`: они остаются в истории слоёв (используйте механизмы секретов сборщика и конфигурацию во время запуска, см. [следующий урок](lesson:devops.fundamentals.configuration-and-secrets));
* объединяйте команды `RUN` с общим кешем пакетного менеджера, чтобы временные файлы не оставались в слое: удаление файла в следующем слое не уменьшает образ, потому что старый слой остаётся;
* добавляйте `HEALTHCHECK`, если оркестратор его использует.

В упражнении моделируется именно инвалидация кеша. Это упрощение: настоящий сборщик учитывает `ARG`, режимы и владельцев файлов, платформу и обновление базового образа, а `.dockerignore` использует более богатые правила, чем три формы шаблонов в упражнении.

## Порядок инструкций и кеш

Смоделируем две версии Dockerfile для Python-приложения и три правки: исходник, зависимости, снова исходник. Считаем, сколько шагов пересобирается.

```python run
def rebuilds(dockerfile, changes):
    """dockerfile: список (текст, источники | None). changes: список наборов изменённых файлов."""
    out = []
    for changed in changes:
        dirty, count = False, 0
        for text, sources in dockerfile:
            if sources is not None and any(c == s or c.startswith(s.rstrip("/") + "/") or s == "." for s in sources for c in changed):
                dirty = True
            if dirty:
                count += 1
        out.append(count)
    return out


good = [("FROM python:3.12-slim", None), ("COPY requirements.txt /app/", ["requirements.txt"]),
        ("RUN pip install -r requirements.txt", None), ("COPY . /app", ["."]), ("CMD python app.py", None)]
bad = [("FROM python:3.12-slim", None), ("COPY . /app", ["."]),
       ("RUN pip install -r /app/requirements.txt", None), ("CMD python app.py", None)]
edits = [{"app.py"}, {"requirements.txt"}, {"app.py"}]
print("good order:", rebuilds(good, edits))
print("bad order: ", rebuilds(bad, edits))
```
```output
good order: [2, 4, 2]
bad order:  [3, 3, 3]
```

В хорошем порядке правка исходника пересобирает 2 шага (только `COPY . /app` и `CMD`), в плохом - 3 (`COPY`, установка зависимостей и `CMD`). В реальных образах `RUN pip install` занимает минуты, поэтому разница ощутима при каждом коммите.

## Что исключает .dockerignore

```python run
def ignored(path, patterns):
    for p in patterns:
        if p.startswith("**/*."):
            if path.endswith(p[4:]):
                return True
        elif p.startswith("*."):
            if "/" not in path and path.endswith(p[1:]):
                return True
        else:
            base = p.rstrip("/")
            if path == base or path.startswith(base + "/"):
                return True
    return False


patterns = [".git/", "node_modules", "*.md", "**/*.pyc"]
for f in [".git/HEAD", "README.md", "docs/guide.md", "node_modules/x/index.js", "src/app.pyc", "src/app.py", "node_modules_notes.txt"]:
    print(f"{f:26}", "ignored" if ignored(f, patterns) else "in context")
```
```output
.git/HEAD                  ignored
README.md                  ignored
docs/guide.md              in context
node_modules/x/index.js    ignored
src/app.pyc                ignored
src/app.py                 in context
node_modules_notes.txt     in context
```

Обратите внимание: `*.md` исключает `README.md` в корне, но не `docs/guide.md`; для всех уровней нужно писать `**/*.md`. Эту тонкость часто упускают, и «исключённый» файл всё равно попадает в образ. Здесь реализован упрощённый набор правил из трёх форм шаблонов, а не вся семантика `.dockerignore`.

## Типичные ошибки

* **Сначала `COPY . .`, потом установка зависимостей.** Любая правка исходника заставляет заново ставить зависимости.
* **Нет `.dockerignore`.** В контекст попадают `.git`, `node_modules`, `.env`; сборка медленная, кеш нестабильный, секреты в образе. Шаблоны для сборочных каталогов пишут с запасом (`**/dist*`, `**/.next*`), чтобы не пропустить `dist-e2e`.
* **Тег `latest` или непиннованная версия базового образа.** Сборка перестаёт быть воспроизводимой.
* **Запуск от root.** Уязвимость в приложении даёт root в контейнере; задавайте числовой `USER`.
* **Секреты в `ARG`, `ENV` или в слое.** Удаление файла в следующем слое не убирает его из предыдущего: он остаётся в образе.
* **Один огромный образ со сборочными инструментами.** Используйте многоступенчатую сборку и копируйте в итоговую стадию только артефакты.
* **Думать, что `RUN` в кеше значит «актуален».** Кеш смотрит на текст команды; внешние изменения (новая версия пакета, обновление системных пакетов) он не заметит.
* **Считать контейнер виртуальной машиной.** Ядро общее; уязвимость ядра хоста затрагивает все контейнеры.
* **Хранить данные внутри контейнера.** Файловая система контейнера эфемерна; постоянные данные хранят на томах.

## Итоги

* Образ - упорядоченные неизменяемые слои плюс метаданные; контейнер - процесс с изоляцией на общем ядре.
* Слой берётся из кеша, если не менялись инструкция, входные файлы (для `COPY` и `ADD`) и все предыдущие шаги стадии.
* Порядок «от редкого к частому»: зависимости раньше исходников.
* `.dockerignore` пишется первым, в корне контекста; исключённые пути не влияют на кеш.
* Многоступенчатая сборка, закреплённый базовый образ, непривилегированный числовой пользователь и отсутствие секретов в слоях - минимум гигиены.
* Дальше: как приложение получает настройки и секреты во время работы, не пересобирая образ, - [конфигурация и секреты](lesson:devops.fundamentals.configuration-and-secrets).
