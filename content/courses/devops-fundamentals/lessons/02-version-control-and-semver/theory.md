## Ветки и версии

Система контроля версий хранит историю изменений. В Git каждая правка попадает в **коммит** - снимок проекта с уникальным хешем и ссылкой на предыдущие коммиты. **Ветка** - лёгкий подвижный указатель на коммит: она сдвигается вперёд с каждым новым коммитом. **Тег** - неподвижное имя коммита, им отмечают выпуск.

Команды работают в одном из двух стилей:

* **Ветки функций.** Каждая задача живёт в своей ветке; её сливают через запрос на слияние (pull request) после ревью. Плюс - изоляция, минус - чем дольше живёт ветка, тем болезненнее слияние и тем позже обнаруживаются конфликты.
* **Trunk-based development.** Все часто (минимум раз в день) вливают небольшие изменения в одну основную ветку, а незавершённое прячут за флагом функции. Это тесно связано с непрерывной интеграцией из [первого урока](lesson:devops.fundamentals.what-is-devops-and-dora): основная ветка всегда должна собираться и проходить тесты.

Выпуск нужно как-то назвать. Номер версии `1.4.2` должен сообщать потребителю, **безопасно ли обновляться**. Для этого придумано **семантическое версионирование (SemVer)**: три числа `MAJOR.MINOR.PATCH` с чёткими правилами.

<!-- section: precise -->
## SemVer 2.0.0

Формат: `MAJOR.MINOR.PATCH[-ПРЕРЕЛИЗ][+BUILD]`.

* **MAJOR** повышают при несовместимых изменениях публичного API (и обнуляют MINOR и PATCH);
* **MINOR** - при добавлении совместимой функциональности (PATCH обнуляют);
* **PATCH** - при совместимых исправлениях ошибок.

Правила описывают **публичный API**, который автор обязан объявить сам. SemVer - договорённость: компилятор не проверит, что вы действительно ничего не сломали. Версии `0.y.z` - начальная разработка, API может меняться как угодно.

**Грамматика.** Числа без ведущих нулей (`01` недопустимо, `0` допустимо). После `-` идёт пре-релиз: идентификаторы из `[0-9A-Za-z-]`, разделённые точками; числовой идентификатор не может иметь ведущих нулей, пустых идентификаторов нет. После `+` - build-метаданные (тоже идентификаторы через точку, ведущие нули разрешены). Префикс `v` в версию не входит (в тегах Git его часто пишут, но это уже другая строка).

**Приоритет (раздел 11).** Сравниваем слева направо:

1. MAJOR, MINOR, PATCH сравниваются как **числа** (`1.10.0 > 1.9.0`).
2. Если числа равны, версия **с** пре-релизом младше версии **без** него: `1.0.0-alpha < 1.0.0`.
3. Если обе с пре-релизом, идентификаторы сравниваются по очереди слева направо: числовые - как числа; буквенные - в порядке ASCII; числовой всегда младше буквенного; если все общие идентификаторы равны, младше тот набор, где идентификаторов меньше.
4. Build-метаданные в сравнении **не участвуют**.

Пример цепочки из спецификации: `1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0`. Обратите внимание на `beta.2 < beta.11`: при строковом сравнении было бы наоборот.

## Сравнение идентификаторов пре-релиза

Ключ сортировки для идентификатора: числовой превращаем в пару `(0, число)`, буквенный в `(1, строка)`; кортежи Python сравнивают по элементам и делают именно то, что требует спецификация. Для набора идентификаторов короткий префикс младше автоматически.

```python run
def ident_key(i):
    return (0, int(i), "") if i.isdigit() else (1, 0, i)


def pre_key(pre):
    # без пре-релиза версия старше: (1,), с пре-релизом: (0, ключи...)
    return (1,) if not pre else (0, tuple(ident_key(i) for i in pre.split(".")))


chain = ["1.0.0-alpha", "1.0.0-alpha.1", "1.0.0-alpha.beta", "1.0.0-beta",
         "1.0.0-beta.2", "1.0.0-beta.11", "1.0.0-rc.1", "1.0.0"]
keys = [pre_key(v.partition("-")[2]) for v in chain]
print("chain is strictly increasing:", all(a < b for a, b in zip(keys, keys[1:])))
print("beta.2 < beta.11 numerically:", pre_key("beta.2") < pre_key("beta.11"))
print("as strings it would be:", "beta.2" < "beta.11")
```
```output
chain is strictly increasing: True
beta.2 < beta.11 numerically: True
as strings it would be: False
```

Ключ сортировки упрощает реализацию: вместо вложенных `if` сравнение выражается структурой данных.

## Разбор строки по грамматике

Чтобы отвергать недопустимые версии, используют регулярное выражение с самого semver.org (в упражнении оно дано в заготовке). Здесь же его краткая проверка:

```python run
import re

SEMVER = re.compile(
    r"^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)"
    r"(?:-((?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*)(?:\.(?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*))*))?"
    r"(?:\+([0-9a-zA-Z-]+(?:\.[0-9a-zA-Z-]+)*))?$"
)
for s in ["1.2.3", "1.2.3-rc.1+build.5", "01.2.3", "v1.2.3", "1.2", "1.2.3-01", "1.2.3-0a"]:
    m = SEMVER.match(s)
    print(f"{s:22}", ("ok " + str(m.groups())) if m else "INVALID")
```
```output
1.2.3                  ok ('1', '2', '3', None, None)
1.2.3-rc.1+build.5     ok ('1', '2', '3', 'rc.1', 'build.5')
01.2.3                 INVALID
v1.2.3                 INVALID
1.2                    INVALID
1.2.3-01               INVALID
1.2.3-0a               ok ('1', '2', '3', '0a', None)
```

Обратите внимание на `1.2.3-0a`: идентификатор `0a` буквенно-цифровой, значит ведущий ноль допустим; а `01` - числовой с ведущим нулём, недопустим.

## Типичные ошибки

* **Сравнивать версии как строки.** `"1.10.0" < "1.9.0"` истинно в лексикографическом порядке. Сравнивайте числа.
* **Считать, что пре-релиз старше релиза.** Наоборот: `1.0.0-rc.1 < 1.0.0`.
* **Учитывать build-метаданные в приоритете.** Они информативны (дата, хеш коммита), но в сравнении игнорируются.
* **Принимать `v1.2.3` или `1.2` как версию SemVer.** Префикс и сокращённая запись не соответствуют грамматике; нормализуйте на входе явно.
* **Повышать MINOR вместо MAJOR при несовместимости.** Потребители доверяют номеру; ложный MINOR ломает сборки у всех, кто обновляется автоматически.
* **Долгие ветки функций.** Слияние растущей ветки с основной превращается в «большой взрыв»; делите работу на малые шаги или используйте флаги функций.
* **Не помечать выпуски тегами.** По тегу `v1.4.2` можно воспроизвести сборку; без тега версию придётся искать в истории.
* **Путать SemVer с обещанием качества.** Номер говорит о совместимости, а не об отсутствии ошибок.

<!-- section: summary -->
## Итоги

* Коммит - неизменяемый снимок, ветка - подвижный указатель, тег - неподвижная метка выпуска.
* Trunk-based development требует частой интеграции в основную ветку и поддерживается флагами функций; ветки функций дают изоляцию ценой отложенных конфликтов.
* SemVer: `MAJOR.MINOR.PATCH`; MAJOR - несовместимое изменение API, MINOR - совместимая функция, PATCH - исправление.
* Приоритет: числа как числа; пре-релиз младше релиза; идентификаторы пре-релиза - числовые как числа и младше буквенных; build игнорируется.
* Грамматику проверяйте формально: ведущие нули, пустые идентификаторы и префикс `v` недопустимы.
* Дальше: версия превращается в артефакт через сборку - [конвейеры сборки как графы зависимостей](lesson:devops.fundamentals.build-pipelines-as-dags).
