## Данные - не код

Представьте анкету, в которой вас просят написать имя, а секретарь затем зачитывает вслух: «Пригласите в кабинет *<ваше имя>*». Если в поле вы напишете «Анна и уведомите всех, что приём отменён», секретарь послушно зачитает и это. Данные превратились в команду.

**SQL-инъекция** - то же самое с базой данных. Программа собирает текст запроса, вставляя в него то, что ввёл пользователь, и база не может отличить «задуманную» часть запроса от «вставленной». Стоит ввести в поле имени `' OR '1'='1`, и условие `WHERE name = '...'` становится истинным для всех строк.

Лекарство простое и надёжное: передавать запрос и данные **раздельно**. В тексте запроса на месте значения стоит плейсхолдер (`?`), а само значение отправляется отдельно, и база воспринимает его только как значение. Такие запросы называются **параметризованными**.

Вторая тема урока - как код обращается к базе. Функция, которая делает один запрос на каждый элемент списка, замедляет приложение сильнее, чем сложный запрос. Эту проблему называют **N+1**, и её легко заметить, если считать запросы. Урок опирается на [соединения](lesson:databases.sql.joins) (ими лечится N+1) и [транзакции](lesson:databases.sql.transactions-and-isolation).

## Параметры, белые списки, привилегии, N+1

**Как работает инъекция.** Запрос `f"SELECT * FROM users WHERE name = '{name}'"` при `name = "' OR '1'='1"` превращается в `... WHERE name = '' OR '1'='1'`: условие истинно всегда. Вариант `x'; DROP TABLE users; --` пытается добавить второй оператор; драйверы, как `sqlite3.execute`, такой запрос отвергают, но это не защита: ущерб можно нанести и одним оператором (прочитать чужие данные через `UNION SELECT`, обойти проверку пароля).

**Параметризация в sqlite3.** Два стиля плейсхолдеров:

* `?` - позиционные: `execute("... WHERE a = ? AND b = ?", (a, b))`; параметры - кортеж или список (для одного параметра - кортеж из одного элемента `(a,)`);
* `:имя` - именованные: `execute("... WHERE a = :a", {"a": 1})`.

Параметр заменяет **только значение** (литерал). Параметром нельзя передать имя таблицы или столбца, ключевые слова `ASC`/`DESC`, а также целый список для `IN`. Для этих случаев:

| что нужно | безопасный приём |
|---|---|
| имя столбца или таблицы, направление сортировки | **белый список** допустимых значений (множество в коде), остальное - `ValueError`; после проверки имя вставляют в текст |
| список значений в `IN (...)` | сгенерировать строку плейсхолдеров `", ".join("?" * len(ids))` и передать значения списком; пустой список обработать отдельно, `IN ()` недопустим |
| подстрока в `LIKE` | экранировать `%`, `_` и символ экранирования в самом значении и указать `ESCAPE '\'`; параметр содержит `%значение%` |
| много однотипных вставок | `executemany` с одним текстом запроса |

Важное: параметризация защищает от инъекции, но не от логических ошибок (например, поиск по `LIKE` без экранирования `%` вернёт лишние строки, и пользователь увидит больше, чем должен). Вручную «чистить» ввод (удалять апострофы) не нужно и ненадёжно: правильный способ не зависит от содержимого строки.

**Наименьшие привилегии.** Учётная запись, под которой работает приложение, должна иметь только нужные права: чтение и запись в своих таблицах, без `DROP`, без доступа к системным таблицам и чужим схемам. В PostgreSQL и MySQL это делают командами `CREATE ROLE`/`CREATE USER` и `GRANT`; SQLite прав доступа не имеет (доступ определяется правами на файл), поэтому ограничение там - это права файловой системы и режим открытия базы (например, только чтение). Привилегии не заменяют параметры: они лишь ограничивают ущерб, если защита всё-таки сломалась.

**ORM.** Библиотеки вроде SQLAlchemy и Django ORM собирают SQL за вас и передают значения параметрами, поэтому обычные запросы через ORM безопасны от инъекций. Но ORM не волшебный: как только вы подставляете строку в «сырой» фрагмент (`text()`, `raw()`, `extra()`), вы возвращаетесь к тем же правилам. ORM также скрывает число запросов: обращение к связанному объекту в цикле часто означает отдельный запрос на каждую итерацию (N+1). Привычка считать запросы нужна и с ORM.

**N+1.** Один запрос возвращает N строк, затем для каждой строки выполняется ещё один запрос: итого 1 + N. Каждое обращение к серверной СУБД стоит сетевой задержки, поэтому цикл из сотен запросов заметно медленнее одного запроса с `JOIN` или одного запроса `WHERE id IN (...)` на пачку. Обнаружить: подписаться на выполняемые операторы методом `conn.set_trace_callback(func)` (Python вызывает `func` для каждого оператора, передавая его текст с подставленными параметрами) и посчитать `SELECT`. В тестах приложений такой счётчик защищает от возврата проблемы.

**Что отличается в других СУБД.** Идея та же. В PostgreSQL драйвер `psycopg` использует `%s`/`%(name)s`, в MySQL (`mysql-connector`, `PyMySQL`) тоже `%s`; это плейсхолдеры, а не форматирование строк Python: параметры передаются вторым аргументом, а не подставляются оператором `%`. Использовать для `LIKE` `ESCAPE` можно во всех трёх СУБД.

## Примеры

**Пример 1. Инъекция в форме логина и её устранение.**

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, password TEXT);
INSERT INTO users VALUES (1, 'alice', 'pa55'), (2, 'bob', 'qwerty');
""")

def login_bad(name, password):
    sql = f"SELECT id FROM users WHERE name = '{name}' AND password = '{password}'"
    print("  SQL:", sql)
    return conn.execute(sql).fetchone()

def login_ok(name, password):
    return conn.execute("SELECT id FROM users WHERE name = ? AND password = ?", (name, password)).fetchone()

attack = "alice' --"
print("уязвимая версия, пароль не нужен:")
print("  результат:", login_bad(attack, "неважно"))
print("параметризованная версия:")
print("  результат:", login_ok(attack, "неважно"))
print("настоящий вход:", login_ok("alice", "pa55"))
```
```output
уязвимая версия, пароль не нужен:
  SQL: SELECT id FROM users WHERE name = 'alice' --' AND password = 'неважно'
  результат: (1,)
параметризованная версия:
  результат: None
настоящий вход: (1,)
```

Последовательность `--` начала комментарий в SQL и отрезала проверку пароля. Параметризованная версия искала пользователя с именем `alice' --` и никого не нашла.

**Пример 2. Что умеют и чего не умеют параметры.**

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT, price INTEGER);
INSERT INTO products VALUES (1, 'Lamp', 50), (2, 'Mouse', 20), (3, 'Cable', 10);
""")

print("qmark:", conn.execute("SELECT name FROM products WHERE price > ?", (15,)).fetchall())
print("named:", conn.execute("SELECT name FROM products WHERE price > :p", {"p": 15}).fetchall())

ids = [1, 3]
marks = ", ".join("?" * len(ids))
print("IN:", conn.execute(f"SELECT name FROM products WHERE id IN ({marks})", ids).fetchall())

# Параметр - значение, а не имя столбца: сортировка идёт по строке 'price', а не по столбцу
print("ORDER BY ?:", conn.execute("SELECT name FROM products ORDER BY ?", ("price",)).fetchall())
print("ORDER BY price:", conn.execute("SELECT name FROM products ORDER BY price").fetchall())

try:
    conn.execute("SELECT 1; DROP TABLE products")
except sqlite3.ProgrammingError as e:
    print("execute отвергает несколько операторов:", e)
print("таблица на месте:", conn.execute("SELECT count(*) FROM products").fetchone()[0])
```
```output
qmark: [('Lamp',), ('Mouse',)]
named: [('Lamp',), ('Mouse',)]
IN: [('Lamp',), ('Cable',)]
ORDER BY ?: [('Lamp',), ('Mouse',), ('Cable',)]
ORDER BY price: [('Cable',), ('Mouse',), ('Lamp',)]
execute отвергает несколько операторов: You can only execute one statement at a time.
таблица на месте: 3
```

`ORDER BY ?` не вызвал ошибки, но и не отсортировал: все строки получили одно и то же «значение» `'price'`, и порядок остался прежним. Это тихая ошибка, а не защита. Для имени столбца нужен белый список (см. упражнение).

**Пример 3. Считаем запросы: N+1 и соединение.**

```python run
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE books (id INTEGER PRIMARY KEY, author_id INTEGER, title TEXT);
INSERT INTO authors VALUES (1, 'Tolstoy'), (2, 'Chekhov'), (3, 'Gogol');
INSERT INTO books VALUES (1, 1, 'War and Peace'), (2, 2, 'The Seagull'), (3, 3, 'Dead Souls'), (4, 3, 'The Nose');
""")

executed = []
conn.set_trace_callback(executed.append)

def n_plus_one():
    result = {}
    for author_id, name in conn.execute("SELECT id, name FROM authors ORDER BY name").fetchall():
        rows = conn.execute("SELECT title FROM books WHERE author_id = ? ORDER BY title", (author_id,)).fetchall()
        result[name] = [t for (t,) in rows]
    return result

def with_join():
    result = {}
    for name, title in conn.execute(
        "SELECT a.name, b.title FROM authors a JOIN books b ON b.author_id = a.id ORDER BY a.name, b.title"
    ):
        result.setdefault(name, []).append(title)
    return result

for func in (n_plus_one, with_join):
    executed.clear()
    result = func()
    print(f"{func.__name__}: запросов {len(executed)}")
print("результаты совпадают:", n_plus_one() == with_join())
print("пример текста из trace:", executed[0][:48], "...")
```
```output
n_plus_one: запросов 4
with_join: запросов 1
результаты совпадают: True
пример текста из trace: SELECT a.name, b.title FROM authors a JOIN books ...
```

Для трёх авторов цикл сделал 1 + 3 = 4 запроса, соединение - один. Для 1000 авторов разница будет 1001 против 1.

## Типичные ошибки

* **Собирать SQL f-строкой, `%` или `+` из пользовательских данных.** Даже «безопасные» на вид числа и идентификаторы из запроса могут быть строками с сюрпризами. Значения - только плейсхолдеры.
* **«Чистить» ввод вручную** (удалять апострофы, `--`, `;`). Любой пропущенный вариант - уязвимость, а честные имена вроде `O'Brien` ломаются.
* **Пытаться параметризовать имя столбца** (`ORDER BY ?`). Запрос не падает, но сортирует по константе. Используйте белый список имён.
* **Подставлять список в `IN` через `str(list)` или `",".join(map(str, ids))`.** Если ids пришли снаружи, это инъекция; делайте плейсхолдеры по длине списка.
* **Не экранировать `%` и `_` в `LIKE`.** Пользователь, введший `%`, получает все строки; это утечка данных, а не просто неточный поиск.
* **Считать execute защитой от `; DROP TABLE`.** Отказ выполнять несколько операторов не мешает читать чужие данные одним запросом. `executescript` же выполняет всё и параметров не принимает: не передавайте ему пользовательские данные.
* **Давать приложению учётную запись администратора.** Любая ошибка превращается в полный контроль над базой.
* **Верить, что ORM всегда безопасен.** Сырые фрагменты с f-строкой внутри ORM так же уязвимы, как прямой SQL.
* **Не замечать N+1.** Цикл с запросом внутри выглядит безобидно на 10 строках и убивает приложение на 10 000. Считайте запросы в тестах.
* **Логировать запросы с подставленными данными в открытом виде** и записывать в логи пароли и токены. `set_trace_callback` показывает значения параметров: не включайте его в продакшене без фильтрации.

## Итоги

* SQL-инъекция возникает, когда данные становятся частью текста запроса. Защита - параметризованные запросы: плейсхолдеры `?` или `:name`, значения отдельным аргументом.
* Параметры заменяют только значения. Имена столбцов и таблиц проверяйте по белому списку, список для `IN` - генерируйте плейсхолдерами, шаблоны `LIKE` - экранируйте и указывайте `ESCAPE`.
* `execute` принимает один оператор, `executescript` - много, но без параметров; это не заменяет параметризацию.
* Наименьшие привилегии ограничивают ущерб; в SQLite они сводятся к правам на файл, в PostgreSQL и MySQL - к `GRANT`.
* ORM генерирует SQL и обычно параметризует значения, но сырые строки внутри ORM по-прежнему опасны, а N+1 в нём возникает легко.
* N+1 обнаруживается подсчётом запросов (`set_trace_callback`) и лечится соединением или одним запросом с `IN`.
