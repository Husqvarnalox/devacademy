## Эффект - синхронизация с внешним миром

Рендер должен быть чистым: функция компонента только считает описание интерфейса. Но приложению нужно и то, что не помещается в описание: подписаться на событие окна, запустить таймер, запросить данные, поменять `document.title`. Всё это - **внешние системы**, то есть то, чем React не управляет. Для синхронизации с ними служит хук **`useEffect`**.

```jsx
import { useEffect } from "react";

function TitleSync({ title }) {
  useEffect(() => {
    document.title = title;
  }, [title]);
  return null;
}
```

Функция в `useEffect` запускается **после того, как React закоммитил изменения** в DOM, а не во время рендера. Второй аргумент - **массив зависимостей**: эффект запускается заново, только если одно из значений в нём изменилось.

Главная идея: эффект описывает не «что сделать при монтировании», а **«как синхронизироваться»** с внешней системой для данных props и состояния. Если эффект что-то захватил (подписку, таймер, соединение), он обязан это освободить - вернуть **функцию очистки**.

Хуки живут только внутри рендера, и на сервере эффекты не выполняются. Сервер-рендер показывает это буквально:

```javascript run
const React = require("react");
const { renderToString } = require("react-dom/server");
const h = React.createElement;

const log = [];
function Widget() {
  log.push("render");
  React.useEffect(() => {
    log.push("effect");
    return () => log.push("cleanup");
  }, []);
  return h("p", null, "готово");
}

console.log(renderToString(h(Widget)));
console.log(log.join(","));
```
```output
<p>готово</p>
render
```

Функция компонента выполнилась (`render`), а эффект - нет: он принадлежит клиенту, где после коммита уже есть DOM.

## Точные правила

### Три формы массива зависимостей

| Запись | Когда запускается эффект |
| --- | --- |
| `useEffect(fn)` | после каждого рендера |
| `useEffect(fn, [])` | после монтирования; очистка при размонтировании |
| `useEffect(fn, [a, b])` | после монтирования и после рендеров, где изменилось `a` или `b` (сравнение через `Object.is`) |

В массиве перечисляют **все реактивные значения**, которые эффект читает: props, состояние, функции и переменные, объявленные в компоненте. Массив не выбирается «как удобнее»: он выводится из тела эффекта. Если значение в массив не попало, эффект работает со старым снимком. Правило линтера `react-hooks/exhaustive-deps` проверяет это автоматически.

### Очистка

Функция, которую возвращает эффект, вызывается **перед каждым повторным запуском** эффекта (с прежними значениями) и **при размонтировании**. Очистка симметрична эффекту: подписка - отписка, `setInterval` - `clearInterval`, соединение - закрытие, запрос - отмена.

### StrictMode и двойной запуск

В режиме разработки `<StrictMode>` после монтирования выполняет `эффект -> очистка -> эффект`. Это сделано, чтобы проверить симметрию: если после такой пары поведение компонента правильное, значит, эффект можно безопасно запускать повторно (так же ведёт себя React при перемещении компонентов, `Suspense` и быстрых переходах). В продакшене эффект выполняется один раз. Поэтому «запускать код один раз на монтирование» не нужно добиваться хитростями: надо исправить очистку.

Модель последовательности (не React, а запись правила):

```javascript run
const events = [];
function effect() {
  events.push("effect");
  return () => events.push("cleanup");
}

const cleanup = effect(); // первый запуск
cleanup();                // имитация очистки StrictMode
effect();                 // второй запуск
console.log(events.join(" -> "));
```
```output
effect -> cleanup -> effect
```

### Загрузка данных: отмена и гонки

Запрос в эффекте создаёт две проблемы. Во-первых, при смене `userId` предыдущий запрос ещё в пути. Во-вторых, ответы могут прийти не в порядке отправки: ответ на старый запрос окажется последним и затрёт свежие данные (это называется гонкой). Решение - в очистке эффекта **отменить запрос** и **игнорировать его результат**:

```jsx
useEffect(() => {
  const controller = new AbortController();
  let ignore = false;
  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then((r) => r.json())
    .then((user) => { if (!ignore) setUser(user); })
    .catch((error) => { if (!ignore) setError(error); });
  return () => { ignore = true; controller.abort(); };
}, [userId]);
```

`AbortController` - стандартный объект; `controller.signal` передаётся запросу, а `controller.abort()` отклоняет его промис с `AbortError`. Флаг `ignore` нужен дополнительно, чтобы работать с функциями, не поддерживающими отмену. Проверим механизм на поддельной функции без сети:

```javascript run
function fakeFetch(url, { signal }) {
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => resolve({ url }), 10);
    signal.addEventListener("abort", () => {
      clearTimeout(timer);
      reject(signal.reason);
    });
  });
}

async function main() {
  const first = new AbortController();
  const pending = fakeFetch("/users/1", { signal: first.signal });
  first.abort();
  try {
    await pending;
  } catch (error) {
    console.log(error.name, first.signal.aborted);
  }

  const second = new AbortController();
  const response = await fakeFetch("/users/2", { signal: second.signal });
  console.log(response.url, second.signal.aborted);
}
main();
```
```output
AbortError true
/users/2 false
```

В тестах курса настоящий `fetch` не используют: в компонент передают функцию загрузки (или подменяют `fetch` через `vi.fn`), и ответом управляет сам тест.

## Примеры

**Пример 1. Подписка на событие окна.**

```jsx
function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);
  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);
  return <p>Ширина: {width}</p>;
}
```

Обработчик создаётся внутри эффекта, поэтому `removeEventListener` получает ту же функцию. Пустой массив уместен: эффект не читает реактивных значений.

**Пример 2. Таймер.**

```jsx
useEffect(() => {
  const id = setInterval(() => setSeconds((s) => s + 1), 1000);
  return () => clearInterval(id);
}, []);
```

Обновляющая функция `s => s + 1` не требует `seconds` в зависимостях.

**Пример 3. Что эффектом не является.**

```jsx
// Плохо: лишнее состояние и лишний рендер
const [fullName, setFullName] = useState("");
useEffect(() => setFullName(first + " " + last), [first, last]);

// Хорошо: вычисление в рендере
const fullName = first + " " + last;
```

Если значение выводится из props и состояния, эффект не нужен. Реакция на действие пользователя («после нажатия показать уведомление») тоже не эффект: она принадлежит обработчику события.

**Пример 4. Когда эффект запускается повторно.** Эффект, зависящий от `[userId]`, при смене `userId` сначала выполнит очистку для прежнего значения, потом новый запуск. Это та же последовательность, что показал пример с `effect -> cleanup -> effect`.

**Пример 5. Сброс состояния через key.** Если при смене `userId` нужно сбросить всё состояние компонента, проще отрисовать `<Profile key={userId} />` : компонент пересоздаётся целиком, эффект синхронизации не нужен.

## Типичные ошибки

* **Эффект для вычисляемых данных.** Запись производного значения в состояние внутри эффекта приводит к лишнему рендеру и рассинхронизации. Считайте в рендере.
* **Реакция на событие в эффекте.** Сообщение после «Сохранить» отправляйте из обработчика клика, а не из эффекта, наблюдающего за состоянием.
* **Нет очистки.** Подписка остаётся после размонтирования, таймер продолжает идти, запрос обновляет несуществующий компонент. StrictMode в разработке намеренно подсвечивает эту ошибку.
* **Неполный массив зависимостей.** Эффект видит устаревшие значения (замыкание на старый снимок). Не отключайте правило линтера: исправляйте эффект.
* **Объект или функция, созданные в рендере, в зависимостях.** `{ id }` каждый раз новый, поэтому эффект запускается на каждом рендере. Выносите объект внутрь эффекта или берите примитивы.
* **`async` как функция эффекта.** `useEffect(async () => ...)` возвращает промис вместо функции очистки. Объявляйте внутри эффекта отдельную `async`-функцию и вызывайте её.
* **Запрос без защиты от гонок.** Без отмены и флага `ignore` поздний ответ на старый запрос затирает свежий.
* **Борьба с двойным запуском StrictMode.** Флаг «уже запускали» скрывает ошибку, а не исправляет её. Добавьте очистку.

<!-- section: summary -->
## Итоги

* Эффект синхронизирует компонент с внешней системой; он запускается после коммита, на сервере не выполняется.
* Массив зависимостей выводится из кода эффекта: все реактивные значения. Без массива - после каждого рендера, `[]` - один цикл за монтирование.
* Очистка выполняется перед повторным запуском и при размонтировании; она зеркальна эффекту.
* StrictMode в разработке выполняет «эффект - очистка - эффект»: корректная очистка делает это незаметным.
* Запросы в эффекте отменяют через `AbortController` и защищают флагом `ignore` от гонок.
* Производные данные считают в рендере, а реакции на действия пользователя пишут в обработчиках.
