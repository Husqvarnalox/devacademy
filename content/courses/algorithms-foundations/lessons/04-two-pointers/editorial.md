# Разбор: тихие отрезки

## Наивное решение
Перебрать левую границу `l`, затем правую `r`, накапливая сумму, пока она не превысит `S`:

```
для l в 0..n-1:
    cur = 0
    для r в l..n-1:
        cur += a[r]
        если cur > S: break
        ответ += 1
```

Если лимит велик (в большом тесте подходит любой отрезок), это `n(n+1)/2 ≈ 5·10^9` шагов. Раннее прерывание не спасает: именно в худшем тесте `break` не срабатывает.

## Идея
Числа положительные, поэтому сумма отрезка монотонна: при расширении растёт, при сжатии убывает. Для каждой правой границы `r` самая левая подходящая граница `l(r)` не убывает при росте `r`. Значит можно держать окно `[l, r]` и двигать оба указателя только вправо.

## Алгоритм
```
l = 0; cur = 0; ans = 0
для r в 0..n-1:
    cur += a[r]
    пока cur > S: cur -= a[l]; l += 1
    ans += r - l + 1
```

## Почему верно
Инвариант: после внутреннего цикла `cur` - сумма окна `a[l..r]`, `l` - наименьшее начало, при котором она не превышает `S`. Все начала от `l` до `r` дают подходящие отрезки (меньшие по включению отрезки имеют меньшую сумму), а все начала левее `l` не подходят, потому что отрезок содержит окно `[l-1..r]`, которое мы уже признали слишком тяжёлым (или отрезок `[l-1..r']` при предыдущем `r' <= r` был тяжёлым и тем более тяжёл теперь). Пустое окно (`l = r + 1`) возникает, если `a[r] > S`, и даёт `0`.

## Сложность
Указатель `l` только растёт и не превосходит `n`, `r` делает `n` шагов: суммарно не более `2n` операций. Время `O(n)`, память `O(1)`.

## Подводные камни
* Ответ до `n(n+1)/2`: 64 бита.
* Сумма окна до `2·10^14`.
* Не пытайтесь считать «длину наибольшего окна» вместо числа отрезков: нужно прибавлять `r - l + 1`.
