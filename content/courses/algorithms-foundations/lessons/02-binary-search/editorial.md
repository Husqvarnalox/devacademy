# Разбор: распил досок

## Наивное решение
Перебирать длину `L` по порядку и для каждой считать число кусков за `O(n)`:

```
L = 1
пока pieces(L) >= k: L += 1
```

Ответ может быть порядка `10^9`, а каждая проверка стоит `n`. Это до `10^14` операций - не уложиться.

## Ключевое наблюдение
Функция `pieces(L) = Σ floor(a_i / L)` **не возрастает** по `L`: чем длиннее кусок, тем их меньше. Поэтому условие `pieces(L) >= k` монотонно: для маленьких `L` оно истинно, начиная с некоторого порога - ложно. Нам нужен последний `L` с истинным условием: бинарный поиск по ответу.

## Алгоритм
```
lo = 0                 # условно подходящее: L = 0 не проверяем
hi = max(a) + 1        # заведомо неподходящее: кусков 0 < k
пока hi - lo > 1:
    mid = (lo + hi) // 2
    если pieces(mid) >= k: lo = mid
    иначе:               hi = mid
вывести lo
```

## Почему верно
Инвариант: `lo` подходит (или `lo = 0`), `hi` не подходит. Он выполнен в начале: любой `L > max(a)` даёт 0 кусков, а `k >= 1`. Каждый шаг проверяет `mid` и переносит ту границу, которая сохраняет инвариант; `hi - lo` убывает минимум вдвое, `lo < mid < hi`, поэтому зацикливания нет. В конце `hi = lo + 1`: `lo` подходит, а следующее значение - нет. По монотонности больше `lo` не подходит ни одно число, поэтому `lo` - наибольшее подходящее. Если `lo = 0`, то даже `L = 1` не подходит, и ответ `0`.

## Сложность
`⌈log2(max(a) + 1)⌉ ≤ 30` проверок по `O(n)`: время `O(n log max(a))`, память `O(1)`.

## Подводные камни
* Сумма кусков до `2·10^14`: нужен 64-битный тип. В Java, C++ и Rust сумму держите в `long`, `long long`, `i64`.
* `max(a) + 1` в качестве `hi`; значение `hi = max(a)` потеряет ответ при `k = 1`.
* Строгое `>` вместо `>=`.
* В Python `sum(x // L for x in a)` на 10^5 элементов и 30 итерациях работает десятки миллисекунд, так что даже интерпретируемому языку хватает с запасом.
