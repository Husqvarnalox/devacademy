## Значения, ссылки и «где это лежит»

В курсе первых шагов вы узнали главное правило: присваивание значимого типа копирует **значение**, присваивание ссылочного - копирует **ссылку**. Здесь мы разбираем то, что стоит за этим правилом, и инструменты, которыми им управляют.

**Стек и куча - деталь реализации, а не семантика языка.** Спецификация C# говорит о *копировании* и *времени жизни*, а не о памяти. Локальная переменная `struct` обычно лежит в кадре вызова, но поле такой структуры внутри объекта лежит в куче вместе с объектом, а компилятор или JIT вправе держать переменную в регистре. Поэтому вопрос «стек или куча?» почти всегда заменяется вопросом «копируется или нет?».

**Упаковка (boxing)** - это превращение значения в объект: `object o = 42;`. Среда создаёт в куче объект, копирует туда число и отдаёт ссылку. Обратное действие - распаковка `(int)o`. Упаковка стоит выделения памяти и работы сборщика мусора, поэтому её избегают в горячем коде.

**`ref`, `out`, `in`** - три способа передать в метод *ссылку на переменную* вместо копии значения:

* `ref` - метод читает и меняет переменную вызывающего;
* `out` - метод *обязан* записать значение, вызывающему не нужно инициализировать переменную заранее (`int.TryParse(s, out var n)`);
* `in` - метод читает переменную без копирования, но менять её не может.

**`Span<T>`** - «окно» на непрерывный участок памяти (массив, часть массива, строку, память на стеке). Срез `span[1..3]` не копирует данные: он указывает на тот же участок.

И наконец, **nullable**: `int?` - настоящий тип `Nullable<int>`, а `string?` - только подсказка для компилятора.

## Точные правила

**Семантика значений и ссылок.** Тип определяет, что копируется при присваивании и при передаче аргумента «по значению» (по умолчанию): у значимого типа - всё значение, у ссылочного - ссылка. Где физически находится значение, определяет контекст, а не тип: локальная переменная, поле класса, элемент массива, замыкание, регистр процессора. Утверждение «структуры живут на стеке» неверно; верно «локальная переменная структуры не требует выделения в куче».

**Упаковка.** Преобразование значимого типа в `object`, в `System.ValueType` или в интерфейс, который тип реализует, - упаковка. Упакованное значение - копия: изменение исходной переменной не видно в упакованной копии. Распаковка должна указывать **точный** тип: `(long)o` для упакованного `int` бросает `InvalidCastException`. Упаковка происходит неявно в `string.Format` со старыми перегрузками `object`, при вызове интерфейсного метода через значение без ограничения `where T : struct, IFoo`, при использовании необобщённых коллекций (`ArrayList`) и так далее. Обобщённые коллекции (`List<int>`) хранят `int` без упаковки.

**Модификаторы параметров.**

* `ref` - аргумент должен быть инициализирован и помечен `ref` в вызове. Метод получает **псевдоним** переменной.
* `out` - переменная может быть неинициализирована; метод обязан присвоить значение до выхода (иначе ошибка CS0177). Объявление `out var x` встраивается прямо в вызов.
* `in` - передача по ссылке только для чтения; удобна для крупных `readonly struct`, потому что копирование не происходит и компилятору не нужны защитные копии. В вызове `in` писать не обязательно.
* `ref readonly` - возврат ссылки без права записи; `ref`-возврат (`ref int Max(...)`) и `ref`-локальные переменные позволяют работать с элементом массива «на месте».
* Нельзя использовать `ref`/`out`/`in` параметры в `async`-методах и итераторах: ссылка на переменную не может пережить точку `await`.

**`Span<T>` и `ReadOnlySpan<T>`.** Это `ref struct`: значение может жить только на стеке (или внутри другой `ref struct`). Отсюда ограничения: нельзя хранить в поле обычного класса (ошибка CS8345), нельзя упаковать, нельзя держать через `await` (CS4007) и использовать как аргумент обобщённого типа без поддержки `allows ref struct`. Взамен вы получаете безопасные срезы без копирования: массив, часть массива, `stackalloc`-буфер и строка (`ReadOnlySpan<char>`) обрабатываются одним кодом. Многие методы разбора принимают `ReadOnlySpan<char>`, поэтому `int.Parse(line.AsSpan(0, 3))` не создаёт подстроку. Для хранения в куче и асинхронного кода существует `Memory<T>`.

**Nullable value types.** `T?` для структуры - это `Nullable<T>` с `HasValue` и `Value`. Арифметика с «пустым» значением даёт «пустой» результат, сравнение `a == b` для двух пустых даёт `true`, а `a < b` - `false`. `Value` у пустого бросает `InvalidOperationException`.

**Nullable reference types (NRT).** При `#nullable enable` (в проекте - `<Nullable>enable</Nullable>`) ссылки считаются ненулевыми, если не помечены `?`. Это **только статический анализ**: нарушение даёт предупреждения (CS8600-CS8604, CS8618 и другие), а не ошибку. Во время выполнения `string` и `string?` - один тип, поэтому `typeof(string?)` не компилируется (CS8639), а `null!` или код без NRT спокойно кладут `null` в «ненулевую» ссылку. Оператор `!` только подавляет предупреждение. Для нулевого значения структур и для ссылок используются два **разных** механизма: первый меняет тип и размер данных, второй - нет.

**Что включено в этом курсе.** Среда запуска собирает одиночный файл как приложение .NET 10 (C# 14). Проверено на SDK 10.0.302: в таком файле уже включены неявные `using` и анализ nullable (присваивание `null` переменной `string` без всяких директив даёт предупреждение CS8600). Директиву `#nullable enable` мы всё равно пишем явно, чтобы код вёл себя одинаково в любом проекте.

## Примеры

**Пример 1. Упаковка - это копия.**

```csharp run
using System;

int i = 42;
object o = i;          // упаковка: объект в куче со скопированным числом
i = 43;
Console.WriteLine($"{o} {i}");

try
{
    long l = (long)o;  // распаковка требует точного типа
}
catch (InvalidCastException e)
{
    Console.WriteLine(e.Message);
}

object a = 5, b = 5;
Console.WriteLine(a == b);       // сравнение ссылок на два разных объекта
Console.WriteLine(a.Equals(b));  // сравнение значений

long before = GC.GetAllocatedBytesForCurrentThread();
for (int k = 0; k < 1000; k++) { object box = k; GC.KeepAlive(box); }
long after = GC.GetAllocatedBytesForCurrentThread();
Console.WriteLine(after - before >= 1000 * 16);   // каждая упаковка выделяет память
```
```output
42 43
Unable to cast object of type 'System.Int32' to type 'System.Int64'.
False
True
True
```

Первые две строки показывают, что упакованная копия независима от переменной. Сравнение `a == b` для `object` - это сравнение ссылок, поэтому две отдельные упаковки пятёрки не равны, хотя `Equals` вернёт `True`.

**Пример 2. `ref`, `out`, `in` и `ref`-возврат.**

```csharp run
using System;
using System.Globalization;

int x = 1, y = 2;
Swap(ref x, ref y);
Console.WriteLine($"{x} {y}");

if (int.TryParse("123", NumberStyles.Integer, CultureInfo.InvariantCulture, out int n))
    Console.WriteLine(n + 1);
Console.WriteLine(int.TryParse("12x", NumberStyles.Integer, CultureInfo.InvariantCulture, out int bad) + " " + bad);

var big = new Vec(3, 4);
Console.WriteLine(Length(in big));

int[] data = { 5, 9, 2 };
ref int maxRef = ref MaxElement(data);   // ссылка на элемент массива
maxRef = 0;                              // запись в сам массив
Console.WriteLine(string.Join(",", data));

static void Swap(ref int a, ref int b) => (a, b) = (b, a);
static double Length(in Vec v) => Math.Sqrt(v.X * v.X + v.Y * v.Y);
static ref int MaxElement(int[] arr)
{
    int best = 0;
    for (int i = 1; i < arr.Length; i++) if (arr[i] > arr[best]) best = i;
    return ref arr[best];
}

readonly record struct Vec(double X, double Y);
```
```output
2 1
124
False 0
5
5,0,2
```

`out`-параметр после неудачного разбора получает значение по умолчанию (`0`). `MaxElement` возвращает не число, а ссылку на ячейку массива, поэтому присваивание через `maxRef` изменило исходный массив.

**Пример 3. `Span<T>`: срезы без копирования.**

```csharp run
using System;

int[] arr = { 1, 2, 3, 4, 5 };
Span<int> middle = arr.AsSpan(1, 3);   // окно на элементы 2, 3, 4
middle[0] = 20;                        // меняет arr[1]
Console.WriteLine(string.Join(",", arr));

Span<int> onStack = stackalloc int[4] { 1, 2, 3, 4 };
onStack[1..3].Fill(0);                 // срез тоже Span: обнуляем два элемента
Console.WriteLine(string.Join(",", onStack.ToArray()));

ReadOnlySpan<char> line = "12:34".AsSpan();
int idx = line.IndexOf(':');
int hours = int.Parse(line[..idx]);              // разбор без подстроки
int minutes = int.Parse(line[(idx + 1)..]);
Console.WriteLine(hours * 60 + minutes);
```
```output
1,20,3,4,5
1,0,0,4
754
```

Ни один срез здесь не выделяет память: `middle`, `onStack[1..3]`, `line[..idx]` указывают на уже существующие данные.

**Пример 4. Nullable value types и nullable reference types - разные механизмы.**

```csharp run
#nullable enable
using System;

int? a = null;
int? b = 5;
Console.WriteLine($"{a == null} {a + 1 is null} {b + 1}");
Console.WriteLine(typeof(int?) == typeof(Nullable<int>));
Console.WriteLine(sizeof(int) + " " + System.Runtime.CompilerServices.Unsafe.SizeOf<int?>());

string notNull = null!;                // подавили предупреждение, null остался
Console.WriteLine(notNull is null);
string? maybe = null;
Console.WriteLine(typeof(string) == "x".GetType());
Console.WriteLine(maybe?.Length ?? -1);
```
```output
True True 6
True
4 8
True
True
-1
```

`int?` занимает больше места, чем `int` (нужен флаг `HasValue`) - это отдельный тип. А `null!` показывает, что NRT ничего не проверяют во время работы.

**Пример 5. Ошибки компиляции, которые объясняют правила (без запуска).**

```csharp
class Holder
{
    public Span<int> Window;                    // CS8345: Span<T> нельзя хранить в поле класса
}

async Task F()
{
    Span<int> s = stackalloc int[2];
    await Task.Delay(1);
    Console.WriteLine(s.Length);                // CS4007: Span<T> нельзя держать через await
}

var t = typeof(string?);                        // CS8639: string? - не тип времени выполнения
```

## Типичные ошибки

* **«Структуры на стеке, классы в куче».** Это упрощение. Поле структуры внутри объекта лежит в куче, локальный `class`-объект тоже в куче, а JIT может вообще не выделять память. Думайте о копировании и времени жизни.
* **Неявная упаковка в горячем цикле.** `object`, интерфейсные вызовы через неограниченный параметр, `string.Format` с `object`, необобщённые коллекции. Выделения видны в профилировщике; в обобщённом коде используйте ограничения и обобщённые коллекции.
* **Распаковка не в тот тип.** `(long)o` для упакованного `int` - `InvalidCastException`. Сначала `(int)o`, потом преобразование.
* **Сравнение упакованных значений оператором `==`.** Для `object` это сравнение ссылок.
* **`ref`/`in` ради «производительности» без измерений.** Для маленьких структур копирование дешевле, чем косвенный доступ; `in` для изменяемой структуры вызывает защитные копии.
* **Хранить `Span<T>` для долгого использования.** Он живёт только на стеке; для полей и асинхронного кода берите `Memory<T>` или массив.
* **Думать, что `string?` защищает от `NullReferenceException`.** Аннотации дают предупреждения; значение `null` всё ещё может прийти из кода без NRT, десериализации или через `!`.
* **Использовать `!` вместо проверки.** Это обещание, которое компилятор не проверяет.
* **Путать `int?` и `string?`.** Первое меняет тип и размер, второе - только анализ.
* **Читать `Value` без проверки.** Используйте `??`, `is { } v` или `GetValueOrDefault()`.

## Итоги

* Стек и куча - детали реализации; семантика C# определяется копированием значения или ссылки.
* Упаковка создаёт в куче независимую копию значения; распаковка требует точного типа. Обобщённые коллекции избегают упаковки.
* `ref` - псевдоним переменной, `out` - обязательный результат, `in` - чтение без копирования.
* `Span<T>` - срез памяти без копирования, но только на стеке: не поле класса, не через `await`.
* `int?` - реальный тип `Nullable<int>`; `string?` - аннотация компилятора. Предупреждения NRT исчезают при компиляции и не защищают во время выполнения.

## Факты

* `Span<T>` и `ReadOnlySpan<T>` - `ref struct`: их нельзя хранить в поле класса (CS8345) и держать через `await` (CS4007); с C# 13 ограничение `allows ref struct` позволяет использовать такие типы как аргумент обобщённого параметра (проверено компиляцией на .NET 10).
* Nullable reference types - анализ времени компиляции: `typeof(string?)` не компилируется (CS8639), а `null!` оставляет в переменной настоящий `null`.
