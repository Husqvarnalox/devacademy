## Куча, стек и цена выделения

Каждая переменная программы где-то живёт. В Go есть два места:

* **Стек горутины.** Быстрое место: выделение - сдвиг указателя, освобождение - возврат из функции, никакой работы для сборщика мусора. Но данные на стеке не могут пережить кадр своей функции.
* **Куча.** Общая область, которую обслуживает сборщик мусора (GC). Значения на куче живут, пока на них есть ссылки, но каждое выделение стоит времени, а каждое живое значение GC придётся обойти и позже освободить.

В Go вы не выбираете место явно. Решение принимает компилятор: **анализ выхода** (escape analysis) выясняет, может ли значение пережить вызов функции или стать доступным кому-то ещё. Если не может, значение остаётся на стеке; если может (или компилятор не смог доказать обратное), оно «убегает» на кучу.

Почему это важно в проектировании: в сервисе с тысячами запросов в секунду число аллокаций на запрос определяет, как часто работает GC и сколько процессорного времени он забирает. Предыдущий урок про [аллокации](lesson:go.pro.allocations) учил убирать лишние выделения структурно (Builder, предвыделение). Этот урок объясняет **почему** значение попало на кучу и как увидеть это в выводе компилятора, а также что именно делает GC и какими ручками его настраивают, когда сократить выделения нельзя.

Порядок работы инженера: профиль показывает горячую функцию, `-gcflags=-m` показывает причины выхода на кучу, правка убирает причину, `AllocsPerRun` фиксирует результат. Настройка GC (`GOGC`, `GOMEMLIMIT`) - следующий рычаг, а не первый.

## Примеры

### Читаем вывод -gcflags=-m

Программа ниже собирает несколько типичных случаев. Её вывод можно запустить, а решения компилятора - получить командой `go build -gcflags='-m -l'` (флаг `-l` отключает встраивание функций; иначе небольшие функции встраиваются в `main`, и сообщения относятся к вызывающему коду, что запутывает чтение).

```go run
package main

import "fmt"

type point struct{ x, y int }

func newPoint() *point {
	p := point{1, 2}
	return &p
}

func sumLocal() int {
	p := &point{3, 4}
	return p.x + p.y
}

func box(n int) any {
	return n
}

func counter() func() int {
	n := 0
	return func() int {
		n++
		return n
	}
}

func show(n int) {
	fmt.Println(n)
}

func huge() byte {
	b := make([]byte, 1<<20)
	return b[0]
}

func fixed() byte {
	var b [64]byte
	return b[0]
}

func main() {
	fmt.Println(newPoint().x, sumLocal(), box(1), counter()(), huge(), fixed())
	show(7)
}
```
```output
1 7 1 1 0 0
7
```

Решения компилятора для этого файла (номера строк - строки файла выше; вывод получен на Go 1.26, формулировки могут отличаться между версиями):

```text
./main.go:8:2: moved to heap: p
./main.go:13:7: &point{...} does not escape
./main.go:18:9: n escapes to heap
./main.go:22:2: moved to heap: n
./main.go:23:9: func literal escapes to heap
./main.go:30:13: ... argument does not escape
./main.go:30:14: n escapes to heap
./main.go:34:11: make([]byte, 1048576) escapes to heap
```

Разбор построчно:

* `8:2 moved to heap: p` - в `newPoint` локальная `p` размещена на куче, потому что `return &p` отдаёт её адрес наружу: значение должно пережить кадр функции.
* `13:7 &point{...} does not escape` - в `sumLocal` указатель не покидает функцию, объект остаётся на стеке. Оператор `&` сам по себе кучу не означает.
* `18:9 n escapes to heap` - в `box` число упаковывается в интерфейс `any` и возвращается; упакованное значение должно жить дольше вызова.
* `22:2 moved to heap: n` и `23:9 func literal escapes to heap` - в `counter` замыкание возвращается и держит ссылку на `n`; обе сущности переживают вызов.
* `30:13 ... argument does not escape` и `30:14 n escapes to heap` - `fmt.Println(n)`: сам срез аргументов `...any` остаётся на стеке, но значение `n`, упакованное в интерфейс для динамического вызова внутри `fmt`, считается ушедшим на кучу. Это типичная скрытая стоимость `fmt` в горячем коде.
* `34:11 make([]byte, 1048576) escapes to heap` - мегабайтный буфер слишком велик для стека, у компилятора есть предел размера для неявных стековых выделений.
* Нет строк для `fixed`: массив `[64]byte` остаётся на стеке, сообщения нет.

Для подробностей используйте `-gcflags='-m=2'`: компилятор объяснит цепочку, из-за которой значение утекло. Строка `leaking param: x` означает, что параметр-указатель (или его содержимое: `leaking param content`) может пережить вызов, и вызывающий код вынужден размещать то, на что он указывает, на куче.

### Место определяет использование, а не синтаксис

```go run
package main

import (
	"fmt"
	"testing"
)

type point struct{ x, y int }

var sink *point

func byValue(i int) int {
	p := point{i, i + 1}
	return p.x + p.y
}

func byPointerKept(i int) {
	p := &point{i, i + 1}
	sink = p // указатель переживает вызов
}

func byPointerLocal(i int) int {
	p := &point{i, i + 1}
	return p.x + p.y // указатель не покидает функцию
}

func main() {
	var r int
	fmt.Println("value:", testing.AllocsPerRun(100, func() { r += byValue(3) }))
	fmt.Println("pointer kept:", testing.AllocsPerRun(100, func() { byPointerKept(3) }))
	fmt.Println("pointer local:", testing.AllocsPerRun(100, func() { r += byPointerLocal(3) }))
	_ = r
}
```
```output
value: 0
pointer kept: 1
pointer local: 0
```

Два варианта с `&point{}` ведут себя по-разному: выделение появляется только там, где указатель сохранён в глобальной переменной. Поэтому «не использовать указатели ради скорости» - плохой совет; правильный: не отдавать наружу то, что можно вернуть по значению.

### Устройство решения упражнения

В заготовке на каждую строку приходится несколько выделений. Фрагмент вывода `go build -gcflags=-m` для неё (сокращён до причин на горячем пути; номера строк относятся к файлу заготовки):

```text
./accesslog.go:72:9: &Entry{...} escapes to heap
./accesslog.go:75:29: leaking param content: e
./accesslog.go:82:32: e.Method escapes to heap
./accesslog.go:82:42: e.Status escapes to heap
./accesslog.go:87:38: method escapes to heap
./accesslog.go:87:46: status escapes to heap
```

* Строка 72: `parseEntry` возвращает `*Entry` - указатель на объект, который должен пережить вызов, значит куча. Решение: вернуть `Entry` по значению; структура из двух строк и двух чисел копируется быстро.
* Строки 82 и 87: аргументы `fmt.Sprintf` упаковываются в интерфейсы и уходят на кучу, плюс `Sprintf` создаёт новую строку-ключ. Решение: ключ карты - структура `key{method string, status int}`; поиск и инкремент по существующему ключу не выделяют память.
* Выделение в `strings.Split` в выводе `-m` для вызывающего кода не видно: срез создаётся внутри `Split`. Эти аллокации находят через `AllocsPerRun`, бенчмарк с `-benchmem` или профиль памяти. Решение: `strings.Cut` возвращает подстроки без выделения срезов.
* Что осталось: `&errors.errorString{...}` и аргументы `Errorf` на пути ошибки. Это допустимо: горячий путь - корректная строка.

Вывод для решения после правок содержит выделения только для `NewAggregator` и пути ошибки.

### Что видит GC и что можно настроить

Когда сократить аллокации нельзя, остаётся управлять частотой работы GC. Две настройки (описаны в [руководстве по GC](https://go.dev/doc/gc-guide)):

* **`GOGC`** (по умолчанию 100): целевой рост кучи относительно живых данных после последней сборки. Живых 200 МиБ и `GOGC=100` означают, что следующая сборка начнётся примерно при 400 МиБ. Больше значение - реже GC, меньше нагрузка на процессор, но выше пик памяти. Меньше - наоборот.
* **`GOMEMLIMIT`** (Go 1.19): мягкий предел общей памяти, управляемой рантаймом. По мере приближения к нему GC работает чаще. Это страховка от OOM в контейнере, но не гарантия: если живые данные не помещаются, программа тратит всё время на GC.

Обе настройки можно прочитать и менять из кода (`runtime/debug`):

```go run
package main

import (
	"fmt"
	"math"
	"runtime/debug"
)

func main() {
	old := debug.SetGCPercent(50)
	fmt.Println("default GOGC:", old)
	debug.SetGCPercent(old)

	limit := debug.SetMemoryLimit(-1) // отрицательное значение только читает предел
	fmt.Println("no memory limit by default:", limit == math.MaxInt64)
}
```
```output
default GOGC: 100
no memory limit by default: true
```

Если переменные окружения `GOGC` или `GOMEMLIMIT` заданы, вывод будет другим: пример показывает значения по умолчанию.

## Точные правила

* **Что решает компилятор.** Значение размещается на стеке, если анализ доказывает, что ссылка на него не переживёт кадр функции. Доказательство консервативно: сомнение приводит к куче.
* **Основные причины выхода на кучу.**
  1. Возврат указателя (или среза, карты, функции, интерфейса, ссылающегося на локальное значение) из функции.
  2. Сохранение указателя в значении, которое живёт дольше: глобальная переменная, поле объекта, канал, структура, переданная наружу.
  3. Упаковка в интерфейс (`any`, `error`, `fmt.Stringer`) при передаче куда-то, где компилятор не видит конец жизни значения; динамический вызов метода интерфейса скрывает от анализа, что делает получатель.
  4. Замыкание, захватывающее переменную и покидающее функцию (возвращено, запущено в горутине, передано как значение).
  5. Размер значения не известен на этапе компиляции или превышает предел стека для неявных выделений (для `make([]T, n)` с переменным `n` решение зависит от версии компилятора).
  6. Рост стека не причина: стек горутины растёт автоматически копированием, это отдельный механизм.
* **Встраивание (inlining)** влияет на результат: после встраивания функции её локальные значения оцениваются в контексте вызывающей, и возвращаемый указатель может остаться на стеке. Поэтому вывод `-m` читают вместе с `-l` и без.
* **Флаги.** `-gcflags=-m` показывает основные решения, `-m=2` с объяснениями, `-l` отключает встраивание, `-gcflags=all=-m` распространяет флаг на зависимости. Формат сообщений не является стабильным API.
* **GC Go.** Конкурентный, неперемещающий, без поколений. Цикл включает обход достижимых объектов от корней (стеки, глобальные переменные); стоимость пропорциональна объёму **живых** данных и числу указателей в них, а не количеству мусора. Поэтому две стратегии снижения давления: меньше выделять (меньше циклов) и меньше держать живого/указательного (дешевле каждый цикл).
* **Указатели в данных.** Большой `[]int` GC не просматривает, а `[]*T` или структуры со строками и срезами просматривает. Плотные данные без указателей (срез структур с числами, индексы вместо указателей) дешевле для GC.
* **GOGC и GOMEMLIMIT.** Пик памяти примерно равен `(1 + GOGC/100) × живые данные`. `GOGC=off` с `GOMEMLIMIT` — допустимая комбинация для контейнера с известным запасом, но опасная: при росте живых данных рантайм переходит к почти непрерывной сборке. Предел задают ниже лимита контейнера, потому что рантайм учитывает не всю память процесса.
* **sync.Pool** переиспользует временные объекты между вызовами и уменьшает выделения, но его содержимое очищается при сборках мусора, а неправильное использование (возврат объекта с «хвостами» чужих данных) вызывает ошибки. Применять после измерений.
* **Проверка нулевых выделений.** `testing.AllocsPerRun` измеряет в установившемся режиме после прогрева; структуры, создаваемые лениво на первом вызове, в измерение не попадают, если прогрев их создал.

## Типичные ошибки

**1. Бороться с `&` и `new`.** Это не синоним кучи. Прежде чем переписывать, откройте `-m` и убедитесь, что значение действительно уходит на кучу.

**2. Читать `-m` без `-l`.** Из-за встраивания сообщения относятся к вызывающей функции, и причина кажется в другом месте. Для понимания анализа конкретной функции отключайте встраивание, для оценки итогового кода смотрите без `-l`.

**3. Игнорировать аллокации внутри библиотечных функций.** `-m` вашего пакета не покажет, что `strings.Split` создал срез. Находите такие места профилем (`pprof -sample_index=alloc_objects`), `-benchmem` или `AllocsPerRun`.

**4. `fmt` в горячем цикле.** `Sprintf`, `Println`, `Errorf` упаковывают аргументы в `any` и создают строки. На горячем пути замените на `strconv.Append*`, `Builder` или структурные ключи; оставьте `fmt` для пути ошибки и логирования.

**5. Ключи карт из склеенных строк.** `m[a+":"+b]` создаёт строку на каждое обращение. Составной ключ-структура сравнивается и хэшируется без выделений.

**6. Считать `GOGC=off` бесплатным ускорением.** Без предела памяти куча растёт неограниченно до OOM. Используйте `GOMEMLIMIT` и измеряйте пик.

**7. Оптимизировать без измерения.** Убрав аллокации в функции, которая вызывается раз в минуту, вы усложнили код без пользы. Показатель успеха - профиль и метрики (частота и длительность циклов GC, `GODEBUG=gctrace=1`), а не отсутствие строк `escapes to heap`.

**8. Хранить мелкие объекты в указательных структурах без нужды.** Миллион `*Item` в карте - миллион объектов, которые GC обходит при каждом цикле. Срез значений `[]Item` или значения в карте дешевле.

## Итог

Вы читаете решения компилятора об аллокациях (`moved to heap`, `escapes to heap`, `does not escape`, `leaking param`), знаете основные причины выхода значения на кучу (возврат и сохранение указателя, интерфейсы, замыкания, размер) и убираете их: возвращаете структуры по значению, избегаете `fmt` и склейки строк на горячем пути, используете структурные ключи. Для остаточного давления вы понимаете `GOGC` и `GOMEMLIMIT` и их компромиссы. Автоматические проверки подтверждают нулевое число аллокаций на горячем пути и неизменность поведения; скорость, потребление памяти и поведение GC они не измеряют, это работа профилировщика и бенчмарков на вашей машине.

## Углублённо: как GC видит ваши данные

Цикл сборки включает короткие паузы остановки мира (подготовка и завершение) и конкурентную фазу разметки, во время которой приложение продолжает работу, а часть процессорного времени уходит на разметку (около 25% по целевой настройке рантайма); при высокой скорости выделения горутины приложения принуждаются помогать GC (assist), что увеличивает задержки. Поэтому высокая скорость аллокаций вредит не только частотой циклов, но и хвостовыми задержками. Диагностика: `GODEBUG=gctrace=1` печатает строку на каждый цикл (размеры кучи до и после, процент процессорного времени GC), а `runtime/metrics` и `runtime.ReadMemStats` дают те же числа программно. Значения и формат трассы зависят от версии Go; ориентируйтесь на [руководство по GC](https://go.dev/doc/gc-guide).
