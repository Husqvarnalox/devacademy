## Гонки данных в рабочем коде

Вы уже запускали горутины и знаете, что они работают одновременно. В продакшене это означает, что общая память - счётчики, кеши, карты настроек - читается и меняется из многих мест сразу. Если не договориться о порядке обращений, возникают две разные беды:

* **Гонка данных (data race).** Две горутины обращаются к одной переменной одновременно, хотя бы одна из них пишет, и между обращениями нет синхронизации. По спецификации и модели памяти Go это неопределённое поведение уровня «результат непредсказуем»: потерянные обновления, «разорванные» значения многословных типов (строка, интерфейс, срез), аварийное завершение рантайма при одновременной записи в карту.
* **Логическая гонка (race condition).** Каждое отдельное обращение синхронизировано, но последовательность «проверил, потом сделал» не атомарна: к моменту действия условие уже изменилось. Детектор гонок это не отмечает, потому что формально гонки данных нет.

Цена в продакшене: метрики занижены, дубликаты записей, редкие падения «раз в неделю под нагрузкой», которые не воспроизводятся на ноутбуке. Поэтому такие ошибки ловят тестами с высокой конкуренцией и детектором гонок до выката.

Инструменты исправления: `sync.Mutex` и `sync.RWMutex` для составных структур и инвариантов, `sync/atomic` для одиночных значений, каналы для передачи владения. В упражнении вы почините реестр метрик со всеми тремя видами дефектов.

## Примеры

### Потерянные обновления и два способа их предотвратить

Без синхронизации `count++` читает значение, прибавляет единицу и записывает обратно; две горутины могут прочитать одно и то же значение. Ниже оба исправления дают детерминированный итог 4000.

```go run
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type lockedCounter struct {
	mu sync.Mutex
	n  int
}

func (c *lockedCounter) Inc() {
	c.mu.Lock()
	c.n++
	c.mu.Unlock()
}

func main() {
	var locked lockedCounter
	var atomicN atomic.Int64
	var wg sync.WaitGroup
	for i := 0; i < 4; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 1000; j++ {
				locked.Inc()
				atomicN.Add(1)
			}
		}()
	}
	wg.Wait()
	fmt.Println(locked.n, atomicN.Load())
}
```
```output
4000 4000
```

Чтение `locked.n` после `wg.Wait()` безопасно: `Wait` возвращается после всех `Done`, и это даёт упорядочивание (подробнее в [следующем уроке про модель памяти](lesson:go.pro.memory-model)).

Атомарная версия быстрее для одного числа, но она ничего не говорит о связи нескольких значений: если нужно обновить сумму и количество так, чтобы читатель не увидел «новую сумму со старым количеством», нужен мьютекс.

### Как выглядит отчёт race detector

Тот же `count++` без защиты, запущенный через `go run -race`, печатает (сокращено, пути заменены на `main.go`):

```
==================
WARNING: DATA RACE
Read at 0x00c000012138 by goroutine 7:
  main.main.func1()
      main.go:16 +0x88

Previous write at 0x00c000012138 by goroutine 9:
  main.main.func1()
      main.go:16 +0x98

Goroutine 7 (running) created at:
  main.main()
      main.go:13 +0x6c
...
```

Как читать: первый блок - обращение, которое поймано; «Previous write» - конфликтующее обращение другой горутины к тому же адресу; «created at» - где горутины запущены. Строка 16 в обоих блоках - это `count++`. Исправлять нужно оба обращения, а не одно.

### Check-then-act: двойная проверка

```go run
package main

import (
	"fmt"
	"sync"
)

type registry struct {
	mu    sync.RWMutex
	items map[string]*int
	made  int // сколько раз реально создавали элемент (под mu)
}

func (r *registry) get(name string) *int {
	r.mu.RLock()
	v, ok := r.items[name]
	r.mu.RUnlock()
	if ok {
		return v
	}
	r.mu.Lock()
	defer r.mu.Unlock()
	if v, ok := r.items[name]; ok { // повторная проверка: могли опередить
		return v
	}
	v = new(int)
	r.items[name] = v
	r.made++
	return v
}

func main() {
	r := &registry{items: map[string]*int{}}
	var wg sync.WaitGroup
	ptrs := make([]*int, 50)
	for i := range ptrs {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			ptrs[i] = r.get("k")
		}(i)
	}
	wg.Wait()
	same := true
	for _, p := range ptrs {
		if p != ptrs[0] {
			same = false
		}
	}
	fmt.Println("created:", r.made, "all same:", same)
}
```
```output
created: 1 all same: true
```

Быстрый путь идёт под `RLock` (читатели не блокируют друг друга), медленный - под `Lock` с повторной проверкой. Без повторной проверки `made` мог бы стать больше 1, а возвращённые указатели различались бы. Замечание: `ptrs[i]` пишут разные горутины в разные элементы - это не гонка, потому что адреса различны.

### Что тест может и не может проверить

Тесты упражнения запускают десятки горутин, которые стартуют одновременно (закрытием общего канала `start`), и проверяют итоги: сумма всех увеличений, один счётчик на имя, независимость снимка. Они **не ищут** гонку напрямую, а проверяют её следствия. В заготовке вызов `runtime.Gosched()` между чтением и записью искусственно расширяет окно гонки, чтобы сбой был воспроизводим всегда; в реальном коде окно в несколько наносекунд, и ошибка проявляется «иногда». Локально запускайте `go test -race -count=5`: детектор находит гонку по самому факту несинхронизированных обращений, даже если итог случайно оказался верным.

## Точные правила

* **Определение.** Гонка данных: два обращения к одной ячейке памяти, хотя бы одно - запись, не упорядоченные отношением happens-before. Правильно синхронизированная программа без гонок ведёт себя так, как будто горутины выполняются по очереди (последовательная согласованность). Подробнее - [следующий урок](lesson:go.pro.memory-model).
* **Mutex.** `Lock` и `Unlock`: `Unlock` синхронизируется с последующим `Lock`. Мьютекс нельзя копировать после первого использования (`go vet` проверяет `copylocks`). Не вызывайте `Lock` повторно из той же горутины: мьютекс Go не рекурсивен, будет взаимная блокировка.
* **RWMutex.** Много читателей или один писатель. Выгоден, когда чтений много и критическая секция читателя не короткая; для коротких секций накладные расходы RWMutex могут превысить выигрыш, поэтому сначала измерьте. Нельзя «повышать» блокировку: `RLock`, затем `Lock` без `RUnlock` - взаимная блокировка; поэтому паттерн «отпустить, взять эксклюзивную, проверить заново».
* **atomic.** Операции над одной ячейкой: `Add`, `Load`, `Store`, `Swap`, `CompareAndSwap`. Предпочитайте типы `atomic.Int64` и др.: поле нельзя случайно прочитать обычным обращением. Для 64-битных значений на 32-битных платформах старые функции требовали выравнивания; типизированные значения решают это.
* **Карты.** Одновременная запись или запись с чтением приводит к аварийному завершению (`fatal error: concurrent map ...`), которое нельзя перехватить через `recover`. `sync.Map` подходит для особых шаблонов (ключи пишутся один раз и читаются много раз, непересекающиеся наборы ключей у горутин); для общего случая обычная карта с мьютексом проще и типобезопаснее.
* **Не отдавайте внутреннее состояние.** Метод, возвращающий карту или срез внутренней структуры, выносит данные из-под защиты. Возвращайте копию, сделанную под блокировкой.
* **Размер критической секции.** Держите блокировку только на время обращения к общим данным: вызов функции пользователя, сетевой запрос или канальная операция внутри секции - источник взаимных блокировок и задержек.
* **Проверка гонок.** `go test -race` обнаруживает только случившиеся во время прогона обращения; замедляет выполнение в разы. Включайте его в CI и повторяйте тесты (`-count`), увеличивая конкуренцию (`-cpu 1,4`).

## Типичные ошибки

**1. Блокировка вокруг записи, но не вокруг чтения.** Читатель без `RLock` гоняется с писателем. Защищать нужно все обращения к данным, а не только «опасные».

**2. Check-then-act на разных блокировках.** `RLock; проверить; RUnlock; Lock; создать`. Исправление - повторная проверка после `Lock` (пример выше).

**3. Копирование структуры с мьютексом.** `func (c Counter) Value()` с получателем-значением копирует `sync.Mutex` вместе с состоянием. Используйте получатель-указатель; `go vet` предупредит.

**4. Захват переменной цикла в Go до 1.22.** В модулях с `go 1.21` и ниже `for i := range ... { go func() { use(i) }() }` разделяет одну `i` между горутинами. Начиная с `go 1.22` в `go.mod` каждая итерация получает свою переменную; в старых модулях передавайте `i` аргументом.

**5. Использовать atomic для составного инварианта.** Два `atomic.Int64` (сумма и счётчик) по отдельности безопасны, но читатель между ними увидит несогласованную пару. Нужен мьютекс или хранение пары в одном значении за атомарным указателем.

**6. Считать зелёный `-race` доказательством.** Детектор не видит непройденных путей и не ловит логические гонки. Это инструмент поиска, а не доказательство корректности.

**7. Пытаться «починить» гонку через `time.Sleep`.** Пауза не создаёт отношения happens-before; она лишь сдвигает вероятность ошибки.

<!-- section: summary -->
## Итог

Вы различаете гонку данных и логическую гонку, выбираете мьютекс или атомарную операцию по структуре инварианта, исправляете check-then-act повторной проверкой и копируете состояние под блокировкой вместо того, чтобы отдавать его наружу. Автоматические проверки подтверждают итоговые значения при высокой конкуренции; отсутствие гонок в непокрытых путях и отсутствие взаимных блокировок они не доказывают, поэтому `go test -race` вы запускаете у себя. Дальше: [модель памяти и публикация значений](lesson:go.pro.memory-model).

## Углублённо: как работает детектор

Детектор гонок Go построен на ThreadSanitizer: компилятор добавляет вызовы инструментации к каждому обращению к памяти и к синхронизирующим операциям (мьютексы, каналы, атомарные операции), а рантайм хранит для каждой ячейки сведения о последних обращениях и «векторные часы» горутин. Если два обращения к одному адресу не упорядочены этими часами, печатается отчёт. Отсюда следствия: нужен cgo; затраты по памяти и времени - в разы; ложных срабатываний практически нет, но пропуски возможны, потому что хранится ограниченная история обращений.
