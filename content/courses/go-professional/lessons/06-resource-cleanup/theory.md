## Освобождение ресурсов — это контракт, а не привычка

Файл, соединение с базой, блокировка, временный каталог, подписка: всё, что нужно вернуть, - ресурс. Рантайм Go не освободит их вовремя: сборщик мусора возвращает память, но не закрывает дескрипторы по расписанию (финализаторы не дают гарантий срока). Утёкший дескриптор не заметен в тестах и проявляется под нагрузкой: `too many open files`, исчерпанный пул соединений, зависшие блокировки.

Сложность не в самом `defer`, который вы знаете. Сложнее ситуации с **несколькими** ресурсами:

* открыли два, на третьем получили ошибку: нужно откатить первые два;
* работа вернула ошибку или запаниковала: закрыть всё всё равно;
* `Close` сам вернул ошибку: её нельзя терять (особенно у файла на запись), но нельзя и прерывать закрытие остальных;
* ошибок несколько: работа упала, а при закрытии упали ещё два ресурса. Какую вернуть? Начиная с Go 1.20 ответ - все: `errors.Join`.

Порядок важен: ресурсы, открытые позже, часто зависят от открытых раньше (транзакция внутри соединения, курсор внутри транзакции), поэтому закрывают в обратном порядке, как стек. В упражнении вы реализуете такой стек с проверкой на фейковых ресурсах, считающих вызовы `Close`.

## Примеры

### defer: порядок и момент вычисления аргументов

```go run
package main

import "fmt"

type res string

func (r res) Close() { fmt.Println("close", string(r)) }

func run() {
	a := res("a")
	defer a.Close()
	b := res("b")
	defer b.Close()

	x := 1
	defer fmt.Println("x at defer time:", x) // аргумент вычислен сейчас
	x = 2
	fmt.Println("work, x =", x)
}

func main() { run() }
```
```output
work, x = 2
x at defer time: 1
close b
close a
```

Построчный разбор: отложенные вызовы идут от последнего к первому; `fmt.Println` получил `x == 1`, потому что аргументы отложенного вызова вычисляются при выполнении `defer`. Для освобождения ресурсов LIFO - ровно то, что нужно.

### defer в цикле: ловушка и выход

```go run
package main

import "fmt"

type file struct{ name string }

func open(name string) *file { fmt.Println("open ", name); return &file{name} }
func (f *file) Close()       { fmt.Println("close", f.name) }

func badLoop(names []string) {
	for _, n := range names {
		f := open(n)
		defer f.Close() // выполнится только при выходе из badLoop
	}
	fmt.Println("badLoop done")
}

func one(n string) {
	f := open(n)
	defer f.Close() // выполнится при выходе из one
}

func goodLoop(names []string) {
	for _, n := range names {
		one(n)
	}
	fmt.Println("goodLoop done")
}

func main() {
	badLoop([]string{"x", "y"})
	goodLoop([]string{"x", "y"})
}
```
```output
open  x
open  y
badLoop done
close y
close x
open  x
close x
open  y
close y
goodLoop done
```

В `badLoop` оба файла открыты одновременно до конца функции; при тысяче файлов это тысяча дескрипторов. В `goodLoop` вынесенная функция закрывает каждый файл сразу.

### Ошибка Close и именованный результат

Если `defer` должен изменить возвращаемую ошибку, результат нужно назвать:

```go run
package main

import (
	"errors"
	"fmt"
)

type conn struct{ name string }

func (c *conn) Close() error { return fmt.Errorf("%s: flush failed", c.name) }

func work(fail bool) (err error) {
	c := &conn{"db"}
	defer func() {
		// Join: nil отбрасывается, поэтому при успешном Close вернётся err как есть.
		err = errors.Join(err, c.Close())
	}()
	if fail {
		return errors.New("query failed")
	}
	return nil
}

func main() {
	fmt.Println(work(false))
	fmt.Println("---")
	err := work(true)
	fmt.Println(err)
}
```
```output
db: flush failed
---
query failed
db: flush failed
```

`errors.Join` печатает ошибки по одной на строку. Если нужно сохранить в журнале только первую, это отдельное осознанное решение, а не побочный эффект `defer c.Close()`.

### Откат при частичном открытии

Главный приём упражнения: накапливайте то, что уже открыто, и при ошибке закрывайте это в обратном порядке.

```go
func OpenAll(o Opener, names []string) (*Group, error) {
	g := &Group{}
	for _, name := range names {
		r, err := o.Open(name)
		if err != nil {
			return nil, errors.Join(fmt.Errorf("open %q: %w", name, err), g.Close())
		}
		g.names = append(g.names, name)
		g.resources = append(g.resources, r)
	}
	return g, nil
}
```

Сначала `g.Close()` откатывает уже открытые, затем `errors.Join` соединяет их ошибки с ошибкой открытия. Если открыть удалось всё, функция возвращает группу, и закрытие становится ответственностью вызывающего: поэтому `Process` оформляет его одним `defer`.

### Паника

`defer` срабатывает и при панике; `recover` вызывать не нужно, если вы лишь хотите очистить ресурсы и позволить панике идти дальше. Присваивание именованному результату при панике бессмысленно: функция уже не вернёт значение. Ресурсы при этом закрываются, а ошибки их закрытия в этом случае некому вернуть: решите, нужно ли их логировать.

## Точные правила

* **Выполнение defer.** При выходе из окружающей функции: возврат, panic, `runtime.Goexit`. Порядок - LIFO. `os.Exit` и фатальные ошибки рантайма (`fatal error`, `log.Fatal`) отложенные вызовы **не** выполняют.
* **Аргументы** отложенного вызова и значение приёмника метода вычисляются при выполнении оператора `defer`. Замыкание же читает переменные в момент выполнения.
* **Именованные результаты** можно менять в отложенной функции: после `return x` результат присваивается, затем идут `defer`, затем функция возвращается.
* **Паника и recover.** `recover` возвращает значение паники только в непосредственно отложенной функции. Полезный шаблон: очистить и не вызывать `recover`, пусть паника продолжается.
* **errors.Join(errs...)** возвращает `nil`, если все аргументы `nil`; иначе ошибку, у которой `Unwrap() []error`. `Error()` объединяет тексты через перевод строки. Для сообщений нескольких ошибок в одну строку пишите собственный тип.
* **Идемпотентный Close.** Повторное закрытие файла возвращает ошибку `os.ErrClosed`, повторное закрытие канала - паника; поэтому собственные типы с `Close` делают безопасными для повторного вызова (флаг или обнуление полей, при конкурентном использовании - под мьютексом).
* **Close и данные.** Для ресурса, в который вы писали, ошибка `Close` может быть единственным признаком потери данных (`bufio.Writer` надо `Flush`, затем закрыть файл и проверить обе ошибки). Для ресурса, который вы лишь читали, `defer f.Close()` без проверки приемлем.
* **Откат.** Паттерн «cleanup stack»: после каждого успешного шага регистрируйте его откат, при ошибке выполняйте откаты в обратном порядке. В коде с большим числом шагов это даёт плоскую структуру вместо вложенных `if`.
* **Контекст.** Если закрытие может зависать (сетевое соединение), передавайте ему таймаут или контекст отмены, чтобы очистка не превращалась в источник утечек (см. [урок об отмене](lesson:go.pro.context-cancellation)).

## Типичные ошибки

**1. `defer` до проверки ошибки.** `f, err := os.Open(n); defer f.Close(); if err != nil {...}` при ошибке вызовет `Close` у `nil`. Сначала проверка, потом `defer`.

**2. `defer` в цикле.** Ресурсы копятся до конца функции. Вынесите тело цикла в функцию или закрывайте явно.

**3. Потерянная ошибка записи.** `defer f.Close()` у файла, открытого на запись. Проверяйте ошибку закрытия через именованный результат.

**4. Прерывание очистки при первой ошибке.** `for ... { if err := c.Close(); err != nil { return err } }` оставляет остальные ресурсы открытыми. Закрывайте всё, ошибки собирайте.

**5. Прямой порядок закрытия.** Зависимые ресурсы закрываются после тех, от которых зависят: транзакция падает, потому что соединение уже закрыто. Ресурсы - стек.

**6. Двойное закрытие.** Явный `Close()` в одном месте и `defer Close()` в другом: вторая попытка вернёт ошибку или вызовет панику. Сделайте `Close` идемпотентным или оставьте ровно одну точку закрытия.

**7. Откат без учёта собственной ошибки.** Вернули `err` открытия и забыли про ошибки закрытия предыдущих ресурсов: диагностика неполная. `errors.Join` соединяет их.

<!-- section: summary -->
## Итог

Вы проектируете освобождение ресурсов как стек: откат при частичном открытии, закрытие в обратном порядке на путях успеха, ошибки и паники, все `Close` вызываются, все ошибки сохраняются через `errors.Join`, повторный `Close` безопасен. Автоматические проверки на фейковом `Opener` подтверждают порядок событий, счётчики и содержимое ошибок; они не проверяют реальные файлы и сетевые ресурсы, а читаемость и выбор политики (например, логировать или возвращать ошибки закрытия при панике) остаются за ревью. Дальше: [тесты, которые ловят ошибки](lesson:go.pro.tests-that-catch-bugs).

## Углублённо: стоимость defer

До Go 1.14 `defer` заметно уступал прямому вызову по скорости; с версии 1.14 «открытое кодирование» (open-coded defers) делает отложенные вызовы в обычных функциях почти бесплатными. Отложенный вызов в цикле или в условном коде всё ещё использует более медленный путь с записью в стек отложенных вызовов. На практике корректность освобождения ресурсов важнее: выигрыш от замены `defer` ручным вызовом измеряется наносекундами, а цена пропущенного `Close` на пути с ошибкой - инцидентом. Измеряйте, прежде чем отказываться от `defer`.
