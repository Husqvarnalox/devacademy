## Когда одна горутина «видит» запись другой

Из предыдущего урока вы знаете, что обращения к общей памяти нужно синхронизировать. Остаётся вопрос глубже: **что именно** гарантирует синхронизация? Ответ даёт **модель памяти** Go - часть спецификации, которая определяет, при каких условиях чтение переменной в одной горутине видит значение, записанное в другой.

Ключевое понятие - **happens-before** («происходит раньше»). Если запись A happens-before чтение B, то B видит A (или более позднюю запись). Если между двумя обращениями такой цепочки нет, а одно из них запись, - это гонка данных, и никаких гарантий нет: компилятор вправе кешировать значение в регистре, процессор - переупорядочить записи, а читатель может увидеть новое значение одного поля и старое другого.

Практически это бьёт по задаче «инициализировать один раз и показать всем»: лениво загружаемая конфигурация, подключение к базе, таблица маршрутов. Наивная версия выглядит безобидно:

```go
if !loaded {          // проверка
    cfg = load()      // действие
    loaded = true     // флаг
}
use(cfg)
```

Здесь две ошибки сразу. Проверка и действие не атомарны: две горутины пройдут `!loaded` и обе вызовут `load` (дорогую, с побочными эффектами). И флаг ничего не публикует: горутина, увидевшая `loaded == true`, не обязана увидеть записанный до этого `cfg` полностью построенным. Решение - не флаг, а примитив синхронизации, создающий happens-before: `sync.Once`, мьютекс, канал, атомарная операция.

## Примеры

### sync.Once: однократная инициализация

`once.Do(f)` вызывает `f` только при первом обращении; все остальные вызывающие блокируются до завершения `f` и после возврата из `Do` гарантированно видят всё, что `f` записала.

```go run
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type table struct {
	once  sync.Once
	rows  map[string]int
	loads atomic.Int32
}

func (t *table) get(k string) int {
	t.once.Do(func() {
		t.loads.Add(1)
		time.Sleep(10 * time.Millisecond) // медленная загрузка
		t.rows = map[string]int{"a": 1, "b": 2, "c": 3}
	})
	return t.rows[k] // безопасно: Do вернулся после записи rows
}

func main() {
	var t table
	var wg sync.WaitGroup
	sums := make([]int, 20)
	for i := range sums {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			sums[i] = t.get("a") + t.get("b") + t.get("c")
		}(i)
	}
	wg.Wait()
	ok := true
	for _, s := range sums {
		if s != 6 {
			ok = false
		}
	}
	fmt.Println("loads:", t.loads.Load(), "all sums are 6:", ok)
}
```
```output
loads: 1 all sums are 6: true
```

Построчный разбор: 20 горутин вызывают `get` почти одновременно; первая входит в `Do`, остальные ждут. Чтение `t.rows` происходит после возврата из `Do`, поэтому запись карты внутри `f` гарантированно видна. Если убрать `once` и заменить его флагом, `loads` стал бы больше 1.

### sync.OnceValues: то же короче

Начиная с Go 1.21 (проверьте `go version` у себя) есть готовая обёртка, запоминающая значение и ошибку:

```go run
package main

import (
	"errors"
	"fmt"
	"sync"
)

func main() {
	calls := 0
	load := sync.OnceValues(func() (int, error) {
		calls++
		return 7, errors.New("disk is full")
	})
	v1, err1 := load()
	v2, err2 := load()
	fmt.Println(v1, err1)
	fmt.Println(v2, err2, "calls:", calls)
}
```
```output
7 disk is full
7 disk is full calls: 1
```

Ошибка запоминается так же, как значение: повторного вызова не будет. Для сервиса, которому нужна повторная попытка после сбоя, `Once` не подходит (см. «Точные правила»).

### Закрытие канала как сигнал готовности

Закрытие канала happens-before получение, которое вернулось из-за закрытия. Поэтому всё, что записано до `close`, видно получателю. Это и есть безопасная публикация без мьютекса: пишем данные один раз, затем закрываем канал.

```go run
package main

import (
	"fmt"
	"sync"
)

type result struct {
	name  string
	items []int
}

func main() {
	var res result
	ready := make(chan struct{})

	go func() {
		res = result{name: "report", items: []int{1, 2, 3}} // запись
		close(ready)                                         // публикация
	}()

	var wg sync.WaitGroup
	totals := make([]int, 4)
	for i := range totals {
		wg.Add(1)
		go func(i int) {
			defer wg.Done()
			<-ready // после этого res виден полностью
			for _, v := range res.items {
				totals[i] += v
			}
		}(i)
	}
	wg.Wait()
	fmt.Println(res.name, totals)
}
```
```output
report [6 6 6 6]
```

Получателей может быть сколько угодно: закрытый канал отвечает сразу всем. Закрыть его можно только один раз (повторный `close` - паника), поэтому закрытие обычно кладут в код, выполняемый однократно, например внутрь `once.Do`.

### Публикация неизменяемого объекта через atomic.Pointer

Если конфигурацию нужно обновлять на лету, неизменяемый объект собирают целиком и публикуют одним атомарным указателем; читатели получают либо старую версию, либо новую, но не полуобновлённую.

```go
var current atomic.Pointer[Config]

func reload() {
    next := &Config{Name: "v2", Limits: buildLimits()} // собрали полностью
    current.Store(next)                                 // опубликовали
}

func handler() {
    cfg := current.Load() // старая или новая версия целиком
    _ = cfg.Limits["rps"]
}
```

Правило: после `Store` объект больше не изменяется. Если его менять, вы вернулись к гонке данных.

### Устройство решения упражнения

В решении поле `once sync.Once` и результат лежат в структуре; `Config()` вызывает `s.once.Do(...)`, внутри которой записываются `s.cfg`, `s.err` и затем `close(s.ready)`. Два способа ожидания работают одинаково надёжно: вызвать `Config()` (заблокируется внутри `Do`, пока загрузка идёт) или принять из `Ready()` (заблокируется до закрытия канала).

## Точные правила

Основные гарантии модели памяти Go (проверьте формулировки в [go.dev/ref/mem](https://go.dev/ref/mem)):

* **Инициализация.** Окончание `init` пакета-зависимости происходит раньше начала `init` зависимого.
* **Оператор `go`.** Запуск горутины happens-before начало её выполнения. Выход горутины ничего не синхронизирует сам по себе: нужен `WaitGroup`, канал или другое средство.
* **Каналы.** Отправка в канал happens-before завершение соответствующего получения. `close(ch)` happens-before получение, вернувшее нулевое значение из-за закрытия. Для небуферизованного канала завершение получения happens-before завершение отправки. Для буфера ёмкости C: k-е получение happens-before завершение отправки номер k+C.
* **Мьютексы.** Для `n < m` вызов `Unlock` номер n happens-before возврат `Lock` номер m.
* **Once.** Возврат `f` из `once.Do(f)` happens-before возврат любого `once.Do(f)`.
* **Atomic.** Если эффект атомарной операции A виден атомарной операции B, то A synchronized-before B; все атомарные операции в программе ведут себя как выполняемые в некотором последовательном порядке.
* **Гонка данных** делает поведение неопределённым в смысле гарантий значений; для многословных типов (интерфейсы, строки, срезы) возможно чтение «разорванного» значения.

Следствия для проектирования:

* **Once запоминает вызов, а не успех.** Если функция вернула ошибку, повторного вызова не будет; сохраните ошибку рядом с результатом и верните её всем. Если нужна повторная попытка, используйте мьютекс и флаг успеха (с проверкой под блокировкой) или внешнюю политику повторов; учтите, что тогда «ровно один вызов» превращается в «не более одного успешного».
* **Нет повторного входа.** Загрузчик внутри `Do` не должен вызывать метод, снова входящий в тот же `Once`: взаимная блокировка.
* **Паника в `f`** считается завершением вызова: `Do` больше не вызовет `f`, а `OnceFunc` и `OnceValue(s)` повторяют ту же панику при каждом вызове.
* **Не копируйте `sync.Once`** после использования (как и мьютекс), храните его по указателю или в структуре, которую не копируют.
* **Быстрый путь.** `Once.Do` после инициализации дешёв (атомарное чтение), так что хранить рядом собственный флаг ради скорости не нужно.

## Типичные ошибки

**1. Флаг вместо синхронизации.** Обычный `bool`, `int` или `*T` не создаёт happens-before. Цикл `for !ready {}` может не завершиться: компилятор вправе прочитать `ready` один раз. Используйте `atomic.Bool`, канал или мьютекс.

**2. Double-checked locking без атомарности.**
```go
if inst == nil {        // чтение без синхронизации
    mu.Lock()
    if inst == nil { inst = build() }
    mu.Unlock()
}
return inst             // может быть увидено частично построенным
```
Первое чтение `inst` - гонка данных. Правильно: `sync.Once`, либо `atomic.Pointer[T]` для проверки и публикации.

**3. Опубликовать объект и продолжить его изменять.** Положили указатель в канал или `atomic.Pointer`, а затем меняете поля: читатель получает объект в неопределённом состоянии. Опубликованное - неизменяемо, либо защищено своим мьютексом.

**4. Надежда на `time.Sleep`.** «Подождём 100 мс, значит, инициализация закончилась» - это не отношение порядка, а везение. В тестах также используйте каналы и `WaitGroup`, а паузы допускайте лишь как способ дать другим горутинам начать работу, но не как проверку порядка.

**5. Закрыть канал дважды или из нескольких горутин.** Паника `close of closed channel`. Закрытие кладут в однократный код (`Once`) или закрывает единственный владелец.

**6. Повторный вход в `Do`.** Метод, вызываемый из загрузчика, снова обращается к тому же `Once` - сервис «зависает» без сообщения. Диагностика: дамп горутин (`SIGQUIT`) покажет ожидание в `sync.(*Once).doSlow`.

## Итог

Теперь вы объясняете корректность конкурентного кода цепочкой happens-before, а не «на практике работает». Для ленивой инициализации применяете `sync.Once` (или `OnceValues`), для сигнала готовности - закрытие канала внутри однократного кода после записи данных, для горячей замены неизменяемых объектов - `atomic.Pointer`. Проверки упражнения подтверждают однократность вызова, полноту объекта и сигнал готовности; корректность на уровне памяти они не доказывают, поэтому гоняйте `go test -race` локально. Дальше: [отмена через context и утечки горутин](lesson:go.pro.context-cancellation).

## Углублённо: почему «на практике работает» не аргумент

Компилятор Go и процессор независимо переупорядочивают обращения к памяти, если это не меняет результат для **одной** горутины. Для другой горутины порядок может выглядеть иначе. На x86 процессор сохраняет порядок записей (модель TSO), поэтому часть ошибок публикации там не проявляется; на ARM, где слабее гарантии, та же программа ломается. Но даже на x86 компилятор вправе вынести чтение обычной переменной из цикла. Модель памяти Go формулируется как договор между программистом и реализацией: если программа не содержит гонок данных, она ведёт себя так, будто горутины чередуются по очереди; если содержит - никаких обещаний. Именно поэтому проверка делается детектором гонок и ревью синхронизации, а не повторным запуском «пока не сломается».
