## Остановить работу вовремя

Горутина стоит дёшево, но не бесплатно: пока она жива, она держит стек, ссылки на данные и, возможно, соединение с базой. В сервисе, который принимает тысячи запросов в секунду, горутина, которая «зависла и забыла», превращается в утечку: память растёт неделями, пока процесс не уберёт OOM killer. При этом горутины нельзя остановить снаружи: у Go нет операции «убить горутину». Остановиться она может только сама, если **наблюдает сигнал отмены**.

Инженерная задача, которую вы решаете в этом уроке, состоит из трёх требований к любому конкурентному коду, обращающемуся к внешнему миру:

1. **Отмена приходит сверху.** Клиент закрыл соединение, истёк срок запроса, соседняя подзадача упала - всё это выражается отменой `context.Context`, который функция получает первым параметром.
2. **Каждое блокирующее место следит за ней.** Ожидание задания, отправка результата, вызов внешней функции - всё либо принимает `ctx`, либо стоит в `select` с `<-ctx.Done()`.
3. **Владелец дожидается тех, кого запустил.** Функция, создавшая горутины, не возвращается, пока они не завершились (`sync.WaitGroup`). Тогда утечки исключены по построению.

Три источника утечек, которые вы будете искать: блокировка на отправке в канал, из которого никто больше не читает; блокировка на получении из канала, который никто не закроет; вызов, не принимающий контекст и ждущий бесконечно.

## Примеры

### Утечка и её исправление

Классическая ошибка: запустили несколько источников данных, взяли первый ответ и вышли. Остальные горутины блокируются на отправке навсегда.

```go run
package main

import (
	"fmt"
	"runtime"
	"time"
)

func firstLeaky() int {
	ch := make(chan int) // небуферизованный
	for i := 1; i <= 3; i++ {
		go func(i int) { ch <- i * 10 }(i)
	}
	return <-ch // возвращаем первый, двое других застряли
}

func firstFixed() int {
	ch := make(chan int, 3) // ёмкость равна числу отправителей: никто не блокируется
	for i := 1; i <= 3; i++ {
		go func(i int) { ch <- i * 10 }(i)
	}
	return <-ch
}

// settle ждёт, пока число горутин перестанет превышать base.
func settle(base int) int {
	for i := 0; i < 200; i++ {
		if n := runtime.NumGoroutine(); n <= base {
			return 0
		}
		time.Sleep(5 * time.Millisecond)
	}
	return runtime.NumGoroutine() - base
}

func main() {
	base := runtime.NumGoroutine()
	firstFixed()
	fmt.Println("fixed, extra goroutines:", settle(base))

	base = runtime.NumGoroutine()
	firstLeaky()
	fmt.Println("leaky, extra goroutines:", settle(base))
}
```
```output
fixed, extra goroutines: 0
leaky, extra goroutines: 2
```

Построчный разбор: в `firstLeaky` один получатель и три отправителя на канале без буфера, поэтому после первого получения две горутины блокируются в `ch <- ...` навсегда. В `firstFixed` буфер вмещает все три значения, отправители завершаются сразу. Функция `settle` - тот же приём «опрос с таймаутом», который используют тесты упражнения: горутины завершаются не мгновенно, и одноразовая проверка нестабильна. Для долго живущих потоков вместо буфера обычно используют `select` с `ctx.Done()`.

### Воркер, который слушает ctx

```go run
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

func work(ctx context.Context, jobs <-chan int, out chan<- int) {
	for {
		select {
		case <-ctx.Done():
			return // остановка по отмене
		case j, ok := <-jobs:
			if !ok {
				return // заданий больше нет
			}
			select {
			case out <- j * j:
			case <-ctx.Done(): // получатель мог уйти: не блокируемся на отправке
				return
			}
		}
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Millisecond)
	defer cancel()

	jobs := make(chan int)
	out := make(chan int) // читать некому: воркер заблокируется на отправке
	var wg sync.WaitGroup
	wg.Add(1)
	go func() { defer wg.Done(); work(ctx, jobs, out) }()

	jobs <- 5 // воркер возьмёт задание и зависнет на отправке результата
	wg.Wait() // вернётся, когда дедлайн отменит ctx
	fmt.Println(errors.Is(ctx.Err(), context.DeadlineExceeded))
}
```
```output
true
```

Без вложенного `select` воркер навсегда завис бы на `out <- j * j`, и `wg.Wait()` не вернулся бы. Правило: **каждая** блокирующая операция канала в долгоживущей горутине должна иметь второй вариант - `<-ctx.Done()`.

### Ошибка с контекстом отмены

```go run
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func fetch(ctx context.Context, url string) error {
	select {
	case <-time.After(time.Second): // «долгий запрос»
		return nil
	case <-ctx.Done():
		return fmt.Errorf("fetch %s: %w", url, ctx.Err())
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel()
	err := fetch(ctx, "http://example.test/a")
	fmt.Println(err)
	fmt.Println(errors.Is(err, context.DeadlineExceeded), errors.Is(err, context.Canceled))
}
```
```output
fetch http://example.test/a: context deadline exceeded
true false
```

### Структура решения упражнения

1. `ctx, cancel := context.WithCancel(parent)` и `defer cancel()`: производный контекст нужен, чтобы первая ошибка могла отменить остальных, не затрагивая родителя.
2. Канал заданий `jobs` и `workers` горутин, каждая в цикле `for i := range jobs`.
3. Отправитель заданий делает `select { case jobs <- i: case <-ctx.Done(): break }`: при отмене он перестаёт раздавать работу и закрывает `jobs`.
4. Воркер перед `fetch` проверяет `ctx.Err()`; при ошибке запоминает первую (под мьютексом) и вызывает `cancel()`.
5. `wg.Wait()` перед возвратом: после него в функции нет живых горутин.
6. Итоговая ошибка: если отменён родитель, то `fmt.Errorf("fetch all: %w", parent.Err())`, иначе первая ошибка загрузки.

### Как проверять отсутствие утечек

Тесты упражнения берут `runtime.NumGoroutine()` до вызова, затем после него опрашивают значение до 3 секунд, пока оно не вернётся к исходному. Блокировка на получении в потерянной горутине держится бесконечно, поэтому такой опрос однозначно отличает утечку от медленного завершения. Ограничение подхода: счётчик общий для процесса, и посторонние горутины (из других тестов, из библиотек) могут исказить результат, поэтому тест измеряет разницу относительно базового значения и не запускается параллельно с другими. Для более точной диагностики есть профиль горутин (`pprof`) и сторонние библиотеки проверки утечек; в продакшене - метрика числа горутин.

## Точные правила

* **`ctx.Done()`** возвращает канал, закрываемый при отмене; для `context.Background()` он `nil` (приём из `nil`-канала блокируется вечно, и это нормально для `select`). **`ctx.Err()`** равен `nil` до отмены, затем `context.Canceled` или `context.DeadlineExceeded` (не меняется после).
* **Отмена распространяется вниз:** отмена родителя отменяет всех потомков, отмена потомка родителя не затрагивает. Поэтому для «отменить соседей при ошибке» создают производный контекст.
* **`cancel` вызывают всегда** (`defer cancel()`): он освобождает таймер и снимает регистрацию у родителя. Повторные вызовы безопасны.
* **Контекст - первый параметр** функции, не поле структуры (исключения редки) и не `nil`; для неизвестного используйте `context.TODO()`.
* **Причина отмены.** `context.WithCancelCause(parent)` возвращает `cancel(err)`; `context.Cause(ctx)` возвращает переданную причину, тогда как `ctx.Err()` остаётся `context.Canceled`. Это полезно, чтобы отличить «клиент ушёл» от «подзадача упала».
* **Что умеет и не умеет отмена.** Она сообщает о намерении остановиться. Функция, которая не принимает `ctx` и не смотрит на `Done()`, не остановится, и `FetchAll` её не прервёт: контракт `Fetcher` требует, чтобы он уважал контекст. Разрешённый компромисс - вернуться, не дожидаясь, но это сознательная утечка, которую нужно ограничивать и документировать.
* **Буфер как средство от утечки.** Буферизованный канал ёмкости, равной числу отправителей, гарантирует, что отправка не заблокируется. Это подходит для схемы «собрать N ответов, взять первый», но скрывает проблему, если число отправителей не ограничено.
* **Порядок закрытия.** Канал закрывает отправитель (владелец), и только один раз; приёмники закрывать канал не должны.
* **Ошибки.** Оборачивайте через `%w`, добавляя контекст (URL, операция); не сравнивайте ошибки по тексту.
* **Что проверяют тесты.** Поведение при отмене, число горутин, содержимое ошибок. Они не доказывают отсутствие гонок и не оценивают структуру кода.

## Типичные ошибки

**1. Отправка в канал без `select` на `ctx.Done()`.** Читатель ушёл - отправитель завис навсегда. Исправление: `select` с `ctx.Done()` или буфер подходящего размера.

**2. Горутина на каждый элемент без ограничения.** Миллион URL - миллион горутин. Пул из N воркеров ограничивает память и нагрузку на внешний сервис.

**3. Игнорирование контекста в цикле.** Цикл `for { doSomething() }` без проверки `ctx.Err()` или `select` не остановится. Для вычислительных циклов проверяйте контекст раз в N итераций.

**4. Возврат из функции без ожидания воркеров.** Ранний `return` на первой ошибке без `wg.Wait()` оставляет воркеров, пишущих в уже не читаемый канал. Владелец дожидается всех.

**5. `time.Sleep` вместо ожидания с отменой.** `time.Sleep(time.Minute)` нельзя прервать. Используйте `select { case <-time.After(d): case <-ctx.Done(): }`, а в циклах - `time.NewTimer` с `Stop`, чтобы не копить таймеры.

**6. Потерять причину при оборачивании.** `fmt.Errorf("fetch: %v", err)` вместо `%w` ломает `errors.Is(err, context.Canceled)`: вызывающий код не отличит отмену от настоящей ошибки и может зря повторять запрос.

**7. Забытый `cancel`.** `ctx, _ := context.WithTimeout(...)`. `go vet` ругается (`lostcancel`); исправление - сохранить `cancel` и вызвать `defer cancel()`.

## Итог

Вы строите конкурентный код, у которого есть владелец, сигнал отмены и гарантированное завершение: контекст сверху вниз, `select` с `ctx.Done()` на каждой блокировке, `WaitGroup` перед возвратом, ошибки с `%w`. Автоматические проверки подтверждают быстрый возврат при ошибке, отмене и дедлайне и отсутствие утечек горутин в тестовых сценариях; они не проверяют `Fetcher`, который игнорирует контекст, гонки данных и читаемость решения. ## Углублённо: что на самом деле делает WithCancel

Производный контекст регистрируется у родителя в списке потомков (если родитель - один из стандартных типов), а `Done()` создаётся лениво при первом обращении. Вызов `cancel` закрывает канал `Done`, записывает ошибку и рекурсивно отменяет потомков. Для `WithTimeout` дополнительно заводится таймер, вызывающий ту же отмену по истечении срока; `cancel` останавливает таймер. Если родитель - пользовательская реализация `Context`, библиотека запускает вспомогательную горутину, которая ждёт `parent.Done()`; это и есть причина, почему важно вызывать `cancel`: иначе такая горутина живёт, пока родитель не отменится. Детали зависят от версии Go; рассчитывайте только на публичный контракт пакета `context`.
