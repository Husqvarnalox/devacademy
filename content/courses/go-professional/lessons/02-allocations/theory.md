## Аллокации на горячем пути

Go выделяет память быстро, но не бесплатно. Каждая аллокация на куче даёт три вида затрат: время на выделение и инициализацию, нагрузку на кеш процессора и работу сборщика мусора (GC), который должен потом эту память найти и освободить. Если функция вызывается раз в секунду, всё это неважно. Если она формирует экспорт на миллионы строк, обслуживает каждый HTTP-запрос или стоит внутри цикла разбора логов, три аллокации на строку превращаются в заметную долю профиля.

Инженерный подход состоит из трёх шагов, и порядок важен:

1. **Измерить.** Профиль или бенчмарк показывает, что именно эта функция горячая и сколько она выделяет. Оптимизация без измерения чаще ухудшает читаемость, чем скорость.
2. **Убрать структурные причины.** Типичные: строка собирается через `+=` или `fmt.Sprintf` внутри цикла; срез растёт с нулевой ёмкости, хотя размер известен; число превращается в строку только затем, чтобы её тут же скопировали.
3. **Зафиксировать результат тестом.** Число аллокаций при одинаковом коде и входе устойчиво, поэтому утверждение `AllocsPerRun <= N` годится для регрессионного теста. Время (`ns/op`) для этого не годится.

В упражнении вы получите работающий, но расточительный код экспорта и должны сократить аллокации без изменения результата.

## Примеры

### Конкатенация против Builder

Строки неизменяемы. Выражение `out += s` создаёт новую строку и копирует в неё всё накопленное, поэтому цикл из N итераций делает порядка N аллокаций и копирует O(N^2) байт. `strings.Builder` держит один растущий буфер, а `Grow` позволяет выделить его сразу.

```go run
package main

import (
	"fmt"
	"strings"
	"testing"
)

var parts = []string{"alpha", "beta", "gamma", "delta", "epsilon", "zeta", "eta", "theta"}

func concat() string {
	out := ""
	for _, p := range parts {
		out += p + ";"
	}
	return out
}

func builder() string {
	var b strings.Builder
	b.Grow(64)
	for _, p := range parts {
		b.WriteString(p)
		b.WriteByte(';')
	}
	return b.String()
}

func main() {
	var s1, s2 string
	a1 := testing.AllocsPerRun(100, func() { s1 = concat() })
	a2 := testing.AllocsPerRun(100, func() { s2 = builder() })
	fmt.Println(s1 == s2)
	fmt.Println("concat allocates more than 1:", a1 > 1)
	fmt.Println("builder allocations:", a2)
}
```
```output
true
concat allocates more than 1: true
builder allocations: 1
```

`testing.AllocsPerRun` можно вызывать не только из тестов: это обычная функция. Здесь выводится не точное число для `concat` (оно зависит от версии компилятора), а факт `> 1`, который устойчив.

Построчный разбор: `concat` на каждой итерации создаёт строку `p + ";"` и ещё одну для `out +=`; `builder` резервирует 64 байта один раз (итоговая длина 41 байт укладывается), дальше только копирует байты внутрь буфера, а `b.String()` возвращает строку над тем же буфером без копирования. Единственная аллокация - сам буфер.

### Предвыделение среза

Если число элементов известно или его дёшево вычислить, `make([]T, 0, n)` избавляет от серии «выделить новый массив, скопировать, отбросить старый», которую делает `append` при росте. Эту механику вы разбирали в [уроке о срезах](lesson:go.pro.slice-internals).

```go run
package main

import (
	"fmt"
	"testing"
)

var src = func() []int {
	s := make([]int, 500)
	for i := range s {
		s[i] = i
	}
	return s
}()

func grow() []int {
	var out []int
	for _, v := range src {
		out = append(out, v)
	}
	return out
}

func prealloc() []int {
	out := make([]int, 0, len(src))
	for _, v := range src {
		out = append(out, v)
	}
	return out
}

func main() {
	var r1, r2 []int
	a1 := testing.AllocsPerRun(100, func() { r1 = grow() })
	a2 := testing.AllocsPerRun(100, func() { r2 = prealloc() })
	fmt.Println(len(r1) == len(r2))
	fmt.Println("grow allocations > 1:", a1 > 1)
	fmt.Println("prealloc allocations:", a2)
}
```
```output
true
grow allocations > 1: true
prealloc allocations: 1
```

### Числа без fmt

`fmt.Sprintf("%d", n)` разбирает форматную строку, упаковывает аргумент в интерфейс и возвращает новую строку. `strconv.AppendInt` дописывает цифры прямо в ваш буфер. Если буфер - небольшой массив на стеке, аллокаций нет совсем.

```go run
package main

import (
	"fmt"
	"strconv"
)

func main() {
	var tmp [24]byte
	b := strconv.AppendInt(tmp[:0], -4096, 10)
	b = append(b, ',')
	b = strconv.AppendInt(b, 255, 16)
	fmt.Println(string(b))
}
```
```output
-4096,ff
```

### Как измерять: тест и бенчмарк

Тест, фиксирующий результат (его используют проверки этого урока):

```go
func TestFormatAllocs(t *testing.T) {
	recs := sample(100)
	var sink string
	allocs := testing.AllocsPerRun(50, func() { sink = FormatCSV(recs) })
	_ = sink
	if allocs > 4 {
		t.Fatalf("allocs = %.0f, want <= 4", allocs)
	}
}
```

Результат присваивается переменной `sink`, чтобы компилятор не счёл вызов бесполезным. Бенчмарк для локального сравнения до/после:

```go
func BenchmarkFormatCSV(b *testing.B) {
	recs := sample(100)
	b.ReportAllocs()
	for b.Loop() { // Go 1.24+; в старых версиях: for i := 0; i < b.N; i++
		FormatCSV(recs)
	}
}
```

Запуск: `go test -run xxx -bench . -benchmem`. Колонки вывода: `ns/op` (время), `B/op` (байт на операцию), `allocs/op` (аллокаций на операцию). Для решения этого урока на 100 записях автор получил `1 allocs/op` против `299 allocs/op` у заготовки; время и байты у вас будут другими.

**Бенчмарки автоматическая проверка не запускает**: их время зависит от нагрузки машины и нестабильно, тест, падающий «иногда», хуже отсутствующего теста. Поэтому проверка опирается на `AllocsPerRun`, а бенчмарк вы запускаете сами.

## Точные правила

* **Что считается аллокацией.** `AllocsPerRun` считает выделения на куче (по данным рантайма). Значение, оставшееся на стеке, не считается: его судьбу решает escape analysis, см. [урок о нём](lesson:go.pro.escape-analysis-and-gc). Поэтому `var tmp [24]byte` и `tmp[:0]` бесплатны, пока срез не «утечёт» наружу.
* **`testing.AllocsPerRun(runs, f)`** выполняет `f` один раз для прогрева, затем `runs` раз, возвращает среднее (округление вниз до целого) и на время замера ставит `GOMAXPROCS(1)`. Не вызывайте её из параллельных тестов (`t.Parallel`): аллокации соседних тестов попадут в счёт.
* **`strings.Builder`**: нулевое значение готово к работе; копировать Builder после первой записи нельзя (паника при следующей записи). `Grow(n)` гарантирует место ещё под n байт. `String()` не копирует данные, поэтому после него Builder лучше не переиспользовать для записи без `Reset`.
* **Цена предвыделения.** Оценка слишком большая - лишняя память живёт, пока жива строка/срез; слишком маленькая - один-два дополнительных роста. Для результата, который долго хранится, избыток ёмкости стоит обрезать или считать точно.
* **Компромиссы.** Ручная запись байтов вместо `fmt` менее гибка и легче ломается (формат копеек, знак, кавычки). Поэтому рядом с ней нужны тесты на краевые значения и сравнение с простой эталонной реализацией - так и устроены проверки упражнения.
* **`b.Loop`** (Go 1.24+) запускает тело цикла нужное число раз и не даёт компилятору выбросить результат вызова; в версиях до 1.24 используют `for i := 0; i < b.N; i++` и сохраняют результат в переменную пакета.

## Типичные ошибки

**1. Оптимизировать без измерения.** Переписанный на байты код, который выполняется один раз при старте, делает программу хуже: сложнее и не быстрее. Сначала профиль (`go test -cpuprofile`, `-memprofile`, `pprof`), затем правка.

**2. Утверждать скорость по ns/op в одном запуске.** Один бенчмарк на ноутбуке с открытым браузером ничего не доказывает. Для сравнения до/после запускайте несколько раз (`-count=10`) и используйте `benchstat`; аллокации же сравнимы сразу.

**3. Считать, что Builder всегда не аллоцирует.** Без `Grow` он растёт, как срез, и при N записях сделает O(log N) аллокаций. С `Grow` и верной оценкой - одну.

**4. Потерять поведение при оптимизации.** Ручное форматирование копеек: `5` центов нужно вывести как `05`; кавычки внутри имени нужно удвоить. Именно такие краевые случаи проверяют скрытые тесты. После оптимизации прогоняйте прежние тесты и добавляйте сравнение с простой версией.

**5. Копировать `strings.Builder` по значению.** Builder защищается от копирования: запись в копию после первой записи вызывает панику. Передавайте `*strings.Builder` (как `writeField` в решении) или `io.Writer`.

**6. Предвыделить `make([]T, n)` вместо `make([]T, 0, n)`.** В первом случае длина уже `n`, и `append` добавит элементы после `n` нулевых. Для накопления нужна нулевая длина и ёмкость `n`.

<!-- section: summary -->
## Итог

Вы умеете находить структурные источники аллокаций (конкатенация, `fmt` в цикле, рост среза), заменять их на `strings.Builder` с `Grow`, `strconv.Append*` и `make` с ёмкостью и фиксировать результат тестом на `AllocsPerRun`. Автоматические проверки подтверждают корректность и число аллокаций; читаемость, уместность оптимизации и реальное ускорение они не проверяют - за этим стоят профиль и бенчмарки на вашей машине. Дальше: [гонки данных](lesson:go.pro.data-races).

## Углублённо: откуда берётся рост ёмкости

При `append` без запаса рантайм выделяет новый массив большей ёмкости; конкретная формула роста (удвоение для малых срезов и меньший коэффициент для больших, плюс округление до размерных классов аллокатора) - деталь реализации и менялась между версиями, поэтому полагаться на неё в коде нельзя. Для измерения важно другое: число аллокаций растёт логарифмически, а скопированные байты - линейно по сумме, так что предвыделение экономит и то и другое. Аллокатор выдаёт память фиксированными размерными классами, поэтому `B/op` в бенчмарке часто больше запрошенного размера.
