## Хороший тест — тот, который падает, когда код неправ

Зелёные тесты ничего не доказывают, если они не умеют краснеть. Набор может проходить, выполнять каждую строку (стопроцентное покрытие) и всё равно пропустить ошибку `<` вместо `<=`: строка выполнена, но результат либо не проверялся, либо проверялся на входе, где обе версии дают одинаковый ответ.

Практический способ оценить набор тестов - **мутационное тестирование**: взять корректный код, внести в него одно небольшое изменение (мутацию: заменить `<` на `<=`, убрать проверку, поменять константу), запустить тесты и посмотреть, упали ли они. Если упали - мутант «убит». Если все тесты зелёные - мутант «выжил», и это значит, что в наборе нет входа, различающего две версии. Выжившие мутанты показывают пробелы в тестах точнее, чем процент покрытия.

В упражнении механика обращена: мутантов вы не создаёте, они спрятаны в скрытом тесте. Вы пишете **таблицу тест-кейсов** как данные (`var Cases = []Case{...}`) по спецификации функции, а проверка таблицы такова:

1. каждый ваш случай согласован со спецификацией (ожидание не придумано);
2. каждый из шести ошибочных вариантов проваливает хотя бы один случай.

Это тренирует главный навык: для каждого правила спецификации находить вход, на котором правильная и неправильная реализации ведут себя по-разному. Вход нарушает **только одно** правило, лежит на границе допустимого и приходит из разных классов эквивалентности.

## Примеры

### Мутант, который выжил

Функция проверяет допустимую длину имени: от 1 до 20 символов.

```go run
package main

import "fmt"

func validOK(n int) bool     { return n >= 1 && n <= 20 }
func validMutant(n int) bool { return n >= 1 && n < 20 } // мутант: <= заменён на <

func main() {
	weak := []int{5, 10, 15}      // «типичные» значения
	strong := []int{0, 1, 20, 21} // границы с обеих сторон

	for _, set := range []struct {
		name  string
		cases []int
	}{{"weak", weak}, {"strong", strong}} {
		killed := false
		for _, n := range set.cases {
			if validOK(n) != validMutant(n) {
				killed = true
			}
		}
		fmt.Println(set.name, "kills the mutant:", killed)
	}
}
```
```output
weak kills the mutant: false
strong kills the mutant: true
```

Слабый набор не отличает версии: на 5, 10 и 15 обе функции согласны. Различает только `20`, то есть значение на границе. Именно такие входы вы подбираете в упражнении.

### Таблица как данные и один обработчик

Табличный тест отделяет **что** проверять (данные) от **как** (цикл). Тогда добавить случай - строка в таблице, а один и тот же набор можно прогнать и против нескольких реализаций, как это делает проверка упражнения.

```go run
package main

import (
	"errors"
	"fmt"
	"strconv"
	"strings"
)

type Case struct {
	Name    string
	Input   string
	Want    int
	WantErr bool
}

// parseKB разбирает "<число>KB" в число килобайт; спецификация: только верхний регистр, без пробелов.
func parseKB(s string) (int, error) {
	num, ok := strings.CutSuffix(s, "KB")
	if !ok || num == "" {
		return 0, errors.New("bad format")
	}
	n, err := strconv.Atoi(num)
	if err != nil || n < 0 {
		return 0, errors.New("bad number")
	}
	return n, nil
}

var cases = []Case{
	{"plain", "10KB", 10, false},
	{"zero", "0KB", 0, false},
	{"no unit", "10", 0, true},
	{"lower case", "10kb", 0, true},
	{"negative", "-1KB", 0, true},
	{"empty number", "KB", 0, true},
}

func main() {
	failed := 0
	for _, c := range cases {
		got, err := parseKB(c.Input)
		bad := (err != nil) != c.WantErr || (!c.WantErr && got != c.Want)
		if bad {
			failed++
			fmt.Println("FAIL", c.Name)
		}
	}
	fmt.Println("cases:", len(cases), "failed:", failed)
}
```
```output
cases: 6 failed: 0
```

В Go для тех же данных принято `t.Run(c.Name, ...)` вместо ручного цикла: падение укажет имя случая, а `go test -run 'TestParse/negative'` запустит только его.

### Как искать входы: методика

1. **Выпишите правила спецификации** отдельными пунктами: формат, порядок, диапазоны, регистр, пробелы, пустой ввод, лимиты.
2. **Для каждого правила**: один вход, который нарушает только его (причина отказа однозначна), и, если правило числовое, значения по обе стороны границы (`max` и `max + 1`).
3. **Положительные случаи** разных классов: каждая единица отдельно, все вместе, пропущенные компоненты, значения «за циферблатом» (90 минут), нули в начале, ноль как значение.
4. **Ожидания считайте вручную** по спецификации. Если вычислили запуском реализации, вы закрепили её поведение, включая ошибки.
5. **Проверяйте себя мутантами**: мысленно сломайте реализацию в каждом правиле (удалить проверку порядка, разрешить повтор, сдвинуть границу) и убедитесь, что есть случай, который такое сломает.

### Как устроена проверка упражнения

В скрытом файле лежит параметризованный эталонный разбор (`parse(s, opts)`) и шесть вариантов с одной включённой «неисправностью»: нет контроля порядка, допускается повтор, минуты ограничены 59, принимается число без единицы, запрещены нули в начале, граница числа сдвинута с 6 до 7 цифр. Тест `TestCasesAgreeWithReference` проверяет, что ваша таблица не противоречит эталону, а `TestMutantsAreDetected` — что для каждого варианта есть случай, на котором его результат расходится с вашим ожиданием. Список мутантов намеренно нельзя вывести из имён: выясняйте его по спецификации.

Чего это не гарантирует: реальные ошибки шире шести заранее известных; таблица, убившая все шесть, может по-прежнему пропустить седьмую. Поэтому в боевом проекте набор мутантов получают инструментами (например, сторонними мутационными тестировщиками для Go) или ревью.

## Точные правила

* **Мутант и оракул.** Оракул - источник правильных ответов: спецификация, эталонная реализация, свойство (например, `Parse(Format(x)) == x`). Таблица с ручными ожиданиями использует спецификацию как оракул.
* **Убит / выжил.** Мутант убит, если хотя бы один тест на нём падает. Доля убитых - «мутационный индекс». Он ниже оптимистичного покрытия строк, но ближе к реальной пользе набора.
* **Эквивалентные мутанты.** Изменение, которое не меняет наблюдаемое поведение (например, замена `i < n` на `i != n` в цикле, где `i` растёт на 1), убить невозможно; в инструментах их отсеивают вручную. В упражнении все мутанты неэквивалентны.
* **Классы эквивалентности.** Входы, которые программа обрабатывает по одной и той же ветке, достаточно представить одним значением. Границы классов - отдельные кандидаты, потому что ошибки off-by-one живут на них.
* **Что вносить в таблицу.** Успешные пути, каждый вид отказа, границы, пустой и «нулевой» ввод, порядок и повторы, регистр, пробельные символы, Unicode (если применимо).
* **Свойства вместо примеров.** Кроме таблицы полезны проверки свойств: идемпотентность, обратимость, монотонность. В стандартной библиотеке есть `testing/quick`, а `go test -fuzz` (с Go 1.18) порождает входы автоматически и хранит найденные падения как регрессионные примеры.
* **Имена случаев** описывают идею («six digits», «wrong order»), а не номер. Через `t.Run(c.Name, ...)` имя становится адресом падения.
* **Не копируйте ожидания из вывода.** Исключение - характеризационные тесты перед рефакторингом, явно помеченные как фиксация текущего поведения.

## Типичные ошибки

**1. Тесты без утверждений.** Вызов функции и `_ = result` даёт покрытие и никакой защиты.

**2. Только «счастливый путь».** Набор из `1h`, `2m`, `3s` проходит и на корректной, и на сильно сломанной реализации. Ошибки живут в отказах и на границах.

**3. Один тест нарушает несколько правил.** Вход `"1H 30M"` содержит и регистр, и пробел; когда реализация отказывает по другой причине, тест зелёный, хотя нужное правило не проверено. Нарушайте по одному правилу.

**4. Пропуск границы с одной стороны.** Проверили `999999s` и не проверили `1000000s`: мутант со сдвинутой границей выживает. Всегда пара значений по обе стороны.

**5. Ожидание, скопированное с реализации.** Тест зелёный по построению и повторяет ошибку. Считайте ожидание отдельно от кода.

**6. Дубликаты вместо разнообразия.** Двадцать случаев вида `5s`, `6s`, `7s` проверяют одно и то же. Меняйте класс входа, а не число.

**7. Хрупкие сообщения об ошибках.** Сравнение текста ошибки в тесте ломается при каждой правке формулировки. Проверяйте факт ошибки, тип (`errors.Is`/`errors.As`) или стабильный код.

<!-- section: summary -->
## Итог

Вы оцениваете тесты не покрытием, а способностью различать версии реализации: подбираете входы, нарушающие одно правило спецификации, берёте значения по обе стороны границ, считаете ожидания по спецификации и мысленно проверяете таблицу мутантами. Автоматическая проверка подтверждает согласованность с эталоном и убийство шести заданных мутантов; она не гарантирует полноту набора против неизвестных дефектов и не оценивает качество названий. ## Углублённо: мутации на практике и их цена

Инструмент мутационного тестирования порождает сотни мутантов (замена операторов, констант, удаление вызовов, инверсия условий) и для каждого запускает набор тестов. Это дорого: время растёт как `число мутантов × время тестов`, поэтому его применяют выборочно (к критичным пакетам, к изменённому коду в пулл-реквесте), используют покрытие, чтобы запускать только релевантные тесты, и ограничивают время каждого запуска. Выжившие мутанты разбирают вручную: либо добавляют случай, либо признают мутацию эквивалентной. Идея же применима и без инструментов: перед тем как закончить таблицу, спросите себя «какую самую вероятную ошибку допустит автор реализации в каждом правиле и упадёт ли от неё хоть один случай?»
