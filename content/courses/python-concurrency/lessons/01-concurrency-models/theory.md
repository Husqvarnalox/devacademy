## Много дел сразу: три способа

Представьте кухню. **Конкурентность** - это один повар, который поставил воду, пока она греется, режет овощи, а когда закипело - возвращается к кастрюле. Дел несколько, и все они «в процессе», но в каждый момент повар делает одно. **Параллелизм** - это несколько поваров, которые режут овощи буквально одновременно. Конкурентность - про *структуру* программы (как организовать несколько независимых дел), параллелизм - про *исполнение* (сколько дел идёт в один и тот же момент на разных ядрах). Можно иметь одно без другого.

Нагрузка бывает двух видов. **I/O-bound** (упирается в ожидание): запросы по сети, чтение диска, ожидание базы данных. Процессор простаивает, пока ответ едет. **CPU-bound** (упирается в процессор): сжатие, разбор больших данных, численные расчёты на чистом Python. Для первой достаточно *перекрывать ожидания*, для второй нужны *дополнительные ядра*.

В Python есть три основных инструмента:

* **Процессы** (`multiprocessing`, `ProcessPoolExecutor`) - у каждого своя память и свой интерпретатор; настоящий параллелизм, но данные приходится передавать через сериализацию.
* **Потоки** (`threading`, `ThreadPoolExecutor`) - общая память, переключением управляет операционная система; удобны для блокирующего I/O.
* **Корутины** (`asyncio`) - один поток, переключение происходит только там, где вы написали `await`; тысячи одновременных соединений дёшево.

Отдельно стоит **GIL** - блокировка в обычном CPython, из-за которой Python-код в нескольких потоках одного процесса не выполняется параллельно. О нём и о том, как он меняется, - ниже.

## Модели и их свойства

| | процесс | поток | корутина (asyncio) |
|---|---|---|---|
| память | изолирована | общая | общая (один поток) |
| кто переключает | ОС (вытесняющая многозадачность) | ОС (вытесняющая) | сам код: `await` (кооперативная) |
| параллельный Python-код (с GIL) | да | нет | нет |
| стоимость создания | высокая | средняя | низкая |
| обмен данными | сериализация (pickle), общая память | напрямую, нужна синхронизация | напрямую, гонок на `await`-границах меньше |

**Вытесняющее и кооперативное переключение.** Потоки и процессы планирует ОС: переключение может случиться между любыми двумя машинными инструкциями. Корутины уступают управление только в точках `await`. Поэтому код между двумя `await` в одной задаче выполняется без вмешательства других задач event loop, но стоит поставить в нём блокирующий вызов (`time.sleep`, синхронный сетевой клиент), и замирает весь цикл.

**GIL в CPython.** Global interpreter lock - мьютекс, позволяющий выполнять байткод Python только одному потоку интерпретатора одновременно. Он защищает *внутренние* структуры интерпретатора (счётчики ссылок, аллокаторы) и упрощает написание расширений на C. Что важно знать:

* GIL **отпускается** на время блокирующих системных вызовов ввода-вывода (чтение сокета, `time.sleep`, ожидание блокировки) и во многих расширениях на C (например, при тяжёлых вычислениях в NumPy или при сжатии в `zlib`). Поэтому потоки реально перекрывают ожидание I/O.
* Чистый Python-код держит GIL, поэтому потоки не ускоряют CPU-bound задачи на нескольких ядрах.
* Поток, долго держащий GIL, должен уступить его по запросу ожидающего потока по истечении интервала переключения. Интервал читается `sys.getswitchinterval()` и меняется `sys.setswitchinterval()` (по умолчанию 0.005 с). Это настройка планирования, а не способ получить атомарность.
* GIL **не делает составные операции атомарными**. `counter += 1` состоит из чтения, сложения и записи; поток может быть вытеснен между ними, и обновление пропадёт. Некоторые отдельные операции (например, `list.append`) на практике безопасны в CPython, но опираться на это в новом коде не стоит: используйте `Lock` и `queue.Queue` (следующий урок).

**Free-threaded сборки.** PEP 703 описывает вариант CPython без GIL. В Python 3.13 такая сборка появилась как экспериментальная. В Python 3.14 по PEP 779 она *официально поддерживается*, но остаётся **необязательной**: дистрибутивы и установщики по умолчанию дают сборку с GIL, а решение о том, чтобы free-threading стал умолчанием, пока не принято (сверьтесь со страницей «What's New in Python 3.14»). Это не отменяет синхронизацию: без GIL гонки на составных операциях проявляются ещё легче, а некоторые расширения на C могут быть несовместимы со сборкой. Определить режим можно через `sysconfig.get_config_var("Py_GIL_DISABLED")` (сборка) и `sys._is_gil_enabled()` (включён ли GIL сейчас; функция начинается с подчёркивания и описана как служебная для таких проверок).

**Как выбрать.**

* CPU-bound и нужен параллелизм: процессы (или free-threaded сборка, если ваши зависимости её поддерживают; или расширения, отпускающие GIL).
* Много ожиданий I/O, библиотеки блокирующие: потоки (`ThreadPoolExecutor`).
* Очень много соединений, есть async-библиотека: `asyncio`.
* Сочетания допустимы: например, `asyncio` + `asyncio.to_thread` для блокирующих вызовов, `asyncio` + `ProcessPoolExecutor` для вычислений.

## Примеры

**Кооперативное переключение на генераторах.** Корутины asyncio устроены идеологически так же: `yield` (в asyncio - `await`) отдаёт управление планировщику, который выбирает следующую задачу. Порядок полностью определён кодом, нет гонок и времени.

```python run
from collections import deque

def worker(name, steps):
    for i in range(steps):
        yield f"{name}{i}"
    return name

queue = deque([("A", worker("A", 2)), ("B", worker("B", 3))])
trace = []
while queue:
    name, gen = queue.popleft()
    try:
        trace.append(next(gen))
    except StopIteration:
        continue
    queue.append((name, gen))
print(trace)
```
```output
['A0', 'B0', 'A1', 'B1', 'B2']
```

**Потоки реально ждут одновременно.** Пять потоков блокируются в `Barrier.wait()`. Барьер откроется только тогда, когда все пять *одновременно* находятся в ожидании, - это доказывает, что блокирующее ожидание не держит остальные потоки, и не требует измерения времени.

```python run
import threading

barrier = threading.Barrier(5, timeout=5)
arrived = []

def wait_here(i):
    arrived.append(i)
    barrier.wait()

threads = [threading.Thread(target=wait_here, args=(i,)) for i in range(5)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("все пять ждали одновременно:", len(arrived) == 5 and not barrier.broken)
```
```output
все пять ждали одновременно: True
```

**Конкурентность без параллелизма.** Корутины asyncio работают в одном потоке: идентификатор потока у них один и тот же.

```python run
import asyncio
import threading

async def where(name):
    await asyncio.sleep(0)
    return name, threading.current_thread().name

async def main():
    return await asyncio.gather(where("x"), where("y"))

print(asyncio.run(main()))
print(__import__("sys").getswitchinterval())
```
```output
[('x', 'MainThread'), ('y', 'MainThread')]
0.005
```

## Типичные ошибки

* **«Больше потоков - быстрее».** Для CPU-bound кода на обычной сборке потоки не дают ускорения, а накладные расходы растут. Сначала определите, что ограничивает нагрузку: ожидание или процессор.
* **«GIL сделает мою структуру безопасной».** Составные операции (`+=`, «проверил - записал») не атомарны. Защищайте общие данные `Lock` или передавайте их через очереди.
* **Блокирующий вызов внутри корутины.** `time.sleep(1)` или синхронный HTTP-клиент в `async def` останавливает весь event loop. Нужны `await asyncio.sleep`, асинхронные библиотеки или `asyncio.to_thread`.
* **Процессы без учёта сериализации.** Аргументы и результаты передаются через pickle; тяжёлые объекты, лямбды и открытые ресурсы не передаются (подробнее - в уроке про `concurrent.futures`).
* **Путаница «конкурентность = параллелизм».** Одна программа на `asyncio` очень конкурентна и совершенно не параллельна.
* **Ссылка на устаревший факт.** Утверждение «free-threading - только экспериментальная фича» верно для 3.13, но не для 3.14; проверяйте версию.

## Итоги

* Конкурентность - структура, параллелизм - одновременное исполнение; нагрузка бывает I/O-bound и CPU-bound.
* Процессы: изоляция и параллелизм; потоки: общая память, ОС-планировщик; корутины: один поток, кооперативные `await`.
* GIL в обычном CPython защищает интерпретатор, отпускается на блокирующем I/O и во многих C-расширениях, не даёт атомарности `+=`.
* Free-threaded сборка: экспериментальна в 3.13, официально поддерживается, но необязательна в 3.14 (PEP 703, PEP 779).
* Выбор: CPU-bound - процессы; блокирующий I/O - потоки; много соединений и async-библиотека - `asyncio`.

## Факты

* `asyncio` появился в Python 3.4 по PEP 3156, а `async`/`await` - в Python 3.5 по PEP 492.
* Интервал переключения потоков по умолчанию 0.005 с; чтобы это проверить, вызовите `sys.getswitchinterval()`.
