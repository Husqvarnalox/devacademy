## Потоки и общие данные

Поток (`threading.Thread`) - это отдельная линия выполнения внутри одного процесса. Все потоки видят одни и те же переменные, и в этом их польза (не нужно ничего копировать) и их опасность: два потока могут одновременно менять одно и то же.

Представьте блокнот на кухне, в который два повара записывают «осталось яиц: N». Если оба прочитали «10», оба забрали по яйцу и оба записали «9», то записано «9», а на самом деле осталось 8. Это **гонка данных** (race condition). Лекарство - **блокировка**: пока один повар работает с блокнотом, второй ждёт. В Python это `threading.Lock`.

Кроме защиты данных потокам нужно координироваться: «дождись сигнала», «подожди, пока появится работа», «не больше трёх одновременно». Для этого есть `Event`, `Condition`, `Semaphore` и, самое удобное для передачи работы, потокобезопасная очередь `queue.Queue`. Правило, которое избавляет от большинства проблем: **не делитесь изменяемыми данными, а передавайте их через очередь**.

Идеи этого урока применимы независимо от GIL (см. [«Модели конкурентности»](lesson:python.concurrency.concurrency-models)): и в обычной сборке, и в free-threaded составные операции нужно защищать.

## Основные средства

**Thread.** `t = threading.Thread(target=f, args=(...), name="...")`; `t.start()` запускает; `t.join(timeout=None)` ждёт завершения. Исключение внутри потока не попадает в главный поток: оно печатается через `threading.excepthook`, а `join` вернётся нормально. Результат нужно передавать явно (очередь, общий список под защитой, Future). **Daemon-поток** (`daemon=True`) не мешает завершению программы: при выходе интерпретатора он останавливается внезапно, без `finally`, поэтому для работы, которая должна закончиться корректно, нужны не daemon-потоки с `join` или сигнал остановки через `Event`.

**Lock.** `lock.acquire(blocking=True, timeout=-1)` и `lock.release()`; практически всегда используйте `with lock:` - освобождение произойдёт и при исключении. Держите блокировку как можно короче и не вызывайте под ней чужой код и операции с долгим ожиданием. Lock **не рекурсивный**: повторный `acquire` из того же потока заблокирует его навсегда. **RLock** помнит владельца и счётчик и допускает повторный вход из того же потока (метод, держащий блокировку, вызывает другой метод, который берёт её же). Это удобно, но часто маскирует плохо продуманную структуру блокировок.

**Составные операции и check-then-act.** Защищать нужно не отдельные чтения и записи, а *инвариант целиком*: «проверил и изменил» должно выполняться под одной блокировкой. `if x < limit: x += 1` с блокировкой отдельно на чтение и на запись всё равно содержит гонку.

**Event.** Флаг для сигналов между потоками: `set()`, `clear()`, `is_set()`, `wait(timeout)`. Подходит для «стоп!» и «готово».

**Condition.** Блокировка плюс очередь ожидающих: поток ждёт выполнения условия, пока другой его не обеспечит. Шаблон: `with cond: cond.wait_for(lambda: условие)` у ожидающего, `with cond: изменить состояние; cond.notify()` у изменяющего. Условие всегда проверяется в цикле или через `wait_for`, потому что пробуждение не гарантирует, что условие истинно.

**Semaphore.** Счётчик разрешений: `with sem:` пускает не более N потоков одновременно (ограничение числа соединений). `BoundedSemaphore` дополнительно ловит лишние `release`.

**Barrier.** Заставляет N потоков дождаться друг друга в одной точке; удобен в тестах.

**Deadlock (взаимная блокировка).** Поток 1 держит A и ждёт B, поток 2 держит B и ждёт A: оба ждут вечно. Условия: удержание ресурса при ожидании другого плюс циклическое ожидание. Способы борьбы: (1) **единый порядок захвата** блокировок (например, по возрастанию `id` объектов) - ломает цикл; (2) `acquire(timeout=...)` с откатом и повтором; (3) не держать две блокировки сразу, если можно обойтись одной или очередью.

**queue.Queue.** Потокобезопасная FIFO-очередь: `put(item)` блокируется при полной очереди (если задан `maxsize`), `get()` блокируется при пустой, `task_done()` и `join()` позволяют дождаться обработки всех элементов. `put_nowait`/`get_nowait` поднимают `queue.Full`/`queue.Empty`. Типовая схема producer/consumer: ограниченная очередь даёт **обратное давление** (backpressure), а для остановки в очередь кладут по одному сигнальному значению (sentinel) на каждого потребителя. Варианты: `LifoQueue`, `PriorityQueue`, `SimpleQueue`. Начиная с Python 3.13, у очередей есть `shutdown()`, но sentinel остаётся универсальным шаблоном.

**Отладка гонок.** Гонка не воспроизводится по требованию: тест, который «обычно проходит», ничего не доказывает. Проверяйте *корректность* вашей защиты: много потоков, понижение `sys.setswitchinterval`, инварианты в конце (сумма, количество). Обнаружить отсутствие гонки тестом нельзя, обнаружить присутствие блокировки - можно (шпион вместо Lock).

## Примеры

**Lock вокруг счётчика.** Четыре потока по 10000 приращений; итог всегда 40000, потому что чтение-сложение-запись выполняются под блокировкой.

```python run
import threading

class Counter:
    def __init__(self):
        self.value = 0
        self._lock = threading.Lock()

    def increment(self):
        with self._lock:
            self.value += 1

counter = Counter()

def work():
    for _ in range(10_000):
        counter.increment()

threads = [threading.Thread(target=work) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print(counter.value)
```
```output
40000
```

**Ограниченный producer/consumer.** Очередь на 2 элемента, два потребителя, остановка sentinel. Результаты сортируются, так как порядок завершения потоков не определён.

```python run
import queue
import threading

jobs = queue.Queue(maxsize=2)
done = []
lock = threading.Lock()

def consumer():
    while True:
        item = jobs.get()
        if item is None:
            return
        with lock:
            done.append(item * item)

workers = [threading.Thread(target=consumer) for _ in range(2)]
for w in workers:
    w.start()
for n in range(6):
    jobs.put(n)          # блокируется, если очередь заполнена
for _ in workers:
    jobs.put(None)       # по sentinel на каждого потребителя
for w in workers:
    w.join()
print(sorted(done))
```
```output
[0, 1, 4, 9, 16, 25]
```

**Deadlock и порядок захвата.** Барьер заставляет оба потока взять свою первую блокировку до того, как кто-то попробует вторую. При разном порядке (A,B и B,A) оба потока на `acquire(timeout=...)` терпят неудачу: так deadlock виден без зависания. При едином порядке (A, затем B) второй поток просто ждёт первого и обе попытки успешны.

```python run
import threading

def attempt(same_order):
    a, b = threading.Lock(), threading.Lock()
    barrier = threading.Barrier(2, timeout=2)
    results = []

    def worker(first, second, sync):
        with first:
            if sync:
                barrier.wait()           # оба уже держат по первой блокировке
            ok = second.acquire(timeout=0.2)
            results.append(ok)
            if ok:
                second.release()
            if sync:
                barrier.wait()           # никто не отпускает первую блокировку, пока оба не попробовали

    if same_order:
        jobs = [(a, b, False), (a, b, False)]
    else:
        jobs = [(a, b, True), (b, a, True)]
    threads = [threading.Thread(target=worker, args=job) for job in jobs]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return results

print("разный порядок:", attempt(same_order=False))
print("единый порядок:", attempt(same_order=True))
```
```output
разный порядок: [False, False]
единый порядок: [True, True]
```

**Condition вместо опроса.** Поток ждёт, пока список наполнится, не жжёт процессор в цикле.

```python run
import threading

items = []
cond = threading.Condition()

def waiter(out):
    with cond:
        cond.wait_for(lambda: len(items) >= 3)
        out.append(list(items))

out = []
t = threading.Thread(target=waiter, args=(out,))
t.start()
for i in range(3):
    with cond:
        items.append(i)
        cond.notify_all()
t.join()
print(out)
```
```output
[[0, 1, 2]]
```

## Типичные ошибки

* **Защита чтения без записи (или наоборот).** Блокировка должна охватывать все обращения к защищаемому состоянию, иначе она бесполезна.
* **check-then-act вне одной блокировки.** `if key not in cache: cache[key] = compute()` без блокировки вокруг обеих строк даёт гонку.
* **Повторный acquire обычного Lock** в том же потоке (например, метод под блокировкой вызывает другой метод под той же блокировкой): самоблокировка. Либо `RLock`, либо реорганизуйте код.
* **Разный порядок захвата** нескольких блокировок: классический deadlock.
* **Бесконечное ожидание.** `queue.get()` без sentinel или таймаута, `join()` без остановки потребителей: программа висит.
* **Исключение в потоке «теряется».** Поток умирает, `join` проходит нормально, результата нет. Ловите исключения в целевой функции и передавайте их явно, либо используйте `concurrent.futures` (следующий урок).
* **Полагаться на daemon для чистой остановки.** Daemon-поток обрывается посреди работы. Используйте `Event` и `join`.
* **Доверять тесту «у меня не воспроизвелось».** Отсутствие гонки в запусках не доказывает её отсутствия.

## Итоги

* Общие изменяемые данные в потоках защищайте `Lock` (`with lock:`), охватывая весь инвариант, включая check-then-act.
* `RLock` допускает повторный вход одного потока; `Event` - сигнал; `Condition` - ожидание условия; `Semaphore` - ограничение числа участников.
* Deadlock лечится единым порядком захвата, таймаутами и сокращением числа одновременно удерживаемых блокировок.
* `queue.Queue(maxsize=N)` - основной способ передачи работы между потоками: потокобезопасно, с обратным давлением; остановка - sentinel на каждого потребителя.
* Не полагайтесь на GIL и на удачные запуски; проверяйте корректность защиты, а не отсутствие сбоев.

<!-- section: facts -->
## Факты

* `Lock.acquire(timeout=...)` возвращает `True` или `False`; именно так в примере выше deadlock виден без зависания.
* В Python 3.13 у `queue.Queue` появился метод `shutdown()` для корректного завершения работы очереди.
