## Горутины и каналы

**Горутина** - это функция, выполняющаяся независимо от вызвавшей её. Чтобы запустить, достаточно поставить перед вызовом слово `go`:

```go
go fmt.Println("из другой горутины")
```

Горутины очень лёгкие (начальный стек - несколько килобайтов), поэтому программы на Go запускают их тысячами. Планировщик среды выполнения сам распределяет их по ядрам процессора.

Горутины нужно как-то **синхронизировать** и обмениваться данными. Для этого в Go есть **каналы** - типизированные трубы между горутинами:

```go
ch := make(chan int)
go func() { ch <- 42 }() // отправка
v := <-ch                // получение: ждёт, пока значение не придёт
```

Девиз Go: *«Не общайтесь через общую память, делитесь памятью через общение»*. Канал одновременно передаёт значение и **синхронизирует** отправителя с получателем.

Три основных вида каналов и приёмов:

1. **Небуферизованный канал** (`make(chan T)`): отправка ждёт получателя и наоборот. Это точка встречи двух горутин.
2. **Буферизованный канал** (`make(chan T, n)`): отправка ждёт, только если буфер полон; получение - если пуст.
3. **`select`** ждёт сразу несколько каналов и выполняет ту ветвь, что готова.

Важное правило: когда `main` завершается, **программа завершается**, даже если другие горутины ещё работают. Поэтому главная горутина должна дождаться остальных - через канал или `sync.WaitGroup`.

## Точные правила

**Горутины.**

* `go f(x, y)` запускает вызов в новой горутине. Аргументы вычисляются в **вызывающей** горутине в момент оператора `go`. Возвращаемые значения функции отбрасываются.
* Порядок выполнения горутин не определён. Если результат зависит от порядка, нужна синхронизация (канал, `WaitGroup`, мьютекс). Использовать `time.Sleep` для «ожидания» - ошибка: она лишь повышает вероятность нужного порядка, но не гарантирует его.
* Горутина, которая никогда не завершится (например, заблокирована навсегда на канале), - **утечка горутины**: она держит память до конца программы.

**Каналы.**

* `make(chan T)` - небуферизованный, `make(chan T, n)` - буфер на `n` элементов. `len(ch)` - сколько элементов в буфере, `cap(ch)` - ёмкость.
* **Отправка** `ch <- v` блокируется, пока нет получателя (небуферизованный) или нет места в буфере. **Получение** `v := <-ch` блокируется, пока нет данных. Форма `v, ok := <-ch` даёт `ok == false`, когда канал закрыт и буфер пуст.
* **Закрытие** `close(ch)` сообщает «больше значений не будет». Закрывает канал **отправитель**, и только один раз. После закрытия: получение возвращает оставшиеся значения из буфера, затем нулевые значения с `ok == false`; отправка вызывает панику `send on closed channel`; повторное закрытие - паника `close of closed channel`; закрытие `nil`-канала - паника `close of nil channel`.
* Закрывать канал нужно только если получателю важно узнать об окончании (например, он читает через `range`). Закрытие не освобождает память: за этим следит сборщик мусора.
* `for v := range ch` читает до закрытия канала. Если канал никто не закроет, цикл никогда не завершится.
* **Направленные типы:** `chan<- T` (только отправка) и `<-chan T` (только получение). Двунаправленный канал неявно приводится к направленному; так функции документируют свои права, а компилятор их проверяет.
* Операции с `nil`-каналом блокируются навсегда; в `select` такая ветвь просто никогда не выбирается (приём для отключения ветви).

**`select`.**

* `select` ждёт, пока готова хотя бы одна из операций с каналами, и выполняет её. Если готовы несколько, выбор **псевдослучаен**.
* Ветвь `default` выполняется, если ни одна операция не готова сразу: так делают неблокирующую отправку и получение.
* Типичные формы: ожидание значения или отмены (`case <-done:`), ожидание с тайм-аутом (`case <-time.After(d):`), мультиплексирование нескольких источников.

**Взаимные блокировки.**

* Если **все** горутины заблокированы и ни одна не может продолжить, среда выполнения завершает программу: `fatal error: all goroutines are asleep - deadlock!` (код выхода 2). Это ошибка, которую нельзя перехватить.
* Обнаружение работает, только если заблокированы действительно все горутины. В серверах и тестах всегда есть другие горутины (таймеры, сетевой опрос), поэтому настоящая взаимная блокировка там проявляется как «зависание» без сообщения.

**`sync.WaitGroup`.**

* `wg.Add(n)`, `wg.Done()`, `wg.Wait()`: счётчик ожидания завершения группы горутин. `Add` нужно вызывать **до** запуска горутины, а не внутри неё.
* **С Go 1.25** есть метод `wg.Go(f func())`: он сам вызывает `Add(1)`, запускает `f` в новой горутине и вызывает `Done` по её завершении. Для кода, который должен собираться более старыми версиями Go, остаётся классическая форма `Add` + `go` + `defer Done`.
* Значение `WaitGroup` нельзя копировать после первого использования; передавайте указатель.

**Переменная цикла и горутины.** С Go 1.22 (версия языка в `go.mod`) каждая итерация имеет свою переменную, и `go func() { use(i) }()` внутри цикла безопасно. В старых версиях её приходилось копировать или передавать аргументом.

## Примеры

**Пример 1. `WaitGroup` и сбор результатов.**

```go run
package main

import (
	"fmt"
	"slices"
	"sync"
)

func main() {
	results := make(chan int)
	var wg sync.WaitGroup

	for i := 1; i <= 5; i++ {
		wg.Go(func() { // Go 1.25+: Add(1) + go + defer Done
			results <- i * i
		})
	}

	// Закрыватель: ждёт всех отправителей и закрывает канал.
	go func() {
		wg.Wait()
		close(results)
	}()

	var got []int
	for v := range results { // читаем до закрытия
		got = append(got, v)
	}
	slices.Sort(got) // порядок прихода не определён
	fmt.Println(got)
}
```

```output
[1 4 9 16 25]
```

Горутины завершаются в произвольном порядке, поэтому результат сортируется перед печатью. Если не закрыть `results`, цикл `range` никогда не закончится.

**Пример 2. Небуферизованный и буферизованный каналы, `select` с `default`.**

```go run
package main

import "fmt"

func main() {
	// Буфер: две отправки проходят без получателя.
	buf := make(chan string, 2)
	buf <- "a"
	buf <- "b"
	fmt.Println(len(buf), cap(buf))

	// Третья отправка заблокировала бы горутину; select с default проверяет это.
	select {
	case buf <- "c":
		fmt.Println("отправлено")
	default:
		fmt.Println("буфер полон")
	}

	fmt.Println(<-buf, <-buf)

	// Небуферизованный канал: отправка и приём "встречаются".
	ready := make(chan struct{})
	data := 0
	go func() {
		data = 42
		close(ready) // сообщение "готово" через закрытие
	}()
	<-ready // ждём; запись data теперь видна
	fmt.Println(data)

	// Получение из закрытого канала не блокируется.
	c := make(chan int, 1)
	c <- 7
	close(c)
	v, ok := <-c
	w, ok2 := <-c
	fmt.Println(v, ok, w, ok2)
}
```

```output
2 2
буфер полон
a b
42
7 true 0 false
```

Закрытие канала `ready` играет роль сигнала: получение из закрытого канала завершается сразу, а запись `data = 42` гарантированно видна после него.

**Пример 3. Конвейер, `select` и отмена.**

```go run
package main

import "fmt"

func gen(done <-chan struct{}) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for i := 1; ; i++ {
			select {
			case out <- i:
			case <-done: // получатель ушёл: выходим, чтобы не утекла горутина
				return
			}
		}
	}()
	return out
}

func main() {
	done := make(chan struct{})
	nums := gen(done)

	for v := range nums {
		fmt.Print(v, " ")
		if v == 5 {
			close(done) // сообщаем всем отправителям: хватит
			break
		}
	}
	fmt.Println()

	// Паники при неправильном использовании каналов.
	defer func() { fmt.Println("recover:", recover()) }()
	c := make(chan int, 1)
	close(c)
	c <- 1
}
```

```output
1 2 3 4 5 
recover: send on closed channel
```

Генератор бесконечный, и без канала `done` его горутина навсегда осталась бы заблокированной на отправке. Отправка в закрытый канал в конце вызывает панику `send on closed channel`.

**Пример 4. Взаимная блокировка (не запускается).** Программа

```go
package main

func main() {
	ch := make(chan int)
	ch <- 1 // получателя нет: все горутины спят
}
```

завершается с `fatal error: all goroutines are asleep - deadlock!` и строкой `goroutine 1 [chan send]:`. Если запустить получателя в другой горутине (`go func() { <-ch }()`), отправка завершится.

## Типичные ошибки

* **`main` не дожидается горутин.** Программа завершается раньше, чем они начнут работать. Ждите через `WaitGroup` или канал, а не через `time.Sleep`.
* **Синхронизация через `time.Sleep`.** Работает «на моей машине» и ломается под нагрузкой; используйте каналы, `WaitGroup`, `sync.Mutex`.
* **Закрытие канала получателем** или закрытие дважды: паника. Закрывает единственный владелец-отправитель; при нескольких отправителях закрывает отдельная горутина после `wg.Wait()` (как в примере 1).
* **Забытый `close` при чтении через `range`.** Читатель ждёт вечно (и среда обнаружит только полную взаимную блокировку).
* **Отправка в канал без получателя** (утечка горутины или deadlock). Предусматривайте отмену через `select` с каналом `done`/`ctx.Done()`.
* **`wg.Add` внутри горутины.** `Wait` может отработать до `Add`. Вызывайте `Add` до `go` (или используйте `wg.Go`).
* **Копирование `WaitGroup`** (передача по значению): горутина уменьшает счётчик копии. Передавайте указатель.
* **Захват переменной цикла в старых версиях Go** (`go.mod` ниже 1.22): все горутины видят последнее значение.
* **Ожидание порядка результатов.** Горутины заканчиваются в любом порядке; сортируйте или индексируйте результаты.
* **Неблокирующий `select` с `default` в цикле** создаёт активное ожидание и грузит процессор.
* **Использование горутин «для скорости» везде.** Накладные расходы на синхронизацию могут превысить выигрыш для мелких задач.

<!-- section: summary -->
## Итоги

* `go f()` запускает горутину; `main` не ждёт остальных, поэтому нужна синхронизация (`WaitGroup`, каналы).
* Небуферизованный канал синхронизирует отправителя и получателя, буферизованный блокирует при заполнении.
* `close` вызывает только отправитель; `range` читает до закрытия; чтение из закрытого канала возвращает нулевое значение с `ok == false`.
* `select` выбирает готовую ветвь, `default` делает операцию неблокирующей, `done`-канал позволяет отменять работу и не терять горутины.
* Если все горутины спят, среда выполнения сообщает `all goroutines are asleep - deadlock!`; `sync.WaitGroup.Go` доступен с Go 1.25.

<!-- section: facts -->
## Факты

* Метод `sync.WaitGroup.Go` добавлен в Go 1.25; для более старых версий используйте `Add` и `Done`.
* Сообщение `fatal error: all goroutines are asleep - deadlock!` печатает среда выполнения и завершает процесс с кодом 2.
