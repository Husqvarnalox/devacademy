## Один запрос - один короткий жизненный цикл

Классический PHP устроен иначе, чем долгоживущие серверы на Java или Node.js. Для каждого запроса (или для каждого запуска `php script.php` в консоли) движок:

1. запускает скрипт с **чистого листа**: все переменные, объекты и подключённые файлы создаются заново;
2. выполняет код сверху вниз;
3. вызывает функции, зарегистрированные через `register_shutdown_function`, затем уничтожает оставшиеся объекты (вызывая `__destruct`);
4. **освобождает всю память** запроса.

Поэтому между двумя запросами в самом PHP ничего не хранится: общий счётчик в обычной переменной не заработает. Данные, которые должны пережить запрос, живут снаружи: в базе данных, файле, сессии, кеше (Redis, APCu). Эту модель называют *share-nothing*. Она упрощает код (нет гонок между запросами внутри процесса) и делает утечки памяти почти безвредными, потому что память возвращается после каждого запроса.

Внутри такого короткого цикла у вас всё равно есть значения, и важно понимать, **что именно копируется**, когда вы пишете `$b = $a`. Это и есть тема урока: как PHP хранит значение (`zval`), когда копирует массив, чем ссылка `&` отличается от объекта.

## Точные правила

**Фазы жизненного цикла.** У процесса PHP (например, воркера PHP-FPM или консольного запуска) есть запуск модулей и расширений, затем для каждого запроса отдельная фаза запуска запроса, выполнение скрипта и завершение запроса. В завершение входят: функции из `register_shutdown_function` (в порядке регистрации; они вызываются и после `exit()`), уничтожение объектов и освобождение памяти. Документация по деструкторам говорит об этом так: деструктор вызывается, как только на объект не осталось ссылок, либо в произвольном порядке при завершении скрипта. На порядок деструкторов при завершении полагаться нельзя.

**Что в CLI.** Консольный запуск - это тот же цикл, но один запрос на процесс. OPcache хранит *скомпилированный код*, а не значения переменных, поэтому share-nothing он не нарушает.

**`zval`.** Любое значение PHP внутри движка - `zval`: небольшая структура с **тегом типа** и **полезной нагрузкой**. Целые числа, числа с плавающей точкой, `true`, `false` и `null` лежат прямо в `zval`. Строки, массивы, объекты и ссылки - это указатели на отдельные структуры, у каждой из которых есть **счётчик ссылок** (refcount): сколько имён и ячеек на неё сейчас указывают. Руководство описывает его так: refcount показывает, сколько переменных указывают на один контейнер значения.

**Присваивание и copy-on-write.** `$b = $a` для строки или массива не копирует данные: оба имени указывают на одну структуру, refcount вырастает до 2. Реальная копия (*разделение*, separation) создаётся только когда кто-то из владельцев **изменяет** значение. С точки зрения программы массивы и строки ведут себя как значения, а стоимость копирования откладывается до записи. Передача массива в функцию и возврат из неё устроены так же.

**Объекты.** Переменная с объектом хранит не сам объект, а его *идентификатор*. `$b = $a` копирует идентификатор, оба имени ведут к одному объекту. Это не ссылка в смысле `&`: если внутри функции присвоить параметру другой объект, снаружи ничего не изменится. Для независимой копии есть `clone`, но он **поверхностный**: вложенные объекты остаются общими, пока вы не реализуете `__clone`.

**Ссылки `&`.** Ссылка - это псевдоним: два имени для одного значения. При создании ссылки значение оборачивается в особую структуру «ссылка», и запись через любое из имён видна через другое. Ссылки работают в присваивании (`$b = &$a`), в параметрах (`function f(array &$x)`), в `foreach` (`foreach ($a as &$v)`) и в элементах массива. Особенность: **элемент массива, который является ссылкой, остаётся ссылкой при копировании массива**. Копия массива делит с оригиналом такие ячейки.

**Циклы и сборщик мусора.** Счётчик ссылок не освобождает циклы (`$a->peer = $b; $b->peer = $a`): после `unset` у каждого объекта refcount остаётся ненулевым. Их находит отдельный сборщик циклов; запустить его вручную можно через `gc_collect_cycles()`; функция возвращает число собранных значений (ноль, если собирать было нечего). Если вам не нужно, чтобы память освобождалась посреди запроса, на сборщик обычно можно не обращать внимания: в конце запроса память всё равно будет освобождена.

**Сравнение со знакомыми языками.** В Java и C# объекты живут в куче под управлением трассирующего сборщика мусора, а не по счётчику ссылок; массивы там - ссылочные типы, а в PHP - значения. В Python всё - ссылки на объекты (и тоже есть счётчик ссылок плюс сборщик циклов), но «значением» ведут себя только неизменяемые типы.

## Примеры

**Пример 1. Завершение скрипта: порядок событий.**

```php run
<?php
class Resource
{
    public function __construct(private string $name)
    {
        echo "open {$this->name}\n";
    }

    public function __destruct()
    {
        echo "close {$this->name}\n";
    }
}

function work(): void
{
    $tmp = new Resource('tmp');
    echo "working\n";
}   // $tmp выходит из области видимости: refcount падает до 0

register_shutdown_function(function () {
    echo "shutdown function\n";
});

$main = new Resource('main');
work();
echo "end of script\n";
```
```output
open main
open tmp
working
close tmp
end of script
shutdown function
close main
```

Объект `tmp` уничтожен сразу при выходе из функции, потому что на него больше нет ссылок. Объект `main` дожил до конца скрипта, и его деструктор вызван после функции завершения.

**Пример 2. Массив - значение, а copy-on-write откладывает копирование.**

```php run
<?php
function usage(): int
{
    return memory_get_usage();
}

$a = range(1, 100000);
$before = usage();
$b = $a;                       // копии данных ещё нет
$afterAssign = usage();
$b[] = 0;                      // запись: теперь PHP разделяет массивы
$afterWrite = usage();

echo 'assign is cheap: ', var_export($afterAssign - $before < 1024, true), "\n";
echo 'write copies:    ', var_export($afterWrite - $afterAssign > 500000, true), "\n";
echo 'count a: ', count($a), ', count b: ', count($b), "\n";
```
```output
assign is cheap: true
write copies:    true
count a: 100000, count b: 100001
```

Мы печатаем только логические значения, а не точные байты: они зависят от версии и настроек.

**Пример 3. Значение, объект и ссылка.**

```php run
<?php
function addToArray(array $items): void
{
    $items[] = 'new';
}

function addByRef(array &$items): void
{
    $items[] = 'new';
}

function renameIt(stdClass $o): void
{
    $o->name = 'changed';      // меняем общий объект
    $o = new stdClass();       // подменяем только локальный идентификатор
    $o->name = 'lost';
}

$list = ['a'];
addToArray($list);
echo count($list), "\n";       // 1
addByRef($list);
echo count($list), "\n";       // 2

$obj = new stdClass();
$obj->name = 'original';
renameIt($obj);
echo $obj->name, "\n";         // changed

$copy = clone $obj;
$copy->name = 'copy';
echo $obj->name, ' / ', $copy->name, "\n";
```
```output
1
2
changed
changed / copy
```

**Пример 4. Ссылка в элементе массива переживает копирование.**

```php run
<?php
$x = 1;
$a = [&$x, 2];
$b = $a;                       // «копия» массива
$b[0] = 99;                    // но ячейка 0 - ссылка на $x
$b[1] = 77;
echo $x, ' ', $a[0], ' ', $a[1], "\n";

$nums = [1, 2, 3];
foreach ($nums as &$n) {
    $n *= 2;
}
foreach ($nums as $n) {         // $n всё ещё ссылка на последний элемент
}
echo implode(',', $nums), "\n";
unset($n);
```
```output
99 99 2
2,4,4
```

Во втором цикле переменная `$n` по-прежнему указывает на последний элемент `$nums`, поэтому на каждом шаге в него записывается очередное значение. Последний элемент превращается в предпоследний. Лечение: `unset($n)` сразу после цикла по ссылке.

**Пример 5. Цикл ссылок и сборщик мусора.**

```php run
<?php
class Node
{
    public ?Node $peer = null;

    public function __destruct()
    {
        echo "destroyed\n";
    }
}

$a = new Node();
$b = new Node();
$a->peer = $b;
$b->peer = $a;
unset($a, $b);                  // счётчики не дошли до нуля
echo "after unset\n";
$freed = gc_collect_cycles();
echo 'collected something: ', var_export($freed > 0, true), "\n";
echo "done\n";
```
```output
after unset
destroyed
destroyed
collected something: true
done
```

## Типичные ошибки

* **Ждать, что значение переживёт запрос.** Обычная переменная, статическое свойство и `static`-переменная функции живут только до конца запроса (в CLI - до конца скрипта). Для хранения между запросами нужна внешняя система.
* **Считать, что `$b = $a` для объекта копирует объект.** Копируется идентификатор; для независимой копии используйте `clone`, а вложенные объекты копируйте в `__clone`.
* **Думать, что `&` ускоряет передачу массива.** Благодаря copy-on-write передача по значению стоит дёшево; ссылка нужна только когда функция *должна* изменить исходный массив, и делает код менее предсказуемым.
* **Забыть `unset($v)` после `foreach (... as &$v)`.** Следующий цикл по тому же имени испортит последний элемент.
* **Не знать, что ссылки в массиве копируются как ссылки.** Массив со ссылочными ячейками не изолирован от копии.
* **Полагаться на порядок вызова деструкторов в конце скрипта и на то, что `__destruct` успеет что-то сделать с внешними ресурсами.** Освобождайте ресурсы явно, а деструктор оставляйте страховкой.
* **Обращаться к `gc_collect_cycles()` как к способу «починить» утечку.** Если утечка вызвана накоплением данных в длинном консольном процессе, ищите, что держит ссылки.

## Итоги

* Каждый запрос начинается с чистого состояния и заканчивается освобождением всей памяти (share-nothing); долгоживущие данные хранятся снаружи.
* Значение в движке - `zval`; строки, массивы, объекты и ссылки хранятся в структурах со счётчиком ссылок, а разделение при записи (copy-on-write) делает присваивание дешёвым.
* Массивы и строки ведут себя как значения, переменная с объектом хранит идентификатор, `&` создаёт псевдоним.
* Ссылка внутри массива и `foreach` по ссылке - главные источники неожиданностей; циклы объектов освобождает сборщик циклов.
