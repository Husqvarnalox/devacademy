## Как браузер просит страницу и получает её

HTTP - это язык, на котором клиент (браузер, скрипт, мобильное приложение) просит у сервера ресурс, а сервер отвечает. Запрос: «дай мне `/index.html`». Ответ: «вот он, код 200, а вот его содержимое». Смысл (методы GET и POST, коды статуса 404 и 500, заголовки) неизменен во всех версиях. Меняется то, **как** это передаётся по сети.

* **HTTP/1.1** - обычный текст. Запрос и ответ читаются глазами. Просто, но на одном соединении запросы идут по очереди, и один медленный ответ задерживает все следующие. Поэтому браузеры открывали по шесть соединений на сервер.
* **HTTP/2** - те же сообщения, но разрезанные на двоичные **кадры**, которые перемешиваются в одном соединении. Много запросов идут одновременно. Заголовки сжимаются, потому что они повторяются от запроса к запросу.
* **HTTP/3** - те же кадры и потоки, но поверх **QUIC**: транспорта, построенного над UDP. Потеря одного пакета больше не задерживает все потоки, а шифрование (TLS) встроено в QUIC.

Знать текстовый формат HTTP/1.1 полезно всегда: curl, логи и отладка показывают именно его. Как писать серверы на этих протоколах, см. [HTTP в Node.js](lesson:nodejs.fundamentals.http-fundamentals), а как аккуратно ходить на сторонние API из Python - [надёжные HTTP-клиенты](lesson:python.automation.robust-http-clients). Транспортом для HTTP/1.1 и HTTP/2 служит TCP ([урок про TCP](lesson:networking.fundamentals.tcp-connections-and-congestion)), для HTTP/3 - UDP ([урок про UDP](lesson:networking.fundamentals.udp-and-dns)).

## Формат сообщений и версии протокола

**Ответ HTTP/1.1:**

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/plain\r\n
Content-Length: 5\r\n
\r\n
hello
```

Стартовая строка запроса: `GET /path HTTP/1.1`; ответа: `HTTP/1.1 КОД ПРИЧИНА`. Дальше идут заголовки (имена нечувствительны к регистру), пустая строка и тело. Заголовок `Host` обязателен в запросе HTTP/1.1.

**Где кончается тело** (RFC 9112, по порядку):

1. Ответы 1xx, 204, 304 и ответ на HEAD тела не имеют.
2. `Transfer-Encoding: chunked` - тело состоит из кусков.
3. `Content-Length: N` - ровно N байтов.
4. Иначе тело длится до закрытия соединения (для ответа).

**Chunked.** Каждый кусок: размер в hex, возможно `;расширение`, CRLF, данные ровно этого размера, CRLF. Конец - кусок размера `0`, затем (необязательные) строки трейлера и пустая строка:

```text
4\r\nWiki\r\n5\r\npedia\r\n0\r\n\r\n
```

Тело выдаётся по мере вычисления (потоковая передача без предварительного знания длины). Длина куска считается в **байтах**, а не символах; данные могут содержать переводы строк.

**Постоянные соединения и очередь.** В HTTP/1.1 соединение переиспользуется (keep-alive), но ответы возвращаются в порядке запросов. Конвейеризация почти не применялась из-за блокировки начала очереди: медленный первый ответ задерживает остальные.

**HTTP/2.** Двоичный формат. Каждый **кадр** начинается 9-байтным заголовком: длина полезной нагрузки (24 бита), тип (8), флаги (8), один зарезервированный бит и идентификатор потока (31 бит). Типы: DATA 0, HEADERS 1, SETTINGS 4, и другие. Запрос и ответ - **поток** с номером; кадры разных потоков чередуются. Заголовки передаются HPACK: байт с битом 1 вверху - индекс в таблице (`0x82` - `:method: GET` из статической таблицы), байт с битами `01` в старших разрядах (`0x40`) - литерал с добавлением в динамическую таблицу и т. д. Строки могут быть закодированы кодом Хаффмана. Остаётся блокировка начала очереди на уровне TCP: потеря одного сегмента задерживает все потоки.

**HTTP/3 и QUIC.** QUIC работает поверх UDP, реализует надёжность и управление перегрузкой для каждого потока отдельно и встраивает TLS 1.3. Потеря пакета блокирует только потоки, чьи данные в нём были. Соединение идентифицируется идентификатором, а не четвёркой адресов, поэтому переживает смену сети. Числа в QUIC кодируются **переменной длиной**: два старших бита первого байта задают длину (`00` - 1 байт, `01` - 2, `10` - 4, `11` - 8), остальные биты и последующие байты (big-endian) - значение.

## Примеры

**Разбор ответа и chunked-тела.** Вручную, на байтах:

```python run
raw = (b"HTTP/1.1 200 OK\r\nContent-Type: text/plain\r\n"
       b"Transfer-Encoding: chunked\r\n\r\n"
       b"4\r\nWiki\r\n5\r\npedia\r\n0\r\n\r\n")

head, _, rest = raw.partition(b"\r\n\r\n")
lines = head.decode("latin-1").split("\r\n")
version, status, reason = lines[0].split(" ", 2)
headers = {k.lower(): v.strip() for k, _, v in (l.partition(":") for l in lines[1:])}
print(version, status, reason, headers)

body, pos = b"", 0
while True:
    end = rest.index(b"\r\n", pos)
    size = int(rest[pos:end], 16)
    pos = end + 2
    if size == 0:
        break
    body += rest[pos:pos + size]
    pos += size + 2
print(body, len(body))
```
```output
HTTP/1.1 200 OK {'content-type': 'text/plain', 'transfer-encoding': 'chunked'}
b'Wikipedia' 9
```

**Кадр HTTP/2 и поля HPACK.** Разберём 9-байтный заголовок кадра и два примера из RFC 7541:

```python run
frame = bytes.fromhex("00000d" "01" "04" "00000001")  # HEADERS, END_HEADERS, поток 1
length = int.from_bytes(frame[0:3], "big")
ftype, flags = frame[3], frame[4]
stream = int.from_bytes(frame[5:9], "big") & 0x7FFFFFFF
TYPES = {0: "DATA", 1: "HEADERS", 4: "SETTINGS"}
print(TYPES[ftype], "length", length, "flags", hex(flags), "stream", stream)

# RFC 7541, C.2.1: литерал с добавлением в таблицу, без Хаффмана
data = bytes.fromhex("400a637573746f6d2d6b65790d637573746f6d2d686561646572")
assert data[0] == 0x40
nlen = data[1]
name = data[2:2 + nlen].decode()
vlen = data[2 + nlen]
value = data[3 + nlen:3 + nlen + vlen].decode()
print(name + ": " + value)

# 0x82: индексированное поле, индекс 2 статической таблицы
STATIC = {1: ":authority", 2: (":method", "GET"), 3: (":method", "POST")}
print(STATIC[0x82 & 0x7F])
```
```output
HEADERS length 13 flags 0x4 stream 1
custom-key: custom-header
(':method', 'GET')
```

**Целые числа QUIC переменной длины.** Примеры из RFC 9000, приложение A.1:

```python run
def varint(data):
    first = data[0]
    size = 1 << (first >> 6)
    value = first & 0x3F
    for byte in data[1:size]:
        value = (value << 8) | byte
    return value, size

for hexstr in ("c2197c5eff14e88c", "9d7f3e7d", "7bbd", "25", "4025"):
    value, size = varint(bytes.fromhex(hexstr))
    print(hexstr, "->", value, "(%d байт)" % size)
```
```output
c2197c5eff14e88c -> 151288809941952652 (8 байт)
9d7f3e7d -> 494878333 (4 байт)
7bbd -> 15293 (2 байт)
25 -> 37 (1 байт)
4025 -> 37 (2 байт)
```

Одно и то же число 37 можно записать и в 1 байт (`25`), и в 2 (`4025`): правильный разбор читает длину из первых двух бит.

## Типичные ошибки

* **Считать размер куска в символах.** Тело может быть в UTF-8 или бинарным; размер всегда в байтах. Разбирайте байты, декодируйте в самом конце.
* **Читать размер куска как десятичный.** Он шестнадцатеричный: `1a` - это 26.
* **Искать тело по `split('\n\n')`.** Граница заголовков - CRLF CRLF, но у реальных серверов бывает и LF LF. Не ломайтесь на переводах строк внутри тела.
* **Забыть трейлеры и расширения кусков.** После нулевого куска могут идти поля, перед CRLF - `;ext=value`.
* **Решить, что HTTP/2 убрал блокировку начала очереди целиком.** На уровне HTTP да, на уровне TCP нет; полностью избавляет QUIC.
* **Считать, что HTTP/3 - HTTP/2 на UDP.** Это отдельное отображение на потоки QUIC с другим сжатием заголовков (QPACK).
* **Путать смысл и передачу.** Метод GET и код 404 одинаковы во всех версиях.
* **Склеивать повторные заголовки неправильно.** Для списков допустима склейка через запятую, а `Set-Cookie` так склеивать нельзя.

## Итоги

* HTTP/1.1 - текстовые сообщения; тело ограничено chunked, Content-Length или закрытием соединения.
* Chunked: hex-размер, CRLF, данные, CRLF; кусок 0 завершает, далее трейлеры.
* HTTP/2: двоичные кадры (9-байтный заголовок), потоки, мультиплексирование и HPACK на одном TCP-соединении.
* HTTP/3: те же семантики на QUIC поверх UDP, без блокировки начала очереди между потоками; числа переменной длины.
* Семантика HTTP общая; меняется формат передачи.
