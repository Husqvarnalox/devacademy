## Как пакет находит дорогу

Представьте почту в большом городе. На конверте написан **адрес получателя** (IP), и он не меняется на всём пути. Но каждый курьер передаёт конверт только **следующему** человеку в цепочке, и для этой передачи нужно знать, кому конкретно отдать письмо в руки. Это **MAC-адрес** следующего узла, и он на каждом участке свой.

* **Ethernet** описывает, как кадр с MAC-адресами доставляется по одному проводу или Wi-Fi-сегменту. Коммутатор (switch) изучает, за каким портом какой MAC, и пересылает кадр только туда.
* **ARP** отвечает на вопрос «я знаю IP-адрес соседа, а какой у него MAC?» Узел кричит на весь сегмент: «Кто владеет 192.168.1.1?» - и владелец отвечает.
* **Маршрутизация** решает, какому соседу отдать пакет, если получатель в другой сети. Маршрутизатор хранит **таблицу**: «для сети X - отдавать соседу Y через интерфейс Z». Когда подходят несколько строк, побеждает самая конкретная (с самым длинным префиксом).

Так пакет «прыгает» от шлюза к шлюзу, а на каждом участке кадр Ethernet создаётся заново: меняются MAC-адреса, а IP-адреса остаются.

В этом уроке вы напишете ядро маршрутизатора: выбор строки таблицы для адреса назначения. Для разбора байтов кадров пригодится [struct](lesson:python.stdlib.json-csv-struct), а как работают сопоставления префиксов с адресами, вы видели в [уроке про CIDR](lesson:networking.fundamentals.ip-addressing-and-subnetting).

## Кадр Ethernet, ARP и таблица маршрутов

**Кадр Ethernet II.**

| поле | размер | содержимое |
|---|---|---|
| Destination MAC | 6 | получатель (unicast, multicast или broadcast `ff:ff:ff:ff:ff:ff`) |
| Source MAC | 6 | отправитель |
| EtherType | 2 | `0x0800` IPv4, `0x0806` ARP, `0x86DD` IPv6 |
| Payload | 46-1500 | данные (короче 46 дополняются нулями) |
| FCS | 4 | CRC-32 кадра |

Младший бит первого октета MAC (I/G) равен 1 у групповых адресов; второй по младшести бит (U/L) отмечает локально назначенный адрес. Поэтому `01:00:5e:...` - multicast IPv4, а `aa:bb:...` - локально назначенный unicast.

**Коммутатор** (L2) смотрит только на MAC-адреса: запоминает, с какого порта пришёл адрес отправителя, и пересылает кадр на порт получателя; неизвестный адрес и broadcast рассылает на все порты. **Маршрутизатор** (L3) смотрит на IP-адрес, принимает решение по таблице и формирует новый кадр для следующего хопа, уменьшая TTL.

**ARP-пакет** (28 байт для Ethernet и IPv4) лежит прямо в кадре с EtherType `0x0806`:

| поле | размер | значение |
|---|---|---|
| hardware type | 2 | 1 (Ethernet) |
| protocol type | 2 | `0x0800` (IPv4) |
| hardware / protocol address length | 1 + 1 | 6 и 4 |
| operation | 2 | 1 запрос, 2 ответ |
| sender MAC / sender IP | 6 + 4 | кто спрашивает (отвечает) |
| target MAC / target IP | 6 + 4 | в запросе MAC нулевой, в ответе - MAC спрашивающего |

Алгоритм отправки пакета на IP-адрес `D`: если `D` в той же подсети (`D & mask == network` интерфейса), ARP-запрос про `D`; иначе ARP-запрос про **шлюз** (следующий хоп из таблицы маршрутов). Ответ кладётся в кэш, а дальше кадр отправляется с найденным MAC.

**Таблица маршрутов.** Строка: префикс/длина, следующий хоп (шлюз) или признак прямого подключения, интерфейс, metric. Пример для хоста:

```text
default     via 192.168.1.1 dev eth0
192.168.1.0/24  dev eth0  (прямое подключение)
127.0.0.0/8     dev lo
```

**Выбор маршрута.** Из всех строк, у которых `address & mask == network`, выбирается строка с самым длинным префиксом (longest prefix match). Если префиксы равны, решает `metric` (меньше - лучше). Маршрут `0.0.0.0/0` (default) подходит всегда, и поэтому используется, только когда нет ничего конкретнее. Если подходящих строк нет, пакет отбрасывается, а отправителю идёт ICMP 'network unreachable'.

Реальные маршрутизаторы хранят сотни тысяч префиксов и ищут не перебором, а в префиксном дереве (trie) или аппаратной памяти TCAM. Принцип остаётся тем же.

**IPv6.** ARP в IPv6 заменён на NDP (ICMPv6): запрос идёт на multicast-адрес запрашиваемого узла, а не на broadcast. Выбор маршрута тот же: самый длинный префикс.

## Примеры

**ARP-запрос по байтам.** Построим широковещательный запрос «у кого 192.168.1.1? сообщите 192.168.1.10» и разберём его обратно:

```python run
import struct

def mac(text):
    return bytes(int(part, 16) for part in text.split(":"))

def ip(text):
    return bytes(int(part) for part in text.split("."))

my_mac, my_ip, target_ip = mac("02:00:00:aa:bb:cc"), ip("192.168.1.10"), ip("192.168.1.1")
arp = struct.pack("!HHBBH6s4s6s4s", 1, 0x0800, 6, 4, 1, my_mac, my_ip, b"\x00" * 6, target_ip)
frame = mac("ff:ff:ff:ff:ff:ff") + my_mac + struct.pack("!H", 0x0806) + arp

print(len(arp), len(frame))
print(frame.hex(" "))

htype, ptype, hlen, plen, oper, sha, spa, tha, tpa = struct.unpack("!HHBBH6s4s6s4s", frame[14:])
print("operation:", {1: "request", 2: "reply"}[oper])
print("who has", ".".join(map(str, tpa)), "tell", ".".join(map(str, spa)))
print("dst is broadcast:", frame[:6] == b"\xff" * 6, "| group bit:", frame[0] & 1)
```
```output
28 42
ff ff ff ff ff ff 02 00 00 aa bb cc 08 06 00 01 08 00 06 04 00 01 02 00 00 aa bb cc c0 a8 01 0a 00 00 00 00 00 00 c0 a8 01 01
operation: request
who has 192.168.1.1 tell 192.168.1.10
dst is broadcast: True | group bit: 1
```

Формат `!HHBBH6s4s6s4s` - ровно таблица из раздела выше. Разбор в обратную сторону использует тот же формат.

**Выбор маршрута вручную.** Таблицу удобно держать как список кортежей `(сеть, длина, шлюз)`:

```python run
def to_int(text):
    value = 0
    for part in text.split("."):
        value = (value << 8) | int(part)
    return value

routes = [
    ("0.0.0.0", 0, "192.168.1.1"),
    ("10.0.0.0", 8, "192.168.1.254"),
    ("10.1.0.0", 16, "192.168.1.2"),
]

def lookup(destination):
    value, best = to_int(destination), None
    for network, length, gateway in routes:
        mask = (0xFFFFFFFF << (32 - length)) & 0xFFFFFFFF
        if value & mask == to_int(network) & mask and (best is None or length > best[1]):
            best = (network, length, gateway)
    return best

for dst in ("10.1.2.3", "10.9.9.9", "8.8.8.8"):
    print(dst, "->", lookup(dst))
```
```output
10.1.2.3 -> ('10.1.0.0', 16, '192.168.1.2')
10.9.9.9 -> ('10.0.0.0', 8, '192.168.1.254')
8.8.8.8 -> ('0.0.0.0', 0, '192.168.1.1')
```

`10.1.2.3` подходит и `/8`, и `/16`, и `/0`, но побеждает `/16`. Это упражнение вы расширите: нормализация префиксов, metric и вывод ARP-цели.

**Тот же IP, другой MAC.** При пересылке меняются только данные канального уровня; IP-пакет остаётся прежним (кроме TTL и контрольной суммы):

```python run
def hop(frame_src, frame_dst, ip_src, ip_dst, ttl):
    return f"eth {frame_src} -> {frame_dst} | ip {ip_src} -> {ip_dst} ttl={ttl}"

print(hop("host", "router1", "192.168.1.10", "8.8.8.8", 64))
print(hop("router1", "router2", "192.168.1.10", "8.8.8.8", 63))
print(hop("router2", "server", "192.168.1.10", "8.8.8.8", 62))
```
```output
eth host -> router1 | ip 192.168.1.10 -> 8.8.8.8 ttl=64
eth router1 -> router2 | ip 192.168.1.10 -> 8.8.8.8 ttl=63
eth router2 -> server | ip 192.168.1.10 -> 8.8.8.8 ttl=62
```

(Если на пути стоит NAT, он ещё и подменит IP-адрес отправителя; для упрощения здесь его нет.)

## Типичные ошибки

* **Спрашивать ARP про удалённый адрес.** Для 8.8.8.8 хост спрашивает MAC шлюза; MAC самого 8.8.8.8 ему не нужен и недоступен.
* **Выбирать первую подходящую строку.** Порядок строк в таблице не определяет приоритет: нужен самый длинный префикс. Первый подходящий маршрут `0.0.0.0/0` перекрыл бы все остальные.
* **Не нормализовать префикс.** В записи `192.168.1.77/24` хостовая часть ненулевая; сравнивайте с `address & mask`.
* **Путать metric и длину префикса.** Metric сравнивается только между маршрутами с одинаковой длиной префикса.
* **Считать, что коммутатор смотрит на IP.** Обычный L2-коммутатор работает с MAC-адресами; маршрутизация - работа L3.
* **Думать, что ARP безопасен.** Любой узел сегмента может ответить на запрос; защиту дают статические записи, динамическая проверка ARP на коммутаторе или шифрование поверх.
* **Забывать про адреса вне таблицы.** Если нет default-маршрута, часть адресов недостижима, и это нормальный результат.

## Итоги

* Кадр Ethernet II: MAC получателя, MAC отправителя, EtherType, данные, FCS; broadcast - `ff:ff:ff:ff:ff:ff`.
* ARP связывает IPv4-адрес с MAC в пределах канала; в IPv6 для этого служит NDP.
* Узел спрашивает MAC адресата, если тот в подсети, и MAC шлюза, если нет.
* Маршрутизатор выбирает строку таблицы по самому длинному префиксу, затем по metric; `0.0.0.0/0` - маршрут по умолчанию.
* На каждом хопе MAC-адреса в кадре заменяются, IP-адреса остаются прежними, TTL уменьшается.
