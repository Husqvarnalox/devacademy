## Письмо в конвертах

Когда браузер отправляет запрос, он не «кидает байты в провод». Данные проходят **вниз по стеку протоколов**, и каждый уровень кладёт их в свой «конверт» с адресом на своём языке:

* **приложение** (HTTP, DNS) формирует сообщение;
* **транспорт** (TCP, UDP) добавляет заголовок с номерами **портов**: для какой программы эти данные;
* **сеть** (IP) добавляет заголовок с **IP-адресами**: между какими компьютерами и по каким сетям доставлять;
* **канал** (Ethernet, Wi-Fi) добавляет заголовок с **MAC-адресами**: кому на этом проводе отдать кадр прямо сейчас.

Получатель делает всё наоборот: снимает конверты снизу вверх. Это и есть **инкапсуляция**. Благодаря ей уровни независимы: IP не знает, Ethernet под ним или Wi-Fi, а HTTP не знает, TCP под ним или QUIC.

У каждого канала есть предел размера: **MTU** (Maximum Transmission Unit), самый большой IP-пакет, который канал примет целиком. Для Ethernet это 1500 байт. Если пакет больше, его нужно разрезать на **фрагменты** или (если резать нельзя) отбросить и сообщить отправителю.

Эти идеи пригодятся во всём курсе. В этом уроке мы научимся считать: сколько байт реально уходит в провод и на сколько кусков разрежется большая датаграмма. Программы работают с байтами и текстом, без сокетов, как в уроке про [HTTP на Node.js](lesson:nodejs.fundamentals.http-fundamentals), где логика тоже вынесена из сетевого кода. Для работы с двоичными данными в Python пригодится модуль `struct` ([json, csv и struct](lesson:python.stdlib.json-csv-struct)).

## OSI, TCP/IP, PDU и расчёт фрагментации

**Две модели.** Эталонная модель OSI - семь уровней: физический, канальный, сетевой, транспортный, сеансовый, представления, прикладной. Стек TCP/IP на практике сворачивает верхние три уровня в один:

| OSI | TCP/IP | Примеры | PDU (единица данных) |
|---|---|---|---|
| 7-5 прикладной, представления, сеансовый | прикладной | HTTP, DNS, TLS | сообщение |
| 4 транспортный | транспортный | TCP, UDP, QUIC | сегмент (TCP), датаграмма (UDP) |
| 3 сетевой | межсетевой (Internet) | IPv4, IPv6, ICMP | пакет |
| 2 канальный | канальный (Link) | Ethernet, Wi-Fi, ARP | кадр |
| 1 физический | (за пределами модели) | кабель, радио | биты |

Номера «уровень 2» и «уровень 3» в жаргоне (L2-коммутатор, L3-маршрутизатор) взяты из OSI.

**Инкапсуляция в числах (Ethernet, IPv4 без опций, UDP).**

```text
[Ethernet 14][IPv4 20][UDP 8][данные приложения ...][FCS 4]
 |<------------- кадр ---------------------------------->|
         |<--- IP-пакет, не больше MTU --->|
```

Ethernet добавляет 14 байт заголовка (MAC получателя 6, MAC отправителя 6, EtherType 2) и 4 байта FCS в хвосте. EtherType говорит, что внутри: `0x0800` - IPv4, `0x86DD` - IPv6, `0x0806` - ARP. В IP-заголовке поле Protocol говорит, что внутри: 6 - TCP, 17 - UDP, 1 - ICMP.

**MTU и MSS.** MTU - предел IP-пакета (заголовок IP плюс данные). Размер кадра больше на накладные расходы канала. MSS (Maximum Segment Size) - предел данных в одном TCP-сегменте: `MSS = MTU - заголовок IP - заголовок TCP`, для Ethernet 1500 - 20 - 20 = 1460. TCP сам режет поток под MSS, поэтому фрагментация IP чаще встречается у UDP.

**Фрагментация IPv4.** Если размер IP-пакета превышает MTU и бит DF сброшен, узел делит поле данных на фрагменты:

* у каждого фрагмента свой IP-заголовок (копия исходного с изменёнными полями), поэтому на данные остаётся `MTU - заголовок`;
* поле **Fragment Offset** занимает 13 бит и измеряется в **блоках по 8 байт**, поэтому данные в каждом фрагменте, кроме последнего, обязаны быть кратны 8: `(MTU - 20) // 8 * 8`;
* флаг **MF** (More Fragments) равен 1 у всех фрагментов, кроме последнего;
* все фрагменты имеют одинаковое поле Identification; собирает пакет только получатель, а потеря любого фрагмента означает потерю всей датаграммы.

Если DF=1, маршрутизатор отбрасывает пакет и возвращает ICMP 'Destination Unreachable, fragmentation needed' с MTU канала: так работает обнаружение Path MTU (PMTUD). Транспортный TCP использует его, чтобы выбрать MSS. В IPv6 фрагментирует только отправитель, а минимальный MTU канала - 1280 байт.

Накладные расходы заголовков влияют на эффективность: чем меньше полезных данных в кадре, тем ниже доля `payload / on-the-wire`. Для 1000 байт UDP-данных это 95,6 %, для одного байта - около 2 %.

## Примеры

**Собираем кадр вручную.** Модуль `struct` упаковывает числа в байты в сетевом порядке (`!` - big-endian). Построим Ethernet-кадр с IPv4 и UDP и посмотрим на размеры каждого слоя. Контрольные суммы пока нули: ими займёмся в уроке про [заголовок IPv4](lesson:networking.fundamentals.ipv4-header-and-checksum).

```python run
import struct

payload = b"hello, network"
udp = struct.pack("!HHHH", 5353, 9999, 8 + len(payload), 0) + payload
ip = struct.pack("!BBHHHBBH4s4s", 0x45, 0, 20 + len(udp), 0x1234, 0x4000, 64, 17, 0,
                 bytes([192, 168, 0, 10]), bytes([192, 168, 0, 20]))
eth = bytes.fromhex("aabbccddeeff") + bytes.fromhex("112233445566") + struct.pack("!H", 0x0800)
frame = eth + ip + udp

print("payload  :", len(payload))
print("UDP      :", len(udp), "(8 + data)")
print("IP packet:", len(ip + udp), "(20 + UDP)")
print("frame    :", len(frame), "(14 + IP packet, без FCS)")
print("ethertype:", hex(int.from_bytes(frame[12:14], "big")))
print("first 34 bytes:", frame[:34].hex(" "))
```
```output
payload  : 14
UDP      : 22 (8 + data)
IP packet: 42 (20 + UDP)
frame    : 56 (14 + IP packet, без FCS)
ethertype: 0x800
first 34 bytes: aa bb cc dd ee ff 11 22 33 44 55 66 08 00 45 00 00 2a 12 34 40 00 40 11 00 00 c0 a8 00 0a c0 a8 00 14
```

Обратите внимание: `0x4000` в поле флагов и смещения - это DF=1 и смещение 0. Разбор чужого кадра идёт теми же срезами в обратную сторону.

**Счёт фрагментов.** Для UDP-датаграммы 3000 байт данных по Ethernet (MTU 1500):

```python run
mtu, ip_header, udp_header = 1500, 20, 8
data = 3000 + udp_header                     # то, что должен перенести IP
per_fragment = (mtu - ip_header) // 8 * 8    # кратно 8
offset = 0
n = 0
while offset < data:
    size = min(per_fragment, data - offset)
    more = int(offset + size < data)
    n += 1
    print(f"#{n}: offset_field={offset // 8} data={size} mf={more}")
    offset += size
print("fragments:", n, "per_fragment:", per_fragment)
```
```output
#1: offset_field=0 data=1480 mf=1
#2: offset_field=185 data=1480 mf=1
#3: offset_field=370 data=48 mf=0
fragments: 3 per_fragment: 1480
```

Смещение второго фрагмента 185: 1480 / 8 = 185. Если бы данных на фрагмент мы взяли 1481 (не кратно 8), поле смещения нельзя было бы записать точно.

**Накладные расходы.** Один байт данных в UDP по Ethernet занимает в проводе кадр минимального размера. Формула эффективности:

```python run
def efficiency(payload, headers):
    return 100 * payload / (payload + headers)

overhead = 14 + 20 + 8 + 4   # Ethernet + IP + UDP + FCS
for size in (1, 100, 1000, 1472):
    print(f"{size:5d} байт -> {efficiency(size, overhead):5.1f}%")
```
```output
    1 байт ->   2.1%
  100 байт ->  68.5%
 1000 байт ->  95.6%
 1472 байт ->  97.0%
```

Для малых сообщений заголовки съедают почти весь кадр (на практике Ethernet дополняет слишком короткий кадр до минимума в 64 байта вместе с FCS, что здесь не учтено).

## Типичные ошибки

* **Путать MTU и размер кадра.** MTU 1500 включает заголовок IP, но не включает 14 байт Ethernet и 4 байта FCS.
* **Считать заголовок транспорта в каждом фрагменте.** UDP- или TCP-заголовок есть только в первом фрагменте: он лежит внутри данных IP, а IP режет данные как непрозрачный блок. Копию заголовка получает только IP.
* **Брать данные во фрагменте не кратными 8.** Смещение измеряется блоками по 8 байт, поэтому все фрагменты, кроме последнего, имеют размер, делящийся на 8 (при MTU 1500 это 1480, при MTU 576 - 552, а не 556).
* **Записывать смещение в байтах.** В заголовке хранится смещение / 8.
* **Забывать про DF.** Современные TCP-стеки ставят DF=1 и подбирают размер сегмента, а не полагаются на фрагментацию.
* **Фрагментировать TCP-поток «руками».** TCP сам делит поток по MSS; фрагментация IP для него - плохой сценарий (потеря одного фрагмента ведёт к повтору всего сегмента).
* **Считать OSI описанием реального Интернета.** Протоколы TCP/IP не раскладываются на семь уровней аккуратно (TLS находится «между» транспортом и приложением, ARP «между» каналом и сетью).

## Итоги

* Данные проходят вниз по стеку, и каждый уровень добавляет заголовок (канальный - ещё и трейлер FCS); получатель снимает их в обратном порядке.
* TCP/IP: прикладной, транспортный, межсетевой, канальный уровни; PDU - сообщение, сегмент или датаграмма, пакет, кадр.
* MTU ограничивает IP-пакет; кадр больше на накладные расходы канала; MSS ограничивает данные в TCP-сегменте.
* При фрагментации IPv4 данные делятся кратно 8 байтам, смещение хранится в блоках по 8, MF=1 у всех, кроме последнего, а собирает пакет получатель.
* DF=1 заменяет фрагментацию на ICMP-ошибку (основа Path MTU Discovery); IPv6-маршрутизаторы не фрагментируют.
