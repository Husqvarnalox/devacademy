## Зачем балансировать

Один сервер не вытягивает весь трафик и является единственной точкой отказа. Поэтому одинаковых серверов несколько, а перед ними стоит **балансировщик нагрузки** (load balancer): он принимает запросы и распределяет их между серверами, а также проверяет, какие серверы живы (health checks), и перестаёт отправлять трафик на упавшие.

Балансировщики бывают двух основных видов.

* **L4** работает с TCP/UDP-потоками: смотрит на адреса и порты, не разбирая содержимое. Он быстрее и проще, но не знает про HTTP.
* **L7** понимает протокол приложения: читает путь, заголовки, куки; может завершать TLS, маршрутизировать `/api` и `/static` на разные группы серверов, повторять запрос на другом сервере. Работает дороже по ресурсам, но гибче. Про протоколы под ним рассказывали уроки [об эволюции HTTP](lesson:networking.fundamentals.http-evolution) и [UDP и DNS](lesson:networking.fundamentals.udp-and-dns) (DNS - грубая форма балансировки: на одно имя возвращают несколько адресов).

Если серверы **не хранят состояние** (stateless), подойдёт любой алгоритм - запрос может обслужить кто угодно. Но если нужен определённый сервер (например, у него в памяти лежит кэш этого пользователя или этой части данных), нужно **согласованное хеширование**: оно отправляет ключ на «своего» владельца и почти не перемешивает ключи, когда серверы добавляются или пропадают. Это главная тема урока и продолжение [кэширования](lesson:system-design.fundamentals.caching): кэш из десятка серверов нужно уметь разделить между ними так, чтобы смена состава не обнуляла его целиком.

## Алгоритмы выбора сервера

* **Round robin**: сервера по кругу. Просто и равномерно по числу запросов, но игнорирует разную стоимость запросов и разную мощность серверов. **Взвешенный** round robin даёт мощным машинам больше запросов.
* **Least connections**: новый запрос получает сервер с наименьшим числом активных соединений. Хорош для долгих или неравных по стоимости соединений.
* **Случайный выбор из двух** (power of two choices): взять два случайных сервера и выбрать менее загруженный. Почти так же хорош, как least connections, но не требует глобального состояния.
* **Хеширование по ключу** (IP клиента, id пользователя): один и тот же ключ всегда попадает на один сервер. Нужно для «липких» сессий и локального кэша.

## Почему не `hash(key) % N`

Самое простое хеширование - `server = hash(key) % N`. Пока N постоянно, оно работает. Но при смене N почти каждый ключ меняет сервер: ключ остаётся на месте, только если `h mod N == h mod (N + 1)`. Для перехода с 4 на 5 серверов это выполняется для 4 остатков из каждых 20, то есть для 20 % ключей, и переезжают 80 %. Для кэша это катастрофа: после добавления сервера почти все запросы - промахи, и вся нагрузка падает на базу.

## Кольцо согласованного хеширования

Идея Каргера и соавторов: хешируем **и серверы, и ключи** в одно пространство, замкнутое в кольцо. Ключ принадлежит первому серверу, которого встретим, двигаясь по кольцу по часовой стрелке (в сторону возрастания хеша; после максимума переходим к минимуму).

* Новый сервер забирает только те ключи, что лежат между ним и его предшественником на кольце: переезжает в среднем `1/N` всех ключей.
* Упавший сервер отдаёт свои ключи только своему преемнику; остальные ключи не двигаются.

**Виртуальные узлы.** Один сервер, хешированный в одну точку, получает диапазон случайной длины, и нагрузка получается неравномерной. Решение: каждый физический узел занимает `V` точек (хеши `node#0 ... node#V-1`). Диапазоны мельче, их размеры усредняются, а при выходе узла его ключи расходятся по многим соседям, а не валятся на одного (иначе соседа может «добить» каскад отказов). Более мощному серверу дают больше точек.

**Реализация.** Точки хранят в отсортированном массиве; поиск владельца - бинарный поиск `bisect_left` за `O(log(N*V))`; добавление и удаление узла - `O(V log(N*V))`.

**Что остаётся за кадром.** Репликация: ключ хранят на следующих `R` различных физических узлах по кольцу (так делает Dynamo), горячие ключи, учёт гетерогенных машин. Альтернативы кольцу - rendezvous hashing и jump consistent hash.

## Сколько ключей переезжает

Сравним `hash % N` и кольцо при переходе от 4 серверов к 5 на 10 000 ключей. Хеш - первые 8 hex-символов md5 (как в упражнении), так что результат детерминирован.

```python run
import bisect
import hashlib


def h(text):
    return int(hashlib.md5(text.encode()).hexdigest()[:8], 16)


def build_ring(nodes, vnodes):
    return sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))


def route(ring, key):
    i = bisect.bisect_left(ring, (h(key), ""))
    return ring[i % len(ring)][1]


keys = [f"key{i}" for i in range(10000)]
old = ["n1", "n2", "n3", "n4"]
new = old + ["n5"]

mod_moved = sum(1 for k in keys if h(k) % 4 != h(k) % 5)
print("mod N moved:", mod_moved, "of", len(keys))

ring_old, ring_new = build_ring(old, 100), build_ring(new, 100)
ring_moved = sum(1 for k in keys if route(ring_old, k) != route(ring_new, k))
print("ring moved:", ring_moved, "of", len(keys))
```
```output
mod N moved: 8028 of 10000
ring moved: 2194 of 10000
```

Около 80 % против примерно 20 %: на кольце ключи переезжают только к новому серверу, остальные остаются на местах.

## Виртуальные узлы выравнивают нагрузку

Раскладываем те же 10 000 ключей по пяти узлам и смотрим отношение самой нагруженной доли к идеальной (чем ближе к 1.0, тем равномернее).

```python run
import bisect
import hashlib
from collections import Counter


def h(text):
    return int(hashlib.md5(text.encode()).hexdigest()[:8], 16)


def imbalance(vnodes):
    nodes = [f"n{i}" for i in range(5)]
    ring = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
    load = Counter()
    for k in range(10000):
        i = bisect.bisect_left(ring, (h(f"key{k}"), ""))
        load[ring[i % len(ring)][1]] += 1
    return max(load.values()) / (10000 / 5)


for v in (1, 10, 100, 1000):
    print(f"vnodes={v}: max/ideal = {imbalance(v):.2f}")
```
```output
vnodes=1: max/ideal = 2.05
vnodes=10: max/ideal = 1.38
vnodes=100: max/ideal = 1.06
vnodes=1000: max/ideal = 1.08
```

При одной точке на узел самый нагруженный сервер получает заметно больше доли; с сотней виртуальных узлов отклонение составляет единицы процентов (дальнейший рост числа точек выигрыш почти не даёт и увеличивает размер кольца).

## Round robin и least connections

Три сервера, соединения разной длительности. Round robin раздаёт по кругу, least connections смотрит на текущую загрузку. Время логическое: соединение `i` длится `d[i]` тактов, такт - один новый запрос.

```python run
durations = [9, 1, 1, 9, 1, 1, 9, 1, 1, 9, 1, 1]   # каждое третье соединение тяжёлое


def simulate(policy):
    busy_until = [0, 0, 0]
    peak = 0
    for t, d in enumerate(durations):
        active = [max(0, b - t) for b in busy_until]
        if policy == "rr":
            s = t % 3
        else:
            s = active.index(min(active))      # наименьшая загрузка, при равенстве - меньший номер
        busy_until[s] = max(busy_until[s], t) + d
        peak = max(peak, max(max(0, b - t) for b in busy_until))
    return peak


print("round robin, max backlog:", simulate("rr"))
print("least loaded, max backlog:", simulate("ll"))
```
```output
round robin, max backlog: 27
least loaded, max backlog: 11
```

Round robin отправляет все тяжёлые соединения на один и тот же сервер, и очередь у него растёт; выбор менее загруженного сервера распределяет тяжёлые соединения по всем.

## Типичные ошибки

* **Использовать `hash(key) % N` для кэша или шардов, число которых меняется.** Любое изменение N перемешивает почти всё.
* **Один узел - одна точка на кольце.** Нагрузка получается неравномерной; нужны десятки-сотни виртуальных узлов.
* **Брать хеш с неравномерным распределением** (например, длину строки, сумму кодов). Нужна хорошая хеш-функция; в упражнении хеш фиксирован, чтобы результаты совпадали.
* **Забыть про замыкание кольца.** Ключ с хешем больше всех точек принадлежит первой точке, а не «никому».
* **Балансировать round robin долгие соединения.** Тяжёлые соединения могут накопиться на одном сервере.
* **Не проверять здоровье серверов.** Балансировщик без health checks исправно шлёт трафик на упавший узел.
* **Считать, что согласованное хеширование решает горячие ключи.** Один очень популярный ключ всё равно попадает на один узел.
* **Путать перемещение ключей с перемещением данных.** После смены владельца данные нужно физически перенести или прогреть кэш заново.

## Итоги

* Балансировщик распределяет запросы и скрывает отказы серверов; L4 быстрее и проще, L7 понимает HTTP.
* Round robin прост, least connections лучше для разных по длительности соединений, хеширование по ключу даёт привязку к серверу.
* `hash % N` перемещает почти все ключи при смене N; кольцо согласованного хеширования - около `1/N`.
* Виртуальные узлы выравнивают нагрузку и размазывают ключи упавшего узла по многим соседям.
* Хеш-функция и порядок обхода должны быть детерминированы - тогда перебалансировку можно предсказать и проверить.
