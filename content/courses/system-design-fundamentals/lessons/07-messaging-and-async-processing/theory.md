## Зачем нужна асинхронность

Пользователь загружает фото. Нужно сделать три превью, проверить на запрещённый контент, обновить поисковый индекс и отправить уведомление. Если делать всё внутри HTTP-запроса, ответ занимает секунды, а любой сбой в цепочке ломает загрузку целиком. Выход: принять запрос, записать сообщение «фото загружено» в брокер и сразу ответить. Остальное сделают **потребители** (consumers) в своём темпе.

Брокер сообщений даёт три вещи:

1. **Развязку во времени.** Продюсеру не нужно, чтобы потребитель был жив именно сейчас.
2. **Сглаживание пиков.** Всплеск нагрузки превращается в очередь, которую потребители разбирают с постоянной скоростью.
3. **Независимое масштабирование.** Добавить потребителей проще, чем ускорить синхронный путь.

Цена: ответ приходит не сразу, а система становится распределённой со всеми последствиями из урока про [согласованность и идемпотентность](lesson:system-design.fundamentals.consistency-and-idempotency): сообщения могут прийти дважды. Параллелизм внутри одного процесса описан в [моделях конкурентности](lesson:python.concurrency.concurrency-models); здесь речь о нескольких машинах.

## Очередь и журнал

В **классической очереди** (например, стандартная очередь SQS) сообщение выдаётся потребителю и после подтверждения удаляется. Очередь не помнит, что было прочитано раньше, и повторно прочитать нельзя.

В **журнале** (Kafka и подобные системы) сообщения добавляются в конец и хранятся заданное время независимо от чтения. У каждого сообщения есть **смещение** (offset): порядковый номер в партиции. Потребитель сам держит позицию чтения. Отсюда следуют полезные свойства: несколько независимых групп читают один поток, а ошибку в обработчике можно исправить и перечитать историю с нужного смещения.

## Партиции и порядок

Тема делится на **партиции**, каждая из которых упорядоченный журнал. Продюсер выбирает партицию по ключу, обычно `hash(key) mod P`, поэтому все сообщения с одним ключом оказываются в одной партиции. Это тот же приём, что и в [партиционировании данных](lesson:system-design.fundamentals.partitioning-and-replication). Порядок гарантируется только внутри партиции; между партициями общего порядка нет. Хотите порядок событий заказа, используйте id заказа как ключ.

Число партиций задаёт верхний предел параллелизма: сообщения одной партиции обрабатывает один потребитель группы.

## Группа потребителей

**Группа** делит партиции между своими участниками: каждая партиция принадлежит ровно одному потребителю. Если потребителей больше, чем партиций, лишние простаивают. Когда участник входит, выходит или падает, происходит **ребалансировка**: партиции перераспределяются. В упражнении используется простое правило: потребители сортируются по имени, партиция `p` достаётся потребителю с индексом `p mod M`.

Группа хранит **зафиксированное смещение** (committed offset) для каждой партиции. После ребалансировки новый владелец продолжает с него, а не с того места, где остановился прежний.

## Семантика доставки

Всё определяется порядком двух действий: обработать сообщение и зафиксировать смещение.

* Смещение **до** обработки: при сбое между ними сообщение потеряно. Это **at-most-once**.
* Смещение **после** обработки: при сбое между ними сообщение будет обработано снова. Это **at-least-once**, обычный выбор по умолчанию.
* **Exactly-once** как «эффект ровно один раз» достигается комбинацией at-least-once и идемпотентного обработчика (ключ дедупликации, как в предыдущем уроке) или транзакционной записью результата вместе со смещением.

Поэтому в упражнении сбой без `COMMIT` порождает `REDELIVERY`: прогресс упавшего потребителя не сохранился.

## Перегрузка, повторы и DLQ

Если потребители медленнее продюсеров, **лаг** (разница между длиной журнала и зафиксированным смещением) растёт. Варианты: добавить потребителей (но не больше числа партиций), ограничить приём (**back-pressure**: отказ или замедление продюсера), сбрасывать нагрузку (load shedding).

Сообщение, которое всегда падает («ядовитое»), нельзя бесконечно повторять: оно заблокирует партицию. Обычно задают число попыток с увеличивающейся задержкой, после чего сообщение уходит в **очередь недоставленных сообщений** (dead-letter queue, DLQ) для ручного разбора. Повторы возможны и по другим причинам, так что обработчик должен быть идемпотентным.

## Позиция и зафиксированное смещение

Минимальная модель одной партиции: потребитель двигает позицию, а фиксирует её отдельно. Сбой возвращает позицию к зафиксированному значению.

```python run
log = ["a", "b", "c", "d", "e"]
committed = 0
position = 0

def poll(n):
    global position
    out = []
    while n > 0 and position < len(log):
        out.append(log[position])
        position += 1
        n -= 1
    return out

print("poll:", poll(3))
committed = position
print("committed:", committed)
print("poll:", poll(2))
position = committed   # crash: uncommitted progress is lost
print("after crash:", poll(5))
```
```output
poll: ['a', 'b', 'c']
committed: 3
poll: ['d', 'e']
after crash: ['d', 'e']
```

Сообщения `d` и `e` обработаны дважды: это и есть at-least-once.

## Когда смещение фиксируют: потеря или дубликат

Сымитируем сбой при обработке сообщения `c`. Если смещение фиксируется до обработки, оно теряется, если после, обрабатывается повторно.

```python run
def run(commit_first):
    log = ["a", "b", "c", "d"]
    committed = 0
    handled = []
    crashed = False
    while committed < len(log):
        msg = log[committed]
        if commit_first:
            committed += 1
        if msg == "c" and not crashed:
            crashed = True
            if not commit_first:
                pass            # restart: offset was not moved
            continue            # crash while handling c
        handled.append(msg)
        if not commit_first:
            committed += 1
    return handled

print("commit before:", run(True))
print("commit after: ", run(False))
```
```output
commit before: ['a', 'b', 'd']
commit after:  ['a', 'b', 'c', 'd']
```

В первом режиме `c` потеряно, во втором будет обработано со второй попытки (в этой модели сбой единичный, поэтому дубликата нет, но сообщение гарантированно дойдёт).

## Ключ, партиция и порядок

Фиксированный хеш (md5) назначает ключи партициям. События одного ключа остаются в порядке, между ключами порядок не определён.

```python run
import hashlib

P = 3
parts = [[] for _ in range(P)]
events = [("order1", "created"), ("order2", "created"), ("order1", "paid"),
          ("order3", "created"), ("order2", "paid"), ("order1", "shipped")]
for key, event in events:
    p = int(hashlib.md5(key.encode()).hexdigest()[:8], 16) % P
    parts[p].append(f"{key}:{event}")
for p, items in enumerate(parts):
    print(p, items)
```
```output
0 []
1 ['order1:created', 'order2:created', 'order1:paid', 'order2:paid', 'order1:shipped']
2 ['order3:created']
```

Внутри каждой партиции события одного заказа идут в порядке создания.

## Типичные ошибки

* **Считать, что порядок глобальный.** Он есть только внутри партиции; без осмысленного ключа порядок событий одной сущности не гарантирован.
* **Фиксировать смещение до обработки** и удивляться потерянным сообщениям.
* **Необработанные дубликаты.** При at-least-once обработчик без идемпотентности (ключ дедупликации, `INSERT ... ON CONFLICT`, версия) будет дважды списывать деньги.
* **Больше потребителей, чем партиций.** Лишние простаивают; параллелизм ограничен числом партиций, поэтому его закладывают заранее.
* **Бесконечные повторы «ядовитого» сообщения.** Нужны лимит попыток, задержка между ними и DLQ.
* **Неограниченная очередь вместо back-pressure.** Перегрузка превращается в рост задержки и памяти, а не исчезает.

## Итоги

* Брокер развязывает продюсеров и потребителей, сглаживает пики и масштабируется независимо.
* Очередь удаляет прочитанное; журнал хранит сообщения, а потребитель держит смещение.
* Порядок гарантируется внутри партиции; ключ определяет партицию.
* В группе каждая партиция принадлежит одному потребителю; активных потребителей не больше числа партиций.
* Фиксация после обработки даёт at-least-once, до обработки - at-most-once; эффект «ровно один раз» делается идемпотентным обработчиком.
* От перегрузки спасают ограниченные очереди, back-pressure, лимит попыток и DLQ.
