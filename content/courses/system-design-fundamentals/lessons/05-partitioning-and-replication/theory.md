## Два способа распределить данные

Когда данные или нагрузка не помещаются на один сервер, их делят двумя независимыми способами.

* **Партиционирование (шардирование)**: разные данные лежат на разных узлах. Пользователи с `id` от 1 до 1 млн - на шарде A, остальные - на шарде B. Так масштабируют **объём** и **запись**: каждый шард принимает только свою долю.
* **Репликация**: копии одних и тех же данных на нескольких узлах. Так повышают **доступность** (узел упал - есть копия) и **пропускную способность чтения** (читать можно с любой копии), а также приближают данные к пользователям.

Обычно используют оба: данные разбиты на шарды, а каждый шард реплицирован на несколько узлов. Репликация не заменяет резервное копирование (ошибочное удаление мгновенно разойдётся по копиям) и не ускоряет запись, потому что каждую запись нужно применить на каждой реплике.

Главная трудность репликации - согласованность: пока копии обновляются, они на мгновение расходятся. Если читатель попал на отстающую копию, он увидит старое значение. Дальше - как организовать копии и сколько узлов опрашивать, чтобы читатель видел последнюю запись. Эта тема продолжается в следующем уроке про [согласованность и CAP](lesson:system-design.fundamentals.consistency-and-idempotency); а то, что транзакции внутри одной базы дают гарантии, которых нет между репликами, показывает урок про [транзакции и изоляцию](lesson:databases.sql.transactions-and-isolation).

## Стратегии шардирования

* **По диапазону**: каждый шард отвечает за непрерывный диапазон ключей (`A-F`, `G-M`...). Диапазонные запросы читают один-два шарда, а порядок ключей сохраняется. Опасность: **горячие точки**. Монотонные ключи (время, автоинкремент) направляют все новые записи в последний шард.
* **По хешу**: `шард = hash(key) mod N` или кольцо [согласованного хеширования](lesson:system-design.fundamentals.load-balancing-and-consistent-hashing). Нагрузка выравнивается, но диапазонные запросы нужно слать на все шарды, а при `mod N` смена числа шардов перемешивает данные.
* **По справочнику (directory)**: отдельная таблица `ключ -> шард`. Гибко (можно переносить отдельных клиентов), но справочник - ещё одна система, которая сама должна быть быстрой и надёжной.

**Горячие точки** возникают и при хорошем хеше: одна знаменитость, один популярный товар. Лечат разбиением горячего ключа (добавляют случайный суффикс и собирают результаты), кэшем, выделением отдельного шарда под самых тяжёлых клиентов. Приём **shuffle sharding** ограничивает радиус поражения: каждого клиента привязывают к небольшому случайному подмножеству шардов, и проблемный клиент не выбивает всех остальных.

Запросы, затрагивающие несколько шардов (соединения, транзакции), дороги: нужны распределённые транзакции или отказ от строгих гарантий. Поэтому ключ шардирования выбирают так, чтобы самые частые запросы попадали на один шард.

## Репликация лидер-фолловер

Один узел - **лидер**, остальные - **фолловеры**. Запись идёт на лидера, он пишет журнал изменений и рассылает его фолловерам; читать можно с фолловеров.

* **Синхронная** репликация: лидер подтверждает запись после того, как её применили фолловеры. Нет потерь при отказе лидера, но запись медленнее и зависит от самой медленной реплики.
* **Асинхронная**: лидер подтверждает сразу, фолловеры догоняют. Запись быстра, но возникает **лаг репликации**: читатель на фолловере видит старое значение, а при отказе лидера последние записи могут пропасть.
* **Полусинхронная**: ждём одного-двух фолловеров, остальные асинхронно.

Типичные аномалии при чтении с отстающего фолловера: пользователь только что записал данные и не видит их («читай свои записи»), или видит новое значение, а потом старое (откат во времени). Лечат чтением своих данных с лидера, привязкой пользователя к реплике, передачей версии в запросе.

## Кворумы без лидера

В системах типа Dynamo нет выделенного лидера: клиент (или координатор) отправляет запись на `N` реплик и считает её успешной, когда ответили `W`; читает у `R` реплик и выбирает значение с наибольшей версией.

**Условие пересечения**: `R + W > N`. Тогда любые `W` реплик записи и любые `R` реплик чтения имеют хотя бы одну общую, и чтение видит последнюю успешную запись. Пример: `N = 3`, `W = 2`, `R = 2`. Выбор параметров - компромисс:

* `W = N`, `R = 1`: быстрое чтение, но одна упавшая реплика останавливает запись;
* `W = 1`, `R = N`: быстрая запись, дорогое чтение;
* `W = R = (N + 1) / 2`: переносит отказ минимального меньшинства.

Допустимое число отказов: для записи `N - W`, для чтения `N - R`. Если `R + W <= N`, возможны устаревшие чтения; их ослабляют фоновой синхронизацией (anti-entropy), чтением с починкой (read repair) и подсказанной передачей (hinted handoff). Но даже при `R + W > N` кворумы не дают линеаризуемости полностью: при одновременных записях, нестрогих кворумах и отказах возможны аномалии, и нужно разрешать конфликты версий.

## Горячая точка: диапазон против хеша

Моделируем 1000 новых записей с монотонными ключами `1000..1999` на четырёх шардах. По диапазону границы фиксированы заранее (`0-499`, `500-999`, `1000-1499`, а последний шард принимает всё от `1500`). По хешу шард равен первым 8 hex-символам md5 по модулю 4.

```python run
import hashlib

keys = range(1000, 2000)           # монотонные ключи: id заказов подряд


def range_shard(key):
    return min(key // 500, 3)      # границы 0-499, 500-999, 1000-1499, 1500+


def hash_shard(key):
    return int(hashlib.md5(str(key).encode()).hexdigest()[:8], 16) % 4


for name, f in (("range", range_shard), ("hash", hash_shard)):
    load = [0, 0, 0, 0]
    for k in keys:
        load[f(k)] += 1
    print(name, load)
```
```output
range [0, 0, 500, 500]
hash [238, 242, 255, 265]
```

При разбиении по диапазону новые записи делят всего два шарда (а будущие - только последний). Хеш выравнивает нагрузку, ценой того, что запрос «заказы с 1200 по 1300» придётся слать на все четыре шарда.

## Условие R + W > N: перебор

Для `N = 5` проверим перебором: существует ли набор из `R` реплик, не пересекающийся ни с каким набором из `W` реплик записи? Если существует - возможна пропущенная запись.

```python run
from itertools import combinations

N = 5
replicas = range(N)
for W in (1, 3, 4):
    row = []
    for R in (1, 2, 3):
        overlap_always = all(
            set(w) & set(r)
            for w in combinations(replicas, W)
            for r in combinations(replicas, R)
        )
        row.append(f"R={R}:{'safe' if overlap_always else 'stale?'}")
    print(f"W={W}", row, "R+W>N:", [R + W > N for R in (1, 2, 3)])
```
```output
W=1 ['R=1:stale?', 'R=2:stale?', 'R=3:stale?'] R+W>N: [False, False, False]
W=3 ['R=1:stale?', 'R=2:stale?', 'R=3:safe'] R+W>N: [False, False, True]
W=4 ['R=1:stale?', 'R=2:safe', 'R=3:safe'] R+W>N: [False, True, True]
```

Перебор совпадает с формулой: пересечение гарантируется ровно тогда, когда `R + W > N`.

## Лаг репликации

Лидер применяет запись сразу, фолловеры - через заданное число тактов. Читатель на фолловере видит старое значение, пока изменение не дойдёт до него. Время логическое.

```python run
leader = {"x": 0}
followers = [{"x": 0}, {"x": 0}]
lags = [1, 3]                       # через сколько тактов фолловер применит запись
pending = []                        # (когда_применить, фолловер, ключ, значение)

for t in range(1, 6):
    if t == 2:
        leader["x"] = 42            # запись на лидере в такт 2
        for i, lag in enumerate(lags):
            pending.append((t + lag, i, "x", 42))
    for item in [p for p in pending if p[0] == t]:
        _, i, k, v = item
        followers[i][k] = v
    print(f"t={t} leader={leader['x']} followers={[f['x'] for f in followers]}")
```
```output
t=1 leader=0 followers=[0, 0]
t=2 leader=42 followers=[0, 0]
t=3 leader=42 followers=[42, 0]
t=4 leader=42 followers=[42, 0]
t=5 leader=42 followers=[42, 42]
```

Фолловер 0 догоняет в такт 3, фолловер 1 - в такт 5; между ними читатели видят разные значения одного ключа.

## Типичные ошибки

* **Шардировать по монотонному ключу.** Все новые записи попадают в один шард.
* **`hash % N` для шардов с меняющимся числом.** Добавление шарда перемешивает почти все данные; нужно согласованное хеширование или виртуальные шарды.
* **Считать, что реплики - это резервная копия.** Ошибочное удаление и порча данных реплицируются.
* **Читать с фолловера сразу после записи на лидер.** Из-за лага пользователь не увидит собственных изменений.
* **Выбрать `R + W <= N` и ожидать актуальных чтений.** Устаревшее значение возможно по определению.
* **Считать `R + W > N` полной гарантией согласованности.** Конкурирующие записи, нестрогие кворумы и отказы требуют разрешения конфликтов.
* **Выбрать ключ шардирования без анализа запросов.** Частые запросы по другому полю превращаются в обход всех шардов.
* **Забыть о перебалансировке.** Перенос шарда нагружает сеть и диски и должен идти постепенно, без остановки обслуживания.

## Итоги

* Партиционирование делит данные (масштаб записи и объёма), репликация копирует их (доступность и чтение).
* Шардирование по диапазону сохраняет порядок, но создаёт горячие точки; по хешу выравнивает нагрузку, но ломает диапазонные запросы.
* Лидер-фолловер: запись на лидера; асинхронная репликация даёт лаг и риск потерь, синхронная - задержки.
* Кворум: `R + W > N` гарантирует пересечение наборов; допустимые отказы - `N - W` для записи и `N - R` для чтения.
* Пересечение кворумов не заменяет разрешение конфликтов и не даёт строгой линеаризуемости.
* Дальше: что именно гарантируют реплики и как жить с ретраями - [согласованность и идемпотентность](lesson:system-design.fundamentals.consistency-and-idempotency).
