## Зачем ограничивать частоту

Любой общий сервис нужно защищать от клиентов, которые шлют слишком много запросов: по ошибке (бесконечный цикл повторов), из жадности (скрейпер) или со злым умыслом (перебор паролей, DDoS). Без ограничения один клиент может занять все ресурсы, и остальные получат отказ. **Ограничитель частоты** (rate limiter) считает запросы каждого клиента и отвечает на лишние отказом: в HTTP это код `429 Too Many Requests` и, желательно, заголовок `Retry-After`.

Ограничение ставят в нескольких местах: на шлюзе перед всей системой, в сервисе для дорогих операций, на клиенте (чтобы не превышать чужой лимит). Это родственная, но отличная задача от балансировки: [балансировщик](lesson:system-design.fundamentals.load-balancing-and-consistent-hashing) распределяет нагрузку между серверами, а лимитер решает, чью нагрузку вообще принимать.

Сразу видна трудность: «100 запросов в минуту» можно понимать по-разному. Минута календарная или «любая последовательная минута»? Допустим ли всплеск из 100 запросов за одну секунду? Разные алгоритмы дают разные ответы. Урок разбирает пять.

<!-- section: precise -->
## Пять алгоритмов

Все они хранят состояние **на ключ** (клиент, ключ API, IP), то есть память растёт с числом клиентов, а не запросов.

**1. Fixed window (фиксированное окно).** Время делится на окна длины `W` (`окно = t // W`), для каждого окна свой счётчик. Запрос проходит, если счётчик меньше лимита. Память: одно число на клиента. Недостаток: **всплеск на границе окон**. Клиент отправляет `L` запросов в последний момент одного окна и ещё `L` в первый момент следующего: за пару миллисекунд проходит `2L`.

**2. Sliding log (скользящий журнал).** Хранится временная метка каждого принятого запроса. Новый запрос проходит, если за последние `W` миллисекунд принято меньше `L`. Точен и без границ, но память порядка `L` меток на клиента.

**3. Sliding window counter (скользящее окно со счётчиками).** Компромисс: два счётчика (текущее и предыдущее окно) и взвешенная оценка: `est = prev * (W - off) / W + cur`, где `off` - сколько прошло от начала текущего окна. Предыдущее окно вносит вклад пропорционально той его доле, что ещё «видно» в скользящем окне. Память мала, граничный всплеск сильно ослаблен. Оценка приблизительна, потому что предполагает равномерность запросов в предыдущем окне.

**4. Token bucket (ведро токенов).** В ведре до `B` токенов; токены добавляются со скоростью `R` за период. Запрос стоит токены и проходит, если их достаточно. Допускает **всплеск** до `B` запросов, а в долгосрочной перспективе скорость не больше `R`. Состояние: число токенов и время последнего пополнения; ведро пополняют лениво, при запросе, без фоновых задач. Самый распространённый выбор для API.

**5. Leaky bucket (дырявое ведро).** Запросы поступают в очередь ограниченного размера, а обрабатываются с постоянной скоростью («утечка»). Если очередь полна, запрос отклоняется. Выход **сглажен** и равномерен, всплеск превращается в задержку. Годится, когда нижележащая система любит ровную нагрузку. Существует и вариант-счётчик («как метр»): уровень воды растёт с запросами и убывает со временем, запрос отклоняется при переполнении, но очередь не хранится.

| Алгоритм | Память на ключ | Всплеск | Точность |
| --- | --- | --- | --- |
| Fixed window | O(1) | до 2L на границе | низкая |
| Sliding log | O(L) | нет | точная |
| Sliding window counter | O(1) | ослаблен | приближённая |
| Token bucket | O(1) | до B | точная для модели |
| Leaky bucket | O(1) или очередь | сглажен | точная для модели |

## Распределённый лимитер и ответ клиенту

Когда серверов несколько, счётчик должен быть общим, иначе клиент получит лимит, умноженный на число серверов. Обычно счётчики держат в быстром хранилище (например, в Redis) и обновляют атомарно; цена - дополнительный сетевой запрос и новая точка отказа. Можно делить лимит между серверами заранее или принять неточность. Атомарность нужна по той же причине, что и [в многопоточных программах](lesson:python.concurrency.threading-and-synchronization): «прочитать счётчик, сравнить, увеличить» без блокировки допускает гонку.

Клиенту при отказе возвращают `429` и `Retry-After`. Клиент должен ждать с экспоненциальной задержкой и джиттером, а не повторять сразу, иначе повторы усиливают перегрузку.

## Всплеск на границе окон

Лимит 5 запросов на окно в 1000 мс. Клиент отправляет 5 запросов в конце первого окна и 5 в начале второго. Сравним фиксированное окно и скользящий журнал.

```python run
def fixed_window(times, limit, window):
    counts, allowed = {}, []
    for t in times:
        w = t // window
        if counts.get(w, 0) < limit:
            counts[w] = counts.get(w, 0) + 1
            allowed.append(t)
    return allowed


def sliding_log(times, limit, window):
    log, allowed = [], []
    for t in times:
        log = [u for u in log if u > t - window]   # забываем метки старше окна
        if len(log) < limit:
            log.append(t)
            allowed.append(t)
    return allowed


burst = [996, 997, 998, 999, 999, 1000, 1001, 1002, 1003, 1004]
fixed = fixed_window(burst, 5, 1000)
log = sliding_log(burst, 5, 1000)
print("fixed window allowed:", len(fixed), "in", fixed[-1] - fixed[0] + 1, "ms")
print("sliding log allowed:", len(log), "in", log[-1] - log[0] + 1, "ms")
```
```output
fixed window allowed: 10 in 9 ms
sliding log allowed: 5 in 4 ms
```

Фиксированное окно пропустило все 10 запросов за 9 мс при лимите 5 в секунду, скользящий журнал - только 5. Скользящее окно со счётчиками даёт результат между ними, это вы проверите в задаче.

## Ведро токенов

Ёмкость 3, один токен каждые 1000 мс; время в миллисекундах. Ведро пополняется лениво - пересчётом при запросе - и сдвигает отметку пополнения на целое число периодов.

```python run
class TokenBucket:
    def __init__(self, capacity, refill, period):
        self.capacity, self.refill, self.period = capacity, refill, period
        self.tokens, self.last = capacity, 0

    def allow(self, now, cost=1):
        k = (now - self.last) // self.period
        if k > 0:
            self.tokens = min(self.capacity, self.tokens + k * self.refill)
            self.last += k * self.period
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False


bucket = TokenBucket(3, 1, 1000)
stream = [0, 0, 0, 0, 500, 1000, 1500, 2999, 3000, 8000, 8000, 8000, 8000]
print(["ALLOW" if bucket.allow(t) else "DENY" for t in stream])
```
```output
['ALLOW', 'ALLOW', 'ALLOW', 'DENY', 'DENY', 'ALLOW', 'DENY', 'ALLOW', 'ALLOW', 'ALLOW', 'ALLOW', 'ALLOW', 'DENY']
```

Первые три запроса - всплеск, четвёртый отклонён; затем скорость ограничена одним токеном в секунду; после долгого простоя (8000) снова проходит всплеск, но не больше ёмкости (три запроса). Это и есть смысл ведра.

## Дырявое ведро как метр

Уровень воды падает с постоянной скоростью (1 единица за 100 мс), каждый запрос добавляет 1, вместимость 3. В отличие от токенов, всплеск ограничен ёмкостью, а вытекание гладкое.

```python run
class LeakyBucket:
    def __init__(self, capacity, leak_per_ms):
        self.capacity, self.leak = capacity, leak_per_ms
        self.level, self.last = 0, 0

    def allow(self, now):
        self.level = max(0, self.level - (now - self.last) * self.leak)
        self.last = now
        if self.level + 1 <= self.capacity:
            self.level += 1
            return True
        return False


from fractions import Fraction

bucket = LeakyBucket(3, Fraction(1, 100))
stream = [0, 0, 0, 0, 50, 100, 150, 200, 1000]
print([("ALLOW" if bucket.allow(t) else "DENY") for t in stream])
```
```output
['ALLOW', 'ALLOW', 'ALLOW', 'DENY', 'DENY', 'ALLOW', 'DENY', 'ALLOW', 'ALLOW']
```

Детерминированная дробь `Fraction` избавляет от ошибок округления `float`: в целочисленных симуляторах стоит поступать так же, переходя на целые единицы (например, мс, умноженные на скорость).

## Типичные ошибки

* **Использовать fixed window и считать, что лимит соблюдается «в любую минуту».** На границе окон проходит до `2L`.
* **Присваивать `last = now` при пополнении ведра.** Дробные доли периода теряются, и ведро пополняется медленнее, чем задано; сдвигайте `last` на целое число периодов.
* **Считать отклонённые запросы в счётчике.** Тогда клиент, «стучащийся» после отказа, лишает себя и разрешённых запросов.
* **Хранить журнал меток без очистки.** Память растёт без границ.
* **Делать счётчик в базе без атомарности.** Прочитать-проверить-увеличить без блокировки или атомарной команды допускает гонку; лимит превышается.
* **Один лимит на всех.** Нужен лимит на клиента или ключ, иначе один пользователь исчерпает его для остальных.
* **Не отвечать `Retry-After`.** Клиенты начнут повторять запросы наугад и усугубят перегрузку.
* **Путать ограничение клиента и сброс нагрузки.** Лимитер защищает от одного клиента, сброс нагрузки (load shedding) - сервис от общей перегрузки; нужны оба механизма.
* **Использовать `float` и системные часы в логике, которую хочется проверить.** Время подавайте параметром, вычисляйте в целых числах.

<!-- section: summary -->
## Итоги

* Лимитер защищает общий сервис от чрезмерных клиентов; отказ - `429` с `Retry-After`.
* Fixed window проще всего, но пропускает до `2L` на границе окон; sliding log точен, но хранит метки; sliding window counter - дешёвый компромисс.
* Token bucket разрешает всплеск до ёмкости и ограничивает среднюю скорость; leaky bucket сглаживает выход.
* Состояние хранится на ключ; в распределённой системе счётчик должен быть общим и обновляться атомарно.
* Детерминированный лимитер: время задаётся параметром, вычисления в целых числах.
