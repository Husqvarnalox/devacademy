## Зачем нужен кэш

Кэш - небольшое быстрое хранилище копий данных, которые дорого получать из основного источника. Чтение из памяти занимает доли миллисекунды, запрос в базу с индексом - миллисекунды, сложная агрегация - секунды. Если одни и те же данные читают много раз, копию стоит держать рядом.

Кэш работает благодаря **локальности**: небольшая доля ключей получает большую долю обращений (популярные товары, свежие записи, горячие профили). Эффективность измеряется **долей попаданий** (hit ratio). Среднее время чтения: `h * t_кэша + (1 - h) * t_источника`. Если источник в 100 раз медленнее, то при `h = 50 %` выигрыш меньше двух раз, а при `h = 99 %` - почти в 50 раз. Поэтому «добавить кэш» не лечит систему без локальности.

Три вопроса, которые приходится решать:

1. **Как данные попадают в кэш и как он синхронизируется с базой** - стратегии: cache-aside, read-through, write-through, write-back.
2. **Что убрать, когда место кончилось** - политики вытеснения: LRU, LFU и другие.
3. **Когда копия устаревает и как не положить базу** - TTL, инвалидация, защита от штурма.

Идея вытеснения вам знакома по [замещению страниц](lesson:os.fundamentals.virtual-memory-page-replacement): оперативная память - кэш диска, а политика выбора жертвы та же. Нагрузка, которую кэш снимает, часто упирается в [индексы и планы запросов](lesson:databases.sql.indexes-and-query-plans), но кэш не заменяет хороший индекс: промах всё равно идёт в базу.

## Стратегии чтения и записи

**Cache-aside** (ленивая загрузка). Приложение само управляет кэшем.

* Чтение: смотрим в кэш; при промахе читаем из базы, кладём в кэш, возвращаем.
* Запись: пишем в базу, затем **удаляем** ключ из кэша (инвалидация). Следующее чтение загрузит свежее значение. Удалять безопаснее, чем обновлять: при гонке двух записей обновление может оставить в кэше устаревшее значение.
* Плюсы: кэш хранит только то, что читали; отказ кэша не ломает систему (медленнее, но работает). Минусы: первый запрос после промаха медленный, возможна короткая несогласованность.

**Read-through**: приложение обращается только к кэшу, а кэш сам загружает данные из базы при промахе. Логика та же, но спрятана в слое кэша.

**Write-through**: запись идёт в кэш, и кэш синхронно записывает в базу, подтверждение приходит после обоих. Кэш всегда согласован с базой, зато запись медленнее (две операции).

**Write-back (write-behind)**: запись подтверждается после попадания в кэш; в базу данные сбрасываются позже пачками. Запись очень быстрая и можно склеивать повторные обновления одного ключа, но **при падении кэша до сброса подтверждённые записи теряются**. Подходит для счётчиков и метрик, а не для платежей.

## Вытеснение

Когда кэш полон, нужно выбрать жертву.

* **LRU** (least recently used): вытесняется давнее всех использованная запись. Хорошо при локальности по времени: недавно использованное скоро понадобится снова. Слабость: разовое сканирование большого набора ключей вымывает полезные записи.
* **LFU** (least frequently used): вытесняется запись с наименьшим числом обращений; при равенстве обычно решает давность. Хорошо держит стабильно популярные ключи и устойчив к сканированию. Слабость: старые «звёзды» с большими счётчиками не уходят, когда популярность сместилась (используют затухание счётчиков).
* **FIFO**, **случайное** вытеснение: просты, иногда достаточно хороши.

Точный LRU требует обновлять порядок при каждом обращении; на практике используют приближения (выборка нескольких ключей и выбор худшего), так делает, например, Redis.

## TTL и согласованность

**TTL** (time to live) ограничивает возраст копии: после срока запись считается отсутствующей. TTL - страховка от забытых инвалидаций и ограничение «устаревания»: данные могут отставать не дольше TTL. Выбор TTL - компромисс: короткий дороже для базы, длинный даёт более устаревшие данные. В упражнении время задаёт вход (логические часы): так симуляция детерминирована и не зависит от настоящих часов.

## Штурм кэша

Популярный ключ истекает, и в этот момент сотни параллельных запросов видят промах. Все идут в базу за одним и тем же значением, база перегружается, ответы замедляются, новые запросы тоже получают промахи - система входит в петлю. Защита:

* **Единый загрузчик** (single-flight, блокировка, «аренда» в memcached): значение грузит один запрос, остальные ждут его результат или получают слегка устаревшую копию.
* **Джиттер TTL**: к TTL добавляют случайную (или детерминированную по ключу) добавку, чтобы однотипные ключи не истекали одновременно.
* **Раннее обновление**: фоновая задача или вероятностный запрос обновляют значение до истечения срока.
* **Ограничение нагрузки на источник** (load shedding) как последняя линия обороны.

## Cache-aside в коде

Смоделируем базу и кэш словарями и посчитаем обращения к базе. Запись удаляет ключ из кэша.

```python run
db = {"user:1": "Ann"}
cache = {}
db_reads = 0


def get(key):
    global db_reads
    if key in cache:
        return cache[key]
    db_reads += 1                 # промах: идём в базу
    value = db[key]
    cache[key] = value
    return value


def put(key, value):
    db[key] = value
    cache.pop(key, None)          # инвалидация, а не обновление


print(get("user:1"), get("user:1"), "db_reads =", db_reads)
put("user:1", "Anna")
print(get("user:1"), get("user:1"), "db_reads =", db_reads)
```
```output
Ann Ann db_reads = 1
Anna Anna db_reads = 2
```

Два чтения подряд стоят одно обращение к базе; запись заставляет следующее чтение сходить в базу снова, зато значение свежее.

## LRU против LFU

Один и тот же поток обращений даёт разные результаты в зависимости от формы нагрузки. Первый поток: пять горячих ключей и «сканирование» - постоянно новые одноразовые ключи. Второй: популярность целиком переезжает на новые ключи каждые 90 запросов. Обе политики написаны за пару десятков строк; нагрузка детерминирована (никаких случайных чисел).

```python run
from collections import OrderedDict


def lru_ratio(seq, cap):
    cache, hits = OrderedDict(), 0
    for k in seq:
        if k in cache:
            hits += 1
            cache.move_to_end(k)
        else:
            if len(cache) == cap:
                cache.popitem(last=False)
            cache[k] = True
    return hits / len(seq)


def lfu_ratio(seq, cap):
    freq, last, hits = {}, {}, 0
    for t, k in enumerate(seq):
        if k in freq:
            hits += 1
            freq[k] += 1
        else:
            if len(freq) == cap:
                victim = min(freq, key=lambda x: (freq[x], last[x]))
                del freq[victim], last[victim]
            freq[k] = 1
        last[k] = t
    return hits / len(seq)


hot = [0, 1, 2, 3, 4]
scan_workload, scan_id = [], 100
for _ in range(40):
    scan_workload += hot + hot + [scan_id, scan_id + 1, scan_id + 2, scan_id + 3]
    scan_id += 4

shift_workload = []
for phase in range(4):
    for _ in range(30):
        shift_workload += [phase * 10, phase * 10 + 1, phase * 10 + 2]

print("scan  LRU", round(lru_ratio(scan_workload, 6), 3), "LFU", round(lfu_ratio(scan_workload, 6), 3))
print("shift LRU", round(lru_ratio(shift_workload, 4), 3), "LFU", round(lfu_ratio(shift_workload, 4), 3))
```
```output
scan  LRU 0.357 LFU 0.705
shift LRU 0.967 LFU 0.242
```

На сканировании LFU держит горячие ключи (около 70 % попаданий против 36 %), а при смене популярности LRU быстро забывает старое (97 % против 24 %), тогда как у LFU старые ключи с большими счётчиками застревают в кэше. Универсальной лучшей политики нет; в упражнении вы пишете LRU, а в задаче повышенной сложности - LFU с арбитражем по давности.

## Штурм кэша: сколько запросов дойдёт до базы

Сто запросов приходят одновременно в тот момент, когда ключ истёк. Сравним «каждый грузит сам» и единый загрузчик. Время здесь логическое: запросы одного тика видят одно и то же состояние кэша.

```python run
def requests_hit_db(concurrent, single_flight):
    in_flight = False
    loads = 0
    for _ in range(concurrent):
        if single_flight and in_flight:
            continue              # ждём результат уже идущей загрузки
        in_flight = True
        loads += 1
    return loads


print("no protection:", requests_hit_db(100, False))
print("single flight:", requests_hit_db(100, True))

# Джиттер TTL: 1000 ключей с одним TTL истекают одновременно, с добавкой - равномерно
base_ttl = 300
same = {}
spread = {}
for key in range(1000):
    same[base_ttl] = same.get(base_ttl, 0) + 1
    t = base_ttl + (key * 7) % 60
    spread[t] = spread.get(t, 0) + 1
print("max expirations per tick, fixed TTL:", max(same.values()))
print("max expirations per tick, jittered TTL:", max(spread.values()))
```
```output
no protection: 100
single flight: 1
max expirations per tick, fixed TTL: 1000
max expirations per tick, jittered TTL: 17
```

## Типичные ошибки

* **Обновлять кэш при записи вместо удаления ключа.** При гонке двух записей устаревшее значение может остаться навсегда (до TTL). Удаление проще и надёжнее.
* **Кэшировать без TTL.** Любая забытая инвалидация превращается в вечные устаревшие данные.
* **Один и тот же TTL для миллиона ключей.** Они истекут одновременно и устроят штурм.
* **Считать кэш источником истины.** Он может быть очищен в любой момент; система обязана работать (медленнее) и без него. Write-back делает кэш единственной копией на время задержки - это осознанный риск.
* **Не кэшировать отрицательные результаты.** Запросы к несуществующим ключам каждый раз идут в базу; кэшируйте «не найдено» на короткий срок.
* **Мерить только среднюю задержку.** Промахи формируют хвост; следите за долей попаданий и за p99.
* **Выбирать политику вытеснения «по умолчанию».** Форма нагрузки (сканирования, смена популярности) решает, что лучше: LRU или LFU.
* **Забывать, что у кэша есть стоимость.** Память, сложность инвалидации и дополнительная точка отказа.

## Итоги

* Кэш выигрывает за счёт локальности; его эффект определяется долей попаданий.
* Cache-aside: читаем через кэш, при записи удаляем ключ. Write-through согласован, но медленнее; write-back быстрый, но может потерять данные.
* LRU вытесняет давнее, LFU - редкое; LRU слаб на сканированиях, LFU медленно забывает прошлое. Выбор зависит от нагрузки.
* TTL ограничивает устаревание; одинаковый TTL у многих ключей и параллельные промахи приводят к штурму.
* Защита от штурма: единый загрузчик, джиттер TTL, раннее обновление.
