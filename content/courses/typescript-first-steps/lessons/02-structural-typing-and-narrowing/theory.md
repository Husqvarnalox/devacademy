## TypeScript смотрит на форму значения, а не на его происхождение

В TypeScript совместимость типов определяется **структурой**: если у значения есть нужные поля нужных типов, оно подходит, как бы оно ни было создано.
Имя типа не важно. Это называется **структурной типизацией** и отличается от номинальной (Java, C#), где два класса с одинаковыми полями несовместимы.

```typescript
interface Point { x: number; y: number }
const p = { x: 3, y: 4, label: "A" };    // лишнее поле label
function norm(a: Point) { return Math.hypot(a.x, a.y); }
norm(p);                                  // 5: форма подходит
```

Второй главный инструмент - **сужение типов** (narrowing). Значение имеет широкий тип (`string | number`, `unknown`), а проверка в коде
(`typeof`, `===`, `in`, `Array.isArray`) сужает его внутри ветки, и компилятор разрешает операции, которые безопасны именно там.

## Структурная типизация, unknown, any, never и проверка во время работы

**Совместимость по форме.** Тип `A` присваиваем в `B`, если у `A` есть все свойства `B` с совместимыми типами. Лишние свойства допустимы.
Исключение: **проверка лишних свойств** срабатывает только для свежего литерала объекта, который передают напрямую: `norm({ x: 1, y: 2, label: "A" })` - ошибка,
потому что в литерале опечатка в имени свойства слишком вероятна. Через промежуточную переменную проверки нет.

**Объединения и дискриминатор.** `type Shape = { kind: "circle"; r: number } | { kind: "rect"; w: number; h: number }`. Поле `kind` с литеральными значениями - **дискриминатор**:
`switch (s.kind)` или `if (s.kind === "circle")` сужает `s` до одного варианта, и доступ к `s.r` разрешён только там, где `s` точно круг.

**`any`, `unknown`, `never`.**

* `any` отключает проверку: с ним можно делать что угодно, и ошибки уходят в выполнение. Он «заражает» выражения, в которых участвует.
* `unknown` - безопасная альтернатива: значение может быть чем угодно, но использовать его можно только после сужения (`typeof`, `in`, проверка формы). Результат `JSON.parse` имеет тип `any`; присвойте его сразу переменной типа `unknown`.
* `never` - тип, у которого нет значений: результат функции, которая не возвращается, и тип «невозможной» ветки. Если вы в `default` присваиваете `s` переменной типа `never`,
  компилятор сообщит об ошибке, когда в объединение добавят новый вариант, а `switch` его не обрабатывает. Это **проверка исчерпываемости**.

**Пользовательские type guard.** Функция `function isCircle(x: unknown): x is Circle` возвращает `boolean`, а запись `x is Circle` сообщает компилятору:
если функция вернула `true`, значение имеет тип `Circle`. Компилятор *не проверяет*, что тело функции действительно проверяет это - ответственность на авторе.

**Типов во время работы нет.** Именно поэтому для данных извне (stdin, JSON, ответ сервера) защитой служит *проверка формы в коде*: убедиться, что значение - непустой объект,
что поле `kind` равно ожидаемой строке, что `r` - число (`typeof r === "number"`). Только после этого значение можно считать типом `Shape`. Библиотеки валидации делают то же самое, а тип потом выводят из описания.

**Сужение не переживает функции и изменения.** Если между проверкой и использованием значение может измениться (изменяемое свойство, вызов функции), компилятор осторожничает и сужение сбрасывает.

## Примеры

**Пример 1. Структурная совместимость.**

Класс `Vec` ниже пишется с явными полями: сокращённая запись `constructor(public x: number)` (параметр-свойство) при срезании типов в Node.js не поддерживается.

```typescript run
interface Point { x: number; y: number }

class Vec {
  x: number;
  y: number;
  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }
}

function norm(p: Point): number {
  return Math.hypot(p.x, p.y);
}

const literalVar = { x: 3, y: 4, label: "A" };
console.log(norm(literalVar));
console.log(norm(new Vec(6, 8)));
```
```output
5
10
```

`Vec` нигде не объявляет, что реализует `Point`: достаточно совпадения формы. Лишнее поле `label` допустимо, потому что объект передан через переменную.

**Пример 2. Дискриминированное объединение и проверка исчерпываемости.**

```typescript run
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "rect"; w: number; h: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle":
      return Math.PI * s.r ** 2;
    case "rect":
      return s.w * s.h;
    default: {
      const unreachable: never = s;
      return unreachable;
    }
  }
}

console.log(area({ kind: "rect", w: 3, h: 4 }));
console.log(area({ kind: "circle", r: 1 }).toFixed(3));
```
```output
12
3.142
```

Если добавить вариант `{ kind: "square" }` и не обработать его, строка с `never` перестанет компилироваться.

**Пример 3. `unknown` требует проверки.**

```typescript run
function describe(value: unknown): string {
  if (typeof value === "number") return "число " + value.toFixed(1);
  if (typeof value === "string") return "строка длиной " + value.length;
  if (Array.isArray(value)) return "массив из " + value.length;
  if (value === null) return "null";
  return "другое";
}

for (const text of ["42", '"abc"', "[1,2]", "null", "{}"]) {
  console.log(describe(JSON.parse(text)));
}
```
```output
число 42.0
строка длиной 3
массив из 2
null
другое
```

Порядок проверок важен: `typeof null` - `"object"`, поэтому `null` проверяется отдельно.

**Пример 4. Тип обещает, данные не обязаны.**

```typescript run
interface User { name: string; age: number }
const u = JSON.parse('{"name": "Ann"}') as User;
console.log(u.age + 1);
```
```output
NaN
```

Компилятор верит, что `age` - число. Во время работы `u.age` равно `undefined`, а `undefined + 1` даёт `NaN`. Проверка формы в коде предотвратила бы эту ошибку.

## Типичные ошибки

* **`JSON.parse(...) as User`.** Это не проверка, а обещание. Принимайте `unknown`, проверяйте поля и только потом возвращайте типизированный результат.
* **Проверять `typeof x === "object"` и сразу обращаться к полю.** `null` тоже «object». Нужны явные `x !== null`, а для массива - `Array.isArray`.
* **Использовать `any` в сигнатуре «временно».** Он заражает вызывающий код, и ошибки появляются во время работы, где типов уже нет.
* **Ждать номинальной типизации.** Два интерфейса с одинаковыми полями взаимозаменяемы: «`UserId` и `OrderId` как `number`» компилятор не различит, пока вы не введёте отличительное поле.
* **Забывать ветку `default` с `never`.** Без неё новый вариант объединения молча попадает в «ничего не вернули».
* **Проверять только наличие поля.** `"r" in x` сообщает, что свойство есть, но не его тип; значение может оказаться строкой.
* **Считать `NaN` ошибкой типов.** Тип `number` включает `NaN` и `Infinity`; их нужно ловить отдельно.

## Итоги

* Совместимость типов определяется структурой, а не именем; лишние поля допустимы, кроме свежих литералов.
* Сужение (`typeof`, `===`, `in`, `Array.isArray`, дискриминатор) делает операции безопасными внутри ветки.
* `unknown` заставляет проверять, `any` отключает проверку, `never` помогает находить необработанные варианты.
* Типы стираются: данные извне нужно проверять кодом. `as` и type guard - обещания, которые должна выполнить программа.
