## HTTP не помнит, кто вы

Каждый HTTP-запрос независим. Чтобы сервер понимал «это тот же пользователь, что вошёл минуту назад», при входе он создаёт **сессию** и отдаёт браузеру её идентификатор, обычно в **cookie**. Браузер сам прикладывает cookie к каждому следующему запросу на этот сайт.

Из этого удобства вытекают три класса проблем:

* **кража идентификатора** - его прочитал скрипт (XSS), перехватили в открытом канале, он оказался в журнале или в URL;
* **подсунутый идентификатор** - злоумышленник заставил жертву использовать **известный ему** идентификатор до входа (**фиксация сессии**);
* **автоматическая отправка** - браузер прикладывает cookie даже тогда, когда запрос инициировала чужая страница (**CSRF**, подделка межсайтового запроса): жертва открыла чужой сайт, а он незаметно отправляет форму на ваш сайт, и браузер подставляет сессию жертвы.

Защита: правильные атрибуты cookie, обновление идентификатора при входе и токен, который чужой сайт не может подставить.

<!-- section: precise -->
## Атрибуты Set-Cookie

| Атрибут | Что делает | Против чего |
|---|---|---|
| `Secure` | cookie отправляется только по HTTPS | перехват в открытом канале ([TLS](lesson:networking.fundamentals.tls-and-diagnostics)) |
| `HttpOnly` | недоступна для `document.cookie` | кражу значения скриптом после XSS (но не против действий от имени пользователя) |
| `SameSite=Lax/Strict` | не отправляется в межсайтовых подзапросах (Strict - вообще не отправляется при переходе с чужого сайта) | CSRF (как дополнительный слой) |
| `SameSite=None` | отправляется всегда; требует `Secure` | нужен только для сознательных межсайтовых сценариев |
| `Path`, `Domain` | область действия; `Domain` распространяет cookie на поддомены | лишняя область - лишняя поверхность |
| `Max-Age` / `Expires` | срок жизни | украденная cookie не должна жить годами |

Префиксы имён усиливают гарантии: `__Secure-` требует `Secure`, `__Host-` требует `Secure`, `Path=/` и отсутствия `Domain`: cookie привязана к одному хосту и её нельзя перезаписать с поддомена.

Сам идентификатор сессии должен быть длинным, случайным и непредсказуемым ([урок про случайность](lesson:security.fundamentals.secrets-and-dependencies)), храниться на сервере или быть подписанным, не передаваться в URL и истекать как по бездействию, так и по абсолютному сроку.

## Фиксация сессии

Если идентификатор до входа и после входа **один и тот же**, тот, кто знал его до входа, получает доступ после. Правило: **выдайте новый идентификатор при любом повышении привилегий** (вход, повышение роли), а старый аннулируйте; не принимайте идентификатор из параметров URL. При выходе сессию уничтожают на сервере, а не только удаляют cookie в браузере.

## CSRF и токены

Идея атаки: изменяющий запрос (`POST /transfer`) можно отправить с чужой страницы, браузер приложит cookie, сервер не отличит. Защита - потребовать в запросе **значение, которого чужая страница не знает**:

* **Синхронизирующий токен** (synchronizer): сервер хранит случайный токен в сессии и вставляет его в форму; при получении сравнивает значение из тела (или заголовка) с сохранённым через `hmac.compare_digest`.
* **Double-submit cookie**: токен кладут и в cookie, и в тело/заголовок запроса; сервер сравнивает два значения. Не требует состояния на сервере, но **наивный** вариант (случайное значение, никак не связанное с сессией) OWASP не рекомендует. Рекомендован **подписанный** вариант: токен = HMAC от идентификатора сессии (и случайной части) секретным ключом сервера, тогда подделать подходящий токен нельзя. Cookie с таким токеном читает скрипт, поэтому её выставляют без `HttpOnly`.
* **SameSite** - полезный слой, но OWASP предлагает считать его **дополнением**, а не единственной мерой; изменяющие операции не должны выполняться по GET.
* Дополнительно проверяют `Origin`/`Referer` и заголовки Fetch Metadata.

Токен не должен попадать в URL (журналы, `Referer`); сравнение - `hmac.compare_digest`. CSRF-токен защищает от межсайтовой подделки, но не от XSS на вашем сайте: скрипт на странице токен прочитает, поэтому [кодирование вывода](lesson:security.fundamentals.output-encoding-and-xss) остаётся основой.

## Заголовок Set-Cookie

`http.cookies.SimpleCookie` из стандартной библиотеки собирает заголовок с атрибутами; порядок атрибутов в выводе определяется библиотекой:

```python run
from http.cookies import SimpleCookie

c = SimpleCookie()
c["sid"] = "abc123"
c["sid"]["path"] = "/"
c["sid"]["secure"] = True
c["sid"]["httponly"] = True
c["sid"]["samesite"] = "Lax"
c["sid"]["max-age"] = 3600
print(c.output(header="Set-Cookie:"))

parsed = SimpleCookie("sid=abc123; theme=dark")
print({k: m.value for k, m in parsed.items()})
```
```output
Set-Cookie: sid=abc123; HttpOnly; Max-Age=3600; Path=/; SameSite=Lax; Secure
{'sid': 'abc123', 'theme': 'dark'}
```

В упражнении вы разбираете такие строки сами и ищете недостающие атрибуты: готовая библиотека тоже полезна, но нужно знать, что она ставит, а что оставляет вам.

## Обновление сессии при входе

Детерминированный «генератор» идентификаторов (счётчик и HMAC) показывает логику без случайных значений. В реальной системе идентификатор берут из `secrets.token_urlsafe`:

```python run
import hashlib
import hmac

SERVER_KEY = b"demo-key-not-a-secret"
counter = 0


def new_session_id():
    global counter
    counter += 1
    return hmac.new(SERVER_KEY, f"sid-{counter}".encode(), hashlib.sha256).hexdigest()[:12]


sessions = {}


def login(session_id, user):
    sessions.pop(session_id, None)     # старый идентификатор аннулируется
    fresh = new_session_id()
    sessions[fresh] = {"user": user}
    return fresh


anonymous = new_session_id()
sessions[anonymous] = {"user": None}
print("before login:", anonymous, sessions[anonymous])
after = login(anonymous, "alice")
print("after login: ", after, sessions[after])
print("old id still valid:", anonymous in sessions)
```
```output
before login: d794a53fa500 {'user': None}
after login:  6b55c2c1200d {'user': 'alice'}
old id still valid: False
```

Идентификатор поменялся, старый перестал работать: подсунутый заранее идентификатор бесполезен.

## Подписанный токен double-submit

Токен привязан к сессии: HMAC от идентификатора сессии. Подставить подходящий токен, не зная ключа, нельзя, а проверка - без состояния:

```python run
import base64
import hashlib
import hmac

KEY = b"0123456789abcdef0123456789abcdef"


def csrf_token(session_id):
    mac = hmac.new(KEY, b"csrf:" + session_id.encode(), hashlib.sha256).digest()
    return base64.urlsafe_b64encode(mac).rstrip(b"=").decode()


def check(session_id, token):
    return hmac.compare_digest(csrf_token(session_id), token)


tok = csrf_token("session-A")
print(tok[:16], check("session-A", tok))
print(check("session-B", tok))
print(check("session-A", "x" * len(tok)))
```
```output
TVC5auhI0XO-fhiC True
False
False
```

Токен сессии A не подходит к сессии B: это и есть привязка. Без неё (наивный double-submit) любой, кто сумел записать cookie, подставил бы свой токен в оба места.

## Типичные ошибки

* **Сессионная cookie без `Secure`/`HttpOnly`/`SameSite`.** Это три строки конфигурации, которые закрывают целые классы проблем.
* **Тот же идентификатор после входа.** Фиксация сессии.
* **Идентификатор в URL.** Он попадает в историю, журналы, `Referer`.
* **GET с побочными эффектами.** Такие запросы обходят защиту SameSite=Lax и токены.
* **Токен CSRF не привязан к сессии** (наивный double-submit) или сравнивается через `==`.
* **Считать SameSite единственной защитой.** Старые браузеры, поддомены и особые сценарии оставляют лазейки; нужен токен.
* **`SameSite=None` без необходимости** и `Domain=example.com` «на всякий случай».
* **Годовой срок жизни у сессионной cookie** без абсолютного ограничения.
* **Хранить в cookie данные и роли без подписи.** Cookie контролирует клиент; значение, которому вы доверяете, должно быть подписано или храниться на сервере (см. [подписи и токены](lesson:security.fundamentals.message-authentication-and-tokens)).

<!-- section: summary -->
## Итоги

* Сессия = идентификатор в cookie; он должен быть случайным, длинным и недоступным для чужих.
* `Secure`, `HttpOnly`, `SameSite`, минимальные `Path`/`Domain`, разумный срок жизни, префикс `__Host-` для сессионных cookie.
* Обновляйте идентификатор при входе и аннулируйте старый (фиксация сессии).
* CSRF: токен, привязанный к сессии (синхронизирующий или подписанный double-submit), сравнение через `compare_digest`; SameSite - дополнение.
* Следующий уровень вопросов - не «кто вы», а «что вам можно»: [контроль доступа](lesson:security.fundamentals.access-control).
