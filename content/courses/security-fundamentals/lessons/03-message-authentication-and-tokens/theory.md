## Как понять, что сообщение не подделали

В прошлом уроке мы проверяли пароль. Теперь задача другая: сервер выдал клиенту токен («этот пользователь вошёл»), клиент прислал его обратно. Откуда сервер знает, что токен не изменили по дороге и что его создал именно он?

Ответ - **код аутентификации сообщения (MAC)**: тег, который вычисляют из сообщения и **общего секретного ключа**. Получатель, знающий ключ, пересчитывает тег и сравнивает. Изменить сообщение и подобрать верный тег без ключа нельзя. Стандартная конструкция - **HMAC** (RFC 2104).

Что MAC даёт: **целостность** (сообщение не менялось) и **подлинность** (его создал владелец ключа). Чего не даёт: секретности (сообщение остаётся читаемым), неотказуемости (ключ знают обе стороны), защиты от повтора (одно и то же сообщение можно прислать дважды - для этого нужны срок действия и одноразовые значения).

**JWT** - распространённый контейнер для таких сообщений: три текстовые части `заголовок.нагрузка.подпись`. Частая беда не в криптографии, а в том, что проверку делают слишком мягко. Этот урок про строгость.

## Почему HMAC, а не hash(key + message)

Интуитивно кажется, что `sha256(key + message)` - хороший тег. Это не так для хешей семейства Меркла - Дамгора (MD5, SHA-1, SHA-256, SHA-512): хеш этих функций по сути равен их внутреннему состоянию после обработки всех блоков. Тот, кто видит `sha256(key + message)` и знает длину ключа, может **продолжить вычисление** и получить корректный тег для `message + дополнение + суффикс`, **не зная ключа** (**удлинение сообщения**, length extension). Здесь мы объясняем это только концептуально: для защиты достаточно знать, что так делать нельзя.

**HMAC** строится как `H((K ⊕ opad) || H((K ⊕ ipad) || message))`: внутренний результат попадает во внешний хеш с ключом, и внутреннее состояние наружу не выходит. Используйте `hmac.digest(key, msg, "sha256")` или `hmac.new(...)`, а не собственные конструкции. SHA-3 и BLAKE2 от этой атаки не страдают, но стандартным остаётся HMAC.

## Структура JWT

```
BASE64URL(заголовок) . BASE64URL(нагрузка) . BASE64URL(подпись)
```

* **Заголовок** - JSON, например `{"alg":"HS256","typ":"JWT"}`.
* **Нагрузка** - JSON с утверждениями: `sub`, `exp` (срок), `nbf` (не раньше), `iss` и своими.
* **Подпись HS256** = HMAC-SHA256 от ASCII-строки `part1 + "." + part2`.

**base64url** - алфавит `A-Za-z0-9-_` без заполнителя `=`. Нагрузка не зашифрована: её читает каждый, подпись только не даёт её изменить.

## Что должен отвергать верификатор

Верификатор получает токен от недоверенной стороны, поэтому **вся проверка - на вашей стороне**:

* **`alg=none`.** Спецификация допускает «небезопасные» JWS без подписи. Если библиотека доверяет заголовку и пропускает токен с `alg=none`, любой выпустит токен от имени любого пользователя. Верификатор не принимает `none`.
* **Подмена алгоритма (algorithm confusion).** Токен заявляет `alg=HS256`, а сервер ожидает RS256 и подставляет **открытый** ключ в проверку HMAC - получается, что секретом служит публичная строка. Правило одно: **алгоритм определяет сервер**, а не токен. Заголовок `alg` лишь сверяют со списком допустимых (в упражнении - одно значение `HS256`, с учётом регистра).
* **Порядок.** Сначала структура и заголовок (минимум, чтобы выбрать алгоритм и ключ), затем подпись, и **только потом** доверие нагрузке.
* **Срок.** Обязательный `exp`: `now >= exp` - токен недействителен; `nbf` - ещё не действует. Время в упражнении подаётся явно: проверки воспроизводимы и не зависят от часов машины.
* **Сравнение подписи** - `hmac.compare_digest`.
* **Подпись по исходным частям.** Считайте её по тем байтам, что пришли, а не по перекодированному JSON.

Рекомендации собраны в RFC 8725 (JWT Best Current Practices).

## Ротация ключей и kid

Ключи нужно менять: по расписанию и после подозрения на утечку. В заголовке передают **`kid`** - идентификатор ключа. Верификатор держит набор доверенных ключей со статусами: `active` (подписывает и проверяет), `retired` (только проверяет - пока доживают выданные токены), `revoked` (отвергается). `kid` приходит от недоверенной стороны, поэтому он - **только ключ поиска** в словаре доверенных ключей; его нельзя подставлять в SQL, в путь файла или использовать, чтобы взять ключ из места, выбранного токеном. [SQL-инъекции](lesson:databases.sql.sql-injection-and-safe-access) и обход путей из следующего урока начинаются именно с таких «безобидных» идентификаторов.

Транспорт токена тоже важен: передавайте его только по [TLS](lesson:networking.fundamentals.tls-and-diagnostics).

## HMAC и сравнение

Фиксированный ключ и сообщение дают воспроизводимый результат. Наивный тег и HMAC различаются, а проверка идёт через `compare_digest`:

```python run
import hashlib
import hmac

key = b"0123456789abcdef0123456789abcdef"
msg = b"user=alice;role=reader"

naive = hashlib.sha256(key + msg).hexdigest()
tag = hmac.digest(key, msg, "sha256")
print("naive", naive[:16])
print("hmac ", tag.hex()[:16])

def check(key, msg, tag):
    return hmac.compare_digest(hmac.digest(key, msg, "sha256"), tag)

print(check(key, msg, tag))
print(check(key, b"user=alice;role=admin", tag))
print(check(b"x" * 32, msg, tag))
```
```output
naive f0cc1320408ce208
hmac  856114c7b6d91c1a
True
False
False
```

Любое изменение сообщения или ключа даёт `False`. Наивный `sha256(key + msg)` не используйте: он уязвим к удлинению сообщения (концептуально см. выше).

## Вектор RFC 7515 A.1

Соберём подпись для примера из приложения A.1 RFC 7515: ключ JWK, заголовок и нагрузка записаны в документе. Если реализация верна, получится строка из RFC:

```python run
import base64
import hmac
import json


def b64u_decode(s):
    return base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))


def b64u_encode(raw):
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


key = b64u_decode("AyM1SysPpbyDfgZld3umj1qzKObwVMkoqQ-EstJQLr_T-1qS0gZH75aKtMN3Yj0iPS4hcgUuTwjAzZr1Z9CAow")
token = ("eyJ0eXAiOiJKV1QiLA0KICJhbGciOiJIUzI1NiJ9."
         "eyJpc3MiOiJqb2UiLA0KICJleHAiOjEzMDA4MTkzODAsDQogImh0dHA6Ly9leGFtcGxlLmNvbS9pc19yb290Ijp0cnVlfQ."
         "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk")
head, payload, sig = token.split(".")

print(json.loads(b64u_decode(head)))
print(json.loads(b64u_decode(payload))["exp"])
mine = b64u_encode(hmac.digest(key, (head + "." + payload).encode("ascii"), "sha256"))
print(mine == sig)
```
```output
{'typ': 'JWT', 'alg': 'HS256'}
1300819380
True
```

Совпадение подписи подтверждает формулу. Обратите внимание, что в заголовке нет ничего, что нельзя было бы подделать: именно поэтому поле `alg` сверяют со списком, а не исполняют.

## Белый список алгоритмов

Минимальная проверка заголовка: значение должно совпасть ровно с ожидаемым. Все «хитрые» варианты отвергаются тем же правилом:

```python run
ALLOWED = "HS256"

def alg_ok(header):
    return header.get("alg") == ALLOWED

for header in ({"alg": "HS256"}, {"alg": "none"}, {"alg": "None"}, {"alg": "hs256"}, {"alg": "RS256"}, {"typ": "JWT"}):
    print(header, alg_ok(header))
```
```output
{'alg': 'HS256'} True
{'alg': 'none'} False
{'alg': 'None'} False
{'alg': 'hs256'} False
{'alg': 'RS256'} False
{'typ': 'JWT'} False
```

Одно сравнение с константой закрывает сразу несколько классов атак: нет списка «запрещённых» значений, который можно обойти регистром или неожиданным типом.

## Типичные ошибки

* **Доверять `alg` из заголовка.** Алгоритм выбирает сервер. Белый список из явных значений, а не «всё, что библиотека знает».
* **Принимать `none`.** Даже «только для тестов» - так он попадает в продакшн.
* **Использовать один ключ для разных алгоритмов или целей.** Публичный ключ нельзя использовать как секрет HMAC; разделяйте ключи по назначению.
* **Читать нагрузку до проверки подписи.** `sub`, `role`, `exp` до проверки подписи - данные злоумышленника.
* **Не проверять срок.** Токен без `exp` или с огромным сроком превращается в вечный пароль.
* **Сравнивать подпись через `==`.** Только `hmac.compare_digest`.
* **Класть в нагрузку секреты.** Она читается всеми, у кого есть токен.
* **Подставлять `kid` в запрос или путь.** Это данные из токена; используйте только как ключ в словаре доверенных ключей.
* **Слабый секрет HS256.** Ключ должен быть случайным и длинным (не меньше длины выхода хеша, 32 байта для SHA-256).

## Итоги

* MAC (HMAC) даёт целостность и подлинность при общем секрете, но не секретность, не неотказуемость и не защиту от повтора.
* `hash(key + message)` небезопасна из-за удлинения сообщения; используйте HMAC.
* JWT = base64url(заголовок).base64url(нагрузка).подпись; подпись HS256 = HMAC-SHA256 по исходной строке `part1.part2`.
* Верификатор отвергает `alg=none`, любой алгоритм вне белого списка, неверную подпись и просроченные токены; подпись проверяется до доверия нагрузке.
* Ротация ключей: `kid` выбирает один из доверенных ключей; `retired` проверяет, `revoked` отвергается.
* Далее - защита от инъекций: [команды и пути](lesson:security.fundamentals.injection-defences).
