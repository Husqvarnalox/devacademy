## Секреты - это то, на чём держится всё остальное

Пароли хешируются, токены подписываются, сессии защищены, права проверяются - но всё это работает, пока **секреты остаются секретами**: ключ подписи, пароль базы данных, токен доступа к API. Три вопроса определяют их судьбу:

* **откуда они берутся** - генератор должен быть непредсказуемым;
* **где они лежат** - не в исходном коде, не в репозитории, не в образе;
* **куда они утекают** - в журналы, сообщения об ошибках, URL, дампы.

Отдельная тема - **чужой код**: большая часть вашего приложения написана не вами, и уязвимость в зависимости становится вашей уязвимостью.

## random и secrets

Модуль `random` реализует детерминированный генератор (вихрь Мерсенна): зная несколько выходов, можно восстановить состояние и предсказать следующие значения; зная начальное значение (seed), можно воспроизвести всю последовательность. Документация прямо говорит, что для безопасности он не годится. Модуль `secrets` берёт случайность у операционной системы и предназначен для токенов, ключей, одноразовых паролей и ссылок для сброса пароля:

* `secrets.token_bytes(n)`, `token_hex(n)`, `token_urlsafe(n)` - случайные токены;
* `secrets.choice(seq)` - случайный выбор (например, символа пароля);
* `secrets.compare_digest(a, b)` - сравнение за постоянное время (как у [HMAC](lesson:security.fundamentals.message-authentication-and-tokens)).

## Энтропия

Если секрет выбирается случайно и равновероятно из алфавита размера `A`, его длина `L` даёт `L * log2(A)` бит энтропии. 128 бит - уровень, при котором перебор неосуществим; идентификаторы [сессий](lesson:security.fundamentals.sessions-csrf-and-cookies) и токены сброса должны быть не слабее. Придуманный человеком пароль обычно намного слабее такой оценки; для хранения паролей действуют правила из [урока про пароли](lesson:security.fundamentals.password-storage).

## Где хранить и как не потерять

* **Не в коде и не в репозитории.** История git хранит удалённые файлы; публичный репозиторий сканируют боты. Утёкший ключ считается скомпрометированным: **ротация** (отозвать и выпустить новый) важнее очистки истории.
* **Источник секретов - окружение развёртывания** (менеджер секретов, переменные среды, смонтированные файлы), а не образ или код. Переменные среды наследуются дочерними процессами и попадают в отладочный вывод, поэтому доступ к ним тоже нужно ограничивать.
* **Минимальный срок и область.** Отдельные ключи для разных сервисов и окружений, возможность быстро заменить.
* **Журналы.** Не пишите пароли, токены, идентификаторы сессий и строки подключения. Если данные пришли из внешнего источника и могут их содержать, добавляйте **маскирование** (как в упражнении) - но воспринимайте его как последнюю линию защиты: шаблоны всегда что-то пропустят.

## Зависимости и цепочка поставок

* **Закрепляйте версии** (`requests==2.31.0`), а не диапазоны, чтобы сборка воспроизводилась; обновляйте осознанно.
* **Хеши.** Режим `--require-hashes` у pip проверяет, что скачанный файл совпадает с ожидаемым хешем.
* **SBOM** (спецификация состава ПО) - перечень компонентов и версий; по нему можно быстро ответить на вопрос «затронуты ли мы новой уязвимостью».
* **CVE и обновления.** Следите за базами известных уязвимостей, сопоставляйте их с перечнем, обновляйте по приоритету (достижимость, эксплуатируемость, критичность).
* **Минимум зависимостей.** Каждая добавляет поверхность атаки.

## random предсказуем, secrets - нет

Не выводим случайных значений (они были бы разными при каждом запуске): проверяем свойства.

```python run
import random
import secrets

a = random.Random(42)
b = random.Random(42)
print("same seed, same sequence:", [a.getrandbits(32) for _ in range(3)] == [b.getrandbits(32) for _ in range(3)])

t1 = secrets.token_urlsafe(16)
t2 = secrets.token_urlsafe(16)
print("token length:", len(t1), len(t2))
print("tokens differ:", t1 != t2)
print("compare_digest:", secrets.compare_digest(t1, t1), secrets.compare_digest(t1, t2))
```
```output
same seed, same sequence: True
token length: 22 22
tokens differ: True
compare_digest: True False
```

Одинаковое начальное значение даёт одинаковую «случайную» последовательность - поэтому `random.seed(время)` для токенов ломает защиту. Токен из 16 байт кодируется 22 символами base64url.

## Энтропия в битах

```python run
import math


def bits(length, alphabet):
    return length * math.log2(alphabet)


print("8 lowercase letters :", round(bits(8, 26), 1))
print("8 letters+digits    :", round(bits(8, 62), 1))
print("12 letters+digits   :", round(bits(12, 62), 1))
print("22 base64url chars  :", round(bits(22, 64), 1))
print("16 random bytes     :", 16 * 8)
```
```output
8 lowercase letters : 37.6
8 letters+digits    : 47.6
12 letters+digits   : 71.5
22 base64url chars  : 132.0
16 random bytes     : 128
```

Восемь строчных букв дают меньше 40 бит - это перебирается; токен из 16 случайных байт даёт 128 бит.

## Маскирование: что оно умеет и чего нет

```python run
import re

FIELD = re.compile(r"([\w-]*(?:password|token|secret))(\s*=\s*)(\S+)", re.IGNORECASE)


def mask(line):
    return FIELD.sub(lambda m: m.group(1) + m.group(2) + "[REDACTED]", line)


print(mask("login password=hunter2 ok"))
print(mask("max_tokens=100 token_count=5"))
print(mask("user typed it as: hunter2"))
```
```output
login password=[REDACTED] ok
max_tokens=100 token_count=5
user typed it as: hunter2
```

Поле с именем `password` замаскировано; `max_tokens=100` не затронуто, потому что имя не *заканчивается* на `token`. Последняя строка показывает предел подхода: секрет, записанный без метки, шаблон не найдёт. Поэтому главное правило - не записывать секреты вовсе.

## Закрепление и хеш пакета

```python run
import hashlib

requirements = """\
requests==2.31.0
flask>=2.0
numpy
"""

for line in requirements.splitlines():
    pinned = "==" in line
    print(f"{line:<18} pinned={pinned}")

artifact = b"contents of a downloaded package file"
expected = hashlib.sha256(artifact).hexdigest()
print("hash matches:", hashlib.sha256(artifact).hexdigest() == expected)
print("tampered matches:", hashlib.sha256(artifact + b"!").hexdigest() == expected)
```
```output
requests==2.31.0   pinned=True
flask>=2.0         pinned=False
numpy              pinned=False
hash matches: True
tampered matches: False
```

Строка с `==` закреплена, диапазон `>=` и голое имя - нет. Хеш файла меняется при любом изменении, на этом основан режим проверки хешей.

## Типичные ошибки

* **`random` для токенов, паролей и кодов.** Нужен `secrets`.
* **Секрет в репозитории** («потом уберём»). Бот найдёт его за минуты; после утечки - только ротация.
* **Секрет в образе контейнера или в аргументах командной строки.** Их видно в слоях образа и в списке процессов.
* **Полный URL с параметрами в журнале.** Токен сброса пароля или ключ API лежит в строке запроса.
* **Подробное сообщение об ошибке клиенту.** Строка подключения к базе в трассировке.
* **Один ключ для всего и навсегда.** Нет ротации - нет способа быстро среагировать.
* **Незакреплённые зависимости и «latest».** Сегодняшняя сборка не совпадает со вчерашней.
* **Установка пакета по опечатке в имени.** Подмена имён (typosquatting) - способ атаки на цепочку поставок; проверяйте имя и источник.
* **Игнорирование предупреждений об уязвимостях** или, наоборот, слепое обновление без тестов.
* **Считать маскирование журналов достаточным.** Оно ловит известные формы, но не секреты произвольного вида.

## Итоги

* Секреты генерируйте `secrets`; `random` предсказуем и для безопасности не годится.
* Энтропия = длина * log2(алфавит); целиться стоит в 128 бит для токенов и ключей.
* Не храните секреты в коде и репозитории; утечка означает ротацию.
* Не пишите секреты в журналы; маскирование - запасной слой, не основной.
* Закрепляйте версии и хеши, ведите SBOM, следите за CVE и обновляйтесь по процессу.
* Курс закрывает основы: [модель угроз](lesson:security.fundamentals.threat-modelling) помогает решить, в каком порядке применять защиты из всех восьми уроков.
