## Войти - не значит «можно всё»

**Аутентификация** отвечает на вопрос «кто вы», **авторизация** - «что вам разрешено». Урок про [сессии](lesson:security.fundamentals.sessions-csrf-and-cookies) закончился тем, что сервер знает пользователя. Теперь у каждого запроса нужно проверить: может ли *этот* пользователь выполнить *это* действие над *этим* ресурсом.

Нарушенный контроль доступа - самая частая серьёзная проблема веб-приложений: в OWASP Top 10 2021 она на первом месте. Типичная причина проста: проверку забыли в одном из обработчиков, потому что «пользователь же не видит такой кнопки».

Три правила на старте:

* **Проверка на сервере при каждом запросе.** Скрытая кнопка не ограничивает доступ - запрос можно отправить напрямую.
* **Запрет по умолчанию.** Нет явного правила - значит, нельзя.
* **Наименьшие привилегии.** Давайте ровно те права, которые нужны для задачи.

## Модели: ACL, RBAC, ABAC

* **RBAC** (ролевая модель): права назначаются *ролям*, роли - пользователям. Проверка: «есть ли у какой-то роли пользователя это право». Просто и понятно, но при росте требований роли размножаются («менеджер-Европа-ночью»).
* **ABAC** (атрибутная модель): правила смотрят на **атрибуты** субъекта (отдел, уровень допуска), ресурса (владелец, отдел, гриф), действия и окружения (время, сеть). Гибко, но политику труднее читать и тестировать.
* **Владение**: право действовать над собственными объектами; на практике это частный случай ABAC (`user.id == resource.owner`).

Реальные системы комбинируют: роли для грубых прав, владение и атрибуты - для проверок на конкретный объект.

## Порядок вычисления

Надёжный вычислитель политики устроен так:

1. неизвестный субъект или ресурс - отказ;
2. **явный запрет побеждает** любое разрешение (даже `*` у администратора и права владельца);
3. иначе разрешает явное совпадение (владение, роль, правило);
4. иначе - **отказ по умолчанию**.

Ошибка разбора, неизвестный оператор, отсутствующий атрибут не должны давать разрешение: система **закрывается при сбое** (fail closed).

## IDOR: проверка владения

**IDOR** (Insecure Direct Object Reference) - приложение отдаёт объект по идентификатору из запроса, не проверяя, принадлежит ли он пользователю. Меняется число в адресе - и открывается чужой счёт. Длинные случайные идентификаторы затрудняют угадывание, но не заменяют проверку: идентификатор мог утечь через ссылку, журнал или письмо. Исправление - включить владельца в запрос или проверить его отдельно, на стороне сервера. Тема перекликается с [внедрением в SQL](lesson:databases.sql.sql-injection-and-safe-access): значения всегда передаются параметрами, а условие владения входит в сам запрос.

## Проверка прав с запретом по умолчанию

```python run
ROLES = {
    "viewer": {"doc:read"},
    "editor": {"doc:read", "doc:write"},
}
USERS = {"alice": ["editor"], "bob": ["viewer"]}


def allowed(user, perm):
    for role in USERS.get(user, []):       # неизвестный пользователь: пустой список
        if perm in ROLES.get(role, set()):  # неизвестная роль: пустое множество
            return True
    return False                           # запрет по умолчанию


for who, perm in [("alice", "doc:write"), ("bob", "doc:write"), ("mallory", "doc:read"), ("alice", "doc:delete")]:
    print(who, perm, "ALLOW" if allowed(who, perm) else "DENY")
```
```output
alice doc:write ALLOW
bob doc:write DENY
mallory doc:read DENY
alice doc:delete DENY
```

Функция возвращает `True` только в одном месте - при явном совпадении; все остальные пути (неизвестный пользователь, неизвестная роль, отсутствующее право) заканчиваются отказом.

## Исправление IDOR запросом с владельцем

```python run
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE invoices (id INTEGER PRIMARY KEY, owner TEXT, total INTEGER)")
db.executemany("INSERT INTO invoices VALUES (?, ?, ?)", [(1001, "alice", 50), (1002, "bob", 75)])


def get_invoice_unsafe(invoice_id):
    # IDOR: идентификатор есть, проверки владельца нет
    return db.execute("SELECT id, owner, total FROM invoices WHERE id = ?", (invoice_id,)).fetchone()


def get_invoice(invoice_id, current_user):
    # условие владения входит в сам запрос; чужой объект неотличим от несуществующего
    return db.execute(
        "SELECT id, owner, total FROM invoices WHERE id = ? AND owner = ?",
        (invoice_id, current_user),
    ).fetchone()


print("unsafe:", get_invoice_unsafe(1002))
print("alice -> 1001:", get_invoice(1001, "alice"))
print("alice -> 1002:", get_invoice(1002, "alice"))
print("alice -> 9999:", get_invoice(9999, "alice"))
```
```output
unsafe: (1002, 'bob', 75)
alice -> 1001: (1001, 'alice', 50)
alice -> 1002: None
alice -> 9999: None
```

Для чужого и несуществующего счёта ответ один и тот же, поэтому по ответу нельзя выяснить, какие идентификаторы заняты.

## Правило с атрибутными условиями

```python run
def holds(cond, user, res):
    lhs, op, rhs = cond
    left = user.get(lhs[5:]) if lhs.startswith("user.") else lhs
    right = res.get(rhs[9:]) if rhs.startswith("resource.") else rhs
    if left is None or right is None:   # нет атрибута: условие ложно
        return False
    return left == right if op == "==" else left != right


rule = [("user.dept", "==", "resource.dept")]
alice = {"dept": "hr"}
doc_hr = {"dept": "hr"}
doc_it = {"dept": "it"}
nobody = {}

for name, u, r in [("same dept", alice, doc_hr), ("other dept", alice, doc_it), ("no attribute", nobody, doc_hr)]:
    print(name, all(holds(c, u, r) for c in rule))
```
```output
same dept True
other dept False
no attribute False
```

Именно эту идею (плюс числа, окружение и запреты) вы реализуете в challenge.

## Типичные ошибки

* **Проверка только в интерфейсе.** Кнопку скрыли, а обработчик не проверяет права.
* **Проверка роли без проверки объекта.** «Пользователь с ролью client может читать счета» - но чьи?
* **IDOR.** Выбор объекта по идентификатору из запроса без проверки владения.
* **Разрешение по умолчанию.** Новый маршрут или тип ресурса оказывается открытым, пока про него не вспомнили.
* **Сбой открывает доступ.** Исключение при разборе политики перехватывается и трактуется как «разрешить».
* **Права по имени роли в коде.** `if role == "admin"` разбросано по проекту; политика в одном месте проверяется и тестируется лучше.
* **Доверие данным клиента.** Роль, флаг `isAdmin` или идентификатор владельца берутся из тела запроса или несигнированного cookie ([подписи и токены](lesson:security.fundamentals.message-authentication-and-tokens)).
* **Числа как строки.** Условие `level >= 10` на строках даёт `"9" >= "10"`.
* **Различие ответов.** «Нет доступа» против «не найдено» раскрывает, какие объекты существуют.

## Итоги

* Аутентификация - «кто», авторизация - «что можно»; проверка на сервере при каждом запросе.
* RBAC удобен для грубых прав, ABAC - для условий на объект и окружение; владение - частный случай атрибутов.
* Порядок: неизвестное - отказ, явный запрет, явное разрешение, отказ по умолчанию; при сбое - отказ.
* IDOR закрывается проверкой владения на сервере; непредсказуемые идентификаторы - лишь дополнительный слой.
* Дальше - [секреты, случайность и зависимости](lesson:security.fundamentals.secrets-and-dependencies): как хранить то, на чём держатся все предыдущие защиты.
