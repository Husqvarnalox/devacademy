## Хеш - не шифр, а пароль - не ключ

**Хеш-функция** превращает любые данные в короткий отпечаток фиксированной длины; обратно отпечаток не развернуть. Сервис не должен знать ваш пароль: ему достаточно хранить отпечаток и сравнивать его с отпечатком введённого пароля. Тогда утечка базы не раскрывает пароли сама по себе.

Но злоумышленник с украденной базой не разворачивает хеши, а **перебирает догадки**: хеширует кандидатов и ищет совпадения. Поэтому нужны три вещи:

* **соль** - случайная строка, уникальная для каждого пароля и хранящаяся рядом с хешем. Одинаковые пароли получают разные хеши, а готовые таблицы становятся бесполезны;
* **медленность** - алгоритм с настраиваемой стоимостью (PBKDF2, scrypt, Argon2id, bcrypt). Для пользователя лишние 100 мс при входе незаметны, а для перебора миллиардов догадок это решающий множитель;
* **сравнение за постоянное время** - чтобы время ответа не выдавало, насколько близка догадка.

Обычный `SHA-256` вычисляется быстро по замыслу, поэтому для паролей он не годится даже с солью. Подробности и актуальные числа - в [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Алгоритмы и параметры

**PBKDF2** (RFC 8018) применяет HMAC к паролю и соли `c` раз. Параметры: функция (`sha256`), соль, число итераций `c`, длина результата. Для HMAC-SHA-256 OWASP называет 600 000 итераций и более, если нужна совместимость с FIPS-140. PBKDF2 нагружает только процессор, поэтому видеокартам он поддаётся лучше, чем алгоритмы с большим расходом памяти.

**scrypt** (RFC 7914) добавляет **память**: параметры `N` (стоимость CPU/памяти, степень двойки), `r` (размер блока), `p` (параллелизм). Память примерно `128 * N * r` байт. OWASP для scrypt: `N = 2^17`, `r = 8`, `p = 1`. Предпочтительным OWASP считает **Argon2id** (19 МиБ, 2 итерации, параллелизм 1), а для унаследованных систем - bcrypt (фактор работы не меньше 10, пароль не длиннее 72 байт). В стандартной библиотеке Python есть `hashlib.pbkdf2_hmac` и `hashlib.scrypt`; Argon2id и bcrypt требуют сторонних пакетов.

**Соль и перец.** Соль не секретна, уникальна и по размеру не меньше 16 байт; её нужно брать из криптостойкого генератора (`secrets.token_bytes`, [следующие уроки](lesson:security.fundamentals.secrets-and-dependencies) объясняют почему). **Перец** (pepper) - секрет приложения, который хранится отдельно от базы (например, в менеджере секретов); это дополнительная мера, а не замена соли.

**Запись самоописывается.** Храните алгоритм, параметры, соль и хеш одной строкой, например `pbkdf2_sha256$600000$соль$хеш`. Тогда старые записи остаются проверяемыми, когда политика ужесточается. При успешном входе, если параметры в записи слабее текущей политики, пересчитайте хеш из только что введённого пароля и сохраните новую запись (**rehash on login**).

**Постоянное время.** `==` для байтов может остановиться на первом различии, и время ответа зависит от длины совпавшего префикса. Это боковой канал по времени. `hmac.compare_digest(a, b)` сравнивает независимо от содержимого. Сравнивайте так любые секреты: дайджесты, токены, подписи.

**Границы доверия.** Запись пришла из вашей базы, но формат всё равно проверяется: повреждённая запись должна давать отказ, а не исключение и не часы вычислений (отсюда верхняя граница числа итераций в упражнении).

Аутентификация живёт не только в хеше: ограничение числа попыток, многофакторная проверка и [TLS](lesson:networking.fundamentals.tls-and-diagnostics) на канале входа важны не меньше.

## Соль и медленность

Фиксированные соли делают вывод воспроизводимым. Обратите внимание: у одного и того же пароля без соли хеш один, с разными солями - разные:

```python run
import hashlib

password = b"correct horse"
print("plain  ", hashlib.sha256(password).hexdigest()[:16], hashlib.sha256(password).hexdigest()[:16])
print("salt A ", hashlib.sha256(bytes.fromhex("aa" * 8) + password).hexdigest()[:16])
print("salt B ", hashlib.sha256(bytes.fromhex("bb" * 8) + password).hexdigest()[:16])

# PBKDF2 с теми же солями и небольшим числом итераций (в реальности - сотни тысяч)
for name, salt in (("A", bytes.fromhex("aa" * 8)), ("B", bytes.fromhex("bb" * 8))):
    print("pbkdf2", name, hashlib.pbkdf2_hmac("sha256", password, salt, 1000, 32).hex()[:16])
```
```output
plain   4104d36f8da2c254 4104d36f8da2c254
salt A  83d4f1f54a13c5be
salt B  4ba491edb3319e9b
pbkdf2 A 12e4536f2ee053c8
pbkdf2 B f27725cc57f24d21
```

Соль меняет результат, но SHA-256 с солью по-прежнему слишком быстр; PBKDF2 превращает одну проверку в тысячи (в проде - сотни тысяч) вызовов HMAC.

## Контрольные векторы и память scrypt

Правильность реализации проверяют по опубликованным векторам. Первый - из RFC 7914 для PBKDF2-HMAC-SHA-256, второй - тест scrypt из того же документа (пустой пароль и соль, N=16, r=1, p=1). Затем посчитаем память для параметров OWASP:

```python run
import hashlib

pb = hashlib.pbkdf2_hmac("sha256", b"passwd", b"salt", 1, 64)
print("pbkdf2", pb.hex()[:32])

sc = hashlib.scrypt(b"", salt=b"", n=16, r=1, p=1, dklen=64)
print("scrypt", sc.hex()[:32])

n, r = 2 ** 17, 8
print("scrypt memory, MiB:", 128 * n * r // 2 ** 20)
```
```output
pbkdf2 55ac046e56e3089fec1691c22544b605
scrypt 77d6576238657b203b19ca42c18a0497
scrypt memory, MiB: 128
```

Первые байты совпадают с RFC 7914 (`55ac046e...` и `77d65762...`), а параметры OWASP дают 128 МиБ памяти на одну проверку - вот почему scrypt и Argon2id дороже для массового перебора.

## Зачем compare_digest

Обычное сравнение останавливается на первом различии. Эта функция показывает, сколько байт совпало до остановки - информацию, которую во времени получил бы наблюдатель. Правильное сравнение скрывает её:

```python run
import hmac


def leaky_prefix(secret, guess):
    n = 0
    for a, b in zip(secret, guess):
        if a != b:
            break
        n += 1
    return n


secret = bytes.fromhex("a1b2c3d4e5f60718")
print(leaky_prefix(secret, bytes.fromhex("a1b2c3d4e5f60700")))
print(leaky_prefix(secret, bytes.fromhex("ffb2c3d4e5f60718")))
print(hmac.compare_digest(secret, bytes.fromhex("a1b2c3d4e5f60700")))
print(hmac.compare_digest(secret, secret))
```
```output
7
0
False
True
```

В первом случае совпало 7 байт, во втором - 0: время, которое бы тратил `==`, различалось бы именно так. `compare_digest` отвечает только да или нет.

## Типичные ошибки

* **Один SHA-256 (или MD5, SHA-1) на пароль.** Слишком быстро. Нужен медленный алгоритм с настраиваемой стоимостью.
* **Одна соль на всех.** Соль должна быть уникальной для каждого пароля и случайной.
* **Свой алгоритм.** Не комбинируйте хеши «для надёжности» и не придумывайте форматы вместо проверенных.
* **Сравнение через `==`.** Используйте `hmac.compare_digest`.
* **Константа вместо параметров в записи.** Если число итераций зашито в код, поднять его позже без поломки старых записей не получится.
* **Слепое доверие к записи.** Неограниченное число итераций из недоверенного источника превращается в отказ в обслуживании.
* **Пароль в логах и отладочной печати.** Сам хеш тоже чувствителен: он позволяет перебор в обход вашего сервиса.
* **Обрезка и нормализация «по пути».** Например, bcrypt молча обрезает пароль до 72 байт; проверяйте ограничения алгоритма.

## Итоги

* Пароли хранят как медленные солёные хеши (Argon2id; scrypt или PBKDF2 как доступные альтернативы), а не шифруют и не хешируют обычным SHA-256.
* Соль уникальна для каждого пароля и хранится рядом; перец - отдельный секрет приложения.
* Запись содержит алгоритм, параметры, соль и хеш; при входе устаревшие параметры обновляют.
* Секреты сравнивают через `hmac.compare_digest`, формат записи проверяют и ограничивают сверху стоимость.
* Далее - как аутентифицировать **сообщения** и токены: [HMAC и JWT](lesson:security.fundamentals.message-authentication-and-tokens).
