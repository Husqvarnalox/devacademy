## Данные, которые стали кодом

Инъекция возникает всегда по одной схеме: программа собирает строку из своего кода и чужих данных, а интерпретатор (SQL-движок, оболочка, файловая система) не отличает одно от другого. Пользователь вводит имя файла `report.txt; делай-что-угодно`, программа склеивает его с командой, и оболочка выполняет вторую часть.

Фильтровать «опасные символы» ненадёжно: список всегда неполный, а нужные символы бывают у честных данных (апостроф в фамилии O'Brien). Надёжное решение - **не смешивать**:

* SQL: значения передаются отдельно от текста запроса (параметризация). Подробно - в уроке [SQL-инъекции и безопасный доступ](lesson:databases.sql.sql-injection-and-safe-access); здесь не повторяем.
* Команды: аргументы передаются **списком**, без оболочки.
* Пути: путь пользователя считается недоверенным и приводится к канонической форме, после чего проверяется вхождение в разрешённый каталог.
* HTML: данные кодируются под контекст вывода ([следующий урок](lesson:security.fundamentals.output-encoding-and-xss)).

Это принцип «глубокой защиты» из [первого урока](lesson:security.fundamentals.threat-modelling) в действии: основной механизм (разделение данных и кода) плюс дополнительные проверки (белые списки, минимальные права процесса).

## Внешние команды

Лучший способ избежать инъекции команд - не запускать команды: у языка почти всегда есть встроенный API (копирование файла, сжатие, HTTP-запрос). Если вызов неизбежен ([модуль subprocess](lesson:python.stdlib.subprocess-and-logging)):

* `subprocess.run(["wc", "-c", "--", name])` - список аргументов, **без оболочки**. Каждый элемент - один аргумент процесса, оболочка не выполняет подстановок, `;`, `&&`, `$()`, обратных кавычек. Строка пользователя остаётся данными.
* `shell=True` с формируемой строкой передаёт всё оболочке. Тогда **вы** отвечаете за экранирование каждого недоверенного значения.
* `shlex.quote(s)` превращает произвольную строку в единый литерал для POSIX-оболочки (оборачивает в апострофы и экранирует апострофы внутри). Это вспомогательное средство для тех случаев, когда оболочка неизбежна; оно не заменяет список аргументов и не защищает от того, что делает с аргументом сама программа.
* Разделитель `--` отделяет параметры команды от данных: без него имя файла `-rf` могло бы быть принято за параметр (инъекция аргументов).
* Белый список допустимых значений (например, из фиксированного набора команд) всегда лучше «очистки».

## Обход каталогов (path traversal)

Приложение хранит загрузки в `/srv/app/uploads` и отдаёт файл по имени из запроса. Если сделать `open(base + "/" + name)`, то имя `../../etc/passwd` выводит за пределы каталога. Это CWE-22. Защита не в поиске слова `..` в строке, а в **проверке результата**:

1. **Декодировать** то, что декодирует следующий уровень (процентное кодирование URL) - один раз и последовательно. Если остаются закодированные символы, значит, ввод закодирован дважды: отвергнуть, а не гадать.
2. **Отвергнуть** недопустимые символы (NUL, обратный слэш) и абсолютные пути: `os.path.join(base, "/etc/passwd")` возвращает `/etc/passwd`, отбрасывая base.
3. **Нормализовать** (`posixpath.normpath`): свернуть `.`, `..` и повторные слэши.
4. **Проверить вхождение** результата в `base` **по компонентам**: `commonpath`, а не `startswith`. Иначе `/srv/app/uploads-evil` сойдёт за вложенный каталог.

Ещё два уровня защиты в реальной системе: правильные **права** процесса (наименьшие привилегии - даже обойдя проверку, процесс не сможет прочитать чужое) и учёт **символических ссылок** (нормализация строк не знает о ссылках; нужны `realpath` и открытие относительно дескриптора каталога). Упражнение работает со строками и ссылок не моделирует.

Ещё лучше исключить сами пользовательские имена: хранить файл под сгенерированным идентификатором, а исходное имя держать в метаданных.

## Данные остаются данными

Строка с точкой с запятой, передаваемая отдельным аргументом, остаётся одним аргументом: дочерняя программа получает её как есть и ничего не выполняется. Затем посмотрим на `shlex.quote` для случая, когда строка команды всё же нужна:

```python run
import shlex
import subprocess
import sys

payload = "report.txt; echo INJECTED"
child = [sys.executable, "-c", "import sys; print(len(sys.argv) - 1, sys.argv[1])", payload]
result = subprocess.run(child, capture_output=True, text=True, check=True)
print(result.stdout.strip())

quoted = shlex.quote(payload)
print(quoted)
print(shlex.split("cp " + quoted + " dest/"))
```
```output
1 report.txt; echo INJECTED
'report.txt; echo INJECTED'
['cp', 'report.txt; echo INJECTED', 'dest/']
```

Дочерний процесс получил ровно один аргумент. `shlex.quote` обернул строку в апострофы, и `shlex.split` (разбор в духе оболочки) снова даёт единый элемент.

## Нормализация и вхождение

Сравним наивные проверки с проверкой по компонентам:

```python run
import posixpath

base = "/srv/app/uploads"


def naive(user):
    return posixpath.join(base, user).startswith(base)


def safe(user):
    joined = posixpath.normpath(posixpath.join(base, user))
    return joined != base and posixpath.commonpath([base, joined]) == base


for user in ("docs/a.txt", "../uploads-evil/x", "a/../../x", "../uploads/x.txt", "/etc/passwd"):
    print(f"{user:22} naive={naive(user)!s:5} safe={safe(user)}")
```
```output
docs/a.txt             naive=True  safe=True
../uploads-evil/x      naive=True  safe=False
a/../../x              naive=True  safe=False
../uploads/x.txt       naive=True  safe=True
/etc/passwd            naive=False safe=False
```

Наивная проверка пропускает `../uploads-evil/x` (общий префикс) и `a/../../x` (проверяет строку до нормализации). Безопасная даёт `False` для обоих, а `../uploads/x.txt` после нормализации лежит внутри каталога и разрешено правилом упражнения.

## Процентное кодирование

Тот, кто принимает путь из URL, видит закодированные символы. Один раз декодировали - получили то, что увидит файловая система; вторая цепочка кодирования признак подозрительного ввода:

```python run
import re
from urllib.parse import unquote

for raw in ("%2e%2e/secret", "report%20final.txt", "%252e%252e/secret"):
    once = unquote(raw)
    twice = bool(re.search(r"%[0-9A-Fa-f]{2}", once))
    print(f"{raw:20} -> {once:18} still-encoded={twice}")
```
```output
%2e%2e/secret        -> ../secret          still-encoded=False
report%20final.txt   -> report final.txt   still-encoded=False
%252e%252e/secret    -> %2e%2e/secret      still-encoded=True
```

Закодированные точки перестали быть невидимыми, после одного декодирования `..` видно, а двойное кодирование отвергается как подозрительное.

## Типичные ошибки

* **Склеивать команду строкой и включать `shell=True`.** Используйте список аргументов; для `shell=True` нужен `shlex.quote` на каждое значение, и это уже запасной вариант.
* **Запрещать конкретные символы вместо разделения данных и кода.** Список «опасных символов» неполон.
* **Искать `..` в сыром вводе.** Запрет подстроки ломает честные имена вроде `notes..txt`, а закодированный вариант `%2e%2e` его обходит. Проверяйте нормализованный результат.
* **`startswith(base)` без разделителя.** Соседний каталог с общим префиксом проходит проверку.
* **Забыть про `os.path.join(base, "/abs")`.** Абсолютный второй аргумент заменяет первый.
* **Декодировать дважды или в разных местах.** Двойное декодирование превращает `%252e` в `.`: проверка и использование видят разные строки.
* **Нормализовать до декодирования.** Проверка видит `%2e%2e`, файловая система - `..`.
* **Считать нормализацию строк достаточной.** Символические ссылки, права и особенности файловых систем (регистр, Unicode) остаются; нужны права процесса и проверка на уровне ОС.

## Итоги

* Инъекции возникают, когда данные смешаны с кодом; решение - разделять, а не фильтровать.
* Команды: список аргументов без оболочки, `--` перед пользовательскими именами, `shlex.quote` только если оболочка неизбежна.
* SQL: параметризация, подробности - в [уроке по SQL-инъекциям](lesson:databases.sql.sql-injection-and-safe-access).
* Пути: декодировать один раз, отвергнуть абсолютные и недопустимые символы, нормализовать, проверить вхождение по компонентам.
* Дальше - кодирование вывода: [XSS и контекст](lesson:security.fundamentals.output-encoding-and-xss).
