## Браузер читает ваш вывод как документ

Предыдущий урок показал принцип: данные не должны превращаться в код. Для веб-страниц «код» - это разметка HTML, атрибуты, встроенные скрипты и URL. Если комментарий пользователя вставлен в страницу «как есть», то символ `<` в нём начнёт тег, и браузер выполнит то, что внутри: это **XSS** (межсайтовое выполнение скриптов).

Виды XSS различаются тем, откуда приходят данные:

* **хранимый** - данные записаны в базу (комментарий) и показываются всем;
* **отражённый** - данные из запроса сразу попадают в ответ (сообщение об ошибке с эхом ввода);
* **DOM-вариант** - вставку выполняет скрипт на странице (`innerHTML = ...`), сервер может об этом не знать.

Защита одна по сути: **кодировать данные под тот контекст, куда они попадают**. Современные шаблонизаторы (Jinja2 с автоэкранированием, шаблоны React) делают это по умолчанию - а ошибки происходят там, где мы обходим их ради «удобства».

<!-- section: precise -->
## Контекст решает

Один и тот же ввод означает разное в разных местах документа, поэтому правило зависит от места:

| Контекст | Что делать |
|---|---|
| Тело HTML (`<p>…</p>`) | заменить `&`, `<`, `>` |
| Атрибут в двойных кавычках | то же, плюс `"` и `'` (и обратная кавычка, перевод строки, табуляция); значение всегда в кавычках |
| URL в `href`/`src` | сначала **проверить схему** по белому списку, затем кодировать как атрибут; значения в параметрах запроса - `urllib.parse.quote` |
| Строка JavaScript | не вставлять данные в код: передать JSON (`json.dumps`) с заменой `<`, `>`, `&`, U+2028/2029 или положить в `data-`атрибут и прочитать из DOM |
| CSS, `style`, обработчики событий | избегать подстановки данных совсем |

Следствия:

* **Универсального экранирования нет.** Экранированное для тела значение в атрибуте без кавычек или в JavaScript остаётся опасным.
* **Кодирование - на выводе, в последний момент.** Храните данные «как есть»; кодируйте, когда знаете контекст.
* **Кодируйте один раз.** Повторное кодирование портит данные, пропущенное - оставляет дыру.
* **`html.escape` из стандартной библиотеки** заменяет `&`, `<`, `>` и (по умолчанию) обе кавычки. Для тела (`quote=False`) и для значения в кавычках он подходит, но не знает о JavaScript, URL и неквотированных атрибутах. Наша таблица атрибута строже: добавляет обратную кавычку и пробельные управляющие символы.

### URL нужно проверять, а не только кодировать

Значение `javascript:...` в `href` синтаксически корректно, и кодирование атрибута его не меняет: браузер выполнит его при клике. Поэтому **белый список схем** (`http`, `https`, `mailto`, относительные ссылки). Браузеры при разборе URL удаляют табуляции и переводы строк и обрезают управляющие символы по краям, а схема нечувствительна к регистру, поэтому проверку ведут над **очищенной** строкой. Чёрный список «запретить слово javascript» обходится этими приёмами; белый список - нет.

### Content-Security-Policy

Заголовок `Content-Security-Policy` ограничивает, откуда страница может загружать и выполнять ресурсы. Минимальная полезная политика: `default-src 'self'` (всё только с вашего домена) и отказ от встроенных скриптов без `nonce` или хеша. Тогда даже пропущенная вставка разметки хуже работает. Но CSP - **второй слой**: он не заменяет кодирование (глубокая защита, как в [первом уроке](lesson:security.fundamentals.threat-modelling)), а неверно настроенная политика (`'unsafe-inline'`) почти ничего не защищает. Заголовки ответа - часть [HTTP](lesson:networking.fundamentals.http-evolution).

## Сравнение с html.escape

Реализуем таблицы из упражнения и сравним результат со стандартной функцией на нескольких строках:

```python run
import html

BODY = {"&": "&amp;", "<": "&lt;", ">": "&gt;"}
ATTR = dict(BODY, **{'"': "&quot;", "'": "&#x27;", "`": "&#x60;", "\n": "&#xA;", "\r": "&#xD;", "\t": "&#x9;"})


def escape(text, table):
    return "".join(table.get(ch, ch) for ch in text)


for s in ('5 < 6 & "x"', "it's", "a`b", "line1\nline2"):
    body_same = escape(s, BODY) == html.escape(s, quote=False)
    attr_same = escape(s, ATTR) == html.escape(s)
    print(f"{s!r:16} body-same={body_same!s:5} attr-same={attr_same}")
```
```output
'5 < 6 & "x"'    body-same=True  attr-same=True
"it's"           body-same=True  attr-same=True
'a`b'            body-same=True  attr-same=False
'line1\nline2'   body-same=True  attr-same=False
```

Для тела таблица совпадает с `html.escape(quote=False)`. Для атрибута таблица строже: на обратной кавычке и переводе строки результаты различаются. Это осознанный запас: старые движки считали обратную кавычку ограничителем значения, а перевод строки в значении полезно сделать видимым.

## Контекст: тело против атрибута

Если вставить значение в атрибут в одинарных кавычках, используя «тело»-экранирование, апостроф выходит из значения. Покажем только результат склейки, чтобы увидеть, где заканчивается атрибут:

```python run
import html

value = "x' class='y"
wrong = "<a title='" + html.escape(value, quote=False) + "'>"
right = "<a title='" + html.escape(value) + "'>"
print(wrong)
print(right)
```
```output
<a title='x' class='y'>
<a title='x&#x27; class=&#x27;y'>
```

В первой строке значение закрыло атрибут `title` раньше времени и добавило свой `class`: атрибуты теперь задаёт ввод. Во второй апостроф закодирован (`&#x27;`), и значение осталось значением. Так же работает любая инъекция: данные меняют структуру. Если бы вместо безобидного `class` ввод смог добавить атрибут-обработчик события, это уже был бы XSS.

## Белый список схем и JSON для JavaScript

Проверим набор ссылок и покажем безопасную сериализацию строки для скрипта:

```python run
import json

ALLOWED = {"http", "https", "mailto"}


def href_ok(url):
    url = url.replace("\t", "").strip()
    head = url.split("/")[0].split("?")[0].split("#")[0]
    if ":" in head:
        return head.split(":")[0].lower() in ALLOWED
    return not url.startswith("//")


for u in ("https://example.com/a", "/docs", "HTTPS://Example.com", "javascript:void(0)", "java\tscript:void(0)", "//other.example/x"):
    print(f"{u!r:28} {href_ok(u)}")


def js_string(value):
    text = json.dumps(value)
    return text.replace("<", "\\u003c").replace(">", "\\u003e").replace("&", "\\u0026")


print(js_string('say "hi" </script>'))
```
```output
'https://example.com/a'      True
'/docs'                      True
'HTTPS://Example.com'        True
'javascript:void(0)'         False
'java\tscript:void(0)'       False
'//other.example/x'          False
"say \"hi\" \u003c/script\u003e"
```

Ссылка с табуляцией в схеме отвергается, потому что очистка выполняется до проверки. Строка для скрипта сериализована JSON-ом, а `<`, `>` и `&` заменены на `<`, `>`, `&`: теперь последовательность `</script>` не закроет тег.

## Типичные ошибки

* **Один универсальный `escape` на всё.** Тело, атрибут, URL и JavaScript - разные контексты.
* **Атрибуты без кавычек.** Пробел заканчивает значение. Всегда ставьте кавычки и кодируйте их.
* **Кодирование без проверки схемы URL.** `javascript:` остаётся ссылкой, которую выполнит клик.
* **Чёрные списки слов (`script`, `javascript`, `onerror`).** Обходятся регистром, пробельными символами и сущностями.
* **Санитизация на входе вместо кодирования на выходе.** Вход не знает будущего контекста, а при смене шаблона дыра возвращается.
* **Отключать автоэкранирование ради удобства** (`|safe`, `dangerouslySetInnerHTML`) для данных пользователя. Исключение должно быть осознанным и проверенным.
* **Вставка данных в `<script>` и в обработчики событий.** Используйте JSON и `data-`атрибуты.
* **Надеяться на CSP как единственную защиту.** Это второй слой; кроме того, политика с `'unsafe-inline'` почти бесполезна.
* **Двойное кодирование.** `&amp;amp;` на странице - след того, что значение кодировали дважды.

<!-- section: summary -->
## Итоги

* XSS = данные пользователя стали разметкой или кодом страницы; виды: хранимый, отражённый, DOM.
* Кодируйте под контекст, на выходе и один раз: тело (`& < >`), атрибут в кавычках (плюс кавычки и пробельные символы), URL (белый список схем + кодирование), JavaScript (JSON, `data-`атрибуты).
* `html.escape` подходит для тела и значения в кавычках, но не знает контекста.
* CSP - дополнительный слой, снижающий ущерб; он не отменяет кодирование.
