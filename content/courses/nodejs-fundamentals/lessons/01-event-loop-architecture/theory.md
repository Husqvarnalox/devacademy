## Из чего состоит Node.js и почему он не «зависает» на вводе-выводе

Node.js - не язык, а программа, которая собрана из нескольких частей. Для понимания остального курса достаточно трёх:

* **V8** - движок JavaScript. Он выполняет ваш код: функции, замыкания, промисы. V8 ничего не знает ни о файлах, ни о сети.
* **libuv** - библиотека на C. Она ведёт **цикл событий** (event loop), таймеры, **пул потоков** и неблокирующий ввод-вывод поверх возможностей операционной системы.
* **Привязки (bindings) и встроенные модули** - слой на C++ и JavaScript, который превращает вызов `fs.readFile(...)` в запрос к libuv и возвращает результат в виде колбэка или промиса.

Ваш JavaScript выполняется **в одном потоке**: в каждый момент идёт одна функция. Чтение файла или сетевой запрос в это время выполняют система или потоки libuv, а когда результат готов, цикл событий вызывает ваш колбэк. Пока ввод-вывод в пути, поток свободен для другой работы. Расплата за это: если ваша функция занимает поток надолго, **все** остальные колбэки ждут.

```javascript
// колбэк вызовет цикл событий, когда libuv закончит чтение
fs.readFile("data.txt", (err, data) => { /* ... */ });
console.log("эта строка выполнится раньше колбэка");
```

Сравните с другими языками: в Go ожидание скрывают горутины ([горутины и каналы](lesson:go.fundamentals.goroutines-and-channels)), в Python тот же приём называется `asyncio` ([основы asyncio](lesson:python.concurrency.asyncio-basics)), в Rust - `async` с исполнителем. Идея одна: не держать поток на ожидании. Промисы и `async`/`await` на уровне языка разобраны в уроке [«Цикл событий, промисы и async/await»](lesson:javascript.fundamentals.promises-and-async); здесь речь о том, как это устроено внутри Node.js.

## Фазы, очереди и пул потоков

**Один оборот цикла.** Цикл libuv в Node.js проходит фазы по кругу:

1. `timers` - колбэки `setTimeout` и `setInterval`, срок которых наступил;
2. `pending callbacks` - отложенные системные колбэки;
3. `idle, prepare` - внутренние фазы;
4. `poll` - получение новых событий ввода-вывода и выполнение их колбэков; если делать больше нечего, цикл ждёт здесь;
5. `check` - колбэки `setImmediate`;
6. `close callbacks` - например, `socket.on("close")`.

**Очереди между колбэками.** После главного скрипта и после **каждого** колбэка Node.js выполняет две очереди, прежде чем двигаться дальше:

1. очередь `process.nextTick`, целиком;
2. очередь **микрозадач** - колбэки промисов (`.then`, продолжения после `await`, `queueMicrotask`), тоже целиком.

Если микрозадача поставила новый `nextTick`, он выполнится после того, как очередь микрозадач опустеет; если `nextTick` поставил микрозадачу, она встанет в конец очереди микрозадач. Эти очереди **не** часть фаз: они прогоняются между ними. Поэтому бесконечно перепланируемый `nextTick` или промис не пускает цикл дальше: ввод-вывод и таймеры «голодают».

**Макрозадачи** - то, что выполняется по фазам: таймеры, колбэки ввода-вывода, `setImmediate`. Микрозадачи и `nextTick` всегда идут раньше следующей макрозадачи.

**`setTimeout(fn, 0)` и `setImmediate(fn)`.** Таймер означает «не раньше чем через заданное время» (минимум 1 мс), а проверка срока происходит в фазе `timers`. В **главном модуле** порядок этих вызовов зависит от того, успел ли пройти 1 мс до первого оборота, и **не определён**. Внутри колбэка ввода-вывода (фаза `poll`) следующая фаза - `check`, поэтому `setImmediate` **всегда** раньше таймера. В программах и тестах опирайтесь только на определённый порядок.

**Пул потоков.** Некоторые операции у операционной системы нет возможности выполнять неблокирующе. Для них libuv держит пул из 4 потоков (размер задаёт `UV_THREADPOOL_SIZE`): файловая система, `dns.lookup`, часть `crypto` (например, `pbkdf2`, `randomBytes`) и `zlib`. Сетевые сокеты пул не используют. Когда занято больше четырёх операций, остальные ждут в очереди пула - это частая причина «странной» медлительности. Для **вычислений на JavaScript** пул не помогает: нужны `worker_threads` или отдельные процессы.

**Блокировка.** Любой синхронный код держит поток: тяжёлый цикл, `JSON.parse` огромной строки, `fs.readFileSync` на большом файле, плохое регулярное выражение. Пока он идёт, не срабатывают таймеры и не отвечает сервер. Решения: разбить работу на части и отдавать управление (`await` на границах, `setImmediate`), вынести в `worker_threads`, использовать потоки (урок про [потоки](lesson:nodejs.fundamentals.streams-backpressure)).

**Версии.** Состав API и версии V8 и libuv зависят от версии Node.js; их видно в `process.versions`. Примеры курса проверены на Node.js 22.

## Примеры

**Пример 1. Из чего собрана среда.**

```javascript run
console.log(process.release.name);
console.log(typeof process.versions.v8, typeof process.versions.uv);
console.log(process.version === "v" + process.versions.node);
```
```output
node
string string
true
```

Строки `v8` и `uv` - версии двух главных компонентов. Сами номера зависят от установки, поэтому в примере выводятся только их типы.

**Пример 2. Порядок внутри колбэка ввода-вывода.**

```javascript run
const fs = require("node:fs");

fs.readFile(__filename, () => {
  setTimeout(() => console.log("таймер"), 0);
  setImmediate(() => console.log("setImmediate"));
  Promise.resolve().then(() => console.log("промис"));
  process.nextTick(() => console.log("nextTick"));
  console.log("синхронно");
});
```
```output
синхронно
nextTick
промис
setImmediate
таймер
```

Колбэк выполняется в фазе `poll`. После него идут очереди (`nextTick`, затем промисы), затем фаза `check` (`setImmediate`) и только в следующем обороте - `timers`. Такой порядок гарантирован, в отличие от того же кода в главном модуле.

**Пример 3. Две очереди обмениваются задачами.**

```javascript run
Promise.resolve().then(() => {
  console.log("микрозадача 1");
  process.nextTick(() => console.log("nextTick из микрозадачи"));
});
Promise.resolve().then(() => console.log("микрозадача 2"));
process.nextTick(() => {
  console.log("nextTick 1");
  Promise.resolve().then(() => console.log("микрозадача из nextTick"));
});
```
```output
nextTick 1
микрозадача 1
микрозадача 2
микрозадача из nextTick
nextTick из микрозадачи
```

Сначала очередь `nextTick`, и новая микрозадача встаёт после уже ожидающих. Затем очередь микрозадач целиком; `nextTick`, поставленный микрозадачей, ждёт, пока она опустеет.

**Пример 4. Синхронный код держит таймер.**

```javascript run
const start = Date.now();
setTimeout(() => console.log("таймер"), 0);
while (Date.now() - start < 30) {
  // занимаем поток на 30 мс
}
console.log("цикл закончился");
```
```output
цикл закончился
таймер
```

Таймер с нулевой задержкой уже «созрел», но выполнить его некому, пока поток занят. Так один тяжёлый обработчик замедляет всё приложение.

## Типичные ошибки

* **Считать, что `setTimeout(fn, 0)` и `setImmediate(fn)` в главном модуле идут в определённом порядке.** Он зависит от нагрузки. Если порядок важен, выстройте его через промисы или вызывайте оба из колбэка ввода-вывода.
* **Бесконечно перепланировать `process.nextTick` или промис.** Очереди выполняются до опустошения, и цикл не доходит до ввода-вывода. Для «уступить циклу» используйте `setImmediate`.
* **Использовать синхронные версии `fs` и тяжёлые вычисления в обработчиках сервера.** Пока вычисление идёт, не обслуживаются другие клиенты. `readFileSync` допустим при старте программы.
* **Думать, что асинхронность значит параллельность вашего кода.** Колбэки по-прежнему идут по одному. Параллельно работает ввод-вывод и потоки пула, но не ваши функции.
* **Рассчитывать, что `setTimeout(fn, 100)` сработает ровно через 100 мс.** Это нижняя граница: поток может быть занят.
* **Мерить порядок таймеров на глаз.** Порядок таймеров с одинаковой задержкой, поставленных подряд, определён (по порядку постановки), но порядок с чем-то внешним (ввод-вывод, сеть) - нет.
* **Забыть про пул из четырёх потоков.** Пять одновременных `pbkdf2` не ускорятся пятикратно: пятая ждёт свободного потока.

## Итоги

* Node.js = V8 (выполняет JavaScript) + libuv (цикл событий, пул потоков) + привязки; ваш код идёт в одном потоке.
* Фазы цикла: `timers`, `pending callbacks`, `idle/prepare`, `poll`, `check`, `close callbacks`; `setImmediate` живёт в `check`, таймеры в `timers`.
* После каждого колбэка выполняются `nextTick`, затем микрозадачи; макрозадачи идут только после них.
* Внутри колбэка ввода-вывода `setImmediate` раньше таймера; в главном модуле порядок не определён.
* Пул потоков (по умолчанию 4) обслуживает файлы, `dns.lookup`, часть `crypto` и `zlib`, но не сокеты и не ваши вычисления.
* Блокирующий синхронный код останавливает все таймеры и колбэки.
